# @deepseek-ai/dsh-client-ui-settings-models

[English](README.md) | [简体中文](README.zh.md) | 繁體中文

模型設定與產品引導外掛程式。同一個 client Cordis 外掛程式會註冊 Models 頁面和兩個有序的首次使用彈出視窗：版本化內測聲明，以及按條件顯示的 DeepSeek 官方憑據步驟。兩個步驟共用同一套彈出視窗元件，並繼續由 `settings.onboarding` 排序。Models 平面把三個協定領域匯聚為一個共享快照：`llm.providers`（可設定提供方目錄，含每條路由的存活／休眠狀態）、`settings.describe`（序列化 schema、分層脫敏值、secret slot）與 `credentials.describe`（不含值的 configured/source/writable 徽標）；頁面據此算繪提供方行，一次只展開一張編輯卡片，且不把路由存活狀態呈現為提供方狀態。

行是*已設定*的提供方（其 profile 在所屬 namespace 中解析得出）；其設定鍵未在任何位置設定的整分節提供方會算繪為其展開的設定卡片而非一行，但僅限首次執行姿態——即尚無任何提供方已註冊且備齊其 profile 所指名的憑據——且僅持續到使用者關閉該卡片為止，此後它就是一行帶缺失金鑰點的普通行。每一類卡片各自持有自己的展開狀態，因此關掉其中一張絕不會丟棄另一張裡的草稿。「新增」流程則是一張承載休眠目錄提供方選擇框的卡片——裸掛載的 `llm-pi-ai` 在任何路由存在之前就能提供其完整的已安裝 catalog。pi-ai 卡片還會編輯該路由的**模型清單**，並可查詢提供方所提供的模型。只有確認引用的憑據已設定時，行才會以綠色實心點標示 API 金鑰狀態；只有確認具名引用缺失時，才會以紅色實心點標示。無引用的提供方原生驗證以及無法取得憑據補充資訊時都不顯示狀態點。編輯器是每個配接器家族各一張的手寫卡片：主欄位是單獨一個 **API 金鑰**輸入框——頁面從不詢問環境變數名；鍵入的金鑰經 `credentials.set` 以**只寫**方式存入 profile 的引用之下，profile 沒有引用時便派生 `<ROUTE>_API_KEY`，pi-ai profile 會把這次派生記錄為 `apiKeyEnv`，因此 `settings.yaml` 從不攜帶金鑰值。為新的 pi-ai 提供方留空金鑰會保存一個不帶引用的 profile，因此能保留提供方原生驗證，例如 Bedrock 憑據鏈或 Vertex ADC。「應用」成功後會寄出本機無障礙狀態訊息，且絕不回顯任何機密內容。收起的「自訂設定」摺疊區承載精選的額外欄位——兩個家族都有 `baseURL`（deepseek 的預留位置顯示公共端點）、各配接器自己的模型目錄，以及配接器未提供的那類 pi-ai 路由的**顯示名稱**與 **API 協定**。這兩個欄位是手工聲明路由為自己命名的東西：建立卡片之所以索要它們，正因為沒有東西能為它們兜底，因此編輯器也夠得著這兩個，而不是把它們留給 `settings.yaml`。清空名稱即取消設定，路由退回自己的 id——預留位置顯示的就是它；協定沒有這樣的兜底。內建目錄路由兩個都不給：它的名稱由目錄條目兜底，它的每個模型各自帶著自己的協定，路由級協定只可能把它們全部覆蓋掉。Provider ID 保持固定：它是 settings 的鍵、是其他每個 namespace 與每一條已記錄工作階段引用的名字，也是頁面讀不回、因而搬不走的憑據引用詞幹。推理等級刻意**不在**其中：它是按模型的能力，而同一提供方下各模型接受的檔位並不一致，因此提供方級的控制元件只可能被設成其中一些模型會拒絕的值——那會連支援該檔位的模型也一並隱藏。輸入框的模型選擇器為每個模型提供它自己的檔位，在那裡切換會把提供方、模型、推理等級一並記為下一個工作階段的預設值。profile 欄位仍留在 `settings.yaml`，供清楚自己路由的部署使用。每條 DeepSeek 模型行可編輯 `id`、選填的顯示名稱 `name` 與選填的 `contextWindow`/`maxTokens`；精選集合以外的現有欄位會在編輯後保留，其餘每個 profile 欄位仍歸 `settings.yaml` 所有。只有當某行僅由使用者層承載時它纔可刪除（刪除會還原組合 base），其本機化確認對話框會在標題、說明和最終操作中點名該提供方。當目錄條目表明擁有該路由的配接器在這個鍵下什麼都沒有時，該行會帶上 **自訂** 標籤。標籤只跟隨這個答案：存了 profile 並不使一條路由成為自訂——收窄一個內建提供方的模型同樣會存下 profile——而什麼都不回答的配接器，其路由保持無標籤，不會被當成內建。

聲明步驟在 `src/onboarding-copy.ts` 中持有完整文案和版本。回環訪問會透過既有 settings API 比較並寫入 `ui-onboarding.welcomeNoticeVersion`；只有明確點擊「繼續」才會記錄當前版本。非回環瀏覽器無法使用這項僅限 Host 的 namespace，因此確認僅在當前行程有效，重載後聲明會再次出現。

聲明完成後，DeepSeek 步驟會從同一個 Models 聯接快照得出首次執行就緒狀態。只要使用者已經能觸達**任何**一個提供方，它就直接完成而不算繪——已註冊且其具名憑據引用已儲存的路由（包括來自啟動環境且只讀的憑據），或 profile 根本不指名引用、因而走原生驗證的路由。只有二者皆無的使用者才會被要求填寫 DeepSeek 官方金鑰。配接器已掛載且活躍、引用可寫但尚未設定時，既有 `ProviderEditor` 會以僅憑據模式算繪在共用引導彈出視窗中；`credentials.set` 仍是唯一的 secret 寫入，且不會改變提供方設定。「稍後設定」只完成協調器當前這一輪。配接器缺失、路由不活躍、聯接失敗、部署只讀或設定／憑據能力不可用時，該步驟不算繪並直接完成；Models 頁仍是診斷介面。

每一次編輯都以 `settings.mutate` 的路徑 op 落到已存分節上——每個變更欄位一條 set、每個清空欄位一條 unset、刪除提供方行則是單獨一條 unset。頁面自始至終只持有**脫敏後**的 descriptor，因此它只修改自己看得見的欄位，而不重建分節。DeepSeek 的 `models` 是一個按值整體替換的陣列：編輯器會顯示繼承而來的生效模型行，直到第一次模型編輯將完整陣列具化到使用者層；重設則會取消該覆蓋。每個模型行承載模型 ID 與顯示名稱，其上下文視窗與最大輸出 token 數則收在該行自己的摺疊區裡，使用與 pi-ai 提供方表單相同的欄位。兩項容量都按數值鍵入，可帶十進位的 `K` 或 `M` 後綴（`256K`、`1M`；`1M` 即 1000K），儲存為純數值，回顯時寫成能夠往返的最短形式。空 ID、重複 ID、顯式填寫的空名稱，以及無法讀取、非正數或非整數的容量都會在寫入前失敗。鍵入的 API 金鑰同樣在它自己的欄位上被判定：trim 之後必須非空，且每個字元都是可列印 ASCII（`[\x21-\x7E]`）——這正是 HTTP 標頭值所能承載的範圍，是 `@deepseek-ai/dsh-llm` 中 `normalizeApiKey` 的孿生體，因原始碼平面分割禁止直接引入而在此映像檔。與整行貼上的 `NAME=value` 環境變數匹配或首尾成對引號包裹的值，會以同一條格式失敗被拒絕；這項貼上行檢查只在瀏覽器中執行，因為 resolver 中的一次誤判會連帶讓環境變數這條路也拒絕該金鑰。只含空白的輸入框會失敗而不是被靜默丟棄；留空則完全不是失敗：在編輯卡片上意味著保持已儲存的金鑰，在新建卡片上則意味著以其他方式鑒權。被拒絕的金鑰會同時攔截寫入與端點探測，因此頁面不會白花一次往返去換取欄位上已經寫明的答案。每次 settings 寫入都攜帶卡片當前的 `revision`，因此來自另一個分頁標籤或對 `settings.yaml` 的外部編輯所產生的並行寫入會以 `settings-conflict` 被拒絕；settings 提交成功後，卡片會在儲存憑據前採用回應返回的脫敏使用者子樹與 revision，因此憑據階段失敗時，重試只會重複該階段。刪除操作只會在 profile 指向頁面派生的 `<ROUTE>_API_KEY` 目標時清除已設定且可寫的憑據，隨後取消設定 profile；兩項操作都具備冪等性，部分失敗會停留在點名目標的確認對話框中供重試。環境憑據、自訂引用和無法識別目標的憑據保持不變。頁面載入完成後會直接訂閱轉發的 owner 事件 `settings/document-updated`、`credentials/updated`、`llm/adapters-updated`，以及本機 `connection/reset`，因此外部的 `settings.yaml` 編輯、第二個分頁標籤或 settings 新生的路由都無需輪詢即可收斂。

## 模型清單與端點詢問

pi-ai profile 的 `models` 清單就在卡片上編輯：一行一個模型，行上顯示 id 與顯示名稱，上下文視窗與輸出上限收在該行的展開區內，右側是兩個無文字的操作——展開與刪除。空清單意味著「使用該路由的內建 catalog」，因此每一行都只會被刻意新增；清空容量會丟棄它，而不是存入一個 schema 會拒絕的值，設定留空的部分由配接器的路由級回退值定尺寸——留空的容量以這些回退值的量級作為預留位置，那只是提示而非映像檔：該欄位按 1000 計 `K`，且部署可以覆蓋這些回退值。不是正整數的容量根本不會被存下。

**取得可用模型**會針對表單**當前顯示**的端點呼叫 `llm.discoverModels`，包括已修改但尚未保存的 API 地址和已鍵入但尚未儲存的金鑰，因此新增一個提供方是一趟走完，而不是「先保存再回來」。回覆會打開一個選擇框而不是直接寫入：已設定過的候選預設不勾選，因此採納一次選擇絕不會覆蓋使用者已更正的容量。無法被詢問的提供方只是繞路而非死路——配接器自己的訊息會顯示在各行旁邊，而這些行仍可手工編輯。

**新增自訂提供方**用來聲明 pi-ai 未提供的路由。它是獨立的一張卡片而非在編輯器上加欄位，因為路由 id 正是在這裡被*選定*的，而在選定之前 settings 地址並不存在：一次 `settings.mutate` 在 `providers.<route>` 上設定整個 profile，金鑰則經 `credentials.set` 單獨傳遞，使用與既有提供方相同的 `<ROUTE>_API_KEY` 派生。手工聲明的路由無法預設的東西會門控建立按鈕——唯一的 **Provider ID**、端點、協定，以及至少一個標識唯一的模型——因此失敗會在使用者仍看著該欄位時點名它。該 id 必須以小寫字母開頭，因為它同時是派生憑據引用的詞幹，而引用是 POSIX shell 識別符號：數字開頭的 id 否則會透過這張卡片的每一項檢查，然後在憑據 seam 上拋出原始正規表達式錯誤。容量不參與門控：端點只按 id 描述的模型（這正是多數清單返回的形態）由配接器的回退值定尺寸。協定選項讀自該 namespace 自己的 schema，而非某個協定欄位或常數，因此它們不會與配接器實際接受的集合發生漂移。只有鍵入了金鑰，這張卡片才記錄約定的 `apiKeyEnv` 引用，與編輯器同一條規則，因此一條為提供方原生驗證聲明的路由不會一齣生就指向一個永遠不會被設定的引用。當 profile 寫入成功而金鑰寫入失敗時，提供方已經存在：卡片會把描述它的欄位定住，只重試憑據——再跑一次 profile 寫入會帶著剛被自己這次寫入取代的 revision，宿主將以 `settings-conflict` 應答，金鑰就再也無法從這裡存下——並且即使使用者隨後取消，也照實報告提供方已建立。

## 模型體驗

無。該分區算繪瀏覽器設定 UI；這裡沒有任何內容進入模型請求。

## 已知限制與暫緩事項

- **卡片上可編輯的只有 API 金鑰與精選摺疊區欄位**：手寫編輯器用 schema 通用的欄位覆蓋面換來了設計稿上的版面配置（[Agent Note](../../../.agents/notes/implemented/architecture/2026-07-30-web-config-plane.md)）。兩個家族都公開 `baseURL` 與模型的 `id`/`name`/`contextWindow`/`maxTokens`；手工聲明的 pi-ai 路由還公開 `displayName` 與 `api`。重試策略、逾時、DeepSeek 模型說明及其他進階欄位仍留在 `settings.yaml` 中；編輯器未展示的現有模型欄位會予以保留。不帶這些約定欄位的 profile schema 只算繪該提示，兩套精選版面配置則以 `llm-deepseek`/`llm-pi-ai` 這兩個 namespace 的名字為鍵。
- **憑據清理範圍刻意保持狹窄**：刪除一行時，僅當其引用與頁面派生的 `<ROUTE>_API_KEY` 目標完全一致，才會清除已設定且可寫的憑據。自訂引用、環境憑據和無法識別的目標會保留，因為該行無法證明自己擁有它們。
- **只有 pi-ai 路由可以手工聲明**：自訂提供方卡片寫入 `llm-pi-ai`——唯一一個其 profile 描述整個提供方的 namespace。`llm-deepseek` 路由是組合面的事實，不是本頁能建立的東西。
- **詢問只覆蓋 OpenAI 相容端點**：配接器只讀這種模型清單回應格式，因此講其他協定的閘道會報告自己無法被詢問，其模型需手工填寫。
- **未聲明的存活路由無處算繪**：未附帶可設定提供方聲明即註冊的路由沒有 settings 地址；它在各選擇器中仍然可見，但不會出現在本頁的行裡。
