# @deepseek-ai/dsh-jobs-local

[English](README.md) | 繁體中文

[`@deepseek-ai/dsh-jobs`](../jobs/README.md) 登錄檔約定的行程本機實作：`LocalJobRegistry` 把每條記錄保存在記憶體中，按 kind 簽發 `<kind>-N` id，並且只交出全新快照，從不交出即時狀態。作為外掛程式載入後即註冊為 `ctx.jobs`。

## 准入

`maxConcurrentJobsPerOwner` 必須是正的安全整數，預設值為 `10`。呼叫生產方之前，`start()` 會統計確切 owner 的 `running` 與 `stopping` 記錄；所有無 owner 任務共享另一個獨立的服務級桶。終止歷史不佔用容量，處於 `stopping` 的任務只有在生產方 `done` 結帳後才釋放名額。

達到容量時，`start()` 會在生產方執行和 id 分配前失敗；錯誤會給出上限，並告訴模型使用 `job_kill`、等待任務完全靜止後再重試。登錄檔不會排隊或搶佔任務，也不會維護第二份可變計數。

## 生命週期

任務屬於其所有者和後端，而不是生產方工具 fiber，因此重載生產方或控制器不會停止任務。某個所有者的第一個任務會把一個會被等待的 effect 附加到對應 `Agent` 對象的 scope 上。所有者的 dispose（資源釋放）會取消該對象的任務，等待生產方完全靜止，並移除其快照；複用的 agent（代理）id 或工作階段 id 無法重定向舊的清理操作。

服務 dispose 會關閉監聽器、取消所有存活任務、等待其記錄完成，並從仍存活的所有者 scope 中分離 effect。如果銷毀期間的取消操作拋出例外，服務會強制將記錄標為失敗，並警告工作可能成為孤立工作，而不會死結。取消操作已返回但 `done` 始終未結帳時，系統無法將其與緩慢停止區分開，銷毀過程可能因此停滯。

結帳遵循首次結帳優先原則：最早出現的終止結果（生產方結帳、作為 `failed` 隔離處理的 `done` 拒絕，或銷毀時的強制失敗）只記錄一次，隨後釋放等待方，再只通知監聽器一次；各監聽器的故障會單獨隔離。掛起的等待會在監聽器執行前把任務標記為已報告，因此完成報告方不會重複寄出通知；銷毀時的取消出於同樣的理由也會標記：面向正在被銷毀的所有者的通知不會有人讀到。完成是一次結帳最後才宣佈的事情，排在記錄提交與可見集變更發布之後，因為報告方可能同步開啟一個模型輪次，而該結帳的其他所有觀察者都必須已經看到已結帳的記錄。

控制器與監聽器按註冊方所在的 scope 分層，形狀與 tools 登錄檔一致：一次註冊歸檔到其註冊上下文的 scope，一次讀取則把全域性層與所有者的 scope 鏈求並集。因此一個行程級登錄檔能逐所有者地回答逐所有者的問題——對自身組合未附加任何控制器的所有者，無論其他組合附加了多少，`start()` 都會拒絕並拋出 `background jobs unavailable: no job controller serves this agent (load @deepseek-ai/dsh-tool-jobs in its composition)`；一次結帳也只會抵達其所有者所屬組合註冊的監聽器。

## 模型體驗

透過生產方外掛程式和 [`dsh-tool-jobs`](../tool-jobs/README.md) 間接影響；它們會呈現 job id、輸出、狀態、取消和完成通知。

#### KV Cache 影響

不會直接導致 KV Cache 失效；請求前綴變更由上述消費端負責。

## 已知限制與暫緩事項

- **任務只存在於行程本機**：記錄會隨 harness 行程終止而消失；持久或跨重新啟動執行需要一個單獨實作該 seam 的後端。
- **靜默無效的取消可能使銷毀過程停滯並持續佔用容量**：如果 `cancel` 返回後始終未結帳 `done`，登錄檔就無法將其與緩慢停止區分開；該任務會在服務剩餘生命週期內持續佔用一個桶名額，只有顯式拋出例外才能安全地強制標為失敗。
