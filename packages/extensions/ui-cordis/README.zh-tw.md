# @deepseek-ai/dsh-client-ui-cordis

[English](README.md) | [简体中文](README.zh.md) | 繁體中文

Cordis 動態外掛程式的瀏覽器半：一個覆蓋整個框架的面板，操作 host 持有的全部定義；以及一張只讀的 `cordis_define` 卡片，記錄某個工作階段定義了什麼。

**面板做成全域性是刻意的。** 模型發起的 `cordis_run` 會在 host 側阻塞於一次 `cordis/request-run` 往返，而它的答案是**有人按下允許**；並且它可能指向一個當前沒人在看的工作階段裡的定義——審批入口若只存在於那個工作階段的對話流裡，就會在它正阻塞模型的時候恰好不可達。所以應答面是一個 `shell.overlay` 條目（本包為 `ui-layout` 補的通用「框架級懸浮席位」，不是自建 React root）：角標計數 = 在跑數 + 待確認數，點開後列出每個定義及其執行控制元件。清單**同理**從不按工作階段過濾；當前工作階段的行置頂成組，其他工作階段的行仍在下方列出。行來自 host 的全域性 `inventory` 呼叫，並在公告改變「有哪些定義」時**重讀而非打修補程式**——因為公告不攜帶名字與用途。而那次讀取覆蓋不到的開放請求**仍然有行**：直接用執行活動自帶的工作階段、標題、用途與請求標識算繪——`cordis_define` 不廣播任何東西，所以在上一次讀取之後定義的包，對本頁是未知的，而它的請求已經在阻塞模型；此時角標數著一個清單給不出的答案，就等於把模型困死。這樣一個請求還會額外觸發一次登錄檔讀取，把執行控制元件補給該行。**歸組只讀每行上一個已解析好的欄位**——有活動的 run 用它自己的工作階段，其餘用登錄檔行的——而不是按階段去問不同的 store；活動的**兩條臂都帶這個欄位**，所以應答一個請求不會讓它的行跳出人剛剛操作的那一組。組內，阻塞著模型的行排在最前。

**卡片是一份記錄。** 它顯示模型寫下的 name 與 purpose、它寫的原始碼，以及那個定義是否在跑——沒有開關、沒有審批，只有一句指向面板的指引。素材只取自凍結的 call/result 切片（標籤取自 `argsRaw`，host 鑄出的 id 取自結果的 `meta.id`），因此 replay 算繪出同一張卡；而有一個讀數天生屬於卡片：本工作階段日誌裡成功的 `cordis_undefine` 是持久且終態的，它**壓過 wire**——在 wire 上，retract 公告與一次普通 stop 長得一模一樣。

**一行同時讀兩個互相獨立的事實。** 「host 在跑什麼」來自 inventory，「**本頁**裝載了什麼」來自 runner 的 live set。每次刷新這兩者必然分叉：host 照舊跑著全部，而全新頁面什麼都沒裝。host 在跑且本頁已裝的行，給出全域性 stop；host 在跑但本頁**沒裝**的行，先給「裝回本頁」、再給那個 stop——**兩個獨立控制元件**，因為「把瀏覽器半裝到本頁」與「為所有頁面停掉這個定義」是兩件不同的事。**只有 host 半的定義完全不參與這一套**：它沒有瀏覽器半可裝，「本頁沒裝」就是它永遠的樣子，所以它的行如實讀作「執行中」，並且只給 stop。未執行時期它給出的是一個如實標注的「執行」——本頁什麼都不會裝進來，控制元件就不這麼說——而 run 請求把 `hasClientHalf` 一路帶給 runner，正是這一位讓它只起 host 半、不去取瀏覽器半。把這兩個事實塌縮成 host 的 `running` 一個，會讓刷新後的頁面只剩全域性 stop，於是文件寫明的刷新復原路徑（拉 inventory、把定義裝回本頁）**沒有任何控制元件可走**。

**裝載成功之後的崩潰，同樣屬於這一行。** 瀏覽器半可以裝載成功、讓 `cordis_run` 答 ok，之後纔在 React 算繪它時拋出例外——像誤用 `setInterval` 這類錯誤的教學文案只會落到瀏覽器主控臺，而模型和看著面板的人都不讀那裡。所以該行會把 runner 記下的、屬於本頁的最後一次算繪失敗就地顯示在行內，與裝載失敗共用同一個位置：一個是「它從來沒裝上」，另一個是「它裝上了、然後拋了」，而一行可以如實地把兩者都顯示出來。這行文案會點名崩潰的那個座位，並回答隨之而來的那個問題——他們的東西還有沒有留在螢幕上：遮蔽式座位會讓崩潰的條目退場，出廠 UI 隨之回來；而 chain 條目會保住自己的位置，它的 UI 可能只是不完整。

兩個面都不把執行態放進元件 state——define 呼叫結帳時卡片會在聊天流裡換位置並重掛。事實活在「誰能關閉它、就歸誰」的觀察量裡：瀏覽器側 runner 擁有開放請求、編排結果（是它寄出 resolve，包括別的頁面先應答的情形）與本頁的 live set及其算繪失敗——它是唯一在監視 `slots.onEntryError` 的一方，也是唯一能把崩潰的條目對映回註冊它的那個包的一方——而本包擁有自己讀來的清單與摺疊過的公告。

`/client` 匯出面是外掛程式體（`apply`/`inject`）加註入面、執行態、埠與事件載荷類型。

## 模型體驗

間接影響，經由這兩個面驅動的 run 與 stop 動詞——run 走瀏覽器側 runner 的編排，stop 走 `dynamicCordisRunner.stop`，與模型的 `cordis_run` / `cordis_stop` 工具是同一批 host 動詞。因此正在執行的定義隨後貢獻了什麼是 runner 的效果，而本包不產生任何模型可見輸入：它只算繪已落日誌的 call/result 切片與一次 host 清單讀取，不加 prompt 內容、不寫工作階段事件，並刻意不為「有人批准 / 拒絕 / 執行 / 停止」留下工作階段日誌痕跡。

#### KV 快取影響

無：沒有任何 prompt 輸入源自這裡，應答一次 run 請求既不延長也不改寫歷史尾部。

## 已知限制與欠帳

- **已展開的面板看不到「不廣播任何東西」的登錄檔變化** —— `cordis_define`，以及對一個並未在執行的定義執行 undefine，都會改變登錄檔卻不寄出下發公告；因此跨過這類變化時，已展開的面板會保留舊行，直到收起再展開（展開即重讀）。run 請求是例外，因為它阻塞模型：它既自己算繪出行，也觸發一次讀取。對一個 host 已不持有的行動手仍然是誠實的：呼叫會答 `definition-missing`，該行隨即轉入終態。「展開期間輪詢」評估過，代價不值，已否決。
- **只有請求、沒有清單的行可應答但不可操作** —— 它只提供允許/拒絕，因為 run/stop 開關需要那次讀取尚未送達的登錄檔行。歸組與文案不受影響（ask 自帶工作階段、標題與用途）。
- **若編排跑在學取之前，該行會消失一次讀取的時長** —— 活動的 orchestrating 臂帶工作階段但**刻意不帶標題**：使用者自發的 run 根本不存在可取標題的 ask，而拿 id 當名字比短暫缺行更難看。所以一個已批准、但登錄檔讀取尚未落地的請求，在學取落地前沒有行。實踐中這次讀取在請求**到達時**就已觸發，所以等到有人應答時它幾乎總已落地。
- **算繪失敗是本頁自己的讀數，而且它來得太晚、趕不上 run 的回執** —— 面板顯示的是 runner 在**本頁**看到的最後一次崩潰，所以一個在本分頁標籤算繪正常的包，即使正在另一個分頁標籤裡崩潰，這裡也什麼都不顯示。它同樣不可能出現在 `cordis_run` 的答覆裡：算繪發生在 run 結帳之後，所以模型只能靠主動去問（`cordis_inspect what:"temporary"`）才知道，而不是從它已經寄出的那次呼叫裡得知。
- **某一頁的裝載失敗對其他頁不可見** —— host 以首個裝載回報結帳一次 dispatch，更晚的回報只記錄不動作；因此在另一頁確認之後瀏覽器半才失敗的頁面，仍會讀作執行中。那一頁能在自己的行上看到原因（runner 會報），其他頁看不到。
- **任何頁面都可以應答任何請求** —— 審批按設計是框架級的，所以某個分頁標籤裡的人可以批准模型為另一個分頁標籤正在看的工作階段所發起的 run。首個應答生效、其餘收斂；收窄「誰有權應答」延後。
- **call head 掉出事件窗的卡片會丟掉標籤** —— 卡片的 name 與 purpose 取自呼叫參數，工作階段長到把它們截斷時，卡片只能以自己的 call id 自稱。面板不受影響：host 清單攜帶標籤。
- **視窗截斷會降級「已解除安裝」這個讀數** —— 卡片憑本工作階段日誌裡成功的 `cordis_undefine` 判定已解除安裝；工作階段長到把那條結果擠出視窗時，該定義只會顯示為未執行。
