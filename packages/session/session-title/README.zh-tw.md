# @deepseek-ai/dsh-session-title

[English](README.md) | [简体中文](README.zh.md) | 繁體中文

由日誌支持的工作階段標題，提供即時確定性回退與一個選填非同步提供方。每次已接受的修訂都是僅寫入日誌的 `session/title` 事件；`foldSessionTitle()` 與 `ctx.sessionTitle.get()` 會選擇最新事件，並返回其事件 seq 和時間戳。

只有使用者 `user/message` 事件中的文字塊符合條件。第一條符合條件的提示詞會安排回退，從其開頭若干詞生成標題，並受所設定 UTF-8 位元組上限約束。系統會規範化空白、移除終端機控制序列，且截斷絕不會切斷碼點。空提示詞和非文字提示詞會等待後續符合條件的輸入。

## 服務：`SessionTitleService`（ctx 鍵：`sessionTitle`）

- `get(session)` 從活躍或重播日誌摺疊最新已接受標題。
- `refresh(session, signal?)` 在需要時物化回退，然後顯式執行已註冊提供方，處理當前符合條件的訊息。提供方錯誤或呼叫方取消都會導致返回的 Promise 被拒絕；取消不會回滾已接受的回退事件。
- `rename(session, title)` 同步接受使用者顯式標題：規範化文字、取代運送中自動工作，並追加一條 `user` 來源的 `session/title` 事件。使用者來源的最新標題會釘住該工作階段——後續使用者訊息不再安排自動修訂；顯式 `refresh` 仍是有意的解釘手段。
- `register(provider)` 安裝唯一選填提供方，並返回可等待的 Cordis effect disposer。第二次註冊會立即拋出；對提供方執行 dispose（資源釋放）會中止待處理和活躍呼叫，等待其結帳，之後才允許註冊另一個提供方。

自動工作絕不會延遲主 agent（代理）回應。只有當帶標記、由迴圈建置的請求，其確切路由與當前已記錄的 `request/header` 匹配時，提供方纔會啟動；即使請求標頭未變而無需新快照，也適用此規則。延遲完成會直接透過 `Session` 追加一個獨立的純日誌事件，而不打開輪次。持久化會立即觀察到該事件，並在常規生命週期檢查點完成刷寫；標題發布本身不會強制刷寫。自動失敗會發出警告並保留最新標題。新的全訊息修訂、提供方 dispose、工作階段 dispose 和顯式刷新都會中止舊工作，過時的完成結果無法追加。並行顯式刷新會在提供方工作之前預留修訂號；重疊的自動／顯式回退請求共享一個工作階段本機正在進行的追加操作。服務與內建模型提供方各自追加自己的字面事件類型，因此不需要通用標題寫入標記、類型斷言或結帳佇列。服務拆卸會取消排隊工作，並在解除安裝完成前等待不回應取消的呼叫結帳完成。

fork 出的工作階段會原樣繼承種子中的標題事件。首訊息節奏不會自動為子工作階段重新生成標題；全訊息節奏可以在子工作階段收到後續使用者提示詞後追加新修訂。

## 設定

所有上限都是必填項；該庫不提供預設值。

| 鍵 | 約定 |
|---|---|
| `fallbackMaxWords` | 確定性回退中以空白分隔的最大正整數詞數。 |
| `fallbackMaxBytes` | 回退允許的最大正整數 UTF-8 位元組數；不得超過 `maxTitleBytes`。 |
| `maxTitleBytes` | 接受任何來源標題的最大正整數 UTF-8 位元組數。 |

## 提供方約定

提供方會提供帶品牌類型的穩定 id、自動模式（`first-prompt` 或 `all-prompts`）和 `generate(request)`。請求攜帶活躍工作階段、截至一次固定修訂的所有符合條件訊息、可用時當前已記錄的主請求路由，以及取消訊號。結果包含非空標題、該請求中互不重複且有序的來源訊息 seq，以及生成該標題時使用的選填提供方／模型路由。服務會在結果持久保存前進行規範化和驗證。

## 模型體驗

### 工作階段標題狀態

#### 模型看到的內容

無。`session/title` 只寫入日誌，絕不會進入工作階段介面、`deriveMessages()`、系統提示詞、工具 schema 或請求前綴。

#### Token 影響

回退與已接受的提供方修訂不會向主 agent 請求增加 token。選填提供方的獨立輔助請求由對應提供方包的文件說明。

#### KV Cache 影響

不影響主請求；標題事件不會改變重建內容或快取鍵。

## 已知限制與暫緩事項

- 刪除標題（不經顯式 `refresh` 就解釘回自動標題）、搜尋和清單索引不屬於此服務。
- 提供方登錄檔有意最多接受一個實作，因此部署若要組合相互競爭的標題策略，必須編寫一個自行負責優先級的提供方。
