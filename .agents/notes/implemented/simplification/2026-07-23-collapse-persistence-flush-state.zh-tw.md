# Agent Note: 將即時持久化歸並到單個刷寫控制器

Status: implemented

[English](2026-07-23-collapse-persistence-flush-state.md) | 繁體中文

[有界寫入批次處理決策](../architecture/2026-08-08-bounded-session-persistence-write-batching.md)取代了本 Agent Note 中的即時調度節奏。單控制器歸屬、失敗保留、按 id 序列化、退役和完全靜止的資源釋放決策仍然有效。

## 問題

持久化協調器使用彼此獨立的緩衝區、初始化容器和退役容器，以及按 id 劃分的操作鏈，表示一個活躍工作階段的寫入生命週期。這些結構反映的是同一個事實：該 `Session` 是否仍有初始化操作或事件必須完成，之後才能釋放其狀態。僅由檢查點觸發的排空還會讓每個事件都停留在易失狀態，直至另一個外掛程式請求 `session/flush`，儘管後端可以在不阻塞同步生產方的情況下開始持久化工作。

## 決策

每個活躍的 `Session` 都有一個生命週期條目，其中包含初始化和一個包私有寫入控制器。該控制器負責 `pending`、固定批次處理計時器、選填的活躍寫入、自動重試暫停和共享刷寫屏障。`session/event` 監聽器將凍結的事件複製到 `pending`；第一個事件設定固定截止時間，後續事件加入但不會重設。一次寫入會取出一個穩定的待處理前綴；寫入期間接納的事件仍留在待處理佇列中，並形成另一個獨立有界的後續批次。

`session/flush` 是即時完全靜止屏障。它等待初始化完成、取消批次處理計時器、等待任何活躍嘗試完成，並排空待處理事件，包括屏障執行期間接納的事件。後臺寫入失敗會被記錄，但不會拒絕同步事件生產方；系統會復原完整且順序不變的批次，並暫停自動重試。新事件會開啟新的固定視窗；顯式刷寫、退役或後端資源銷毀會立即重試，並在失敗再次發生時向呼叫方暴露失敗。

初始化只進入現有的按 id 操作鏈一次，並在佔有該輪執行權時呼叫未序列化的核心操作。該操作鏈與活躍控制器保持分離，因為公共 `create`、`append`、`load` 呼叫即使沒有 `Session` 對象仍可能發生競態，依然需要按標識序列執行。

崩潰修復僅適用於冷態標識。對於活躍標識，`load(id)` 會在等待刷寫完成前，先對記憶體中的權威事件生成快照，再將這些事件與 `SessionState.meta`（即持久化寫入實際使用的標頭）一同返回；若輪次仍打開，則在不讀取或修復儲存的情況下拒絕該次載入。冷態載入會先在按 id 操作鏈內同步佔用對應標識，再等待讀取已儲存前綴或執行修復寫入；在這項佔用解除前，`session/created` 發布邊界會拒絕同 id 活躍工作階段的發布並將其回滾。HMR（熱模組替換）接管仍由 `loadStored` 與協調器的 cwd 檢查獨立處理，會截斷撕裂的儲存，但不會閉合權威的活躍輪次。

活躍控制器對映同時也是退役登錄檔。退役成功時，系統排空並移除其控制器；退役失敗時，控制器保留在對映中。後端資源銷毀會停止接納事件，刷寫所有仍存在的控制器，等待其餘按 id 操作完成，然後關閉後端。無需另設退役集合來重新發現未完成的工作。

## 備選方案

**保留僅由檢查點觸發的延後寫入。** 這種方式可以形成更大的批次，但會讓持久性相依性另行掛載的檢查點策略，並使檢查點之間因崩潰而丟失資料的視窗達到最大。有界後臺調度仍會合並突發事件，並在強制屏障之間持久化進度。

**在整個協調器範圍內使用一個刷寫 promise。** 這種掛接方式適用於單個文件，但全域性 promise 會序列化互不相關的工作階段。每個活躍工作階段各有一個控制器，既能讓不同工作階段的後端操作獨立推進，又由按 id 操作鏈保護同一標識的操作。

**永久鎖存首次後臺寫入錯誤。** 這會讓後續每次刷寫都得到確定的結果，卻會阻止現有的資源銷毀重試從暫時性儲存故障中復原。保留批次但不鎖存錯誤，可以同時保留可觀測性和重試能力。

**拒絕對所有活躍工作階段的載入。** 這樣做很安全，但會讓持久化消費端和測試無法再使用既有的閉合活躍工作階段快照。先生成快照再刷寫，為呼叫提供了穩定的線性化點：刷寫成功即可證明正是該快照已持久化，而活躍路徑絕不呼叫崩潰修復。

## 驗證

- 針對控制器的測試使用假時鐘證明固定視窗不會重設，隨後阻塞第一次追加，在該次寫入期間接納另一個事件，並在不呼叫 `session/flush` 的情況下觀測到自動執行的第二個持久批次。
- 共享協調器約定仍覆蓋記憶體、JSONL 和 SQLite 後端上的活躍工作階段接管、衝突、崩潰修復，以及工作階段和後端的資源釋放。
- 失敗和資源銷毀測試會讓寫入失敗的批次保持待處理，在關閉前重試這些批次，並證明尚在執行的控制器會延遲後端關閉。
- 共享後端約定會持久化一個仍打開的活躍輪次，證明 `load` 會拒絕且不會寫入合成閉合事件，隨後完成該輪次並讓其所有者退役，最後重新載入完全相同的已完成輪次。
- AgentLoop 回歸測試讓 `resume()` 與一個仍打開的活躍輪次發生競態，並證明原有的 agent（代理）仍能完成該輪次並將其持久化，其間不會注入 `interrupted` 邊界。
- 一個受控後端會阻塞 `loadStored`，在修復操作持有標識佔用期間嘗試發布同 id 工作階段，並證明回滾不會留下殘留控制器，之後可以成功復原一個閉合工作階段。
- 無所有者認領約定會為活躍 `Session` 設定不同的 `createdAt`，並證明活躍載入和之後的冷態載入均返回最初儲存的標頭。

## 後果

活躍工作階段條目把初始化與一個控制器放在一起；該控制器負責待處理事件、計時器、活躍寫入、重試暫停和刷寫屏障。協調器仍以獨立容器保存已持久化的標識狀態、準備好的冷態 Session、標識退役等待方和按 id 操作鏈，因為即使不存在可寫的活躍 Session，這些生命週期仍然存在。有界寫入縮短了通常情況下因崩潰而丟失資料的視窗，相比即時調度產生更少的後端批次，同時不改變強制屏障。

`session/flush` 不再決定普通持久化何時開始。它仍是迴圈和檢查點策略使用的順序與錯誤觀測邊界，因此檢查點成功仍表示在其完成前接納的每個事件都已持久化。
