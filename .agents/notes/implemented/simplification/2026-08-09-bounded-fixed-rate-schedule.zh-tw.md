# Agent Note: 有界固定速率 Schedule

Status: implemented

[English](2026-08-09-bounded-fixed-rate-schedule.md) | [简体中文](2026-08-09-bounded-fixed-rate-schedule.zh.md) | 繁體中文

## 問題

使用者需要簡單的重複提醒，但[持久、僅限 Session 內的提醒](../feature/2026-08-05-durable-web-schedule.md)最初採用的週期層把固定間隔和日曆表達式當成一個通用子系統。它增加了 Cron 語言與求值器、時區敏感的發生時點搜尋、tzdata 重播規則、跨記錄的 300 秒准入門控、持久化的門控證據、延遲交付欄位，以及門控耗盡狀態。即使所請求的行為只是“每 N 秒重複一次”，這些機制仍會擴大持久協議與 live owner。

cold 或 busy Session 也無法有效重播每個錯過的間隔。這樣做會產生模型輪次積壓，其規模取決於停機時長；如果改為按交付時間移動下一個目標，則會使固定速率發生漂移。

## 決策

保留的週期 selector 只有 `every_seconds`，其值必須是至少為 300 的安全整數。建立時會把第一個目標存為建立時刻加上一個間隔。每次 dispatch 都會儲存記錄 id 和一個由牆鐘確定的 `acceptedAt`；純整數運算會選出不晚於該決策時點、與建立錨點對齊的最新發生時點，並直接推進到其後的第一個對齊目標。系統不會枚舉、持久化或重播錯過的發生時點。

沒有一次性提醒到期時，所有不同的逾期 Every 記錄都會按目標時間和建立順序參與同一個 follow-up 批次。每條記錄恰好貢獻一個最新發生時點，該批次中的每個 dispatch 都使用相同的決策時點。已到期的一次性提醒仍然優先，因此已經承諾的單次提醒不會被隱藏在週期批次中。

至少 5 分鐘是每條 Every 規則自身的屬性，而不是全域性門控。系統不存在 `lastRecurringAcceptedAt`、`deliveryNotBefore`、冷卻、配額、門控耗盡狀態或通用週期記錄抽象。如果運算無法表示下一個採用四位年份的 UTC 目標，最後一次 dispatch 會終結該記錄。

日曆表達式與 Cron 表達式，以及相應的求值器相依性、parser、canonicalizer、時區搜尋、頻率證明、持久記錄和 dispatch variant、測試、快照與第三方聲明條目均已移除。嚴格的版本 1 decoder 會拒絕預發布階段的舊 Cron 記錄，而不是遷移它們或透過相容性殘留接受它們。

## 已考慮的替代方案

**保留全域性週期准入門控。** 共享門控可以約束模型輪次總數，卻會使無關提醒彼此延遲，並需要持久的跨記錄歷史。批次處理已經會把當前所有逾期固定速率記錄合併成一個模型請求，而每條規則自身的最小間隔會約束喚醒頻率。

**重播每個錯過的發生時點。** 這樣可以保留每個名義事件，卻會在停機後產生無界積壓，並不符合提醒的使用習慣。只追趕最新一次可以傳達當前到期工作，而不會假裝 Session 一直處於 live 狀態。

**從 dispatch 時刻開始推進。** 這種運算更簡單，卻會把固定速率變成發生漂移的延時迴圈。保留下一個與錨點對齊的目標，才能維持使用者設定的間隔。

**把 Cron 保留為選填分支。** 即使隔離在 selector 之後，Cron 仍需要日曆文法、相依性、時區與夏令時策略、重播校驗和龐大的測試範圍。固定間隔可以提供實用的週期場景，而無需擴散這些複雜性。

**每個輪次只 dispatch 一條 Every 記錄。** 這會序列處理無關的逾期工作，使後續多個輪次只能處理這組記錄。一個批次既能保留彼此獨立的提醒，又能約束模型請求數量。

## 驗證

嚴格 decoder 與不變式測試會拒絕不受支持的規則和 dispatch 形狀。領域測試與屬性測試證明最小頻率校驗、建立錨點運算、只選擇最新一次、推進和範圍耗盡。執行時期測試證明一次性提醒優先、所有逾期 Every 記錄共享一個批次、每條記錄只有一個發生時點、固定順序，以及不會立即迴圈處理積壓。組裝 Web 快照證明，一個包含 2 條逾期記錄的批次會產生一條普通 assistant 回應，以及兩個使用相同時點的持久轉換，並且不存在 Schedule UI sidecar。原始碼、相依性與生成目錄審計會拒絕 Cron 和全域性門控殘留。

## 後果

- 持久規則 union 包含 After、At 與 Every；工具 selector union 包含 `after_seconds`、`at` 與 `every_seconds`。
- 重新打開長期 cold 的 Session 時只會產生當前提醒工作，不會集中觸發大量歷史輪次。
- 多條逾期 Every 記錄共享一個模型請求，但不共享調度狀態，也不會彼此延遲。
- 基於日曆的週期性需要未來的產品邊界，而不是休眠相容程式碼。
