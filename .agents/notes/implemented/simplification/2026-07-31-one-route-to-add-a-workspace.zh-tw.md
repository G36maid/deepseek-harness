# Agent Note: 新增 Workspace 的唯一路徑

Status: implemented

[English](2026-07-31-one-route-to-add-a-workspace.md) | [简体中文](2026-07-31-one-route-to-add-a-workspace.zh.md) | 繁體中文

## 問題

兩處 Workspace 表層——側邊欄區頭的 `+` 與工作階段主視覺區的 chip——都提供了兩條獲得 Workspace 的路徑：**打開本機資料夾…** 拉起組合的目錄流程，**新建工作區** 接收一個名稱並建立 `<workspaceRoot>/<name>`。兩者重疊：瀏覽佔用者自帶 **新建資料夾** 能力，因此「選一個目錄」本就覆蓋了「建一個目錄」。兩個入口意味著同一結果有兩套詞彙、一個自帶重名規則的名稱對話框，以及一個操作者既看不到也選不了的建立位置。

刪掉較弱的那個入口後，側邊欄區頭只剩一個動作，於是引出了本決策一並裁定的展示問題：只有一行的浮層應該長什麼樣。

## 決策

新增 Workspace 只有一條路徑：透過組合的目錄流程選一個宿主機目錄，新建的或已存在的都可以。入口是 `menu.addWorkspace`（「新增工作區…」/ "Add workspace…"）；按名稱建立的對話框及其 `create.*`／`menu.createWorkspace`／`workspace.new` 文案全部刪除。標籤命名的是結果而非機制，因為它現在是通往該結果的唯一一扇門——找「新建」的使用者必須能找到它。

**選單的存在是為了在多個目標之間消歧。** 當只剩新增這一個入口時——僅新增的側邊欄表層，或清單為空的主視覺區——錨點手勢*就是*該動作：直接拉起流程，不渲染浮層。只有一行的浮層多花一次點擊，卻沒有任何選填項。這條規則是一個謂詞（`addIsTheOnlyEntry`）覆蓋兩處表層，而不是逐表層特判。

由該規則派生出兩條邊界，它們同屬這個決定：

- **清單為空只有在基線落地後纔算最終結果。** `phase` 仍為 `pending` 時，主視覺區保留選單與載入狀態，而不是跳進一個即將到達的 workspace 會使其變得多餘的流程。僅新增表層不列任何東西，因此從不等待。
- **目錄流程的洞沒有佔用者時，就沒有任何可新增的手段。** 此時側邊欄區頭乾脆不渲染按鈕，而不是留下一個點了沒反應的按鈕；主視覺區的選單則繼續作為選擇器工作，列出已有內容——而當同樣沒有內容可列時，它什麼也不彈：空浮層會宣稱一個並不存在的選擇。這是 seam 文件化的無流程默認行為走到它的結論：佔用者不在，唯一的建立能力也就不在。主視覺區的錨點 chip 歸 ui-conversation 所有，因此本包能壓掉浮層，卻無法隱藏該 chip。

直接拉起的這條路徑同樣遵守選單項聲明的 busy 規則：某次選取仍在接納中（`flowBusy`）時，錨點手勢會被攔截，效果與停用該選單項完全相同，從而避免遲到的結果與第二個流程發生競態。

`WorkspaceCreateFlow` 現更名為 `WorkspacePickFlow`，其 `createOnly` prop 更名為 `addOnly`；注入的 `createWorkspace` 從 `{ name } | { path }` 收窄為 `{ path }`。

## Wire 與 CLI（命令列介面）表層

`workspace.create` 只接受 `{ path }`；wire schema 與 `WorkspaceApi` 沒有 `name` 成員。閘道沒有 `workspaceRoot` 設定；用戶端約定只透過 `WorkspaceCreateInput`、`WorkspaceRuntime.create` 與 `intentName` 提供按路徑接納，`dsh web` 沒有 `--workspace-root` flag。`workspace-name-conflict` 仍保留在 wire 上，作為 `workspace.rename` 的標題重名錯誤。

## 測試

`connectFreshWorkspace`——所有 web e2e 場景啟動時都會走的輔助函式——會預先備好 `<root>/workspace`，再經對話框的路徑編輯器接納它，因此產出的工作階段 cwd 與按名稱建立時完全一致，場景 golden 保持有效。選擇預先備好而不是在對話框內新建，是為了讓該輔助函式在一個場景可能發生的多次連線之間保持冪等（第二次建立同一個資料夾會失敗，而建立對話框會在失敗時把流程停在原地）。在選擇器內新建資料夾——同一條路徑的另一半——由 `workspace-management.e2e.ts` 覆蓋，它承擔針對性覆蓋：在對話框自己建立的資料夾上新增兩個 workspace、接納 basename 相同的不同目錄並保持彼此獨立、在另一個目錄上複用已刪除的標題、以及瀏覽對話框的 aria golden。

`smoke-real.e2e.ts` 是唯一啟動未打修補程式的出廠設定樹的場景，其中 `-auto` 行會按宿主機解析；它現在透過 `--config` overlay 釘死 `-browse`，使開發機的顯示環境無法決定選擇器是否可被驅動程式。

## 考慮過的替代方案

**保留 `打开本地文件夹…` 作為標籤。** 否決：合併後該入口既能打開也能建立，用機制命名會恰好對那些入口被我們刪掉的使用者隱藏建立這一半。反方理由——「本機」二字有效區分了瀏覽器所在機器與 harness 所在機器——在下一步就由對話框自身的標題和麵包屑回答了。

**保留雙入口選單，讓 `新建工作区` 也打開同一個流程。** 否決：同一動作兩個標籤正是本次改動所消除的混淆，而不是它的縮小版。

**為了與主視覺區選單保持一致而保留只有一行的浮層。** 否決：不提供選擇的浮層是一次浪費的點擊，讀起來像半成品。這裡要一致的是*規則*（有選單 ⇔ 存在選擇），不是控制元件。

**為將來可能新增的入口（克隆倉庫、遠端目錄）保留選單殼。** 否決，依據「require a current owner and need」：這樣的入口目前並不存在，而等它到來時再復原選單，比現在就發一個空殼的改動更小。

**在同一改動中刪除 wire 的按名稱建立分支。** 否決，因為 UI 決定不相依性後端與 CLI 刪除，後兩者各自的約定和測試構成一項可獨立評審的改動。

**在 e2e scaffold 中經 host 註冊 workspace，而不驅動程式對話框。** 否決：那會讓全部 15 個場景與選擇器解耦，整條 lane 將無法證明倖存的這條路徑能走到可用的 composer。現在每個場景都會走真實對話框來接納自己的目錄；只有「新建資料夾」那一半集中在一個場景裡，因為處處重複只會讓共享輔助函式失去冪等性，卻換不來額外訊號。

## 後果

- UI 只在操作者選擇的目錄下建立 Workspace 資料夾。沒有伺服器端控制的設定約束其位置；需要該約束的部署必須明確加入該約束。
- picker 設定的可達範圍決定剩餘路徑可用的宿主機檔案系統；不存在另一個設定好的父目錄。
- 掛載 `ui-workspace` 但沒有 directory-picker 包的組合無法新增 Workspace，也不渲染按鈕。
- 主視覺區的 chip 仍聲明 `aria-haspopup="menu"`，而直接拉起的路徑實際彈出的是對話框。要讓該聲明如實反映實際行為，需要把流程的展示方式經 `conversation.hero.workspace` 的 owner 約定上報——決定權在流程，播報權在 chip，兩者分屬不同的包——因此這被列為一項具名的後續工作，而不是一處無聲的不一致。本次新增的側邊欄按鈕完全不作任何 popup 聲明。
