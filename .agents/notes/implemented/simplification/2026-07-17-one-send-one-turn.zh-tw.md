# Agent Note: 刪除普通 send 的隱式批次處理

Status: implemented

[English](2026-07-17-one-send-one-turn.md) | [简体中文](2026-07-17-one-send-one-turn.zh.md) | 繁體中文

## 問題

假設呼叫方連續兩次呼叫 `Agent.send()`，先提交訊息 A，再提交訊息 B。隱式批次處理可能只因為驅動器讀取佇列時兩則訊息都在等待，就把 A、B 放進同一個輪次。呼叫方明明呼叫了兩次，agent loop（代理循環）卻悄悄把它們變成一個工作單元。

這種分組取決於執行時期機，而不是呼叫方的意圖。因此，即使所有呼叫方使用相同 API，來自同一個同步呼叫棧、相鄰微任務、事件監聽器和模型回呼的呼叫也可能產生不同分組。

這種分組改變的不只是模型呼叫次數。一個普通輪次包含一條已領取 follow-up、`turn/start`、`turn/end` 和持久性檢查點。如果訊息 B 與訊息 A 共用輪次，B 可能直接進入 A 的模型請求，而不是先看到 A 在工作階段日誌中已經關閉的結果。若系統讓一條 follow-up 進入、卻拒絕另一條，還需要引入呼叫方沒有請求的混合狀態。

## 決策

一次成功的 `send()` 建立一個獨立的 FIFO 佇列項。該佇列項如果執行，就是所在輪次中唯一的普通訊息。佇列項可能在啟動前被丟棄，因此精確保證是最多一個輪次，而不是必定一個輪次；兩次 send 絕不會被悄悄合併。

訊息插入之前，`send()` 會檢查 agent 狀態，並接受已有標識且經過深度凍結的值。持久化 splice 與 `agent/inbox/inserted { message }` 會保留其 `MessageId`；在驅動器領取或丟棄該訊息之前，可以透過 `Inbox.replace()` 與 `Inbox.remove()` 尋址。當前生命週期由[已領取 pre-step inbox 決策](../architecture/2026-07-31-claimed-pre-step-inbox-lifecycle.md)規定。

如果訊息 A、B 都進入處理，B 的輪次只能在 A 記錄 `turn/end` 且 A 的持久性檢查點處理結束後開始。因此，B 的請求能看到 A 在同一工作階段日誌中留下的已關閉結果。檢查點錯誤會照常報告，但處理結束只表示解除這道順序屏障，不表示失敗的寫入已經持久化。面向整個 agent 的 `cancel()`、dispose（資源釋放）或 `turn/start` 之前的失敗也可能丟棄尚未啟動的佇列項，而不打開一個空輪次。

輪次邊界上，迴圈會先打開輪次，再在待處理 next-step 輸入之後領取一條 follow-up。`agent/pre-step` 要麼拒絕提案，要麼返回進入步驟的完整批次。被拒絕的 follow-up 保持已刪除，並關閉一個受阻的無步驟輪次，不寫入模型可見歷史。實作中不存在混合普通 follow-up 分支。

上述不合批規則只適用於普通 follow-up 輸入。`steer()` 會把輸入放入 next-step inbox 並喚醒驅動器。在輪次期間，迴圈可以在後續步驟邊界領取它；agent 空閒時，這個會喚醒的 next-step 批次會啟動一個新輪次。批次被領取後纔到達的輸入會等待後續邊界，而取消或 dispose 可以將其丟棄。

`inject()` 繼續新增面向模型的上下文，但不提交普通輸入，也不喚醒驅動器。即使 agent 空閒，它也始終在 next-step inbox 中等待後續 pre-step；AgentLoop 只會在 enter 決策於輪次內返回它時，將其記錄為 `user/message`。`cancel()` 仍是面向整個 agent 的操作，可以清空所有尚未啟動的普通輸入、steering（中途引導）和注入，並中止當前步驟。`status` 和 `whenIdle()` 描述的也是整個 agent，而不是某一則訊息。

## 曾考慮的替代方案

**保留普通 send 的自動批次處理，以減少模型呼叫。** 當訊息進入佇列的速度超過驅動器的處理速度時，這種做法可以提高吞吐量，但會讓輪次邊界取決於調度，並讓後一則訊息在前一輪關閉且到達檢查點之前執行。本決策保留可預測的邊界，並接受額外呼叫。未來若要加入批次處理功能，必須提供呼叫方可見的顯式約定，並有測量結果作為依據。

## 驗證

- 單元測試和基於屬性的測試從同一呼叫棧、相鄰微任務、不同生產方和重入回呼提交 send；每則訊息都會得到一個按 FIFO 排序的獨立輪次。
- stdio 建置產物測試提交兩行輸入，並觀察到兩個模型請求和兩個輪次邊界。
- 延遲和拒絕第一個輪次的檢查點，都能讓下一個輪次保持等待，並證明其請求會看到前一條助手結果。
- 失敗路徑測試覆蓋 pre-step 拒絕、監聽器失敗、面向整個 agent 的取消、dispose 和 `turn/start` 之前的失敗；首次 pre-step 的各種退出都會關閉邊界平衡的無步驟輪次，訊息不會合並，之後仍需處理的工作也能繼續清空。
- 其他測試分別覆蓋輪次打開時、輪次失敗後和空閒時的 `steer()`，以及待處理的 `inject()`、面向整個 agent 的狀態和 `whenIdle()`。

## 後果

普通輪次的邊界可預測：訊息 A、B 始終分開，B 只能在 A 關閉並到達檢查點後執行。呼叫方仍然拿不到逐次 send 的完成控制代碼；待處理訊息可透過其 `MessageId` 移除，面向整個 agent 的取消可以丟棄整個尚未啟動的隊尾，而狀態與完全靜止仍是面向整個 agent 的觀察。

代價是模型請求和檢查點都會增加。繁忙佇列可能需要更長時間才能清空；如果生產方持續提交訊息，佇列也可能成長。只有建立顯式且經過測量的約定後，才能重新引入普通 send 批次處理。
