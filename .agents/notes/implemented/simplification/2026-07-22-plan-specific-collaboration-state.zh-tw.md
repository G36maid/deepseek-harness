# Agent Note: plan 專用協作狀態

Status: implemented

[English](2026-07-22-plan-specific-collaboration-state.md) | [简体中文](2026-07-22-plan-specific-collaboration-state.zh.md) | 繁體中文

## 問題

產品只交付了 `plan`，首個 plan mode 實作卻引入了通用的具名模式登錄檔。`ModeConfig.modes`、定義名稱校驗、`ctx.modes.list()`、已退役定義的回退邏輯，以及測試中合成的 `review` 模式，都只為支持假想中的未來協作模式而存在。plan 引導、`/plan` 和 `exit_plan_mode` 這些生產專用行為仍位於同一個包內，因此通用 API 並未將可複用機制與 plan 策略隔離開來。

「mode」一詞還橫跨互不相關的領域。沙盒模式是由 `ctx.sandboxPolicy` 擁有、以 `sandbox/mode` 記錄日誌的強制執行策略；plan mode 則是一種協作方式，會貢獻引導內容和經評審的退出路徑。若把兩者都視為同一個具名模式抽象的實例，就會掩蓋二者各自獨立的歸屬關係。傳輸協議的通用詞彙並不能證明 harness 需要通用模式領域。

Plan mode 還需要持久協作狀態、可評審的計畫產物、顯式人工決策邊界，以及跨復原與 fork 的請求重建。即使移除通用登錄檔和 ACP（Agent Client Protocol）互動投影，這些要求仍歸 plan 功能所有。

## 決策

Plan mode 擁有一個 plan 專用產品包：位於 `packages/plan/plan-mode/` 的 `@deepseek-ai/dsh-plan-mode`。持久化事實為 `plan/mode: { active: boolean }`，由 `foldPlanMode(events)` 摺疊，空日誌值為 `false`。`ctx.planMode.get(agent)` 返回 `{ active, pending? }`，`set(agent, active)` 則記錄在邊界生效的選擇。pre-step、重試、追加失敗和 dispose（資源釋放）柵欄保留相同的狀態轉換歸屬。

設定嚴格為 `{ section: string }`。該包自行註冊固定的 `plan:policy` 段、`/plan [message]`、精確匹配的 `/plan off` 主動退出形式，以及 `exit_plan_mode`。不帶參數的 `/plan` 選擇啟用；其他非空參數則先選擇啟用，再透過 `agent.steer()` 傳送去除首尾空白後的文字，使該文字在受影響的步驟中成為一條記錄到日誌的普通使用者訊息。`/plan off` 選擇未啟用，不產生模型輸入，並可取消仍待在邊界生效的進入選擇。即使 plan mode 未啟用，退出工具仍保持註冊，以確保請求工具目錄穩定。

面向人類的組合擁有 plan 選擇與評審。本筆記最初把 ACP 協議級的 `default`/`plan` 選擇器保留為布林服務之上的配接器；[ACP 作為僅面向自動化的協議](2026-07-23-acp-automation-only-protocol.md) 取代了那個協議投影，因此 ACP 組合現在既不掛載 plan mode，也不提供模式選擇協議。

沙盒模式與審批策略仍是彼此獨立的強制約束軸。Plan mode 既不讀取也不寫入二者；此次簡化也沒有為這些概念引入共享基類型、登錄檔或預設抽象。

### 邊界與模型約定

`plan/mode` 僅記錄到日誌且不進入表層，因此復原、fork 和壓縮（compaction）都能復原該狀態，無需即時映像檔。spawn 出的 agent（代理）初始處於未啟用狀態，因為建立時沒有 plan 選項。待生效的使用者選擇會在初始或續步 pre-step 時，或在請求復原重試時，於受影響的請求組裝前寫入日誌；持久追加失敗會讓意圖保持待定，留到後續邊界處理。

啟用狀態在提示詞順序 50 處貢獻部署提供的區段。未啟用狀態不貢獻區段，但 `exit_plan_mode` 在兩種狀態下都保持註冊，因此狀態轉換會改變已記錄的請求標頭，卻不改變原生工具 schema 或 Code Mode SDK。使用者發起的轉換只會在上一條請求標頭描述相反狀態時追加一條來源為外掛程式的通知；第一次請求前的選擇或最終狀態未變化的選擇不會追加通知，經批准的工具退出則相依性其工具結果，不再追加第二條通知。

### 經評審的退出

`exit_plan_mode` 要求呼叫方 agent 處於啟用的 plan mode，並提交一份非空、以標題開頭的 markdown 計畫。使用者互動問題將這份原樣計畫作為詳情，並提供 `Approve`、`Keep planning` 和自由文字回饋。僅當唯一選擇為 `Approve` 且沒有自訂文字時才視為同意；其他所有回答都會留在 plan mode，並向模型返回糾正性回饋。經批准的退出會成為一項靜默的待生效選擇，使 plan 引導在當前工具批次的剩餘部分繼續有效，並在下一次請求前移除。

工具將提交的計畫渲染為 generic 卡片，標題取自第一個標題。使用者互動提供方缺失或失敗、評審失敗，或評審待定期間外掛程式被 dispose，均會拒絕退出，並保留手動 `/plan off` 作為人類退出路徑。

## 刪除的介面

- 任意定義對映、模式名正規表達式、保留名稱規則以及逐定義命令迴圈。
- `ModeDefinition`、解析後的定義對映、`ctx.modes.list()`、字串值的 get/set 狀態，以及未知或已退役模式處理。
- 僅用於測試的 `review` 模式用例，以及可透過設定新增其他模式的表述。
- 通用的 `mode/set` 與 `mode:policy` 名稱；plan 包擁有 `plan/mode` 與 `plan:policy`。

## 考慮過的替代方案

**保留私有的通用登錄檔，目前只暴露 plan。** 不予採納，因為沒有第二個生產消費端時，仍需維護和測試未使用的名稱與設定機制。未來若出現另一種協作狀態，可以從兩個具體案例出發建立合適的共享 seam。

**將沙盒或審批策略摺疊進 plan 狀態。** 不予採納，因為協作引導、執行約束和權限決策有不同的歸屬方、生命週期語義和消費端。由 mode 擁有的沙盒上限還會讓使用者顯式選擇沙盒看似成功，實際卻被靜默忽略。

**讓一種呈現傳輸擁有 plan 狀態。** 不予採納，因為 TUI、Web、復原、fork、提示詞組裝和退出工具都需要獨立於任何單一傳輸使用同一項已記錄事實。呈現配接器只擁有各自的投影。

**拆成能力 seam 三包，或把狀態放進 agent loop（代理循環）。** 不予採納，因為 plan mode 沒有可替換後端，而現有的工作階段、提示詞、工具、命令和生命週期擴充點已經提供所需的全部掛鉤。

**將狀態切換寫入表層訊息，或把計畫存入文件。** 不予採納，因為協作狀態是僅日誌事實，工具參數已經記錄了可評審的計畫。重複寫入表層會消耗模型上下文，而計畫目錄會形成第二個持久歸屬。

**按 plan 專用名稱允許清單或全域性策略棧篩選工具。** 不予採納，因為可變性是每個工具自身的屬性，包括未來工具和 MCP 工具，而不應由每個 plan 部署維護一份清單。只有出現具體消費端後，effects 元資料才能建立共享策略；在此之前，plan mode 是引導機制，不是安全邊界。

**透過審批 seam 或普通文字完成評審。** 不予採納，因為計畫評審不是權限決策，需要原樣的計畫產物和糾正性自由文字，而且必須以已記錄的工具呼叫作為結構化轉換。使用者互動 seam 提供了這項約定。

## 驗證

- 包測試透過布林服務繼續覆蓋邊界順序、重試、追加失敗、HMR（熱模組替換）資源釋放、提示詞組裝、穩定的原生 schema 與 Code Mode schema、評審結果和不變式。
- 命令測試覆蓋不帶參數的 `/plan`、`/plan <message>`、啟用狀態下的 `/plan off`、取消待生效的進入選擇、未啟用狀態下的冪等性、不存在 `/mode` 和 `/review`，以及隨 effect 作用域移除。
- 無金鑰 TUI 場景透過 `/plan <message>` 進入、透過 `/plan off` 退出，並證明每個已提交的 `plan/mode` 都先於其所改變的請求標頭，進入訊息在 plan 引導下記錄到日誌，且退出後的請求不含該引導。
- 完整的 `exit_plan_mode` 評審流程有包測試，但互動式 ACP 場景退役後沒有組裝應用快照；當前無金鑰 TUI 場景只覆蓋命令進入和直接退出。

## 後果

該實作只用一套詞彙描述一項已交付功能。若要新增另一種協作方式，必須顯式作出設計決策，而不能只增加設定項；自動化用戶端不會透過 ACP 獲得面向人類的模式控制。根據倉庫的預發布格式策略，本次遷移有意拒絕舊的 `mode/set` 日誌與 `modes.plan.section` 設定。

Plan 狀態仍可重建，工具 schema 仍保持穩定，但如果行程在下一邊界前退出，空閒狀態下待生效的選擇會丟失。進入或離開 plan mode 會改變提示詞順序 50 處及其後的內容；如果模型忽略引導，仍可能執行修改，除非部署另行設定沙盒、審批或檔案系統策略。
