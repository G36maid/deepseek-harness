# Agent Note: CI 消費端獨立建置

Status: implemented

[English](2026-07-30-independent-ci-consumer-build.md) | 繁體中文

## 問題

[大型執行器拓撲](2026-07-22-evidence-based-larger-hosted-runners.md)將靜態閘門清單和建置後消費端清單分配給不同作業，但二者共用的建置由靜態作業負責。靜態作業要等所有靜態閘門完成後才上傳生成的目錄樹，消費端作業則在復原該目錄樹前聲明瞭作業級相依性。基於編譯輸出的快照與發布校驗確實需要完整建置，但不相依性執行時期相依性閉包檢查、文件生成、模組圖驗證或 Knip。

這項過寬的相依性使執行器可用性成為必需關鍵鏈的一環。一次故障切換執行中，靜態作業等待執行器 8 分 1 秒，隨後執行 1 分 41 秒；直到此時，消費端作業才能進入同一個共享池，它又等待 10 分 34 秒，隨後執行 1 分 58 秒。複用靜態作業的建置省去了部分倉庫工作，卻讓兩次原本相互獨立的執行器分配序列發生。

## 決策

3 個必需 Linux 作業分別進入執行器分配。覆蓋率仍只消費原始碼。靜態作業負責無需消費生成輸出的原始碼檢查與文件檢查。消費端作業負責唯一一次 Linux 建置，以及文件型別檢查、基於編譯輸出的快照、發布校驗、NodeNext 檢查和 built-bin 冒煙測試。

消費端內部的閘門圖保留實際相依性關係。建置和只消費原始碼的 Node 相容性檢查率先啟動；publint 等待建置完成，已建置包不變式檢查會驗證該發布檢視表，所有編譯輸出消費端都等待這項驗證完成。因此，示例和 Web 快照仍會在普通 Node 下驗證當前 `lib/` 輸出；同時，沒有任何 GitHub 作業需要等待無關作業或傳輸已建置目錄樹產物。

Windows 與序列參考聚合流程仍各自負責自身建置。本變更僅涉及Pull Request的必需 Linux 拓撲；`all checks passed` 仍聚合約一批具名作業，任一相依性未成功時都會失敗。

## 曾考慮的替代方案

**繼續發布靜態作業的建置。** 此方案只需建置一次，卻無法表達實際的步驟級相依性：GitHub 會讓消費端等到整個靜態作業結束後纔可請求執行器。故障切換池飽和時，再次排隊的延遲超過了省下的建置時間。

**在兩個作業中分別獨立建置。** 在靜態作業中保留建置、同時移除作業相依性，可以復原平行分配，但每個Pull Request都會對同一目錄樹編譯兩次。將文件型別檢查和建置職責移給消費端，則仍只需建置一次。

**新增專用建置作業。** 職責單一的生產方能讓相依性名稱與實際關係相符，但會在消費端之前新增第 4 個需要設定和分配執行器的階段。所有需要持續使用生成輸出的任務都已由消費端作業負責，因此單獨增設生產方也沒有第二個相互獨立的消費端。

**僅在故障切換期間合併靜態作業與消費端作業。** 單個長作業可以避免第二次分配，但帶條件分支的作業清單與結果聚合會形成第二套 CI 拓撲。獨立作業能讓託管池與故障切換池使用同一作業圖。

## 後果

靜態作業與消費端作業的排隊延遲會相互重疊，不再累加。消費端的活動耗時包含建置；靜態作業則變短，產物上傳、下載、壓縮和解壓步驟全部消失。Linux 建置總次數仍為 1 次。

靜態作業失敗不再阻止消費端清單生成自身證據；最終判定仍會失敗。建置與文件型別檢查失敗會歸入 `node 24 / snapshots and artifacts` 而非 `node 24 / static`，這一歸類與輸出相依性的實際歸屬一致。
