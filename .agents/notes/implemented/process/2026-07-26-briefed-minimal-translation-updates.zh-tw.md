# Agent Note: 基於簡報的最小化翻譯更新

Status: implemented

[English](2026-07-26-briefed-minimal-translation-updates.md) | [简体中文](2026-07-26-briefed-minimal-translation-updates.zh.md) | 繁體中文

## 問題

[雙語配對約定](2026-07-02-bilingual-docs-and-pairing-gate.md)早已規定對側檔案按最小幅度更新：把被改的一側與其上次確認狀態做 diff，據此修補對側檔案，絕不整篇重譯；但倉庫內建的工作流程讓每次更新都付出整篇文件等級的開銷。負責翻譯的 subagent 在動手處理一個兩行的 diff 之前，要先載入完整的指導語料（guidance corpus），即 skill（技能）、配對約定、翻譯規則、192 行的術語表、語體樣例與行文標準；要透過 `git cat-file` 手工重新推導上次確認狀態以來的 diff；每輪迭代還要重跑全語料配對閘門，而該閘門為校驗一個配對要解析整棵樹裡的每一個配對。一次小的英文行文修改，動輒花掉數十倍於其應得份額的 token 用量與分鐘數，被懲罰的恰恰是約定想要的行為：在同一個 PR（Pull Request）裡把對側檔案一並帶上。

## 決策

擴充的手動工作流程使用生成的簡報（briefing）而非指導語料來更新配對；該工作流程中的新配對仍採用保持不變的整篇文件路徑。常規 agent 工作採用由[輕量翻譯決策](2026-08-08-lightweight-routine-documentation-translation.md)定義的直接路徑。

- **`pnpm run gen-translation-brief [--apply] [pair...]`**（[scripts/gen-translation-brief.ts](../../../../scripts/gen-translation-brief.ts)，組裝邏輯在 [scripts/translation-brief.ts](../../../../scripts/translation-brief.ts)）針對每個失去同步的配對，列印被改一側從其記錄在案的上次確認 blob 到當前工作區的 diff，並附上以能安全對齊的最窄粒度對映的這次改動，對映失敗時粒度確定性地逐級放寬：僅落在配對中逐位元組一致的圍欄程式碼區塊內的改動會直接算出（`--apply` 會把它拼接進對側檔案，並在寫入前用配對閘門的結構簽章校驗所得結果）；否則，每個有改動的 Markdown 單元（標題、段落、表格行、清單項、圍欄程式碼區塊、塊引用、HTML 塊、分隔線、連結定義；匹配依據是以容器為作用域的種類序列）都帶上各自的上次確認源文、當前源文與當前對側文字及行號；無法對齊的單元回退到按深度匹配的標題章節；當章節也無法對齊或兩側同時漂移時，簡報會明說這一點並省略對映，而不是靠猜。術語錶行只與改動塊匹配（英文術語按詞邊界匹配，含複數變形）；當目標側是中文時，簡報還會跟蹤每個相關術語在整篇文件中的首次出現：一旦某次編輯使其移位，騰出的與接收的兩處區間就會附一條解釋性說明加入簡報，因為「首次出現」括注必須隨之移動。單元對映、程式碼拼接與首次出現機制採納了增量提示詞管線工作的規劃器設計；該項工作中接入提供方的對比評測，已為自動管線獨立驗證了同一套範圍階梯。簡報就是譯者的全部工作集；簡報回答不了的決策，仍以完整的真源文件作為升級求證路徑。
- **顯式呼叫時，[dsh-translate-docs](../../../skills/dsh-translate-docs/SKILL.md) 中的更新路徑**消費這份簡報：機械類改動（只涉及圍欄程式碼區塊）用 `--apply` 應用，不動用 subagent；行文類 diff 交給 subagent，其提示詞就是簡報本身，而非指導語料；核驗只對改動塊逐句進行，不覆蓋整篇文件。
- **配對閘門接受配對參數。**`verify-translation-pairing [pair...]` 只檢查被點名的配對（配對三個文件中的任意一個，或其裸詞幹，都能指代該配對）；全語料掃描仍是 `doc-sync`（文件同步閘門）與 CI 執行的無參數形式。`--write` 現在要求點名已確認的配對：裸 `--write` 會拒絕執行，重新記錄全部配對必須顯式寫 `--write --all`；原因是舊的裸形式會默默為樹中每一個漂移的配對背書，包括呼叫者從未看過的那些，純行文層面的漂移於是可以永遠保持綠燈。每份記錄的註釋都寫明針對該配對自身的按對命令。寫下記錄之前，`--write` 用 `git hash-object -w --stdin` 存入每一側的精確位元組，並在內容尋址的本機 `refs/dsh/translation-pairing/snapshots/` ref 下固定該 blob；未提交的上次確認快照因此能被簡報生成器之後的 `git cat-file` 取回，而不只是留下一個 Git 無法解析的 hash 名稱或暴露於垃圾回收。

## 基準測試

該決策來自對本倉庫歷史上十次真實配對更新的受控重播（2026 年 7 月；每例改動 1 到 64 行英文，涵蓋 README、RFC、Agent Note 與使用者文件）。每個樣例都在臨時倉庫中重建到其真實的上次確認狀態，英文改動保持未提交，再用全新的 subagent 分別跑過相互競爭的各條工作流程：維持現狀的語料載入路徑、簡報路徑、無指導對照組、整篇重譯、小模型上的簡報路徑，以及每個 agent（代理）一次處理三對文件的批次方案。產出先經機械閘門把關，再由評委盲評打分；評委還同時收到真實的歷史更新與原樣未動的過時對側檔案作為對照。

- 簡報路徑在盲評的忠實性、保留度與流暢度上與現狀路徑打平（兩者都達到或超過真實歷史更新的水準），而在未發生停滯的樣例上只花費約三分之一的 token 用量與牆鐘時間（全部十例的中位數：相對 token 成本單位 276k 對 595k，輪次數 14 對 32）。
- 整篇重譯被證實有害，而不只是浪費：它丟棄經評審的措辭，盲評保留度因此崩塌（4.4/10 對 9.8）；它還使各更新組保持住的既定術語發生漂移（既定譯法本就寫在對側檔案自身的正文裡）；而且它是成本最高的一組。
- 無指導對照組的質量同樣立得住（對一次更新有約束力的上下文，是 diff 加上對側檔案自身經評審的正文，而非指導語料），但簡報以幾乎可忽略的額外成本，換來固定的工作集、內聯的術語，以及兩側同時漂移的警告。
- 以簡報為輸入，小模型的表現與大模型持平，因此更新路徑不再假定翻譯必須由前沿模型完成。
- 把三對文件合併給同一個 subagent，相比三次各自帶簡報的執行沒有可靠的節省，還把互不相關的失敗耦合在一起；該方案被否決。

在同樣這十個樣例上進行的第二次正面對比重播，把本文最終交付的簡報與其早前僅按章節的形態（沒有單元層級、沒有直接算出的機械路徑、上下文只含對側檔案、不跟蹤首次出現）相對照。行文質量與成本兩相持平（兩兩盲評裁定各有勝負，差距僅在文風），而最終交付的形態在兩項客觀結果上勝出：兩個只涉及圍欄程式碼區塊的樣例在一秒之內完成且不消耗任何模型 token，產出與經人工評審的歷史更新逐位元組一致；而在那個編輯使某術語在整篇文件中的首次出現發生移位的樣例上，最終交付的簡報所標記的移位復現了經人工評審的括注遷移，僅按章節的形態則留下一處「首次出現」違例，留待評審去捕捉。

## 曾考慮的替代方案

- **保留原工作流程，只讓閘門支持按對檢查**：閘門掃描本是較小的開銷，大頭在語料載入與翻查歷史。只收窄檢查範圍，約 3 倍的開銷仍會原地保留。
- **把整篇重譯作為更新路徑**（樸素管線的做法）：依據基準測試證據否決，理由是保留度崩塌、術語漂移、成本最高。約定的最小更新規則得以延續，且從此有資料支撐。
- **每個 subagent 批次處理多對文件**：否決。沒有實測出節省（簡報本身已對固定內容做了去重），而且一對文件停滯或陷入混亂會把其餘配對一並拖住。
- **在伴隨記錄中保存逐段的翻譯記憶條目**（用分段 hash 取代整文件 hash）：否決。配對兩側的段落邊界可以合理地不同，任一側都可能先撰寫，這類條目還會不斷膨脹並在合併時產生衝突。基於現有整文件 hash 按需計算的區間對映，在對齊可信時能復原同樣的對齊關係，不可信時會明確說明。
- **給自動提示詞管線加一個更新模式（prompt-v5）**：推遲，本文不做設計。今天沒有任何呼叫方在驅動 [scripts/translation-prompt.ts](../../../../scripts/translation-prompt.ts)，實際的成本中心是 agent 路徑。管線在擁有消費端之前，維持其整篇文件的 v4 約定。

## 後果

- 在顯式呼叫的擴充工作流程中，一次小的行文修改，其對側檔案更新只需生成一份簡報，外加一個小而聚焦的任務（不讀指導語料、不翻查歷史、迴圈內不做全語料掃描），同一 PR 內完成更新的義務保持不變。
- 簡報生成器成為一致性記錄的第二個消費端：記錄的 blob hash 如今還驅動 diff 還原與章節對映，這進一步強化瞭如實維護記錄的動機。
- 每個不同的已確認快照都會保留一個內容尋址的本機 ref 和對象。因此，中途放棄的重新記錄可能留下額外的持久固定項，但它不會改變任何分支或提交歷史；這種本機保留正是防止垃圾回收讓已接受配對記錄失效所付出的代價。
- 不帶參數的 `--write` 不再可用；靠肌肉記憶的呼叫者必須點名配對或傳 `--all`。這正是目的所在：批次背書如今是一個可見的、有意為之的動作。
- 按對檢查意味著一個更新迴圈可以在別處某個無關配對處於紅燈時自己保持綠燈；`doc-sync`/CI 中的全語料檢查仍然承載樹級不變式。
- 區間對映只在上次確認源文、當前源文與當前對側文字三方的種類序列一致時纔信任一處對齊；對映失敗時粒度確定性地逐級放寬（單元 → 章節 → 整篇文件）而不是靠猜，因此被重構過的文件拿到的是一份明確寫著「請自行定位相關區域」的簡報，絕不會是一張錯誤的地圖。
- 「首次出現」的一次移位可能讓簡報擴大到直接改動塊之外；這一成本是「首次出現」約定的明確後果，而非對齊啟發式。

## 測試

[scripts/translation-brief.spec.ts](../../../../scripts/translation-brief.spec.ts) 固定單元與章節的區間提取（以容器為作用域的種類、只按深度對齊章節從而讓已翻譯的標題文字仍能對映、首個標題前的序言）、對齊與改動索引偵測、機械程式碼拼接及其每一個拒絕條件、帶詞邊界與複數變形約束的雙向術語行匹配、首次出現移位跟蹤、圍欄升級，以及渲染後簡報的約定（帶三方上下文的單元條目、機械／章節／整篇文件三種範圍、分方向的規則摘要、按對的收尾命令）。[scripts/translation-pairing.spec.ts](../../../../scripts/translation-pairing.spec.ts) 固定未提交快照的精確位元組持久化與取回、在不可用對象進入伴隨記錄前失敗、參數歸一化（配對的任一文件或裸詞幹都歸一到錨點），以及 CLI（命令列介面）用例矩陣：按對檢查、裸 `--write` 拒絕執行、`--write <pair>`、`--write --all`、`--list` 的互斥性、未知標志。
