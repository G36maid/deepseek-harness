# Agent Note: 子系統目錄與 `ts type-equiv` 漂移閘門

Status: implemented

[English](2026-06-20-core-data-structures-catalog.md) | [简体中文](2026-06-20-core-data-structures-catalog.zh.md) | 繁體中文

## 問題

試圖理解 harness 的讀者可以在 [architecture.md](../../../../docs/architecture.md) 中找到它的*行為*（服務圖、工作階段/輪次/步驟生命週期、事件分類體系），卻找不到一個統一描述其*詞彙*的地方，也就是這些行為所傳遞的資料結構。類型定義只存在於原始碼中，散落在 `packages/*/src/types.ts` 各處，因此要理解「什麼是 `Message`、`SessionEvent`、`StreamChunk`」，就必須直接閱讀聲明。文字目錄會有所幫助，但複述或複製貼上類型定義的目錄會在欄位發生變化時立即腐化，而不同步的類型文件比沒有文件更糟，因為讀者會信任它。

因此，這項工作有兩個相互交織的問題：**這樣的目錄應包含什麼**（範圍問題——harness 有數十種跨包邊界的類型，把它們全部羅列出來對誰都沒有幫助），以及**如何避免貼上的類型定義發生漂移**（持久性問題）。本 Agent Note 記下了這兩項決策。與它歷史上配套的[已歸檔的 Cordis 事件與服務目錄自動生成決策](../../archived/process/2026-06-20-generated-cordis-catalog.md)從*接線*維度形成補充：本文對資料結構編目，另一篇則對傳遞這些結構的事件和服務編目。

## 決策

新增的 `docs/subsystems/` 目錄對這些詞彙編目，並配有新的 `verify-type-equiv` doc-sync（文件同步閘門），使每個貼上的類型聲明及其 JSDoc 與原始碼保持同步。

### 何為「核心」——主幹與子系統的分界線

> **作為頁面範圍界定規則已被取代**，見[按包錨定的子系統頁面](2026-08-03-package-anchored-subsystem-pages.md)：每頁現在錨定到聲明其詞彙的包分組。下文的 `ts type-equiv` 機制仍然有效。

範圍界定的決定性測試是 `ShellExecRequest`/`ShellExecSpec`/`ShellRunResult`：bash 是一個能力 *seam*，不屬於 agent loop（代理循環）主幹；如果這些算「核心」，那麼「核心」就意味著*所有跨包詞彙*，目錄淪為平鋪羅列；如果不算，「核心」就意味著*中央主幹*，bash 詞彙歸入其自身的子系統頁面。後者勝出，由此確定了整體結構：一個**分層資料夾**，而非一份平鋪文件。

確定其餘案例的規則是：***你編寫、持有或接收的類型是核心；為其提供類型推導、渲染或持久化的機制是子系統頁面細節。*** 逐一驗證如下：

- 一個數據結構是**核心**的，如果它流經 agent loop 主幹——無論載入了哪些外掛程式，迴圈在每個輪次都會持有、派生、流式輸出或記錄它（`Message`、`StreamChunk`、`SessionEvent`、`Agent` 控制代碼）——**或者**它是外掛程式作者面對某條管線時編寫的唯一標志性類型（`ToolDefinition`）。
- `ToolDefinition` 是核心（它是每個工具作者編寫的東西），**即使迴圈從不持有它**——對於這一個標志性類型，編寫層面的重要性壓過了嚴格的「流經主幹」規則。但它的類型推導機制——`ValueSchemaSpec`、`ParameterSchemaSpec`、`InferValue` 與 `InferArgs`——是子系統頁面細節。這就是主幹與子系統分界線的精確表述。
- `ToolSchema` 是核心（它是流經每個步驟的模型請求 `GenerateOptions` 的一個欄位），即使它在概念上屬於工具管線——當*流經主幹*與*概念歸屬*衝突時，前者勝出。
- 工具展示詞彙（`ToolCallView`/`ToolResultView` 等）、`SessionPersistence` 持久性 seam 以及 bash 詞彙歸入子系統頁面。

`core.md` 是一份**自包含的主幹文件**：它給出每個主幹結構的確切類型定義，輔以最少的行文，並連結到同級子系統頁面取得包所擁有的細節；目錄的 [README](../../../../docs/subsystems/README.md) 索引全部頁面。最初的子系統頁麪包括 `llm-streaming.md`、`session.md`、`persistence.md`（沿記憶體模型與持久性 seam 的分界線從工作階段頁面拆出）、`tools.md` 和 `shell.md`。

### `ts type-equiv` 機制——既逐字又防漂移

持久性要求很具體：文件展示當前類型聲明與原始 JSDoc 的**逐字**內容（讓讀者看到真實形狀和原始碼約定，而非複述），**並且**以機械方式保證其與原始碼匹配。倉庫已經會編譯 ` ```ts ` 圍欄塊（`doc-typecheck`），但真正接受型別檢查的塊需要匯入噪音，而且只能證明*可賦值性*——欄位改名或 JSDoc 變化仍可能透過。因此：

- 完整的類型聲明及其 JSDoc 會逐字貼上到專用的 ` ```ts type-equiv ` 圍欄中。簡潔的 ` ```ts public-api ` 圍欄承載類的原始碼等價環境聲明投影，用於實作體不應進入目錄的類。`doc-typecheck` 會識別並跳過這兩種圍欄（裸聲明無法獨立編譯），並且**將它們排除在 opt-out 比例之外**——它們是單獨受檢的類別，而不是未經檢查的草圖。
- 新增的 `scripts/verify-type-equiv.ts` 透過 TypeScript 解析器提取每個塊，並斷言其聲明結構和每條 JSDoc 註釋都與所聲明的符號匹配，只忽略格式空白和非 JSDoc 註釋。普通塊保留完整聲明。`public-api` 投影保留類的公共欄位、構造函式、訪問器和方法及其原始 JSDoc，同時移除實作體以及私有或受保護成員。之所以選擇它而非編譯式 `_Check` 斷言，是因為目錄所保留的是原始碼名稱與文件一致性，而不是可賦值性。
- 每個類型塊的文件、symbol 和原始檔都記錄在集中的 `scripts/type-equiv.manifest.json`（`{ doc, symbol, source }` 條目）中，**而非**行文中的指令註釋。指令碼在每個主 type-equiv 塊與一條 manifest（中繼資料清單）條目之間強制執行 **1:1 對應**，因此一個塊永遠不會被靜默漏檢，一條條目也永遠不會腐爛。只有當配對 `.zh.md` 塊的完整受跟蹤圍欄序列在順序、類型和按位元組精確的正文上均與無後綴兄弟文件匹配時，才會複用後者的條目；否則閘門會獨立檢查該塊，發現沒有 manifest 條目後失敗。
- 接入 `doc-sync`，因此相關文件變更時會在本機執行它，CI 也會與其他文件檢查一起執行它。

### 維護是作者的職責，閘門作為兜底

`verify-type-equiv` 能捕獲已記錄類型的*貼上漂移*，但無法告訴你一個全新的核心類型沒有被記錄。因此 AGENTS.md 和 `dsh-code-review` skill（技能）已更新，要求在變更新增或重塑已記錄類型時同步更新目錄——閘門處理漂移，人處理新類型。

## 曾考慮的替代方案

- **平鋪羅列所有跨包詞彙**：`ShellExecRequest` 測試案例否決了它。如果 seam 詞彙算「核心」，目錄對誰都沒幫助；分層的主幹與子系統結構勝出。
- **用編譯式 `_Check` 可賦值性斷言**代替原始碼匹配：否決。可賦值性不會保留名稱或 JSDoc；同類型欄位改名或約定註釋變化仍會透過。
- **將每個類型塊的原始檔寫進指令註釋**：否決，改用集中 manifest；其強制的 1:1 對應確保一個塊永遠不會被靜默漏檢，一條條目也永遠不會腐爛。

## 驗證教訓

`verify-type-equiv` 必須掃描完整的 Markdown 範圍，而不僅是 manifest 點名的文件。否則，未列入清單的 `type-equiv` 塊就會逃過所宣稱的一一檢查。因此，閘門會將此類塊報告為未列入清單的塊。本 Agent Note 將這條默認拒絕放行的掃描規則，連同主幹與子系統的分界決策及逐字匹配決策一並記錄；生成的 Cordis 目錄在[其已歸檔的 Agent Note](../../archived/process/2026-06-20-generated-cordis-catalog.md) 中有對稱的設計記錄。

## 後果

- 這些詞彙現在有一個**無法悄然漂移**的唯一歸屬：原始碼中的欄位或公共類成員發生變化後，`doc-sync` 和 CI 中的 `verify-type-equiv` 會持續失敗，直至貼上內容刷新。Cordis 服務方法仍由生成的服務目錄負責，而不會在此重複。
- 主幹與子系統分界線是一個可複用的範圍界定工具，而非一次性的：同一條「你編寫/持有/接收的東西是核心；為其提供類型推導/渲染/持久化的機制是細節」規則，後來也被用於界定事件/服務目錄的 harness 層與繼承層分層。
- `ts type-equiv` 圍欄是繼 ` ```ts `（編譯）和 ` ```ts ignore-check `（草稿）之後的第三種文件塊類別。後續的姊妹閘門又增加了第四種 ` ```ts cordis-catalog `（生成簽名），複用了相同的跳過並排除處理。
- 新增或重塑核心類型現在附帶一項文件義務，作者必須履行（閘門無法偵測缺失的*新*類型），由 `dsh-code-review` 檢查清單兜底。
- 自 2026-07-27 起，子系統頁面層級覆蓋每個承載服務的子系統：九個精簡頁面（權限預設、計畫模式、執行時期不變式、HTTP 載體、儲存——同時擁有 `ctx.storage` 與 `ctx.storageDomain`——終端機擴充、工作區、用戶端模組、遙測）覆蓋了原先沒有頁面的十個 `ctx` 服務，於是每個 harness 服務和事件作用域都有恰好一個所屬的 subsystems 頁面——這是把按子系統生成的服務/事件參考寫入這些頁面（而非平鋪目錄）的前提。
