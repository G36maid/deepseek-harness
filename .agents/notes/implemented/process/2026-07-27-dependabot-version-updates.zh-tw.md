# Agent Note: Dependabot 版本更新採用 30 天冷卻期

Status: implemented

[English](2026-07-27-dependabot-version-updates.md) | [简体中文](2026-07-27-dependabot-version-updates.zh.md) | 繁體中文

## 問題

來自包登錄檔的相依性與 GitHub Actions 相依性都需要定期更新機制。每個新版本一經發布便立即採用，會增加受到遭入侵的版本和早期回歸影響的風險；但完全依靠手動更新，又會導致相依性版本差距持續擴大。以原始碼形式納入倉庫的 Cordis 不能當作登錄檔相依性處理，而共用一份鎖定檔的工作區必須透過同一棵包樹更新。

## 決策

默認分支包含 [`.github/dependabot.yml`](../../../../.github/dependabot.yml)，其中為包含 `native/landlock-run` 的根 pnpm 工作區、`python/sdk` uv 項目和 GitHub Actions 設定了每週一次的版本更新檢查。每個更新項都將 `cooldown.default-days` 設為 `30`，因此某個版本只有在發布至少 30 天后才符合更新條件，並會在下一次每週檢查時生成更新提案。[倉庫內 Landlock 發布決策](2026-08-06-in-repository-landlock-release.md)負責共享工作區邊界。

根 pnpm 工作區的版本更新掃描排除 `vendor/**`，其中的原始碼和 manifest（中繼資料清單）只能透過 [vendoring 流程](../../../../vendor/README.md)變更。GitHub 僅將 `exclude-paths` 用於版本更新；如果安全更新 PR（Pull Request）涉及隨原始碼納入倉庫的 manifest，則改由 vendoring 流程處理，以替代自動生成的 PR，而不會將其原樣合併。Dependabot PR 會獲得倉庫的 `kind/dependency` 類型標籤和 `area/infra` 區域標籤，執行常規 PR 檢查，並且仍須由維護者評審；該自動化不會合並這些 PR。

倉庫設定已啟用相依套件漏洞警報和 Dependabot 安全更新。GitHub 不會對這些安全更新應用版本更新冷卻期，因此安全修復仍可立即進入更新流程。如果相依性解析還選中了其他剛發布的傳遞相依性，pnpm 安全更新 PR 仍可能無法透過倉庫的鎖定檔發布時長校驗；此類 PR 應等待隔離期結束或縮小更新範圍，不得因此放寬政策。倉庫為協調剛發布版本而設定的例外，不會納入 Dependabot 的冷卻期排除項：自動版本更新統一等待 30 天；經過明確評審的手動更新仍可遵循相應的發布流程。

pnpm 更新項讓統一工作區繼續使用已固定的 pnpm 11，不會僅為了自動化而降級版本。當前 Dependabot 更新器會安裝根 `packageManager` 指定的版本，並讀取根鎖定檔的 `9.0` 格式；由提供方執行的更新任務仍作為整合檢查。

## 考慮過的替代方案

- **立即進行版本更新。** 不採用，因為這會取消所要求的版本發布後隔離期，使項目在每個上游版本的發布初期就採用該版本。
- **CI 透過後自動合併。** 不採用，因為相依性變更可能改變執行時期、建置和發布行為；是否接受更新仍須經過常規評審決策。
- **為 native 設定獨立的 npm 掃描。** 不採用，因為 Landlock manifest 屬於根工作區和根鎖定檔；拆分更新會重建一個套件管理員已不存在的歸屬邊界。根掃描僅排除隨原始碼納入的 manifest。
- **Renovate 或定期執行的 agent（代理）。** 二者都能為發布已滿一定時長的版本提出更新，但所要求的服務是 Dependabot，而且倉庫 CI 已將其 PR 視為不可信的相依性來源。
- **為需協調的剛發布版本設定冷卻期豁免。** 自動化路徑不採用，因為此類版本需要明確的同步決策或模型目錄決策，不能由通用更新提案代替。

## 後果

- 隔離期結束後，常規相依性更新會以規模較小、便於評審的 PR 形式到達，無需維護者定期手動發現更新。
- 由於每週評估一次更新資格，相應更新 PR 通常會在版本發布後 30 至 36 天出現。
- Dependabot 不會延遲安全更新提案；倉庫檢查仍可阻止無關的剛發布傳遞相依性，評審流程也會維持 vendoring 邊界。
- 維護者仍負責決定是否合併每項更新，並診斷 pnpm 11 更新任務報告的任何提供方限制。
