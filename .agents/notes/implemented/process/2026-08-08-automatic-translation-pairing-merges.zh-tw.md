# Agent Note: 自動組合翻譯配對記錄

Status: implemented

[English](2026-08-08-automatic-translation-pairing-merges.md) | [简体中文](2026-08-08-automatic-translation-pairing-merges.zh.md) | 繁體中文

## 問題

一份雙語一致性記錄包含兩側 Markdown 文件的精確 blob hash。因此，當兩個分支分別更新同一已確認配對的不同部分時，即使 Git 能幹淨合併兩側 Markdown 文件，記錄中的兩行 hash 仍會發生衝突。選擇任一側都會留下過時 hash；手工重新生成記錄則會重複執行一項確定性操作，並阻止本可自動完成的合併。

## 決策

`*.i18n.yaml` 使用由倉庫維護的 `dsh-translation-pairing` 合併驅動。worktree 本機的 Git 安裝指令碼在設定 Lefthook 的同時註冊該驅動命令；Git 設定仍限定於當前 worktree，因為受跟蹤的屬性可以指定驅動，卻無法攜帶其可執行命令。

安裝指令碼會在發布 worktree 整合前載入確切的 Node/tsx 入口點。Git 會呼叫倉庫內已提交且不相依性 Node 的 shell 啟動器；該啟動器會在每次執行驅動前重複這項探測。執行時期或入口點不可用時，即使文字合併乾淨完成，啟動器也會將 Git 的普通三方文字合併結果寫入伴隨檔案並返回沖突狀態，使 Git 保留未合併的索引階段，絕不接受未經驗證的元資料。

驅動會解析祖先、當前和另一側的記錄，並載入其中 hash 指向的六個 Markdown blob。它分別對英文文件的三個 blob 與中文文件的三個 blob 執行 Git 默認的三方文字合併，要求兩次合併都乾淨完成，校驗語言切換列與配對結構簽章，儲存兩個合併後的 blob，再將其 hash 寫入規範記錄。這一過程組合兩個父提交中已經存在的確認；它絕不會為普通的單側文件編輯寫入記錄。

記錄格式錯誤、對象缺失、配對文件採用其他合併策略（包括原本未單獨指定策略的路徑繼承了非文字 `merge.default`）、任一配對文件存在內容衝突，或合併後的配對違反結構檢查時，驅動會讓伴隨檔案保持為普通的未解決衝突。新增、刪除及重新命名情形仍需手工處理，因為它們的路徑歸屬關係無法由上述基於三份記錄的操作處理。

`pnpm run resolve-translation-pairing-conflicts` 會在合併已經停止後應用同一演算法。寫入任何伴隨檔案之前，它會驗證伴隨檔案仍保留 Git 生成且未經改動的衝突結果，並驗證暫存區中配對文件的 blob ID 以及工作樹中的文件位元組都與工具獨立完成的合併結果一致。即使其他配對仍需手工處理，它也會將所有可安全生成的記錄作為一個批次寫入並暫存；隨後報告剩餘的配對衝突並以非零狀態退出，確保呼叫方不會把僅部分解決誤認為合併已經完成。

`pre-merge-commit` 與 `pre-commit` 會對照兩側文件在索引中的精確位元組，校驗暫存的 `.i18n.yaml` 文件。這些掛鉤會驗證驅動輸出，但不會重新生成記錄，因此繞過掛鉤也無法默默確認發生漂移的譯文；CI 中全語料的 `doc-sync`（文件同步閘門）仍是權威檢查。

## 失敗約定

| 普通 `git merge` 期間的失敗 | 可觀察狀態 | 復原 |
|---|---|---|
| 全新安裝無法探測驅動或安裝 Lefthook | 不會發布新的驅動或掛鉤路徑設定；任何新增整合都會回滾到原有的掛鉤尋找方式。 | 復原相依性並重新執行 `node scripts/install-lefthook.mjs`。 |
| 安裝後 Node、tsx 或驅動入口點變得不可用 | 合併停止，伴隨檔案狀態為 `UU`；索引階段 1/2/3 保留，worktree 中的伴隨檔案包含 Git 的文字結果，`MERGE_HEAD` 存在，且不建立提交。 | 復原相依性並執行 `pnpm run resolve-translation-pairing-conflicts`，或執行 `git merge --abort`。 |
| 瞭解倉庫狀態的驅動拒絕記錄 | 合併停止，伴隨檔案保持未解決狀態且不建立提交；驅動會列印修復配對文件和執行顯式衝突解決命令的路徑。 | 修復配對文件衝突或記錄，然後執行列印出的衝突解決工作流程，或中止合併。 |
| 驅動行程以大於 128 的狀態碼崩潰 | Git 中止合併策略，既不寫入 `MERGE_HEAD`，也不產生未合併的索引階段。 | 修復執行時期並重新執行合併。 |
| `pre-merge-commit` 拒絕原本能幹淨完成的文件合併 | 不再有未合併條目，完整結果已暫存且 `MERGE_HEAD` 存在，但不會建立合併提交。 | 修復掛鉤失敗並執行 `git commit`，或執行 `git merge --abort`。 |

安裝指令碼回滾失敗時，會同時報告最初的安裝錯誤和每一項回滾錯誤。此時 worktree 設定可能只完成了一部分，因此貢獻者會先修復或檢查設定再執行合併，而不是相依性靜默回退。

## 驗證

指令碼測試透過已安裝的啟動器覆蓋無衝突組合，並覆蓋執行時期缺失與入口點損壞時的文字回退、安裝指令碼探測回滾、拒絕合併的 `pre-merge-commit` 掛鉤、從含未解決條目的索引中顯式復原、可安全解決的配對與配對文件衝突的配對並存、被編輯過的伴隨檔案、非文字默認合併設定、記錄解析和 worktree 本機安裝。既有的全語料校驗器繼續證明已提交的記錄與兩側配對文件相符。

## 考慮過的替代方案

**選擇 ours 或使用 Git 的 union 驅動。** 任一父提交的記錄都指向合併前的內容，而 union 會產生重複或亂序的 hash 鍵。兩者都無法表示合併後的配對文件。

**在 `post-merge` 中或僅透過提交掛鉤重新生成。** 發生衝突的合併不會執行 `post-merge`，而且該掛鉤無法改變合併結果。只有暫存區不含未解決條目後才會觸發提交掛鉤，因此僅用掛鉤無法清除生成文件衝突。

**用倉庫命令包裝每次合併。** 包裝命令可以根據已由合併填充的索引解決衝突，顯式衝突解決命令也保留這條復原路徑，但直接執行 Git、stack 工具、rebase 和 cherry-pick 時仍會在此前停止。合併驅動纔是這些操作共用的文件級擴充點。

**透過 GitHub Actions 或應用解決。** 託管自動化可以更新 PR（Pull Request）分支，卻會引入憑據、並行控制與分支修改。本機執行或由 agent（代理）驅動的 merge-forward 工作流程已經具有檢出目錄與推送權限，因此倉庫不把遠端自動化納入該機制。

## 後果

完成安裝的 worktree 會自動消除僅由配對記錄引起的衝突，同時仍由人工處理配對文件衝突並評判翻譯質量。GitHub 託管的可合併性計算不會執行 worktree 本機的可執行命令，因此仍須由貢獻者或 agent 將 base 分支合入當前分支並推送結果提交，遠端衝突標記才會消失。

安裝指令碼會在 worktree 設定中預留 `merge.dsh-translation-pairing.*`，並拒絕與之衝突的自訂值。與倉庫貢獻者掛鉤一樣，自動組合相依性已安裝的 Node 相依性；執行時期不可用時會產生可見的未解決文字結果，而不是選擇過時元資料。
