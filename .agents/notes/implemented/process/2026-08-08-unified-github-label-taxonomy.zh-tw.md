# Agent Note: 統一 GitHub 標籤分類體系

Status: implemented

[English](2026-08-08-unified-github-label-taxonomy.md) | [简体中文](2026-08-08-unified-github-label-taxonomy.zh.md) | 繁體中文

## 問題

PR（Pull Request）標籤回答兩個相互獨立的問題：工作帶來哪一類變更，以及會對哪些持久的倉庫領域產生實質影響。混用這兩個維度，或同時保留同義的無前綴標籤與帶命名空間的標籤，都會使查詢含義模糊；封閉的領域清單則會迫使新領域歸入不準確的類別。

Issue 已有原生 Issue Type 和獨立的來源分類體系。在這兩類對象上複用 PR 類型或來源標籤會產生重複元資料，並削弱每個標籤族的含義。

## 決策

每項開放或已合併的 PR 都帶有恰好一個規範的 `kind/*` 標籤，以及至少一個表示實質受影響領域的 `area/*` 標籤。未合併即關閉的 PR 保留經遷移的歷史標籤關係，但不會憑空補充缺失分類。管理用途的標籤可以並存，但不能滿足這兩個維度中的任一個。

### 變更類型

類型集合封閉且互斥：

| 變更類型 | 含義 |
|---|---|
| `kind/feature` | 新增行為或有意改變行為。 |
| `kind/bug-fix` | 修正錯誤行為。 |
| `kind/doc` | 以文件變更為主導意圖。 |
| `kind/testing` | 在不改變產品行為的前提下修改測試或測試基礎設施。 |
| `kind/cleanup` | 在保持行為不變的前提下，維護或簡化實作或倉庫流程。 |
| `kind/dependency` | 在沒有其他主導意圖時更新相依套件。 |

類型記錄主導意圖。配套測試、文件、清理或相依性調整不會蓋過功能變更或缺陷修復這一主導意圖。新增類型會改變這些分類規則，因此必須明確修改分類體系和政策。

倉庫政策會拒絕不支持的 `kind/*` 值，並將統一過程中移除的所有別名列為保留名稱：`kind/bug`、`kind/documentation`、`feature`、`bug-fix`、`doc`、`cleanup`、`testing`、`dependencies`、`ci`、`cli`、`llm` 和 `web-search`。精確保留這組已遷移的名稱，可以防止過時的同義名稱被重新建立成看似無關的管理用途標籤。

### 領域

領域表示持久的產品或工程主題，而不是臨時專項、歸屬關係或偶然觸及的每條路徑。一項 PR 修改不同的行為或 API 時帶有多個領域標籤，但不會用一個總括標籤和一個較窄標籤重複描述同一項變更。GitHub 上現行的 `area/*` 名稱和說明定義當前清單；本記錄定義簡短標籤說明無法可靠容納的選擇情形。

- `area/web` 覆蓋瀏覽器與 Electron 圖形介面，`area/vscode` 覆蓋編輯器擴充，`area/api` 覆蓋跨介面協議與各語言 SDK。
- `area/planning` 覆蓋目標、計畫、待辦和調度，`area/workflow` 則覆蓋可執行工作流程與背景工作執行時期。
- `area/artifact` 有意合併產物、附件與多模態交付。只有當這些關注點再次需要獨立評審或查詢時，纔有理由拆分標籤。
- `area/tools` 適用於通用登錄檔、schema 與執行約定。具體能力使用自身的領域標籤，除非它還修改了其中一項約定。
- `area/hooks` 表示 Claude Code 與 Codex 橋接，`area/infra` 覆蓋建置、發布、CI、倉庫閘門、生成器、相依性與開發者工具，`area/windows` 覆蓋原生 Windows 產品支持，而不是 CI runner 的選型。

領域集合有意保持可擴充。當現有說明都無法如實涵蓋一個持久且可複用的領域時，agent（代理）無需另行批准，即可建立一個簡潔的 `area/<lowercase-kebab-case>` 標籤。agent 不得為單個 PR、偶然涉及的路徑、臨時項目、狀態、個人或團隊建立領域，並且必須在應用新標籤後向請求者報告該標籤及理由。僅為避免新增一個確有必要的領域標籤而複用不準確的領域，不可接受。

### Issue 與遷移

Issue 使用原生 Issue Type，而不是 `kind/*`；其 `area/*` 標籤仍然選填。`source/*` 標籤記錄 Issue 的建立方式，不適用於 PR。優先級、GitHub 默認標籤和工作流程觸發器仍是相互獨立的管理元資料。

遷移標籤時，須先保留語義，再移除別名：先新增規範替代標籤，核驗可加標籤對象，再移除廢棄的標籤關係。只有在所有 PR 和 Issue 都不再使用某個標籤後才能將其刪除，且絕不整組替換無關標籤。

## 考慮過的替代方案

**無前綴標籤。** 無前綴名稱可以減少視覺噪聲，但無法表明標籤分類的是意圖、領域、來源、優先級還是自動化用途。同時保留無前綴和帶命名空間的同義標籤，也會使查詢和政策執行含義模糊。

**不區分維度的單一標籤集合。** 某個標籤存在，並不能證明意圖和語義範圍都經過了考慮。

**倉庫政策中的固定領域允許清單。** 持久的倉庫領域會演進。`area/*` 命名空間仍可機械識別，而現行說明承載可擴充清單。

**按包或路徑派生的領域。** 領域描述跨越包邊界的語義影響，而變更路徑會包含偶然涉及的測試、文件和支持文件。

**為每種交付載體或媒體生命週期單設標籤。** 瀏覽器與 Electron 交付共用一個圖形介面領域，產物、附件與多模態交付目前也共用一個評審／查詢領域。只有當拆分能復原有用的獨立分類時，才應在後續分類體系變更中進行。

**用寬泛的實作標籤取代產品或工程主題。** 一項具體能力並不只是其工具、介面、檔案系統或行程實作。通用實作領域只在其自身行為或 API 變化時適用。

**在 Issue 上使用類型標籤。** 原生 Issue Type 已負責這項分類；再用標籤複製會造成漂移。

**每個 PR 恰好一個領域。** 內聚的變更可能對多個獨立 API 或行為產生實質影響，丟棄次要領域會隱藏受影響範圍。

## 後果

評審人和自動化流程可以分別查詢意圖、語義範圍、Issue 的建立方式、優先級和工作流程觸發條件。維護者必須閱讀變更內容和現行標籤說明，而不能根據標題前綴或路徑推斷分類。當某種類型或某條非顯然的領域邊界發生變化時，現行標籤清單、本記錄中的決策依據和政策執行必須同步更新；分類體系遷移還會產生明確的歷史回填和驗證成本。
