# Agent Note: 匯出 JSDoc 閘門

Status: implemented

[English](2026-07-06-export-jsdoc-gate.md) | [简体中文](2026-07-06-export-jsdoc-gate.zh.md) | 繁體中文

## 問題

[Cordis JSDoc 完整性閘門](../../archived/process/2026-07-04-cordis-jsdoc-completeness-gate.md)使得 Cordis 介面上的參數和回傳值不可能缺少文件——`interface Events` 成員和 `ctx.<key>` 服務類——但這只覆蓋外掛程式作者可匯入介面的一小部分。AGENTS.md 中的規則「每個匯出（以及非顯而易見的方法）都必須有解釋語義的 JSDoc」在其他地方仍只是由評審檢查的文字約定，而且沒有任何機制要求普通匯出函式帶 `@param`/`@returns`。採納時的一次調查發現 34 個包中有 203 個文件不完整的模組級匯出：seam 相關輔助函式（`runBash`、`readForEdit`、`htmlToMarkdown`）、格式編解碼器、完全無文件的介面和類型別名——恰恰是 IDE 消費端懸停查看的那些名稱。

## 決策

新增閘門 `scripts/verify-export-jsdoc.ts`（`pnpm run verify-export-jsdoc`，接入 `doc-sync`（文件同步閘門），與 `verify-cordis-catalog` 並列），遍歷每個 `packages/<group>/<pkg>/src/` 目錄樹下的所有模組級匯出名稱。解析與檢查輔助函式從 `gen-cordis-catalog.ts` 移入共享的 `scripts/jsdoc.ts`，使得「已文件化」在兩類介面上含義一致：描述性文字在第一個塊標籤處截止、每個可檢查參數需要非空 `@param`、非 void 且有顯式標注的回傳值需要非空 `@returns`、過時的 `@param` 報錯，違規項彙總為一份報告。

按聲明類型劃分的約定：

- 每個匯出名稱都需要帶有非空描述文字的 JSDoc。
- 函式類匯出（函式聲明；初始化器為函式或帶有內聯可呼叫標注的 const；非識別符號的函式默認匯出）遵循完整的函式約定，分類前會剝離包裝表達式（括號、`as`/`satisfies` 類型斷言、非空斷言）。如果 const 聲明器標注了一個具名類型（`export const f: Handler = …`），簽名約定推遲到該類型自身的聲明處，`@returns` 保持選填；內聯的 `(x: T) => U` 標注或單呼叫簽名字面量本身就是匯出簽名，適用完整約定；而混合了呼叫/構造簽名與其他成員的字面量則直接拒絕（沒有單一簽名可供標籤對照——請提取具名類型）。
- 匯出類需要類等級的描述文字；公開方法（包括靜態方法——可透過匯出名稱訪問）遵循函式約定；公開屬性和訪問器需要描述文字（get/set 對由 getter 覆蓋）。重載實作體免檢——簽名承載文件。
- 匯出介面、類型別名和枚舉需要聲明等級的描述文字；成員等級的強制有意推遲（承載關鍵成員約定的 seam 服務類已在 Cordis 閘門之下）。
- 匯出命名空間遞迴檢查（在 ambient `declare` 命名空間內，每個成員隱式匯出）；命名空間本身僅在不與同名的已文件化聲明合併時才需要描述文字（Config-namespace 慣用法只需文件化外掛程式一次）。
- `declare module`/`declare global` 體和 `export … from` 重匯出語句被跳過：augmentation 不是包的匯出，重匯出的定義在其定義處檢查。`export import X = N.member` 別名需要文件化自身——其目標可能是遍歷不會訪問的非匯出命名空間成員——且閘門僅支持純描述文字的目標類型：可呼叫、類或命名空間目標攜帶別名描述文字無法承載的簽名/成員約定，閘門會拒絕並要求直接匯出該聲明。
- 其餘情況一律默認拒絕：`export =` 直接拒絕；即使參數使用綁定模式，只要基類未為其命名，仍需 `@param`；dispatch 不識別的匯出語句類型本身就是違規——沒有任何匯出形式能因遺漏而免檢。

三類豁免避免閘門要求樣板程式碼，精神與 Cordis 閘門的 `this`/`next` 豁免一致（為已豁免的名稱編寫文件是允許的；只有缺失纔不被檢查）：

- **繼承成員。** 重寫從其基類聲明繼承文件。新增的公開 API 仍需文件：新增參數、將 protected 成員公開重寫、或將基類的 void 返回改為具體類型。繼承尋找和推斷回傳值分類是閘門唯一需要型別檢查器的工作；其他檢查使用 AST。
- **外掛程式協議槽位。** 頂層的 `name`/`inject`/`reusable`/`Config` 常數和 `apply` 入口，以及外掛程式類上的同名靜態成員，屬於框架協議：其形狀由 Cordis 固定，模組文件註釋加 `interface Config` 承載外掛程式的真實語義。
- **構造函式**，與 Cordis 閘門一致：外掛程式類由框架構造，類文件承載全部說明。

`collectExportJsdocViolations()` 返回違規清單（CLI（命令列介面）在非空時以 1 退出），因此 `packages/core/agent/tests/verify-export-jsdoc.spec.ts` 中的負路徑測試直接斷言發現項，透過 fixture（測試前置資料）包驅動每一種拒絕和每一種豁免。

## 曾考慮的替代方案

- **eslint-plugin-jsdoc**（`require-jsdoc`/`require-param`/`require-returns`）：覆蓋了機械核心，但無法表達本倉庫的約定。繼承成員豁免需要跨包的類型解析，協議槽位和命名空間合併慣用法是 Cordis 特有的，而完整性語義（標籤前描述文字、過時標籤報錯、彙總報告）已在 `scripts/jsdoc.ts` 中與 catalog 生成器共享。兩套微妙不同的「已文件化」定義，正是本倉庫「單一歸屬」規則所要防止的失敗模式。
- **擴充 `gen-cordis-catalog.ts`**：catalog 生成器渲染一個精選 API 並守衛其新鮮度；倉庫級遍歷沒有 catalog 可渲染。共享輔助函式、保持遍歷獨立，使每個閘門的職責清晰可讀。
- **強制介面/類型別名的成員文件**：推遲。這會使檢查範圍成倍成長，而檢查對象大多隻是含義直觀的欄位；承載關鍵成員約定的 seam 服務類已有閘門。如果評審中出現成員文件漂移再重新考慮。

## 後果

- 新匯出不能在缺少文件的情況下落地：`verify-export-jsdoc` 會使 `doc-sync` 和 CI 失敗。採納時發現的 203 處缺口已在同一變更中補齊，因此閘門落地時所有檢查均已透過。
- 匯出函式必須標注返回類型（採納時已全面滿足，現在成為閘門相依性），並在 `@param` 需要命名參數時使用識別符號參數。
- seam 文件是權威的：實作從其繼承鏈繼承文件，值得保留在實作上的行為說明是補充，而非必需。
- 閘門建置一個 `ts.Program`（約 6 秒）——唯一需要類型解析的文件閘門；在已編譯文件片段的 `doc-sync` 內可以接受。
- 協議槽位名稱按約定保留在模組頂層；一個恰好命名為 `apply` 或 `Config` 的非協議匯出將不被檢查——已接受，記錄於此。
