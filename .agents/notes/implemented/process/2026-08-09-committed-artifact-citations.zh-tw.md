# Agent Note: 引用已提交的產物，絕不引用設計工作階段序號

Status: implemented

[English](2026-08-09-committed-artifact-citations.md) | [简体中文](2026-08-09-committed-artifact-citations.zh.md) | 繁體中文

## 問題

大型設計與評審工作階段會留下工作速記：決策序號、審計條目代號、計畫章節編號、任務與棧序號、評審人裁定。這些速記在工作階段 transcript（文字記錄）還開著時讀起來順理成章，一旦關閉就什麼也解析不到。一次全倉庫審計發現該模式集中在 `packages/client`：裸寫的 `(decision 12/16/19/20/21)` 引用中只有決策 21 有已提交的歸屬文件；`(audit C2/S1/S3/S7)` 代號在任何地方都沒有對應的審計文件；`design §4.7`／`web2 §0`／`plan §1.4` 指向未提交的草稿；計畫階段標籤（`T2/T5/T9`、`P-I`、`W5`）；持久 JSDoc 裡的棧內位置（"a later PR in this stack"）；以及「ruling」（裁定）、「design ledger」（設計臺帳）一類詞彙。同樣的幾類模式也出現在測試、CSS 註釋、生成器範本、CI 註釋與 Agent Note 中（「本 PR／本分支／本評審輪」視角、評審編排式的歸因、目標其後已經交付卻仍寫著「推遲到後續 PR」的過時說法）。[文件標準](../../../../docs/AGENTS.md)早已禁止了變更歷史這一半（previously/now、PR（Pull Request）與 commit 引用），卻沒有為引用寫下對應的規則，於是無法解析的序號不斷落進倉庫。

## 決策

持久行文（註釋、JSDoc、文件、Agent Note、測試註釋與測試標題）只引用已提交的產物，無需 grep 考古即可在倉庫內解析：

- 點名歸屬的 Agent Note（其路徑在每個文件裡至少出現一次，行內用可檢索的名稱）、文件頁面路徑，或 GitHub issue 編號。PR、commit、分支與棧位置依文件標準在文件與程式碼中仍在禁止之列；issue 是持久且可引用的，Agent Note 與事後檢討（postmortem）可依[文件標準](../../../../docs/AGENTS.md)的變更故事歸置規則引用已合併的 PR 與 issue 作為證據。
- 決策有已提交歸屬文件的設計工作階段序號替換為該決策的名稱——曾以「決策 21」記錄的序號如今是「純文字引用決策」，歸屬於 [web 輸入狀態機 note](../architecture/2026-07-25-web-input-machine-and-slash-pipeline.md)；該序號本身在倉庫內無從解析，已全部移除。沒有歸屬文件的序號予以刪除，其事實性語句改寫為可獨立成立的表述。
- 已修復的回歸以現在時反事實句固定下來（「沒有 X 就會發生 Y」、「樸素的 X 會……」），絕不寫成倉庫歷史（「過去曾 Y」）。
- 已實作的 Agent Note 陳述已交付的現實：「推遲到後續 PR」的說法若其目標已經交付，就改為點名那篇已交付的 note。
- 已錄制的 fixture（測試前置資料）、快照與已歸檔的 Agent Note 不受此約束：已錄制的模型輸出與封存的歷史保持原有行文。在 note 的變更故事段落內，歷史階段名稱（「首版交付了 X」）符合只描述當前狀態的要求；「this cut」這類指示當前版本的標記在任何地方都仍被禁止。

一次全倉庫清理把這些規則應用到了各個行文表面，包括生成器持有的範本（`scripts/gen-doc-graphs.ts`、`scripts/gen-tool-catalog.ts`、typert 生成器的頁面提示語，改後重新生成）、type-equiv 原始碼中的 JSDoc（改後重新同步到文件頁）以及雙語對側檔案（改後重新記錄配對）。[dsh-trim-cot-leakage 技能](../../../skills/dsh-trim-cot-leakage/SKILL.md)把這些規則落地為可執行工作流程：審計分類法、已提交的成批召回檢索，以及用於判斷保留或刪除內容的少樣本示例。

## 曾考慮的替代方案

- **把設計臺帳與審計文件提交入庫，讓序號得以解析。**不予採納：工作階段 transcript 是工作產物，不是持續維護的參考資料；提交它們會在 Agent Note 之外形成一套平行且不受閘門約束的決策語料，其內部編號也仍會漂移。
- **為被禁詞彙建一道機械閘門。**暫緩：這類詞彙是無界的自然語言，審計中以查全為目標的成批檢索需要人工判斷，才能把洩漏與正當行文區分開（作名詞的「wait」、表轉折的「actually」、執行時期的新舊狀態）。若該模式再次出現，候選方案是一道窄而高查準的閘門（例如 `\(decision \d`、`\(audit [A-Z]\d`、`\bcut \d`、`this cut`、裸 `\bT\d\b`、`P-I`、`used to `、裸 `\bv1\b` 與 `§\d`——最後一種需排除章節編號有已提交歸屬的引用，如 web-styling.md 自身的 §N）；對本次清掃自身的評審恰好在這些檢索未覆蓋的案例中發現殘留，因此它們位居候選清單之首。
- **刪除引用了失效產物的設計理由。**不予採納：事實性語句都得到保留或改寫；依行文標準的完整命題規則，刪掉的只有引用、評審編排與推導過程記錄。

## 驗證

審計的成批 grep 檢索（英文與中文、註釋與行文、對 `.agents/` 加 `--hidden`）在已錄制 fixture、已歸檔 Agent Note、該清理技能自身文件與本筆記引用的證據之外沒有命中任何設計序號引用；`verify-type-equiv`、各 `gen-*` 新鮮度檢查與 `verify-translation-pairing` 把重新生成與重新記錄的表面固定下來。覆蓋缺口：沒有閘門會拒絕新的序號引用，這條規則由評審把關。

## 後果

- 註釋中的引用憑路徑或名稱即可解析；讀者永遠不必為追溯一條引用而重建已關閉的工作階段。
- 設計工作階段必須先把決策落進 Agent Note，持久行文才能引用這些決策；序號速記只留在工作階段內部。
- 引用變長了（用一條 note 路徑取代「(decision 21)」），換來的是無需 grep 即可解析。
