# Agent Note: 基於實證選用 GitHub 託管大型執行器

Status: implemented

[English](2026-07-22-evidence-based-larger-hosted-runners.md) | [简体中文](2026-07-22-evidence-based-larger-hosted-runners.zh.md) | 繁體中文

## 問題

高度區塊的 CI 拓撲透過把主 Node 工作分散到 40 個 Linux 作業、把 Windows 工作分散到 9 個作業來達到延遲目標。大多數閘門本身的耗時短於程式碼檢出、執行器設定、快取復原和相依性安裝這些準備階段，因此反覆執行多輪設定既增加成本，也帶來延遲波動。一次託管執行中最慢的 Linux 作業用時 49 秒，而一個 Windows lint 區塊卻耗時 231 秒，其中僅程式碼檢出、快取復原和安裝就佔了 158 秒。

大型執行器可以讓 CI 只承擔一次設定開銷，再由倉庫調度器在內部平行執行，但無法僅憑核心數選出有實際價值的規格。關鍵通道基準測試的效能提升不呈單調變化，完整倉庫聚合流程暴露出的瓶頸也不同於單獨執行型別檢查或網站建置時的瓶頸。

## 決策

企業保留僅限本倉庫使用的 Ubuntu 和 Windows x64 大型執行器池。普通Pull Request直接指定 3 個 32 核執行器池：Ubuntu 24.04 用於完整覆蓋率，Ubuntu latest 用於其餘主 Node 24 清單，Windows 2025 用於阻塞性 Windows 約定。公網 IP 已停用；工作流程並行仍設有邊界，因為自動擴縮容上限既不會分配閒置機器，也不意味著倉庫工作可以無限擴充。

必需主路徑相依性這些企業級執行器池。GitHub 標準託管作業保留 Node 22.19、Node 26 和 Python SDK 相容性約定，而[可移植復原邊界](2026-07-23-portable-required-pull-request-ci.md)與[序列參考流程](2026-07-21-serial-cross-platform-ci-reference.md)則在 `master` 上持續提供完整的標準執行器證據。`suite=larger-runner-benchmark` 比較已預配規格上相互獨立的關鍵通道，`suite=consolidated-runner-benchmark` 則比較完整聚合流程。每項基準測試都會先報告實測的處理器和記憶體容量，再執行倉庫工作。

原有的閘門級和粗粒度主流程區塊作業已從工作流程中移除。相應的靜態、lint、覆蓋率、快照和場景區塊選擇器也已從倉庫中移除，因此未使用的診斷路徑無法繼續維繫第二套 CI 架構。

Linux 主流程使用 3 個相互獨立的 32 核作業。覆蓋率單獨執行，並設有自己的工作執行緒上限；靜態調度器負責不消費生成輸出的原始碼和文件閘門。第三個作業負責唯一一次 Linux 建置，隨後讓 lint、Node 24 執行時期相容性、相依性建置產物的快照、文件型別檢查和所有產物消費端基於該目錄樹啟動。這種[消費端獨立建置](2026-07-30-independent-ci-consumer-build.md)使 3 個作業都能立即請求執行器，而無需重複編譯或傳輸僅供本次執行使用的產物。生成的 NodeNext 消費端目錄不會納入 Oxlint 的文件發現範圍，因為這些行程重疊執行時，產物檢查會刪除這些目錄。pnpm store 會得到復原，但快取上傳不會進入Pull Request關鍵路徑；Oxlint 沒有由倉庫管理的結果快取。效能報告採用每個作業從 `startedAt` 到 `completedAt` 的區間；執行器排隊延遲是容量證據，而非倉庫執行時間。

閘門相依性關係保持顯式。覆蓋率消費原始碼，不等待建置。文件型別檢查以消費端通道的完整 project-reference 輸出為輸入。快照重播和發布消費端等待生成的輸出，而 Node 版本相容性作業會驗證對執行時期敏感的原始碼載入，且不重複主原始碼項目圖的型別檢查。PTY 和子行程套件繼續使用自身有界的內部並行，不繼承執行器的核心數。

產物邊界保持顯式。`scripts/publint-all.ts` 對記憶體中的發布檢視表呼叫 publint 支持的 API；該檢視表由每個 manifest（中繼資料清單）聲明的文件和 npm 強制要求的元資料組成，從而避免為每個包啟動一次套件管理員 pack 行程。`scripts/verify-built-package-invariants.mjs` 將已聲明的 `lib/` 文件暫存到真實包下，並透過普通 Node 和 Cordis Loader 規範化匯入其已編譯的自身引用；發布約定只要遺漏一個執行時期區塊，檢查仍會失敗。

在這項企業級必需拓撲中，Windows 透過一次 32 核環境設定同時承載阻塞性建置、生產網站與觀測性建置產物約定，重複的 lint、覆蓋率和快照清單則由 Linux 負責。後續的[Pull Request雙 Windows 拓撲](2026-08-08-native-windows-pull-request-ci.md)新增一個獨立且不阻斷的標準託管原生作業；該作業會獨立強制執行受支持原始碼覆蓋率，同時不延長這條付費必需路徑。

一次分支頭精確的全規格基準測試在修正建置儘早啟動邏輯前，對每種 Linux 池都執行了完整且未區塊的主 Node 聚合流程：

| Linux 完整主流程 | 4 核 | 8 核 | 16 核 | 32 核 | 64 核 | 96 核 |
|---|---:|---:|---:|---:|---:|---:|
| 活動耗時 | 243 秒 | 144 秒 | 103 秒 | 87 秒 | 62 秒 | 65 秒 |

96 核執行軌跡中的倉庫閘門耗時 39.14 秒。型別檢查佔用 25.71 秒，隨後一項調度器相依性使耗時 2.13 秒的建置和耗時 11.29 秒的快照重播都要等到型別檢查結束後才啟動。同一次執行已經分別證明建置和型別檢查可以獨立執行，原 CPU 通道也曾讓二者並行執行。移除這項相依性後，耗時 33.30 秒的 lint 成為實測關鍵閘門，而只有建置輸出的消費端仍保留相依性關係。64 核執行軌跡暴露了相同的空閒鏈：型別檢查、建置和快照依次執行，共耗時 44.85 秒，而相互獨立的 lint 和文件建置分別在 36.83 秒和 36.15 秒內完成。因此，只有倉庫調度器能夠為更多核心持續提供工作時，增加核心數纔有價值。

同一項基準測試還測量了每種已預配規格上的 Windows 必需建置項：

| Windows 阻塞性建置 | 4 核 | 8 核 | 16 核 | 32 核 | 64 核 | 96 核 |
|---|---:|---:|---:|---:|---:|---:|
| 活動耗時 | 152 秒 | 104 秒 | 104 秒 | 92 秒 | 103 秒 | 110 秒 |

Windows 倉庫工作在超過 16 核後收益很小，但 32 核池可以讓完整的外層清單同時啟動。一次重新定向的生產驗證在 173 秒內完成了單機 Windows 完整清單，其中包括覆蓋率和快照重播，因此 Windows 繼續採用合併執行方式。

用戶端包相依性圖增大後，快取機制和調度器壓力也成為實測工作負載的一部分。在一次分支頭精確的候選執行中，Linux 的倉庫閘門耗時 39 秒，完整作業耗時 69 秒；Windows 的倉庫閘門耗時 117 秒，完整作業耗時 228 秒。Windows pnpm 快取的 154 MB 歸檔下載耗時約 2 秒，但解壓縮耗時 27 秒，隨後安裝耗時 23 秒，作業結束後的保存又耗時 14 秒。一次無快取的全規格執行軌跡在 27 秒內完成了同一臺 32 核 Windows 執行器上的安裝。因此，未來若要啟用大型執行器，需要測量完整作業，而不能只測閘門耗時。

任何比較都必須計入主機設定。一個標準 Node 26 作業曾在總共 67 秒的耗時中，把 36 秒用在 `Set up job` 上；`actions/setup-node` 從託管 toolcache 找到 Node 後，仍花費 46.56 秒輸出快取的 Windows 環境詳情。一個 Linux 候選作業還在註冊 50 KB 的 Bubblewrap 包時耗時 18 秒，因為託管映像掃描了 202,507 個包資料庫文件。[`scripts/prepare-ci-bubblewrap.sh`](../../../../scripts/prepare-ci-bubblewrap.sh) 改為驗證固定版本的 payload 並將其解壓縮到臨時執行器目錄，執行功能性隔離探針，並讓這項準備工作與相依性安裝重疊執行。

內層與外層工作執行緒上限是相互獨立的控制機制。一次分支頭精確、使用 32 個工作執行緒的 ESLint 實驗使 lint 耗時增至 52.28 秒、覆蓋率耗時增至 42.71 秒；同一次執行中，一項配接器空閒逾時測試失敗。後來一次同時執行 8 項閘門的執行軌跡將覆蓋率耗時降至 35.17 秒，但生產網站建置被延後，直到聚合流程耗時達到 41.06 秒時才完成。因此，不能僅憑核心數照搬同等規模的工作執行緒上限。

行程約束的覆蓋率項目恰好包含 5 個套件文件。32 個 fork 曾兩次導致 Node 24 的 CJS 詞法分析器崩潰，後來一次使用 16 個 fork 的執行又復現了工作行程丟失和無效的覆蓋率結果。因此，單次 Vitest 呼叫會對大範圍測試清單使用執行緒，只為涉及行程全域性狀態、`process` API 或對時間敏感的行程 I/O 的套件保留 fork。這份有限的 fork 清單包括本機 bash 行程通路套件和 pi-ai 配接器套件，因為聚合爭用改變了二者的時序觀測結果。這些故障表明，選擇工作執行緒數量時，上限取決於覆蓋率結果能否保持確定性，而非標稱核心數。

只有在 `master` 移動時，才執行完整的 Linux、macOS 和 Windows 序列參考。Pull Request使用企業級執行器必需路徑和標準託管相容性作業，其他大型執行器規格僅透過手動觸發運行。

另有一條序列 Linux 參考在每次 `master` 推送時執行於公司自有的自託管池（`vm-backup` 標籤：一臺 64 核虛擬機器，執行 6 個常駐的 systemd 管理執行器實例）。它是熱備演練而非必需檢查：每次執行都重新證明這臺持久化虛擬機器能夠執行完整的未區塊聚合流程。實際切換機制已預先布線：三個必需 Linux 作業透過寫入權限持有者可管理的倉庫變數 `DSH_CI_FAILOVER_LINUX` 解析執行器池，因此故障回應就是設定一個變數並重跑——無需合併（合併本身會被正在失敗的檢查阻塞，形成死結）（[切換手冊](2026-07-26-ci-failover-runbook.md)）。該熱備通道由 push 觸發，執行的始終是基礎分支自身的工作流程定義。但需要注意：故障切換期間，`pull_request` 作業確實會帶著 PR merge 引用自帶的工作流程定義到達這些執行器——信任邊界是倉庫成員資格（倉庫為私有且停用 fork，選擇器排除 Dependabot），詳見[故障切換手冊](2026-07-26-ci-failover-runbook.md)的記錄。

## 曾考慮的替代方案

**保留 3 個粗粒度 Linux 主流程通道。** 核心、CPU 和生產網站作業均達到延遲目標，但它們需要 3 輪設定，而且在大型執行器已經可用後仍對主 Node 工作進行區塊。全規格執行軌跡表明，讓單機聚合流程超過 1 分鐘的是一項不必要的相依性，而非主機容量不足。

**將原有的閘門級區塊拓撲保留為手動參考。** 一套閒置的第二拓撲會讓數百行工作流程、選擇器模組和場景分區行為繼續存活。全規格和序列套件無需保留任何必需作業都不執行的生產程式碼，也能提供計時與完整性對照。

**在每個發布校驗器中復原使用套件管理員打包。** 不予採用，因為這會為每個包重複啟動一個套件管理員子行程。根據 manifest 建置的發布檢視表和已暫存的編譯後自身引用，只需一份行程內清單即可保留發布文件約定。

**在每個 Node 版本上先建置，再執行覆蓋率或型別檢查。** 不予採用，因為覆蓋率只消費原始碼，編譯器分析也不相依性執行時期。相依性建置產物的消費端仍等待生成的輸出，相容性作業則在每個已聲明支持的 Node 版本上驗證對執行時期敏感的路徑。

**使用 64 核池執行完整主聚合流程。** 由於託管設定快了 9 秒，其取樣活動耗時比 96 核結果少 3 秒，但倉庫閘門慢了 5.72 秒。基準測試套件保留兩種規格，因為映像或定價的持續變化可能反轉比較結果。

**讓建置繼續等待型別檢查。** 此方案會給相互獨立的編譯器呼叫排定先後順序，並把快照重播變成 3 階段關鍵鏈。建置輸出本身有獨立的成功相依性關係，因此只有快照和發布消費端需要等待它。

**將靜態作業的建置發布給建置後消費端。** 僅供本次執行使用的產物能保留同一份建置結果，但工作流程要消費它，只能先等待整個靜態作業完成，再請求另一臺執行器。[消費端獨立建置](2026-07-30-independent-ci-consumer-build.md)則轉而讓實際消費端負責唯一一次 Linux 建置。

**將完整必需路徑保留在 GitHub 標準託管容量上。** 此方案可以避免相依性倉庫外部的執行器設定，但標準執行器上的分支頭精確執行仍明顯更慢，也可能因共享容量而排隊更久。標準託管相容性作業和序列參考流程保留可移植證據，無需讓這套較慢的拓撲成為普通主路徑。

**將必需的 Windows 檢查和觀測性 Windows 檢查保留在不同作業中。** 這種拆分在工作流程層保留狀態語義，卻需要付款兩次設定開銷。`run-gates` 在一個行程內保留了相同的必需與非阻塞區別。

**透過系統套件管理員安裝 Bubblewrap。** 此方案會使用主機的包資料庫，即使包內容很小，也可能主導整個作業耗時。固定版本的解壓縮方式配合隔離探針，無需修改託管映像即可保留執行時期約定。

## 後果

必需拓撲中的每個 32 核通道只承擔 1 輪設定開銷，且不保留區塊選擇器。每個普通Pull Request都會消耗付費的企業級 Linux 和 Windows 執行器分鐘數；只有在重新測量有價值時，手動基準測試才會加入其他規格。

GitHub 會把每次大型執行器執行向上取整到整分鐘計費，因此完整作業測量能同時呈現計費時長與工作流程複雜度。拆分 Linux 會重複兩輪設定，但消費端通道擁有唯一一份已建置目錄樹，且覆蓋率、靜態閘門與建置後消費端分別進入執行器分配；合併 Windows 則避免重複其耗時更長的設定。

效能目標是觀測結果，而非取消截止時間或正確性要求。當映像、相依性、調度器或定價發生變化而需要重新測量時，仍可使用手動全規格和序列套件。

企業級執行器標籤缺失或改名時，必需主作業會持續排隊。標準託管相容性作業與 `master` 參考流程仍會報告有用證據，但不能替代必需聚合流程；因此，執行器分配是一項倉庫 CI 無法修復的運維相依性。
