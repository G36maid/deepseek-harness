# Agent Note: 將未來指導價值較低的 Agent Note 凍結在活躍記錄集合之外

Status: implemented

[English](2026-07-26-frozen-agent-note-archive.md) | [简体中文](2026-07-26-frozen-agent-note-archive.zh.md) | 繁體中文

## 問題

implemented Agent Note 作為當前決策記錄持續維護，因此活躍記錄集合中的每個路徑、符號、預設值、譯文、圍欄程式碼區塊、包引用和出站連結都會形成維護義務。當決策依據可以指導未來工作時，這項成本合理；但對於已經收尾的 UI 細節、小型修復、已被取代的實作機制，或當前權威依據已轉移到別處的流程歷史，這項成本並不值得。刪除所有低價值的已實施記錄會抹去有用的歷史證據，而保留每一項被否決的提案，又會留下既無採納可能也無啟發意義的想法。這套記錄集合需要一道留存邊界，在區分活躍指導與凍結歷史的同時，避免讓歸檔成為另一個維護層級。

## 決策

只有 implemented Agent Note 可以歸檔。當一份已實施記錄的交付決策已經完整落地，且其決策依據、備選方案、後果、否定性保證和重新引入條件不太可能再指導未來工作時，將其移入歸檔。基礎性邊界、持久語義與協議語義、安全規則、反覆出現且看似誘人的設計選擇和尚未解決的重新引入條件，無論記錄的存續時間或字數如何，都繼續作為活躍記錄保留。proposed Agent Note 絕不進入歸檔；過時的提案應轉為 rejected。僅當 rejected Agent Note 仍能避免一種誘人且影響重大的錯誤時保留，否則將其三個配對文件完整刪除。

歸檔路徑為 `.agents/notes/archived/{kind}/yyyy-mm-dd-topic.md`，其中省略了冗餘的 `implemented` 層級。歸檔變更會移動完整的英文、中文和一致性伴隨記錄三個文件，保留 `Status: implemented`，並在兩種語言的文件中緊接該狀態行插入 `Archived: YYYY-MM-DD`。歸檔時只允許做文件遷移、新增該元資料行、相應地重新記錄伴隨記錄，以及機械修復入站連結。

根目錄的 `.rgignore` 會將歸檔目錄排除在從上層目錄開始的搜尋之外。尋找歷史內容時會顯式指定歸檔目錄，因此仍可按需訪問，同時不會把凍結事實混入對活躍決策的檢索。

歸檔後，這三個文件永久凍結，只作為歷史背景，不再是當前權威依據。不得因為包重新命名、行為變化、翻譯標準、格式規則、出站連結失效或後續文件約定而更新歸檔文件。活躍文件可以有意連結到歸檔 Agent Note，也可以把該連結重定向到當前權威依據，或直接刪除。倉庫閘門因此會校驗指向歸檔文件的連結，但絕不把歸檔文件作為連結源來校驗。

[`verify-archived-agent-notes`](../../../../scripts/verify-archived-agent-notes.ts) 負責維護凍結邊界。它只接受封閉集合中的 Agent Note 類別，要求三個配對文件完整、狀態為 implemented，且歸檔日期有效並互相匹配；它還會用雙方當前的 Git blob hash 校驗伴隨記錄，並在僅附加的 manifest（中繼資料清單）中按路徑和 SHA-256 內容 hash 封存每項產物。其 `--write` 模式會先證明每條現有封存記錄對應的內容都未改變，再僅附加新歸檔的產物。Pull Request CI 會提供可信的基準 SHA，並在執行校驗器前檢出完整歷史，因此複用執行器上的淺克隆檢出無法漏掉基線 manifest。普通的 Agent Note 格式、翻譯配對、換行、Markdown 連結、包路徑、Mermaid、文件 TypeScript 和類型等價閘門都排除歸檔原始檔，因此這些閘門持續演進的標準不會產生修改歷史記錄的壓力。

[`dsh-archive-agent-notes`](../../../skills/dsh-archive-agent-notes/SKILL.md) 工作流程負責分類判斷。它要求逐份 Agent Note 做語義審計，使用程式碼和當前文件識別現行權威依據，僅把字數作為初步篩選手段，收錄經過校準的保留、歸檔和刪除示例，並報告真正處於邊界的結果，以供評審。

在編寫新的 Agent Note 時就檢查取代關係，而不是推遲到日後清理記錄集合時再處理。作者會將新記錄與涵蓋同一項決策、機制或被否決備選方案的活躍記錄進行比較，並逐項判定屬於完全取代還是部分取代。符合條件的 implemented Agent Note 三文件配對會在同一個Pull Request中歸檔；僅部分被取代的記錄，以及仍保有獨立價值的決策依據，會繼續作為活躍記錄保留並與新記錄互相連結，而匹配到的 proposed 和 rejected Agent Note 則遵循各自的生命週期規則。

## 曾考慮的替代方案

**刪除每一份移出活躍記錄集合的記錄。** 不予採納，因為已實施記錄可能對未來的指導價值較低，卻仍能為已經收尾的決策提供有用的歷史證據。按內容 hash 封存的歸檔既能保留這些證據，又不會假裝它們仍然反映當前狀態。

**繼續將每一份 implemented 和 rejected Agent Note 作為活躍記錄保留。** 不予採納，因為不再幫助未來決策的記錄會不斷增加維護成本和搜尋噪聲。尤其是 rejected Agent Note，只有能避免一種可能發生的謬誤時，才值得保留。

**讓歸檔 Agent Note 繼續出現在默認的倉庫搜尋結果中。** 不予採納，因為歸檔事實按設計可能已經過時，並可能僅憑字面匹配就排在當前結果之前。需要尋找歷史內容時，可以顯式搜尋歸檔目錄。

**把取代關係清理留到定期審計記錄集合時再做。** 不予採納，因為替代記錄的作者掌握著關於歸屬和重疊的最新證據。推遲處理會留下冗餘的活躍權威依據，並增加日後分類的成本。

**同時歸檔 rejected 或 proposed Agent Note。** 不予採納，因為歸檔狀態表達的是「已經實施的歷史決策」。過時的提案需要明確轉為 rejected；無法提供防錯價值的 rejected Agent Note 則應刪除，而不是再放入第二個低價值存放區。

**繼續對歸檔 Agent Note 應用所有文件閘門。** 不予採納，因為後續新增的格式、翻譯、程式碼、包或連結規則會迫使維護者重寫歷史快照。改由專用校驗器負責完整性與不可變性。

**允許更新事實，只凍結決策依據。** 不予採納，因為這會重新引入活躍記錄集合的判斷和翻譯負擔，也會讓讀者無法分辨哪些條款屬於歷史。當前事實應寫在活躍文件或新的活躍 Agent Note 中。

## 後果

活躍記錄集合由預計仍會影響未來工作的決策組成；未來指導價值較低的實施歷史仍可顯式搜尋和連結，卻不再消耗維護精力，也不會出現在從上層目錄開始的搜尋中。編寫新記錄時會包含一項範圍明確的取代關係檢查，因此取代既有決策的新決策無法悄然留下冗餘的活躍記錄。當被否決的記錄不再保護有意義的選擇時，可以清除這類雜項；提案也無法透過歸檔悄悄逃避明確結論。歸檔機制增加一份 manifest、一個專用校驗器和一個顯式的一次性元資料步驟。歸檔中的事實和出站連結可以按設計逐漸過時，因此讀者和 agent（代理）必須以活躍程式碼與文件為權威依據，並且僅將歸檔 Agent Note 作為歷史引用。
