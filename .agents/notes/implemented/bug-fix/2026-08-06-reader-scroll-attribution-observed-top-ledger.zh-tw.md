# Agent Note: 經由 observed-top ledger 的讀者滾動歸因

Status: implemented

[English](2026-08-06-reader-scroll-attribution-observed-top-ledger.md) | [简体中文](2026-08-06-reader-scroll-attribution-observed-top-ledger.zh.md) | 繁體中文

## 問題

ChatView 的貼底跟隨此前只把滾輪／觸控板手勢識別為讀者輸入：釘在底部（floor）期間，一個沒有對應滾輪位移的滾動事件會被視為程序化滾動並被拉回底部。因此觸控平移、拖動原生捲軸與鍵盤翻頁都無法離開流式 transcript（文字記錄）的底部，在手機上尾部實際上被鎖死。這種僅認滾輪的輸入來源判定是 [sticky-composer 筆記](2026-07-29-sticky-composer-conversation-scroll.md)中有意的暫緩：該筆記拒絕為「此次窄範圍修復」建立通用輸入狀態機，把其餘所有滾動來源都留在模型之外。

## 決策

讀者輸入不再依據設備來識別。ChatView 維護一份 observed-top ledger（`observedTopRef`）：即最近一次由主線程交付、或由元件自身寫入的 `scrollTop`，並在每一個程序化寫入點（貼底跟隨、打開時復原、前置錨定、尺寸變化跟隨以及滾動交付本身）同步記錄。滾動事件到達時，偏離 `min(ledger, floor)` 超過半畫素的位置即為讀者輸入；落在 ledger 上的位置（遲到的程序化交付），或恰好落在收縮後底部上的位置（內容收縮後的瀏覽器鉗制），則維持當前的所有權狀態。此後所有權只經由讀者輸入、按既有閾值規則變化：位置距底部在 `FOLLOW_THRESHOLD` 以內則重新貼底，超出則釋放跟隨並顯示「回到底部」。滾輪監聽器及其 epoch 簿記已刪除；元件只監聽 `scroll`，因此滾輪、觸控、捲軸、鍵盤以及未來任何輸入來源都由同一條規則覆蓋。

## 約定變更：收縮與重新成長被合併的鉗制

如果一次收縮鉗制的版面配置在同一次渲染更新內、趕在該鉗制的滾動事件交付之前重新成長，那麼這個事件在幾何上與讀者輸入無法區分，因此它現在會被判讀為讀者並釋放跟隨（可經「回到底部」復原）。現實中由 React 提交（commit）驅動程式的收縮與重新成長仍會被吸收：layout effect 中的跟隨會在每次提交後重新貼底並重新記錄 ledger，而僅收縮的鉗制會恰好落在 `min(ledger, floor)` 上。只有在同一次更新內先收縮再重新成長的非 React 重排會被誤歸因。舊的滾輪模型在這種競態情形下會保持跟隨；單元測試約定已在同一變更中改寫為只吸收純收縮的保證。

## 測試

`packages/client/ui-conversation/tests/chat-view.client.spec.tsx` 中的單元測試直接釘住 ledger 約定：`readerScroll` 輔助函式交付一個元件從未寫入過的位置，程序化交付落在 ledger 上，流收尾階段的收縮鉗制保持跟隨。`apps/web/tests/chat-scroll-contract.e2e.ts` 中的兩個場景擴充了[瀏覽器 e2e 車道](../testing/2026-07-24-web-gui-browser-e2e-lane.md)：在已停穩的 transcript 上做鍵盤翻頁，以及對著按節奏推進的流式輸出做一次觸控式慣性快滑（momentum fling）；兩者在僅認滾輪的實作下均為紅、在 ledger 下均為綠。

該車道的 Chromium 無法合成任何非滾輪的設備滾動，這限定了 e2e 能真實驅動程式的範圍：觸控來源的 `Input.synthesizeScrollGesture` 與手工構造的 `Input.dispatchTouchEvent` 序列都能交付 DOM 事件，卻從不移動滾動容器（無頭模式與 Xvfb 下的有頭模式皆然）；`default` 手勢來源合成的是滾輪事件；合成器捲軸則完全無視合成的滑鼠輸入，且只有移除 `--hide-scrollbars` 後才能看到捲軸槽。鍵盤是唯一可用的非滾輪原語，因此由它承擔真實輸入管線的證明；快滑場景則把觸控的特徵（元件從未寫入過的逐幀衰減位移）直接重播進滾動容器。

## 曾考慮的替代方案

**保留僅認滾輪的模型。** 否決：它本身就是缺陷所在。觸控、捲軸與鍵盤讀者無法從流式尾部奪走所有權，而每種新支持的設備都需要單獨開一個特例。

**逐一枚舉輸入設備。** 在滾輪 epoch 旁邊加掛 `touchstart`/`pointerdown`/`keydown` 監聽器是最顯而易見的擴充。否決：拖動原生捲軸在其滾動事件到達之前不暴露任何可供鎖存的輸入事件；設備清單會隨瀏覽器新增輸入來源而逐漸腐化；而且每個監聽器都需要自己的合成器交付寬限視窗——這正是 sticky-composer 筆記當初就拒絕建置的那個輸入狀態機。

**用啟發式吸收收縮與重新成長被合併的鉗制。** 針對底部失配的寬限視窗，或推遲到 rAF 的複查，本可讓這種競態下的鉗制不被判讀為讀者。否決：流式輸出以區塊節奏（24 ms）改寫底部，而幀間隔約 16 ms，因此任何寬限視窗要麼會在流式輸出期間吞掉真實的觸控輸入（重新打開本次變更所修復的缺陷），要麼短到蓋不住它想針對的競態。轉而接受這一誤歸因，它是可復原的。

**在 e2e 中驅動程式真實的觸控與捲軸設備。** 否決來自環境，而非偏好取捨：每條合成路徑（CDP 觸控手勢、觸控事件序列、經典捲軸上的合成滑鼠、Xvfb 下的有頭模式）都逐一試過，均無法滾動；細節見上文「測試」一節。

## 後果

每種讀者輸入現在都以同一方式擁有貼底跟隨，而程式碼更少：滾輪監聽器、它的 epoch 計數器以及輸入前基線簿記均已移除，歸因搭載在元件本就維護的狀態之上。sticky-composer 筆記中的版面配置、滾輪鏈式處理與前置錨定決策原樣保留，仍為權威；其窄範圍的輸入來源規則由本筆記取代。代價就是上文的約定變更：一次收縮與重新成長被合併的非 React 鉗制現在會暫停跟隨，直到讀者回到底部或按下「回到底部」；以此換來流式輸出期間觸控、捲軸與鍵盤的正確性。e2e 車道獲得的非滾輪覆蓋僅限其瀏覽器能夠合成的範圍；若手勢合成在未來某個 Chromium 版本中開始可用，可以在不改變所斷言約定的前提下，把快滑模擬替換為真實的觸控劃動。
