# Agent Note: 有界背景工作準入

Status: implemented

[English](2026-08-11-bounded-background-job-admission.md) | [简体中文](2026-08-11-bounded-background-job-admission.zh.md) | 繁體中文

## 問題

模型可以在不同工具呼叫和後續回合中啟動後臺 Bash、PowerShell、PTY 操作與一次性 subagent。agent loop 的 `maxParallelToolCalls` 只限制單個步驟中尚未返回的呼叫；每個後臺生產方會立即返回 job id，因此反覆啟動會讓仍存活的行程或子工作無限成長。

行程內任務登錄檔已經擁有確切任務 owner 與權威生命週期狀態，但終止歷史和即時記錄保存在一起，且沒有準入策略。在請求取消時立即釋放容量也不正確：處於 `stopping` 的生產方仍可能擁有行程、PTY 或子任務，直到 `JobHooks.done` 結帳。

## 決策

`LocalJobRegistry` 擁有 `maxConcurrentJobsPerOwner` 設定欄位。它只接受正的安全整數，預設值為 `10`，並透過 Service Provider 的 Cordis schema、typed `agent-spine-demo` 組合包與 ACP 應用設定提供。組合包只傳輸該值；其含義歸行程內 Service Provider 所有。

[通用任務執行時期決策](../architecture/2026-06-20-generic-long-running-tool-runtime.md)擁有共享 Task 生命週期與控制 API；本記錄只擁有行程內准入策略。

`start()` 在現有任務控制器、任務欄位與存活 owner 檢查之後、`JobStart.run()` 之前執行准入。它從登錄檔當前記錄派生活動數量，而不保存另一份計數：

| 記錄 | 佔用容量 | 釋放事實 |
|---|---:|---|
| `running` | 是 | 生產方 `done` 結帳 |
| `stopping` | 是 | 生產方 `done` 結帳 |
| `completed`、`killed` 或 `failed` | 否 | 已經終止 |

有 owner 的任務按確切 `Agent` 對象身份分桶，與 owner 清理保持一致。複用同一工作階段 id 的替代 agent 獲得獨立桶。無 owner 的任務共享一個服務級桶，因此省略 owner 不會成為無界旁路。

桶已滿時，`start()` 會在生產方執行和 job id 分配前拋出例外。診斷包含當前上限，並告訴模型使用 `job_kill`、等待任務完全靜止後再重試。拒絕不會建立執行資源、排隊項、預留或公開任務記錄；後續成功啟動仍會取得按 kind 正常遞增的下一個 id。

owner 與服務釋放保留現有順序：請求取消，在生產方釋放資源期間繼續讓 `stopping` 佔位，等待結帳，然後移除記錄。因此，准入策略遵循讀取、通知與清理共同使用的同一生命週期事實，而不會把取消請求誤當成資源釋放。

可繼續後臺 subagent 仍不納入此預算。它們擁有持久 child session 與即時 Activation，而不是 Task 記錄；限制它們需要獨立的使用者結果與生命週期約定。本決策也不會新增 Task 快照、工作階段日誌、wire、持久化、行程級 CPU 或記憶體預算、佇列、優先級、搶佔或自動終止最舊任務。

## 驗證

任務 Service Provider 測試覆蓋默認與顯式上限、生產方執行前拒絕、id 計數器不變、`stopping` 佔位、每種終態釋放、確切 owner 隔離、同工作階段替代對象、共享無 owner 桶、非法設定、owner 清理和服務拆除。spine 與 ACP 組合測試固定 typed 轉發。一條 keyless ACP 重播以 1 為上限啟動真實 Loader 組合，啟動一個真實後臺 Bash 行程，觀察第二次啟動返回可操作錯誤，按返回的 job id 停止第一個任務，並驗證被拒絕生產方的標記文件從未生成。

## 曾考慮的替代方案

**相依性 `maxParallelToolCalls`。**否決，因為後臺工具呼叫一返回 job id 就會釋放其步驟槽位；該設定無法限制在後續步驟和回合中繼續存活的工作。

**在 `job_kill` 成功時釋放容量。**否決，因為取消成功只會把任務改為 `stopping`。生產方在 `done` 結帳前仍可能持有資源，立即准入替代任務會突破已設定的即時資源上限。

**使用一個全域性行程桶。**否決，因為一個繁忙 agent 會拒絕無關工作階段，而無 owner 的宿主工作仍需要一個明確的有界桶。確切 owner 身份已經定義清理生命週期，並提供正確分區。

**排隊、搶佔或終止最舊任務。**否決，因為每種策略都會增加超出 fail-closed 上限要求的順序、所有權和取消行為。顯式拒絕讓模型透過現有 `job_kill` 控制自行決定哪些工作不再需要。

**維護一張可變活動計數表。**否決，因為登錄檔已經保存權威記錄與狀態。第二份計數需要回滾和結帳同步，卻無法提供直接派生所缺少的使用者結果。

## 後果

單個確切 owner 無法再無限建立由 Task 承載的即時資源，無關 owner 則保留獨立額度。緩慢停止會讓桶保持滿載直到 `done` 結帳，這是有意行為：設定值限制的是仍可能擁有資源的工作，而不是取消請求。如果生產方的 `cancel` 返回後始終不結帳 `done`，它會在服務剩餘生命週期內持續佔用一個名額並阻塞銷毀，因為登錄檔無法安全推斷資源已經釋放。

每次啟動都會掃描行程內登錄檔。成本隨保留的 Task 歷史成長；為了保持單一狀態權威，並利用足以約束常見即時集合的較小預設值，接受這一代價。終止歷史仍可供現有讀取與清單使用，但不消耗容量。
