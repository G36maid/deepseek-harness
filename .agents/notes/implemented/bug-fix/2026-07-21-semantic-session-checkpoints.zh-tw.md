# Agent Note: 語義工作階段檢查點

Status: implemented

[English](2026-07-21-semantic-session-checkpoints.md) | [简体中文](2026-07-21-semantic-session-checkpoints.zh.md) | 繁體中文

## 問題

持久化機制會緩衝所有同步 `session/event`，直到 agent loop（代理循環）執行最後的輪次檢查點才寫入。一個輪次是正確的對話交易，但作為唯一的當機復原點過於粗粒度：如果在耗時的模型請求或工具呼叫期間發生硬崩潰，整個進行中的輪次都可能丟失，其中包括識別已嘗試操作所需的請求封套。系統還會使用同一種不作區分的中斷錯誤，修復沒有結果的工具呼叫，因此復原執行的模型無法判斷呼叫是否已經開始，可能會盲目重試帶有副作用的操作。

## 決策

`dsh-session-checkpoint-policy` 以零設定外掛程式的形式與持久化後端共同載入，並負責語義持久性屏障。在 `agent/pre-step` 時，該外掛程式會在推導下一個請求前刷新待持久化的提示詞輸入或前一批迴應/結果。該外掛程式惰性包裝 `llm/stream`，在記錄 `request/header` 之後、構造配接器流之前，刷新當前工作階段。該外掛程式還在有序的執行前策略之後包裝頂層 `tools/execute`，在進入工具主體前刷新已記錄的 `tool/call`；巢狀分發則複用外層模型可見呼叫。迴圈的最終 `turn/end` 檢查點仍是輪次的收尾邊界，並會在處理另一個已排隊輪次或觀察到空閒狀態之前完成。

持久化與檢查點調度仍是相互獨立的 Cordis 外掛程式。後端使請求的 `session/flush` 邊界持久化，但不選擇邊界；只載入後端而不載入本策略仍是有效組合，並保留迴圈提供的較粗檢查點。第一方持久化應用與執行時期會顯式載入兩者，專用部署則可以有意省略或替換本策略。註冊順序決定其他 `agent/pre-step` 監聽器追加的事件是否先於本檢查點；提示詞輸入以及前一批由迴圈自身記錄的助手訊息與有序結果都已在日誌中。

檢查點失敗與取消在副作用邊界上採取失敗關閉策略。請求檢查點被拒絕時，系統不會分發給配接器；工具檢查點被拒絕時，系統會返回錯誤結果，不呼叫工具主體。如果在工具檢查點等待期間收到取消，策略會重新檢查訊號，並返回標準的 `ABORTED_BEFORE_DISPATCH` 結果。步驟間檢查點被拒絕時，系統會在發起下一個模型請求前結束該輪次。輪次的最終檢查點被拒絕時，系統會即時報告該失敗，但不會阻止後續排隊工作。持久化寫入的序列化仍由協調器負責，因此並行的工具檢查點不會產生重複的事件序列。

ACP（Agent Client Protocol）應用在一個有序 Cordis effect 中統一持有其橋接層、檢查點策略與持久化後端。Cordis 會並行解除安裝同級外掛程式的 effect；如果分別載入，橋接層仍在為被中斷的輪次收尾時，持久化後端就可能已經解除安裝。組合生命週期會先解除安裝橋接層，等待其各 agent 完全靜止，並刷新真實的 `step/end` 與 `turn/end`，再移除檢查點調度與持久化。

崩潰修復會區分持久化證據。如果模型寄出了工具請求，卻沒有 `tool/call`，系統會將其標記為 `TOOL_NOT_STARTED`；如果仍有需要，可以重試。如果持久化的 `tool/call` 沒有結果，系統會將其標記為 `TOOL_OUTCOME_UNKNOWN`；對應的模型可見結果只允許重試只讀或冪等操作，並指示模型在決定如何處理有副作用的工作前，先驗證外部狀態或詢問使用者。支持冪等鍵的模型提供方可以取得穩定的 `callId`，但 Harness 不承諾副作用恰好執行一次這一通用保證。

## 考慮過的替代方案

刷新每個事件或流式區塊雖能儘可能減少丟失，但會把本機追加與 `fsync` 延遲帶入熱路徑，破壞流式輸出的吞吐穩定性。將這些屏障放入 `agent-loop`，雖能防止該迴圈漏裝，卻會將檢查點策略隱藏在機制中，並失去 Cordis 層的替換與排序能力。僅保留輪次刷新可以維持吞吐量，但會丟失安全復原所需的請求與執行意圖。自動重試所有未匹配呼叫只對部分工具安全，可能會重複不可逆的副作用。

## 後果

發生硬崩潰時，當機復原會在最近的語義邊界保留完整的模型請求、持久化的工具意圖與完整且已結束的步驟，但允許上一個邊界之後的部分流式區塊仍可能丟失。默認的 CLI（命令列介面）、TUI、ACP、Python SDK 執行時期、headless 持久化測試與 JSON-RPC 組合都會在持久化後端旁載入該策略。單元測試覆蓋順序、檢查點期間的取消、失敗關閉行為、巢狀分發、dispose（資源釋放）與 Loader 形狀，以及最終檢查點的順序與故障隔離；一個被 `SIGKILL` 終止的真實子行程透過 JSONL 證明系統可以復原請求與工具意圖，共享持久化約定則證明各後端都支持這兩種復原分類。崩潰 harness 會等待預期的標記內容，而不是僅等待路徑存在，因此文件在寫入前因打開而可見時，不會導致該 harness 提前終止子行程。無金鑰 ACP 與 SDK 快照證明重試風險指引會進入復原後的歷史記錄與下一個模型輪次，取消流程正常收尾時系統會持久化由迴圈實際生成的閉合邊界，且 SDK 關閉流程會觀察到已完整持久化的輪次。
