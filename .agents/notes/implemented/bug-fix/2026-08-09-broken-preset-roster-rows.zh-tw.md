# Agent Note: 損壞的 preset 是名單行，不是空缺

Status: implemented

[English](2026-08-09-broken-preset-roster-rows.md) | [简体中文](2026-08-09-broken-preset-roster-rows.zh.md) | 繁體中文

## 問題

文件成為唯一的組裝編輯器之後，手動編輯造成的損壞有兩種形態，且都要拖到最糟的時刻才暴露。`agent.cordis.yml` 解析不了的 preset 在名單上是一張完全正常的行——選填擇、可複製、可設為默認——直到下一個工作階段嘗試掛載才失敗；一旦被設為默認，所有新工作階段都無法啟動。組裝文件被整個刪掉的目錄則從名單上消失，卻仍在磁碟上佔著它的 id：`copy` 以「先刪除既有 preset」拒絕這個名字，`remove` 卻回答「找不到」——兩條互相矛盾的錯誤，除了手動刪目錄別無出路。

## 決定

發現過程負責健康，受損目錄是**攜帶 `broken` 原因的名單行**，絕不是空缺。`scanRoot` 把名字是可用 preset id 的每個目錄都當作一個 preset 槽位：組裝缺失 → broken（「仍佔著該 id；刪除目錄或復原文件」），組裝不可讀/解析失敗/不是具名行清單 → broken 並攜帶解析器的首行。形狀檢查用載入器自己的 `entryListSchema`（含 `!!js` 的方言）解析，因此健康檢查絕不會把載入器接受的組裝叫作損壞；名字不符合 `PRESET_ID` 的目錄直接跳過，因為複製永遠不可能與之相撞。`broken` 依次落在 `AgentPreset`、`agentPreset.list` 的線上條目和 UI 行上。掛載路徑（`mount`/`recompose`/`standingKeyFor`）經 `resolveMountable` 用發現時記下的原因在前置拒絕；`resolve` 照樣應答（刪除/讀取/上報都需要這一行），而 `copy` 的名單檢查現在看得見幽靈，讓「已存在」的拒絕變得可操作——要刪的損壞卡片就在同一頁上。

介面按職責分開：管理區把損壞行渲染為標記卡片（紅邊、「已損壞」徽記、原樣展示原因、卡片主體與複製停用，自訂行保留位置與刪除——文件正是修復處，刪除正是幽靈的出路；損壞的內建行連查看器也不給），而兩個選擇器（通用設定行、新工作階段 chip）經 `presetOptions` 完全不列損壞的 preset——它們選的是下一個工作階段的組裝，端出無法組裝的選項只會推遲失敗。

## 後果

- 幽靈死路端到端消除：目錄以損壞行列出，刪除即清掉，釋放的 id 立刻可用（單測、元件測試與 e2e 各自覆蓋）。
- 事後才損壞的預設值仍會在工作階段啟動處大聲失敗——選擇器隱藏損壞行，但沒有任何東西改寫已存的默認；`resolveMountable` 的前置拒絕讓每種不可載入形態得到同一則訊息，而不是相依性載入器內部的報錯。
- 健康檢查隨每次 `list()` 執行：每次讀名單對每個 preset 一次讀取加解析，接受的理由與不做快取的發現相同——名單很小，新鮮是契約。
- 複製損壞 preset 只在 UI 層拒絕（按鈕停用並給出原因）；宿主的 `copy` 保持形狀無關。損壞來源產出同樣損壞、同樣可見的副本——沒有能力增益，而宿主側拒絕需要為一條被停用按鈕擋住的路徑專門發明錯誤詞彙。

## 關鍵細節

- **`PRESET_ID` 移到 `types.ts`**，讓發現與創作共享同一份包含邊界詞彙；authoring 原樣轉發匯出。
- **原因只留一行。** js-yaml 會附上多行程式碼框摘錄；名單卡片不是終端機，`compositionProblem` 只保留首行。
- **mount.spec 的兩個競態用例特意不動**：`ensureStanding` 仍可能拿到刪除前一刻解析出的 preset（私有路徑測試），其 stamp/unstampable 語義不變——健康檢查發生在此之前的公開路徑上。
- **創造模式的引導隨同一 PR 落地**：`cordis` preset 的 persona 禁止編輯隨附安裝（損壞 `cordis` 會停用這一模式本身），並把創作指向 `${DSH_HOME:-$HOME/.dsh}/.agent-presets/<id>/`；其技能教了 `preset.yml` 元資訊、先複製再改的流程與一次升級的沙盒現實（preset 根目錄在工作階段工作區之外）。已實測：被要求直接改隨附 `cordis` 組裝時，組裝出的 agent 援引兩條規則拒絕並給出複製路徑；被要求真正建立 preset 時，它落在 `$DSH_HOME` 下並把寫入合併為一次升級。該引導中關於驗證的那一半——agent 無法自己啟動工作階段，因而設定頁的紅色標記是使用者的檢查項——已由[創作 preset 的 agent 自行掛載校驗其組裝](2026-08-11-preset-authoring-agent-validates-its-own-composition.md)取代：下文的結構檢查不是校驗，而 `standingKeyFor` 才給了 agent 真正的校驗手段。本篇的健康檢查決策不變。

## 曾考慮的替代方案

隱藏損壞 preset 但在複製時用更好的報錯拒絕該 id：幽靈仍然無法從任何介面清除。深度校驗（讀名單時解析每一行的模組）：掛載已經擁有這一失敗並帶回滾，每次讀名單逐行 import 既不便宜也不更可操作。阻止 `settings` 寫入指向損壞預設值：settings 領域是通用的，而名單是活目錄——此刻缺失或損壞的名字到下一個工作階段可能已經有效，掛載的響亮失敗纔是擁有那一刻的強制點。
