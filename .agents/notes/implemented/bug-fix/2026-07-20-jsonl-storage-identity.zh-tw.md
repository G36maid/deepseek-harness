# Agent Note: 在變更前綁定 JSONL 工作階段身份

Status: implemented

[English](2026-07-20-jsonl-storage-identity.md) | [简体中文](2026-07-20-jsonl-storage-identity.zh.md) | 繁體中文

## 問題

JSONL 尋找會根據請求的工作階段 id 在各個項目目錄中選出物理日誌，而解析得到的 `SessionHeader` 會提供後續修復和追加操作使用的元資料。如果這兩個事實沒有綁定，為工作階段 A 選中的日誌就能聲明工作階段 B 的 id 或 cwd，並將修復或後續追加重定向到 B 的路徑。當同一個編碼後 id 出現在多個項目目錄中時，項目掃描也必須給出確定的結果。SQLite 不存在這種歧義，因為主鍵查詢會將元資料和事件綁定到請求的 id。

## 決策

`loadStored(id)` 是協調器唯一的已存前綴尋找操作。JSONL 後端掃描所有項目目錄，要求名稱與該 id 的編碼值匹配且其中包含 transcript（文字記錄）的工作階段目錄至多有一個，解析其中的 transcript，然後驗證 `header.id === id`，並驗證選定路徑要麼等於 `logPath(root, header.cwd, header.id)`，要麼經檔案系統路徑規範化後，兩種寫法解析為同一份 transcript。`list()` 執行相同的路徑驗證，並拒絕跨項目目錄重複的 id。

協調器會獨立斷言返回的 id，並在修復、發布狀態或持久化後綴之前比較已存 cwd 和活動工作階段的 cwd。協調器保留一份已驗證元資料的獨立副本；JSONL 的追加和修復操作根據該副本派生路徑。因此，`PersistenceBackend<TornMarker>` 介面既不需要限定範圍的活動工作階段尋找，也不需要儲存定位器類型。

如果設定的 JSONL 根目錄已存在，外掛程式載入時該路徑必須是可讀目錄。根目錄不存在仍然是有效設定，首次物化時會建立該目錄。後端對每個工作階段只支持一個活動寫入方；在所有者完成 dispose（資源釋放）且所有寫入停止之前，另一個後端實例或行程不得變更該工作階段。

## 考慮過的替代方案

**按工作階段 id 扁平化儲存。** 扁平命名空間會讓重複發布在同一路徑上衝突，但路徑驗證和重複項拒絕無需讓檢查相依性扁平的全域性命名空間，也能消除身份缺陷。

**透過協調器傳遞不透明儲存定位器。** 定位器可以將 JSONL 變更直接綁定到選定路徑，但 JSONL 可以根據已經驗證的元資料重新得到該路徑。為 SQLite、測試後端、追加和修復操作增加一個泛型和參數，會讓每個實作都承擔只有文件後端需要的概念。

**協調多個活動寫入方。** 專用協調服務、行程級全域性登錄檔或跨行程鎖會定義新的部署拓撲，而不是修復身分驗證。受支持的拓撲只有一個活動寫入方；禁止覆蓋的硬連結發布仍會裁決初始的同 id 建立競態。

## 後果

JSONL 日誌的身份不匹配、位置錯誤和重複會在修復或協調器狀態變更前失敗。尋找開銷仍與項目目錄數量成正比，單一活動寫入方的所有權仍是明確限制。協調器和 JSONL 測試固定了修復前拒絕、兩個受影響日誌的位元組均保持不變、列出時的路徑驗證、重複 id 拒絕、項目路徑規範化衝突與大小寫別名，以及載入時的根目錄驗證。
