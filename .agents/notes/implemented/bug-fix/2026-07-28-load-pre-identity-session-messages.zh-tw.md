# Agent Note: 載入訊息標識機制引入前持久化的工作階段

Status: implemented

[English](2026-07-28-load-pre-identity-session-messages.md) | [简体中文](2026-07-28-load-pre-identity-session-messages.zh.md) | 繁體中文

## 問題

帶標識的不可變訊息變更將四種持久化事件載荷替換為完整訊息值。現有的 v0 JSONL 和 SQLite 工作階段仍保留緊鄰該變更之前的形狀：使用者事件和 steering（中途引導）事件直接攜帶 `content`/`source`，assistant 事件攜帶 `content`/`provenance`，工具結果則攜帶 `callId`/`content`/`isError`。這些工作階段的標頭仍與 `SESSION_FORMAT_VERSION` 匹配，但當前形狀驗證會拒絕它們，導致復原流程無法構造活躍的 `Session`。

訊息表示改變時沒有提升版本，導致這些日誌無法僅憑標頭與當前的 v0 日誌區分。執行時期需要一條範圍受限的匯入規則，既能復原受支持的第一方後端所建立的資料，又不削弱對無關過時事件或格式錯誤事件的驗證。

## 決策

`PersistenceCoordinator` 會在後端解碼之後、當前訊息驗證之前，規範化訊息標識機制引入前的四種特定訊息載荷。它將載荷現有的語義欄位包裝進當前按角色區分的訊息形狀，並為其分配確定性的匯入用 `MessageId`：`legacy-message:<session-id>:<event-seq>`。舊版 `tool/result` 的內容替換會繼承替換目標匯入後的 id，從而保持當前僅改寫內容的不變數。

同一項規範化也用於 `load`、`inspect`、無 owner 的已載入狀態認領其活躍工作階段，以及 HMR（熱模組替換）前綴接管。因此，前綴比較會將活躍工作階段的當前形狀 seed 與同一份規範化儲存檢視表進行比較。看似當前形狀、但欄位缺失或無效的包裝層不會被修復；不受支持的事件詞彙、請求 header、版本和 surface 關係仍沿用現有拒絕路徑。

這項升級只發生在學取時。儲存中的舊版記錄保持不變；工作階段復原後，只會在其後追加當前形狀的事件。確定性標識使重複載入以及新舊形狀混合的日誌無需執行後端專用的重寫交易，也能復現相同的訊息 id。

## 考慮過的替代方案

**按照預發布相容性立場拒絕這些日誌。** 這是處理其他 v0 形狀變動的默認方式，但即使每個舊欄位都能明確對映到當前訊息表示，它仍會導致真實的第一方工作階段無法復原。

**就地重寫完整的儲存日誌。** 這會使產物規範化，但違反僅附加儲存約定，還需要為 JSONL 和 SQLite 分別實作原子替換機制，並將一次讀取相容性修復擴大為遷移系統。

**每次載入時隨機生成 id。** 這些訊息會滿足類型形狀，卻無法在檢查、復原、重新啟動以及新舊形狀混合追加之間保持穩定標識。

## 後果

訊息標識機制引入前的 JSONL 和 SQLite 工作階段可以復原，並保留原始的訊息內容、來源、assistant 的提供方／模型欄位、工具呼叫關聯、錯誤、元資料和 surface 替換。除此之外，返回事件與當前匯入的訊息快照無法區分，並且仍然經過深度凍結。

這是一個顯式的同版本匯入例外，而非通用的 v0 相容層。若要增加另一個例外，必須在持久化邊界提供另一套完整且無歧義的對映；當前資料若格式錯誤，系統仍會拒絕，而不會猜測如何將其變成有效資料。共享的協調器約定會在記憶體參考實作、JSONL 和 SQLite 後端上驗證這項升級，包括重新載入時的確定性，以及工具結果替換時的標識繼承。
