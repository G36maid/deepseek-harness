# Agent Note: 審批接管面板與輸入框共用同一文字高度上限

Status: implemented

[English](2026-07-30-approval-panel-command-cap.md) | [简体中文](2026-07-30-approval-panel-command-cap.zh.md) | 繁體中文

## 問題

審批面板是一次 composer 接管：當一次沙盒越權申請處於等待狀態時，它在 composer 容器中取代 InputBar，展示模型給出的理由、與之配對的命令，以及一行拒絕／允許按鈕。這兩段文字都是長度不受限的模型輸出，而卡片當時沒有任何高度上限。命令一長——而這正是現實中的常見形態，因為越權申請針對的就是沙盒剛剛拒絕的那條命令，而被拒絕的命令往往是一次很長的內聯寫入——卡片就會一直變高，直到操作按鈕行離開視口。使用者能讀到這次申請，卻無法回應它：按鈕存在，只是在螢幕之外，位於一個已經佔滿整列的吸底容器裡。

被它取代的 InputBar 一直是有上限的（14 行，之後由 textarea 自行滾動），因此這次接管也是 composer 唯一一個可以無限增高的狀態——被選中時容器高度驟增，回應之後又驟降。

## 決策

面板的理由與命令移入同一個滾動區域（`data-approval-scroll`），其高度上限與 composer 的草稿區完全相同；琥珀色狀態條與操作按鈕行位於該區域之外，因此無論內容多長，兩個按鈕都留在卡片內。

這個上限是一個值、兩個消費端，以 `--dsh-composer-text-max-height: 336px` 聲明在 `ConversationRoot` 的 `.composerSeat` 上——它是 composer 鏈唯一的共同祖先，因為兜底的 InputBar 與被選中的接管面板是兄弟節點。`InputBar` 的草稿滾動容器與面板的滾動區域都讀取它，於是同一個容器不可能給它的兩種狀態設出不同上限：設計同學要求的「可以跟輸入框最大高度統一」，如今是樣式表中的一個事實，而不是抄在兩個文件裡的一個數字。該區域取 `box-sizing: border-box`，因此上限指的是它的外框高度，與 composer 草稿區佔據的是同一個盒子。

該區域自身是一個 Tab 停靠點（`tabIndex={0}`，帶名稱的 `role="group"`）。提問 composer 的滾動體不需要這樣做——它的選項行本身可聚焦，會把容器一起帶過去；而這裡除文字之外別無內容：沒有自己的停靠點，僅用鍵盤的使用者能走到按鈕卻走不到命令尾部，於是可能批准了自己沒讀完的東西。

面板卡片把 `--dsh-scrollbar-thumb{,-hover}` 重新綁定到 l2 那一對，這是每一個位於高層表面上的滾動區域都必須做的（[捲軸約定](../../../../packages/client/ui-theme/src/styles/scrollbar.css)）。

## 曾考慮的替代方案

**給整張卡片設上限，而不是給文字區域設。** 一條聲明，不需要重構結構，而且它讀起來就是字面意義上的「與輸入框相同的最大高度」。之所以否決：卡片還裝著狀態條和操作按鈕行——總高 336px 時，理由與命令只能分到約 250px，比它們所取代的草稿區更矮，而且兩邊數字能對上純屬狀態條高度的巧合。給文字區域設上限，才能讓兩種狀態在同一文字高度處收住，而這正是讓底部不再跳動的那條性質。

**像提問 composer 那樣按視口設上限（`min(60vh, 520px)`）。** 同為接管面板的兄弟元件已經這麼做了，因此這是本機既有先例。之所以否決：設計同學的要求是與 InputBar 對齊，而兩個接管面板形態並不相同——提問 composer 的滾動內容是一組需要使用者互相比較的選項，能佔多少視口就該佔多少；審批面板的滾動內容則是一條命令，使用者在決定之前掃讀即可。按視口設上限還會讓容器高度在被選中時再次跳動，只是方向相反。

**對命令做省略號或截斷處理。** 不需要滾動區域，不需要上限，按鈕也不會移位。之所以否決：命令正是被審批的對象，隱去它的尾部等於要求使用者為自己讀不到的文字背書。在這裡截斷還是不可復原的——面板就是審批的全部介面，沒有「展開更多」的落腳處。

**把操作按鈕行留在滾動區域內，只給該區域設上限。** 比把按鈕行固定住少動幾處。之所以否決：這會把缺陷搬進卡片內部——按鈕滾出該區域，使用者得先發現有捲軸才能碰到它們。

## 後果

- 長命令在卡片內滾動，拒絕／允許按鈕留在螢幕內。在建置產物用戶端上於 900x1000 與 900x700 實測：該區域報告的 `scrollHeight` 超過 `clientHeight`，兩個按鈕都留在卡片內、也都留在視口內。
- 選中接管面板不再改變 composer 容器能達到的高度，因此審批到來或解決時，上方的 transcript（文字記錄）不會有數百畫素的重排。
- InputBar 的 14 行上限現在透過一個自 `.composerSeat` 繼承而來的自訂屬性解析，且落在真正滾動草稿的那個盒子上（[兩層文字共用同一個滾動容器](2026-07-31-composer-text-layers-share-one-scrollport.md)把該聲明從自增高映像檔層移了出去）。把輸入欄渲染到該容器之外會丟掉這條聲明（一個沒有兜底值的未解析 `var()`），因此未來的 composer 宿主必須帶上這個屬性——這也正是它聲明在共享容器上、而不是應用根節點上的原因。
- 該場景錄制的命令是一段 200 個 token 的字元塊，遠超一次往返所需。這個代價是有意付出的：沒有能越過上限的內容，這個上限無法被證偽，而模型會把任何規整的載荷壓縮掉（第一次錄制時，模型把「alpha 重複 400 次」寫成了 `printf 'alpha %.0s' {1..400}`，一條什麼也證明不了的單行命令）。

## 驗證

`apps/web/tests/approval-composer.e2e.ts` 驅動程式的是真實組合：一個只讀工作階段、一次被拒絕的寫入、模型的越權重試，以及在面板上點擊完成的回應。幾何斷言在兩個視口高度上針對活動面板執行，並有守衛防止它空洞地成立——該區域必須確實處在滾動狀態，且實測上限必須等於 composer 自身的上限，後者由測試在傳送之前從活動的草稿滾動容器上讀出，而不是把該畫素值寫死。

在建置產物用戶端上雙向確認過。撤銷上限後，該區域報告 `scrolls: false`，並長到命令的完整高度（900x1000 下，錄制的字元塊為 1798px，而設上限後為 336px）；在 900x700 下卡片高 680px、視口高 700px，操作按鈕行底邊落在 y=749——位於視口下方，與設計同學的回饋完全一致。復原上限後，該場景在重播模式下透過。

要復現按鈕跑到螢幕外，需要的是比滾動視口更高的卡片，而不只是一張很高的卡片。composer 容器為 `position: sticky; bottom: 0`，因此在滾動視口尚能容納卡片時它會一直吸附在視口底部，按鈕仍然可見——在 900x1000 下，未設上限的卡片喫掉了整個 transcript，卻仍把操作按鈕行留在螢幕內。只有當卡片長過滾動視口，sticky 纔再也無法守住底邊，按鈕行隨之沉入視口下方。

幾何斷言塊與 golden 僅在重播模式下執行，這樣錄制模式才能走到寫入 fixture（測試前置資料）那一步，而不是在版面配置檢查處中斷。

該場景只保留一份 golden——等待中的面板；回應之後的狀態改為對世界作斷言（決策結果、越權命令寫出的那個文件、`DONE`、面板消失、輸入框重新可用）。一份「已回應 transcript」的 golden 立不住：第一次被拒絕的嘗試渲染的是作業系統自己的拒絕文字，而這段文字因平臺而異（macOS 為 `bash: notes.txt: Operation not permitted`，Linux 為 `bash: line 1: notes.txt: Read-only file system`）。任何 transcript 中含有被沙盒拒絕命令的場景都會繼承這一點，因此這類拒絕只能進斷言，絕不能進 golden。

該面板以用戶端模組包的形式發布：單跑 `pnpm run build:web` 不會帶上對 `ApprovalPanel.module.css` 的改動，也不會帶上 `ApprovalPanel.tsx` 中新增的 `data-` 掛鉤——必須先執行包建置，否則瀏覽器測試通道會對著一個比工作樹更舊的用戶端做斷言。
