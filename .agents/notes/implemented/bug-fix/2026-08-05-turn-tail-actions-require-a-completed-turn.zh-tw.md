# Agent Note: 輪次尾部 IconActions 要求輪次已完成

Status: implemented

[English](2026-08-05-turn-tail-actions-require-a-completed-turn.md) | [简体中文](2026-08-05-turn-tail-actions-require-a-completed-turn.zh.md) | 繁體中文

## 問題

assistant IconActions 此前只從已定稿的 transcript（文字記錄）推導：每個輪次中最後一條含內容文字的 assistant 擁有該行。這個量只有在輪次關閉後才穩定。輪次仍在產出步驟時，模型在工具呼叫前寫下的敘述就是當時該輪次的最後一條內容 assistant，於是它在工具執行期間取得該行，等下一步的文字落定又把它交出去。讀者會看到複製、分支和時鐘出現在一句中間敘述下方，把流程推開一行 28px，然後消失。該行在這個狀態下本身也是殘缺的：分支控制元件已經透過 `turnEnds` 判定為停用，`Ran for` 標籤已經透過 `turnTimings` 判定為不顯示，只有複製可用。

[已歸檔的訊息 chrome 決策](../../archived/feature/2026-07-29-web-message-icon-actions-and-clock.md)一直聲稱輪次中間的敘述不帶 chrome，但推導過程從未拿到能讓這句話成立的完成訊號。

## 決策

`assistantActionsSeqs` 接收 `ConversationSnapshot.turnEnds`，只在事件視窗中存在該輪次 `turn/end` 時才授予該行。已完成輪次內部的歸屬不變，仍是其最後一條含內容文字的 assistant。仍在產出步驟的輪次不授予任何座位，因此其敘述不會掛載該行；輪次關閉時，座位在已定稿答案下方一次性出現。

這與分支控制元件和執行時期長標籤使用的完成事實相同，因此同一行的三個部分現在口徑一致。輪次是否完成讀自持久的 `turn/end` 事件，而不是從 `running`、流式 partial 或運送中工具呼叫推斷，與[已完成輪次尾部決策](2026-08-02-message-fork-actions-require-completed-turn-tail.md)一致。任何結束原因類別都會關閉輪次，因此已中止輪次凍結的尾部保留其操作欄，而崩潰殘留的開放輪次會在載入時由日誌修復補上 `turn/end`。

`hasContentText` 移入 `chat-flow.ts`，由 `AssistantMarkdown` 匯入，使歸屬門控與掛載門控無法各自漂移。

## 考慮過的替代方案

**用 `running` 加流式 partial 或第一個運送中工具呼叫指認開放輪次，據此扣留。** 這一做法曾在最初的變更中短暫存在，隨後被刪除。它推斷完成狀態而不是讀取完成狀態，還需要一個特例，避免輪次已被接受但尚未產出第一步時把上一條回答的座位取走；這正是已完成輪次尾部決策為分支控制元件否決過的推斷。`turnEnds` 按輪次回答同一個問題，不需要推斷，也不需要特例。

**輪次進行中保留該行，只把控制元件置為不可用。** 不予採納：輪次中間的敘述不是一個降級的答案，它根本不是答案。複製仍然會寫入一句中間文字，該行在輪次結束時仍然要移動到真正的尾部。

**讓每個已定稿的內容節點長期保留該行。** 在此重新否決，理由與最初的決策相同：在每一步下重複複製、分支和時鐘會使流程顯得雜亂。它也解決不了本次報告的問題，因為分支控制元件只有落在尾部纔有意義。

## 後果

執行中的輪次在觸發它的使用者氣泡之下不再有任何訊息操作欄，而更早的每個已完成輪次仍保留各自的座位；座位在 `turn/end` 到達時一次性出現，此刻已定稿答案下方會多出一行 28px。`turn/end` 落在載入視窗之外的輪次不授予座位，而翻頁不會造成這種情況，因為一個輪次的結束事件排在它自己的節點之後。`apps/web/tests/turn-tail-actions.e2e.ts` 透過組裝後的應用釘住兩種狀態：`hang` sidecar 作用在第二次模型呼叫上，把一個首步先敘述再呼叫 bash 的輪次掛住，兩份預期輸出分別記錄掛起中的流程和停止之後的流程。包級測試直接覆蓋該推導以及執行中輪次的渲染結果。
