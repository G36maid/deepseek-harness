# Agent Note: composer 的兩層文字共用同一個滾動容器

Status: implemented

[English](2026-07-31-composer-text-layers-share-one-scrollport.md) | [简体中文](2026-07-31-composer-text-layers-share-one-scrollport.zh.md) | 繁體中文

## 問題

composer 的文字由兩層疊放繪製（見 [InputBar](../../../../packages/client/ui-conversation/src/client/skeleton/InputBar.tsx)）：`<textarea>` 持有值、選區與遊標，但它自己的字形以 `color: transparent` 渲染；使用者看到的每一個字元都由其下的 `[data-input-backdrop]` 層繪製，該層同時承載 claim token 高亮、chip 與提示影子文字。這一拆分正是 chip 與高亮得以存在的前提——textarea 無法為自身文字的某個區間單獨設定樣式。草稿框的高度上限為 14 行，因此超過上限之後總得有東西滾動。

兩層各自持有一個滾動偏移，會分兩個階段失效，本次改動是其中的第二個。

第一個階段是靜態的。backdrop 為 `position: absolute; inset: 0; overflow: hidden`——只裁剪、不滾動——瀏覽器也不會把它的偏移與 textarea 關聯起來，於是超過上限之後遊標在動而文字凍結在第 1 行。未達上限時這一點不可見，因為兩層都停在 0；該缺陷與高度上限同齡，藏在所有截圖所捕獲的那個靜止狀態背後。當時的修復是用一個 `scroll` 監聽把 textarea 的 `scrollTop` 映像檔到 backdrop 上，這讓兩層在**靜止時**保持一致。

第二個階段正是隨後被使用者報告的現象：從長草稿的頂部快速滑動時，遊標像帶著慣性一樣從自己的文字裡往上飛出去，過一會兒又落回原位。原因就是那個映像檔。滾輪手勢在合成執行緒上滾動 textarea，不經過主線程；而驅動程式賦值的 `scroll` 事件在其後纔派發，因此中間這些幀裡遊標位於新偏移、每一個字形卻仍位於舊偏移。在同一套幾何的獨立環境上實測：把偏移改變 200px 並在本任務結束之前讀取遊標與其字形之間的距離，chromium 分離 203px、firefox 202px、WebKit 203px，一兩幀之後才收斂到固定的行盒常數（3/2/3）。每個引擎、每次手勢都如此，且滑動越快分離越遠。

任何監聽都無法消除這個間隙，因為這個間隙正是監聽的定義：它在自己所回應的那件事之後才執行。凡是用 JavaScript 維持兩個盒子相等的做法，都會落後於那個不經詢問就搬動其中一個盒子的合成器一幀。

## 決策

只保留一個滾動盒，讓它同時裝下兩層。

`[data-input-scroll]` 是 composer 唯一的滾動容器，14 行的高度上限落在它身上。容器內部的自增高棧與**整份**草稿等高——隱藏的映像檔層處於常規流中且不再設上限，因此由它把棧撐到完整文字高度——backdrop 與 textarea 以絕對定位騎在這個高度上。textarea 為 `overflow: hidden`，自身沒有可滾動溢位，也就再無法持有任何偏移。

於是瀏覽器在同一幀、同一個合成器上，把同一個偏移施加給兩層。遊標與字形的綁定來自結構本身，而不是來自持續維護：沒有程式碼要跑，沒有事件要等，也沒有任何狀態可能落後一幀。滾輪接力處理器保留，只是從 textarea 改掛到滾動容器上，並且仍是這個盒子上唯一的監聽。

上一版機制所需要的兩樣東西隨它一起消失：

**backdrop 的尾行哨兵。** 它的存在只是為了讓兩個盒子的滾動範圍相等——textarea 會在末尾換行之後為遊標保留一個行盒，而 `white-space: pre-wrap` 會摺疊文字節點的尾隨換行，因此以換行結尾的草稿會讓 backdrop 少一行，把映像檔偏移鉗制在遊標上方一行。改為單一滾動容器後，backdrop 自身的範圍不再決定任何事：映像檔層為兩層統一定高，兩層頂端對齊，內容更早結束的那一層只是在最後一行什麼都不畫。值得記住的是這類草稿形狀而不是那套機制：正是它在「兩個盒子必須就高度達成一致」的時代量出了 628 對 652。

**折行寬度這一前提。** 現在三層都在滾動容器內部解析自身寬度，因此一條佔版面配置寬度的捲軸對它們的代價由結構保證相等。這也就關閉了被取代的那篇筆記記錄為「懸置且沒有任何屬性能修」的分歧：WebKit 會為 `overflow-y: auto` 的 textarea 預留槽位，卻不為它旁邊 `overflow: hidden` 的層預留，把 textarea 排成 768 對 776——在長草稿上值 2 到 5 個折行，也就是在唯一能觀察到它的那個引擎上把字形放到了錯誤的遊標之下。改動後在獨立環境實測，Playwright 自帶的三個引擎上三層寬度均一致。

**由 composer 自己完成的編輯，現在會主動請求回視。** 貼上與剪下都會抑制原生編輯——草稿與撤銷日誌歸狀態機所有——再用 `setSelectionRange` 復原遊標，而這不會帶來任何回視：在 chromium 與 WebKit 上實測，貼上一大段之後檢視錶停在原處，遊標卻落在所粘內容的末尾。該缺陷早於本次改動（Firefox 只在舊幾何下恰好會回視），在此修復，是因為單一滾動容器才終於讓「回視」成為我們能自己做的事。兩處復原共用一個 helper：它以隱藏的映像檔層為標尺——同一份草稿、同一套度量、同一折行寬度，因此在遊標索引處摺疊一個 Range 就能報出遊標位置，無需任何 caret API——並且只滾動到剛好把該行帶進可見範圍為止，與瀏覽器為輸入所做的一致。

有一種形狀需要單獨的規則，因為引擎之間在這裡並不一致：緊跟在換行之後的遊標，落在一條沒有任何內容可供度量的行上——以換行結尾的草稿正是終止於此。chromium 對這個摺疊位置**根本不返回任何 client rect**（一個全零盒子，會把回視帶向反方向），firefox 報的是上一行，WebKit 報的纔是對的那一行。因此該 helper 改為度量遊標剛離開的那個換行——它的盒子就是遊標來的那一行——再往下走一行；三者隨即落在同一個偏移上（649/652，遊標所在行位於 336px 盒內的 315）。即使草稿以連續換行結尾，覆蓋該換行的非摺疊 Range 在三個引擎上都會返回真實矩形，因此每個尾隨空行都能沿用同一條規則定位。

現在唯一相依性瀏覽器而非相依性我們自己的，是把遊標滾入可見範圍：textarea 沒有了自己的偏移，它的 scroll-into-view 必須向上走到滾動容器。實測的每個引擎都會這麼做——在草稿末尾輸入會把滾動容器帶到遊標處（chromium、firefox、WebKit 分別為 625、626、628，最大值 628），用 `ArrowUp` 把遊標一路走回去會滾回去，滾離遊標後再輸入也會回到遊標。

## 備選方案

**用 `scroll` 監聽把 `scrollTop` 映像檔到 backdrop 上。** 被取代的那個決策，靜止時是正確的：正是它讓長草稿第一次可以滾動。現在被否決，是因為它在運動中不可能正確——它是主線程對合成執行緒事實的回應——並且它需要兩個前提持續成立（範圍相等、折行寬度相等），而單一滾動容器根本不需要這兩個前提，其中每一個都已經失效過一次。

**用 `transform: translateY(-scrollTop)` 平移 backdrop，而不是賦一個偏移。** 延遲相同：仍在主線程，仍由同一個事件驅動。它還會把範圍分歧蓋住而不是讓兩層真正一致，於是隻要有什麼東西去測量 backdrop，錯配就會重新浮現。

**用滾動驅動程式動畫（`animation-timeline: scroll()`）驅動程式 backdrop。** 這會把耦合放到合成器上執行，在保留兩個盒子的前提下確實能消除延遲。因支持度被否決：Safari 尚未實作、Firefox 也是近期纔有，因此在缺少它的引擎上 composer 會保留被報告的缺陷，而其回退路徑正是這次要替換掉的機制。

**兩層都由 JavaScript 驅動程式滾動：textarea 設 `overflow: hidden`，滾輪處理器在同一個任務裡給兩個偏移賦值。** 滾輪手勢期間不會分離，因為沒有我們就沒有東西會滾動。被否決，是因為它用手寫近似替換了原生滾動——慣性、觸控板回彈、拖拽捲軸、鍵盤滾動——而且遊標回視路徑（瀏覽器設定 textarea 自己的偏移）仍然是非同步落地的。

**把上限留在映像檔層上，只在今天的結構外面套一個滾動容器。** 那樣兩層仍是「視窗大小」而非「草稿大小」：絕對定位子元素的 `inset: 0` 是相對滾動容器的 padding box 解析的，而不是相對其可滾動溢位區域，於是兩層會從本該墊在它們下面的內容上滾開。棧必須與整份草稿等高，這套排布纔有意義。

**給 backdrop 加 `overflow: auto`，讓它自己滾動。** 那樣它就有了一個自己的偏移需要保持同步，即同一個問題再加一條畫在輸入框上的捲軸。backdrop 是 textarea 的投影，不是一個可獨立導覽的介面。

**去掉 backdrop，直接給 textarea 自己的文字上樣式。** 這會消除分層，也一並消除這一整類失步。被否決是因為它不可實作：textarea 只渲染一段統一的文字，claim token 高亮、chip 與提示影子文字——backdrop 存在的理由——無從表達。為修滾動而失去它們，是拿一個有界缺陷換一次功能刪除。

**用 `contenteditable` div 渲染草稿。** 一個元素、一個偏移、區間可上樣式。因代價與缺陷嚴重不成比例被否決：`contenteditable` 會把輸入法組合、撤銷/重做、選區語義與貼上規範化重新壓回我們身上，而這些目前都由 textarea 加輸入狀態機處理，且狀態機已經持有一份假定 textarea 值語義的撤銷日誌。

**給三層都加 `scrollbar-gutter: stable`。** 在 textarea 還是滾動者時試過並已回退：WebKit 只對 `overflow-y: auto` 生效、不對 `overflow: hidden` 生效，那 8px 的差距原樣留著，卻讓每個 chromium 使用者無條件損失 8px 文字列寬。現在已無意義——三層共享同一包含塊，沒有什麼需要預留。

**給滾動的那一層加 `scrollbar-width: none`。** 靠隱藏滑桿來抹平寬度。被否決：草稿超過上限時 composer 是有意顯示滑桿的——`.card` 綁定 l2 捲軸 token 正是為此——而它是唯一提示「長草稿在下面還有」的可供性。

## 影響

- 遊標不可能離開自己的字形。瀏覽器滾動的是同一個盒子，因此「textarea 把某一行放在哪」與「backdrop 把這一行畫在哪」之間的距離在任何偏移下都是一個固定的行盒常數，手勢進行中也不例外。場景測試度量的正是這個數。
- 捲軸從 textarea 移到了滾動容器上——視覺位置相同，只是外移了一層。`.card` 的 l2 token 綁定仍會繼承下去。
- chip、claim token 高亮與文字引用標記在滾動時仍與其字形對齊，因為它們定位在 backdrop 內部、隨之移動。除去掉哨兵之外，裝飾掃描沒有變化。
- 在 Firefox 與 WebKit 上，點進一個草稿超過上限的 composer 現在還會把工作階段 transcript（文字記錄）滾動到底部：遊標的 scroll-into-view 會越過 composer 的滾動容器一路走到 transcript 的滾動容器，而一個比自身盒子矮的 textarea 從不會引發這一步。chromium 不會。已實測，並試過 `overscroll-behavior: contain` 與 `contain: paint`，兩者都攔不住這次上行——沒有任何 CSS 能終止 scroll-into-view 的接力。接受：它滾向底部，而 composer 本來就在底部，而其替代方案是在每個引擎上都出現遊標與文字明顯分離。
- 翻頁與拖拽選區的行為未變，二者均做了新舊對照實測。`PageDown`/`PageUp` 本來就不會移動 textarea 的插入點——chromium 是滾動一頁並保持 `selectionStart` 不變，新舊幾何皆然，區別只在於滾的是哪個盒子。拖拽選區越過下邊緣仍會自動滾動，且落點一致（chromium 628/628、firefox 625/620、WebKit 170/170——WebKit 自動滾動較慢，但改動前後一樣慢）。
- composer 自己發起的 `focus()` 全部加了 `preventScroll`——解除鎖定/切工作階段的 effect，以及工具列按鈕上那個保持焦點的 mousedown——因此一次沒有任何手勢要求的聚焦，不會再透過更高的 textarea 的回視鏈把 transcript 挪走。抑制這條鏈之後，遊標就回到了我們手上，而這在一條路徑上確實要緊：composer 的 DOM 跨工作階段複用，因此切到更長的草稿時舊偏移會留著，而換值會把遊標放到新草稿的末尾。三引擎實測，這會讓遊標落在停在 0 的盒子下方 940px 處；於是該 effect 會在自己的滾動容器裡把它帶回來，落點 625/628——正是舊幾何靠瀏覽器達到的 628。mousedown 那條不需要回視：遊標沒動過，而下一次敲鍵會拿到瀏覽器原生的回視。另一個只負責回視的 effect 會處理渲染後纔到達的非空草稿：`ConversationSession` 在自己的 mount effect 中注入持久化草稿，而該 effect 在本元件的 effect 之後執行，因此如果沒有這個獨立 effect，第一次回視會量到空映像檔，且不會再為隨後出現的草稿重跑。第二個 effect 從不聚焦，因此傳送後清空或傳送失敗後復原這類普通的空/非空轉換不會從其他控制元件奪走焦點。
- 撤銷/重做可以在不復原遊標、也不回視的情況下改動草稿：狀態機重放上一版草稿，DOM 選區停在瀏覽器鉗位後的位置。這早於本次改動且未被改動——在此點名，是因為另外兩處復原都會回視，會讓這處遺漏看起來像有意為之；真被報告時 helper 就在旁邊。
- 任何新增在 backdrop 旁邊的層都屬於滾動容器**內部**，並且必須與草稿等高，否則就會重新引入這一缺陷。這是 composer 長期存在的風險點：兩層拆分對 chip 與高亮是承重的，因此耦合必須來自結構，而不是靠維護。

## 測試

[input-bar.spec.tsx](../../../../packages/client/ui-conversation/tests/input-bar.client.spec.tsx) 中的單元用例斷言 jsdom 能看見的部分：同一個滾動盒同時包含 textarea 與 backdrop，backdrop 的文字現在就是草稿本身、不多不少，且渲染後纔到達的持久化草稿會回視其遊標，同時不從其他控制元件奪走焦點。jsdom 對任何元素都報告 `scrollHeight === clientHeight` 且從不滾動，因此幾何屬於瀏覽器場景；滾輪接力用例改為樁接滾動容器的度量，而非 textarea 的。

[composer-draft-scroll.e2e.ts](../../../../apps/web/tests/composer-draft-scroll.e2e.ts) 在 chromium 中針對建置產物度量其餘部分：全新工作區的空白 composer 中一份 40 行草稿，零模型呼叫。每個度量都在遊標自己的坐標系裡讀取——即 textarea 把第 n 行放在哪，含其自身偏移——再與 backdrop 同一行文字上的 DOM Range 相比，因為這個差值正是使用者看到的東西。決定性的用例改變偏移，並**在本任務結束之前**重新讀取該差值，也就是在任何 `scroll` 監聽可能執行之前：單一滾動容器下為 0，映像檔方案下則是整個增量。空洞性保護先斷言草稿確實超過了帶上限的盒子；其餘用例分別覆蓋高度上限、三層同一折行寬度、滾輪手勢、以換行結尾的草稿，以及過去由 textarea 自身滾動承擔的遊標回視路徑——滾離遊標後輸入，必須把滾動容器帶迴游標處。

另有一個用例端到端覆蓋貼上路徑：短草稿、遊標停在末尾，然後派發一個攜帶真實剪貼簿資料的 `paste` 事件——與 Cmd-V 送達的是同一個事件，走同一個處理器——再檢查偏移與所粘內容的最後一行。它等待的是偏移而不是「草稿是否溢位」，因為復原發生在狀態機提交草稿之後的下一幀；沒有這次回視的建置會卡在這個等待上失敗。

支撐該決策的兩套幾何對比是在實作之前於獨立環境度量的，因為新舊排布無法在應用裡同時存在：同任務分離度舊為 203/202/203px、新為 3/2/3px（chromium/firefox/WebKit），折行寬度舊在 WebKit 上為 768 對 776、新在三個引擎上均為 1264/1264/1264，而新幾何下 textarea 自身的可滾動溢位為 0——正是這一點讓第二個偏移不可能存在，而不只是碰巧相等。

注意 composer 打包在 client-module bundle 內，因此只跑 `pnpm run build:web` 並不會帶上 `InputBar.tsx` 的改動——必須先跑包建置，瀏覽器泳道纔看得到；對著過期 `lib/` 跑場景，斷言的是比當前程式碼樹更舊的用戶端。
