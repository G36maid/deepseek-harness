# Agent Note: 工作階段列只在一個軸上滾動

Status: implemented

[English](2026-08-04-conversation-column-one-axis-scroll.md) | 繁體中文

## 問題

當中間列被拉窄——無論是拖視窗還是拖側邊欄——hero 態的整條工作階段列下方就會出現一條橫向捲軸。溢位的元素是 hero 的裝飾性背景橢圓：`.heroGlow` 的寬度取 hero 盒子的 `1051/776`，好讓它的模糊在 userSpace 中隨輸入卡片一同縮放；這也意味著只要列比它窄，它就會伸出列外。

這處外溢是設計使然，保持不變。真正讓它對使用者可見的是它所處的滾動容器。`[data-conversation-scroll]` 只聲明瞭 `overflow-y: auto`，另一個軸留在初始值 `visible`；而一個在某一軸上滾動的盒子，會把另一軸的 `visible` 計算為 `auto`。於是每一條比該橢圓窄的列都真的給出了一段橫向滾動範圍——在筆記本實際會產生的幾檔寬度上，實測為 24–95px。

## 決策

`.scrollBody` 聲明 `overflow-x: hidden`。這條列明確聲明自己是單軸滾動容器，而不是把第二個軸交給推導。

裁剪行為不變。`overflow-y: auto` 早已使該盒子成為在兩個軸上都裁剪的滾動容器，因此這條聲明收回的只是捲軸和使用者手勢；橢圓保留它的外溢、模糊半徑和同樣的繪製範圍，列也保留縱向滾動。輸入區那條鏈路上沒有任何東西移動。

## 曾考慮的替代方案

**把橢圓縮到列內。** 否決。橢圓的寬度正是讓它 `stdDeviation="50"` 的模糊隨輸入卡片縮放的依據（figma 313:14109）；約束寬度會使列越窄模糊越緊，等於為修一條捲軸而製造一處視覺回歸。

**給橢圓套一層裁剪盒。** 否決。這層盒子唯一的職責是抵消列本就會裁剪的溢位，而推匯出的 `overflow-x: auto` 仍然留在原處，等著下一個外溢的元素——transcript（文字記錄）裡這樣的候選者不少。

**相依性外框的 `.centerCol { overflow: hidden }`。** 它幫不上忙。那處裁剪在滾動容器之外，只能在列邊界處遮住橢圓探出的部分，而裡面的容器照樣可以滾過去夠到它。使用者報告的那條捲軸屬於內層容器。

**在測試裡斷言 `scrollWidth === clientWidth`。** 作為判據被否決，因為它區分不出兩種狀態：`hidden` 裁剪外溢，而不是把它重排掉，所以修復前後讀到的滾動範圍一樣。唯一有差別的是拒絕使用者手勢，這正是該場景所測量的。

## 測試

[apps/web/tests/conversation-column-overflow.e2e.ts](../../../../apps/web/tests/conversation-column-overflow.e2e.ts) 掃過一組把橢圓寬度夾在中間的視口寬度，在每一檔上於列上觸發橫向滾輪事件並讀取 `scrollLeft`。提交的 golden 逐檔記錄該關係；最寬的一檔是橢圓根本不外溢的對照。

兩道防線保證該場景不流於形式。空斷言防線斷言窄檔上橢圓確實仍伸出列外，使這項主張不可能因為症狀出於無關原因消失而透過。變異對照則在頁面內把 `overflow-x: auto` 強制改回，證明同一手勢在同一時序下能把列帶到正向滾動邊界。測試直接測量該邊界，因為穩定的捲軸槽可能讓部分外溢處於滾動原點的負向。沒有這項對照，`scrollLeft` 讀到 0 同樣可以解釋為滾輪事件根本沒送達。

## 後果

工作階段列在任何寬度下都不再給出橫向捲軸，輸入區鏈路上的裝飾性外溢從暴露為滾動範圍改為被裁剪。代價是這條列下真正過寬的內容會被裁掉而非可滾動夠到：這類介面各自擁有自己的滾動容器，markdown 程式碼塊和軌跡表格已經如此。
