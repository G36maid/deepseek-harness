# Agent Note: 讓受支持平臺的測試聚焦語義

Status: implemented

[English](2026-07-22-cross-platform-test-fixtures.md) | [简体中文](2026-07-22-cross-platform-test-fixtures.zh.md) | 繁體中文

## 問題

單元測試與覆蓋率測試套件會在 Windows、macOS 和 Linux 上執行，但平臺無關行為可能被平臺特有的 fixture（測試前置資料）掩蓋。字面 POSIX 路徑在 Windows 上會變成相對於驅動程式器的路徑；帶主機名的 `file:` URI 在 Windows 上可能是有效的 UNC 路徑；子行程管道關閉或事件迴圈調度在不同宿主上的穩定時點也不一致。FIFO、可執行模式位和目錄搜尋權限位等僅存在於 POSIX 的檔案系統狀態，在 Windows 上沒有可直接構造的 fixture。

把 fixture 文法當成產品行為，要麼會誤報回歸，要麼會促使生產程式碼引入抹去原生路徑語義的歸一化。

## 決策

測試平臺無關行為時，使用宿主的 `node:path` 和 `node:url` API 構造絕對路徑與 `file:` URI，再根據約定要求斷言原生絕對輸出或穩定的工作區相對輸出。無效 URI fixture 使用一種在所有受支持平臺上都會被 `fileURLToPath()` 拒絕的編碼形式。

傳輸故障測試會注入連線的訊息寫入器，並傳入與真實 Node 流相同的非同步寫入回呼錯誤。生產寫入器仍會把分幀訊息寫入子行程 stdin。這種方式讓真實子行程保持存活，使測試無需觸及平臺特有的管道控制代碼，也能確定性地區分傳輸故障與行程退出。

語言伺服器的資源清理會終止整棵後代行程樹：POSIX 使用負數行程組 ID，Windows 同步執行 `taskkill /T /F`。Windows 只會忽略 taskkill 返回的「行程樹已經不存在」狀態；命令執行失敗、權限錯誤及其他終止行程樹的失敗仍屬於資源清理失敗。只讀的提供方查詢僅在選定的池化傳輸於該次查詢開始前或執行期間失效時重試一次；伺服器仍存活時返回的錯誤不會觸發重試。終端機測試會等待可觀察的渲染輸出，不假設一次事件迴圈輪轉已經足夠。

對於真正僅存在於 POSIX 的原語，測試只在該用例上排除 Windows。相鄰的跨平臺用例仍會固定拒絕非普通文件、不可用命令和無法訪問的工作目錄的行為。Windows 上受支持的路徑仍受逐文件覆蓋率閘門約束，不會隨測試文件一起排除。

## 曾考慮的替代方案

**將所有路徑和 URI 歸一化為 POSIX 字串。**這會使斷言保持一致，但也會改變正確的 Windows 行為：外部路徑是原生絕對路徑，UNC 文件 URI 有效，而且已設定的主目錄會按照宿主路徑規則解析。

**操縱子行程管道內部狀態，直至寫入失敗。**CRT 描述符與 libuv 控制代碼在不同宿主和 Node 版本上的所有權不同，因此這種做法測試的是未文件化的 fixture 機制，而非連線的寫入失敗約定。

**在 Windows 上跳過整個測試文件或包。**過寬的排除會隱藏受支持的行為。只排除無法在 Windows 上構造相應狀態的單項 fixture；相關約定仍保持覆蓋。

## 後果

可移植 fixture 需要更顯式地構造，因為預期路徑要從共享的原生常數派生，傳輸故障則透過狹窄的寫入器掛鉤注入。僅適用於特定平臺的排除項必須配有相鄰的跨平臺斷言，以繼續覆蓋相應的產品行為。協議級優雅關停失敗後，Windows 上的資源清理相依性宿主的 `taskkill` 命令；命令同步執行成功時，可確保 dispose（資源釋放）在有限時間內完成，並確保清理返回前即可觀察到後代行程退出；若行程樹終止失敗，資源釋放邏輯仍能觀察到該失敗。
