# Agent Note: 可指令碼控制的 LLM 協議層故障伺服器

Status: implemented

[English](2026-07-25-scriptable-llm-wire-fault-server.md) | [简体中文](2026-07-25-scriptable-llm-wire-fault-server.zh.md) | 繁體中文

## 問題

配接器單元測試使用本機 HTTP 伺服器對各類提供方故障逐一分類，重試測試則使用行程內的指令碼化 `LlmAdapter` 證明已關閉步驟的復原能力。這兩個邊界都無法提供可複用的伺服器，以便同時執行交付版本的 HTTP 配接器、agent loop（代理循環）和重試策略；開發者也無法僅修改現有應用的 base URL 與 API key，就讓應用連線到確定性的傳輸故障。

連線遭拒、首個事件前連線被重設、未收到 `[DONE]` 即正常 EOF、合法但無內容的完成，以及輸出部分內容後連線被重設，會產生不同的配接器與復原結果。把它們統一視為普通 mock 故障，會掩蓋提供方邊界是否保留了這些區別，以及失敗請求的區塊是否確實沒有進入已提交的模型歷史。

## 決策

`@deepseek-ai/dsh-llm-mock-server` 是一個私有支持包，提供可匯入的 Node HTTP 伺服器。倉庫內的 `pnpm run mock:llm` 原始碼入口提供一個用於手動故障注入的獨立行程；該包不公開可安裝的二進位命令。它接受相容 OpenAI 的根路徑和 `/v1` chat-completions 路徑，校驗選填的 bearer token，捕獲請求，並對每個已接受請求消耗一個顯式行為。指令碼耗盡時會明確報錯；只有設定 `repeatLast` 才會重複最後一個行為。

請求行為覆蓋 socket 重設、傳送 header 後中斷連線、傳送部分內容後中斷連線、停滯、合法空完成、正常關閉但被截斷的流、畸形 payload、典型 HTTP 故障、完整的文字/推理/工具呼叫回應、慢速流式輸出以及達到 token 上限的完成。真正的 `connection_refused` 由 CLI（命令列介面）的監聽器生命週期階段實作，因為已經綁定埠的請求處理器無法拒絕自身的 TCP 連線。

指令碼項 `random` 會為每個請求重新執行一次加權選擇。伺服器公開並記錄其無符號 32 位 seed，允許呼叫方提供相對權重，並內建一套偏重成功結果的壓力測試設定，將傳輸、協議、提供方、逾時和語義空結果混合在一起。該設定用於提供可調的測試壓力，並非對生產事故發生頻率的估算；`connection_refused` 仍不進入請求級隨機池。

伺服器只報告協議層事實，不判斷是否可重試。真實組合測試讓請求依次經過 `dsh-llm-deepseek`、`dsh-agent-loop` 和 `dsh-llm-retry`：在現有默認策略下，連線遭拒、硬中斷連線、部分輸出後重置、空閒逾時以及合法的無內容完成均可復原；正常關閉的部分輸出 EOF 仍歸類為 `STREAM_CLOSED`，默認不重試。該包不會改變這些策略。

## 驗證

包測試覆蓋所有請求行為、跨區塊 UTF-8 請求解碼、不消耗指令碼的 HTTP 校驗、指令碼耗盡與重複、停滯連線清理、CLI 解析及延遲邊界、IPv6 base URL、隨機 seed 可復現性、權重校驗、單結果遙測、生命週期清理，以及逐文件覆蓋率閘門下的配套不變式外掛程式。重試整合套件透過真實 HTTP/SSE（Server-Sent Events）配接器，驗證準確的請求次數、帶編號的重試步驟、請求體完全一致、失敗的部分區塊不會洩漏、語義空結果復原、正常 EOF 分類、逾時復原、監聽器延遲啟動後從真實連線遭拒中復原，以及有界重試耗盡。

## 曾考慮的替代方案

**使用 Python 實作伺服器**：不予採納。Node 的標準 HTTP 與 socket API 足以暴露所有所需故障，而 TypeScript 可以讓伺服器、CLI 解析器、測試、包建置、lint 和覆蓋率全部留在倉庫現有工具鏈中。引入第二套執行時期會增加環境與子行程相依性，卻不能增強協議隔離。

**在配接器測試中繼續使用各自獨立的內聯 mock 伺服器**：不予採納。這些 fixture（測試前置資料）無法作為獨立伺服器啟動並供現有應用連線，還會讓不同測試套件重複實作行為編排、隨機化、遙測和連線清理。支持包讓測試共享同一套實作，又不會將其提升為產品 API。

**僅使用行程內的 `LlmAdapter` mock**：不予採納。它會繞過 fetch、HTTP 狀態與 header 解析、SSE 分幀、socket 終止以及配接器的空閒看門狗，而這正是這套測試基礎設施要覆蓋的邊界。

**公開可安裝的 workspace 二進位命令**：不予採納。pnpm 會在倉庫建置產物存在之前連結相依套件的二進位命令，從而讓乾淨安裝與僅供測試的產物產生耦合。倉庫內的原始碼命令支持相同的手動故障注入，而不會新增包安裝介面。

**隨伺服器一起修改默認重試策略**：不予採納。伺服器用於揭示既有語義，而非決定策略。是否將復原能力擴充到 `STREAM_CLOSED`，需要單獨決策，並權衡成本、延遲和重複生成風險。

## 後果

開發者只需修改提供方 URL/key 設定即可復現故障序列；自動化測試則可透過顯式指令碼和 seed，讓 socket 層故障保持確定性。同一套協議 fixture 現在可以暴露硬重設、正常截斷與復原後的空完成之間的差異，而不會拼接多次嘗試的內容或修改模型歷史。

伺服器新增了一個私有支持包和一套行為詞彙，二者必須同時相容直接測試與倉庫內的 CLI 示例。按請求到達順序執行的指令碼有意由所有用戶端共享；隨機模式的預設值代表壓力測試權重，而非實際執行規律；精確模擬連線遭拒時，需要讓用戶端嘗試與監聽開始前的時間區間協調一致。
