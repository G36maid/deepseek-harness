# Agent Note: 子行程沙盒——約束 seam、原生 runner、升級機制與按工作階段模式

Status: implemented

[English](2026-07-06-sandbox.md) | [简体中文](2026-07-06-sandbox.zh.md) | 繁體中文

## 問題

一個編碼 agent（代理）需要如下產品路徑：bash 子行程（以及依附其上的掛鉤命令）默認在受限的文件沙盒下執行；當且僅當沙盒實際拒絕了某個操作時，模型可以為同一操作請求一次使用者批准，獲批後以更寬的權限重試一次。本設計刻意不聲稱覆蓋所有工具：fs/web/todo 在行程內執行，`execve` 包裝層對它們毫無意義（§ 行程內工具）；跨工具族的統一邊界屬於分階段後續工作（§ 延遲階段）。如果沒有共享詞彙，每個工具都會各自重新發明批准欄位、拒絕解析、重試匹配和權限狀態提示。

harness 是一個 SDK，因此約束必須是開發者可組合的能力：是否啟用沙盒、每個平臺使用哪個後端，都應作為一等條目寫在葉子 `cordis.yml` 中，而非藏在某個執行器的私有機制裡。而首選 runner `bwrap` 恰恰在沙盒最重要的主機上不可用（精簡容器、停用了非特權 userns、LSM 拒絕 `mount`），因此備選 runner 必須隨 SDK 一起交付，而不能假設主機已有。

僅有約束還留下兩個缺口。拒絕後沒有升級路徑就是死路：模型只能放棄，這會迫使運維人員全域性設定 `workspace-write` 或 `danger-full-access`，從而使沙盒形同虛設。而沙盒模式和批准策略也會透過部署設定或選填的 UI 策略控制元件在 agent 生命週期內變化；執行與模型可見的策略必須派生自同一份已記錄的狀態。

## 決策

一個 seam、一條按平臺的本機後端鏈、一個消費端，加上兩個上層控制項：按呼叫的升級路徑與按工作階段的執行時期模式。以下所有內容均從葉子 `cordis.yml` 組合而來；不觸及 `agent-loop`。跨工具族 fs 強制與按工作階段工作區根目錄已經作為後續設計落到同一策略載體上；剩餘階段——`subagent-acp` 消費端、更多環境與 Windows 鏈——仍列在 § 延遲階段。

### 部署方式

四條 `cordis.yml` 條目即可將一個無約束的編碼 agent 轉變為沙盒產品路徑；[`examples/acp-agent`](../../../../examples/acp-agent/README.md) 默認使用此組合：

```yaml
- id: sandbox
  name: '@deepseek-ai/dsh-sandbox-local'   # the per-platform runner provider (ctx.sandbox)
- id: bash
  name: '@deepseek-ai/dsh-bash-sandbox'    # the confined executor, replacing dsh-bash-local behind ctx.shell
  config:
    mode: workspace-write                  # the deployment default every session starts from
    workspaceRoot: !!js process.cwd()      # the boundary workspace-write may write under
- id: approval
  name: '@deepseek-ai/dsh-user-approval'        # the escalation gate's channel (the approval Agent Note)
  config:
    policy: ask
- id: permission
  name: '@deepseek-ai/dsh-permission-presets'      # one product-facing select over both mechanism knobs
```

這一替換對 `ctx.shell` 的所有消費端透明：bash 工具、掛鉤命令和背景工作照常執行，直接使用提供方返回的已包裝 argv 啟動。刪除 `sandbox` 和 `permission` 條目、將 `bash` 替換為 `@deepseek-ai/dsh-bash-local` 即為退出——執行復原為無約束，升級欄位從工具 schema 中消失，因為它們是基於已掛載執行器的能力門控，而非基於設定。僅省略 `approval` 則保留約束但以自身錯誤文字關閉每次升級；`permission` 還要求 approval seam 和約束執行器同時存在，因此組合不完整的 preset 層會在載入時明確報錯。

設定錯誤會顯式導致失敗：`mode` 不在封閉詞彙中時在外掛程式載入時被拒絕；主機上沒有可用後端時在 `confine()` 階段拋出結構化的 `SANDBOX_UNAVAILABLE`，而非降級為無約束執行。如果所選 runner 以可歸因的 `ENOENT` 或 `EACCES` 拒絕，消費端會在任何命令開始前透過 spawn 通道報告同一基礎設施錯誤；其他 spawn 錯誤仍保留本機命令啟動語義，同時也不會執行任何內容。`dsh-sandbox-local` 上的 `runnerCommand` 是運維人員對一個 bwrap 相容 runner 的顯式斷言（跳過鏈和探測）；它同時充當 keyless 測試的確定性 fake-runner 掛鉤。

被拒絕的文件操作返回 `[sandbox: file access denied under <mode> mode]` 標記，並附帶不要繞過拒絕的指令。約束執行器新增配對的 `sandbox_permissions` 和 `justification` 欄位，用於一次經批准的重試，該重試必須嚴格寬於工作階段的有效模式。授權僅放寬該次重試；拒絕則不執行任何內容，返回 `the user rejected escalating this command to "<mode>"`，且不允許再次請求。由歸屬方派生的待處理策略上下文會說明當前文件策略，但不會取代這些強制執行邊界。當 `dsh-permission-presets` 與某個 UI 配接器一起組合時，一個 preset 同時選定兩個旋鈕值；不匹配的組合摺疊為 `custom`。[ACP（Agent Client Protocol）自動化組合](../../../../examples/acp-agent/README.md)不掛載該 UI 服務，而是顯式選定其部署模式。

### 設計細節

#### 範圍界定

OS 子行程約束適用於 bash 執行器（包括掛鉤命令），後續還將適用於 ACP subagent 子行程。檔案系統、web 和其他工具在行程內執行，需要在各自的 seam 層面實施策略；argv 包裝層無法約束一個閉包了 `ctx` 的函式。既有的 bash request/spec 拆分承載按呼叫的覆蓋，而 `tools/pre-execute` 和 approval seam 負責一次性策略決策。

#### seam：`ctx.sandbox`

`dsh-sandbox` 負責定義詞彙和 `SandboxProvider` 約定：`confine(argv, policy)` 返回呼用方應當 spawn 的替代 argv（經過包裝，使行程及其所有子行程在約束下執行），加上所選後端達到的 `enforcement` 完整度、其拒絕方言（`denialSignatures`，該後端核心在拒絕文件操作時列印到 stderr 的子串），以及其結構化 runner 失敗證據（`runnerFailureRules`，選填的允許退出碼加上排除整行精確資訊性行後按行匹配的致命簽名）；沒有可用後端時拋出失敗關閉的 `SANDBOX_UNAVAILABLE` 錯誤，絕不靜默放行。詞彙：`SandboxMode`（`read-only` / `workspace-write` / `danger-full-access`，僅限文件操作——不聲稱覆蓋網路和行程可見性）、`SandboxEnforcement`（`full` / `partial`）、`SandboxExecutionPolicy`（每次能力呼叫的完整 mode + 工作區根目錄）以及 `SandboxPolicy`（提供給約束後端的子集）。

策略隨每次呼叫而非提供方攜帶：兩個消費端可以在同一時刻以不同策略約束（bash 在 `read-only` 下執行，而一個受約束的子 agent 保持其狀態目錄可寫），且經批准的升級重試是一次帶有更寬策略的新呼叫——在設定固定的提供方模式下無法表達。

該 seam 僅約束與宿主共享檔案系統和核心的子行程。容器、microVM 和遠端執行器不是此 seam 的後端——它們以環境一致的組替換整個能力 seam（`ctx.shell`、`ctx.fs`）的 Service Provider，因為一個 bash 在容器中執行而 fs 工具寫主機的 agent 生活在兩個割裂的世界中。

留待需要時再決定：網路限制是作為獨立的 `network_mode` 到來，還是在某個 runner 同時強制兩者後合併進 `sandbox_mode`；以及 `SandboxPolicy` 是現在就增加額外的可寫根授權（launcher 已支持 `--rw <path>`），還是等到升級機制需要時再加。

#### 本機後端與隨附 launcher

`dsh-sandbox-local` 在提供方生命週期內選擇一個平臺 runner 並快取結論。Linux 功能性探測 `bwrap` 然後 Landlock；macOS 使用 Seatbelt。不支持的平臺和不可用的 runner 失敗關閉。每次包裝攜帶後端特定的拒絕簽名和 runner 失敗規則，以便 `dsh-bash-sandbox` 區分被拒絕的文件操作與損壞的沙盒。Landlock runner 失敗需要退出碼 125，加上一行不是通知的 `landlock-run:` 診斷；即使子行程以 1、2 或 125 退出，精確匹配的部分強制執行通知仍只是資訊。Bubblewrap 和 Seatbelt 仍僅依據簽名，因為兩者的公開約定均未保留 launcher 失敗狀態。`runnerCommand` 保留面向運維人員的 `runnerFailureSignatures` 設定，要求其中條目均為非空單行，並將它們對映為一條內部致命規則。消費端會直接 spawn 每個返回的 argv，因此缺失的 runner、不可執行的 runner，或 shebang 解釋器不可用的可執行指令碼會透過可歸因的 `ENOENT`／`EACCES` spawn 通道失敗，而成功啟動的子行程以 126 或 127 退出時仍按普通結果處理。運維人員設定的指令碼必然要先啟動解釋器，再應用自身 profile。

launcher 是一個約 300 行的 C 程序（純 C11，直接使用 Landlock UAPI——除靜態連結的 musl 外無其他庫，因此審計面僅為該文件加核心的穩定 syscall 約定）：`--ro <path>` / `--rw <path>` 授權，`--`，被包裝的 argv；它為自身安裝規則集並執行 `exec`（規則集跨 `execve` 繼承，且它在限制前設定 `no_new_privs`）；`--probe` 在一個短生命週期子行程中強制最大規則集，僅當核心確實強制時才以 0 退出；所有 launcher 失敗都會以 125 退出且不執行子行程，並列印一行致命的 `landlock-run:` 診斷。成功完成 exec 的子行程也可能返回 125，因此僅憑退出狀態不能作為 launcher 失敗的證據。較舊的 ABI 會在執行子行程之前列印精確的 `landlock-run: partial enforcement (older Landlock ABI)` 通知，因此該行不是致命證據。

Landlock launcher 原始碼和包家族位於 `native/landlock-run`，與 harness 消費端同倉，並屬於根 pnpm workspace。[倉庫內 Landlock 發布決策](../process/2026-08-06-in-repository-landlock-release.md)負責共享鎖定檔、原生建置、打包演練和 npm 發布邊界。平臺二進位由 npm 選擇，入口包擁有路徑解析、探測、CLI（命令列介面）參數、致命前綴和部分強制執行通知，而 harness 將沙盒模式對映為授權。將入口點與其二進位一起版本化，使探測解析和啟動文法保持對齊。

後端 profile 共享模式約定但在必要的主機授權上有所不同。Landlock 和 Seatbelt 在 read-only 模式下僅允許 `/dev/null`；workspace-write 還允許各自所需的主機臨時目錄根。每次包裝攜帶後端特定的拒絕簽名。Landlock 在較舊的 ABI 無法管控所有操作時報告 partial enforcement，而成功的 bwrap 和 Seatbelt profile 報告 full enforcement。

#### bash 消費端

`dsh-bash-sandbox` 擴充 `LocalBashExecutor`，把精確的 `['bash', '-c', command]` argv 交給 `ctx.sandbox`，並直接 spawn 提供方返回的 argv。這樣，隨附的原生 runner 建立約束後，shell 語義與 `BASH_ENV` 仍由內層 Bash 處理。提供方錯誤原樣傳播。行程啟動前，只有當呼叫方擁有的 workdir 經獨立驗證可用，Node 報告 `ENOENT` 或 `EACCES`，並且錯誤符合以下一種形態時，才判定為 runner 失敗：`error.path` 等於提供方返回的 `argv[0]`，同時 `syscall` 為 `'spawn'` 或精確的 `'spawn <runner>'`；或者 `error.path` 不存在，同時 `syscall` 為精確的 `'spawn <runner>'`。其他錯誤碼、無效 workdir、資源失敗、無關 syscall 與無結構拒絕保留本機命令啟動語義。前臺執行會將 runner 失敗轉為 `SANDBOX_UNAVAILABLE` 並附上原始詳細資訊；非同步後臺拒絕則蓋章 `runnerFailed: true`、`denied: false`。如果 `SubprocessRuntime` 同步拋出同樣能指明 runner 的形態，後臺啟動會拋出 `SANDBOX_UNAVAILABLE`；其他同步錯誤原樣傳播。行程啟動後，前臺與後臺共用一個 runner 失敗分類器：先排除資訊性行，再要求規則的退出碼檢查與餘下的一行致命診斷同時匹配。匹配結果優先於拒絕：前臺執行拋出 `SANDBOX_UNAVAILABLE`，並以該致命行作為詳細資訊；結帳後的 `ShellProcess` 會蓋章 `sandbox.runnerFailed`，bash 生產者再透過通用 `job_output` 渲染它。

模型會在歸屬方派生的 `sandbox:policy` 上下文中看到當前有效的文件策略；靜態工具描述則解釋拒絕標記（`[sandbox: file access denied under <mode> mode]`），鼓勵嘗試可能被拒絕的命令，並禁止繞過拒絕重試。當升級欄位被公佈時，被拒絕的結果還會攜帶升級提示本身，使被認可的同輪次重試在決策點獲得提示，而非相依性模型回憶描述（§ 升級機制）。[當前策略決策](2026-07-30-current-sandbox-policy-context.md)負責該上下文的理由與邊界。

#### 升級機制：拒絕後一次經批准的更寬重試

`ShellExecRequest.sandboxPolicy` 是選填的完整按呼叫輸入；解析後的 spec 使該欄位顯式。`ShellExecutor.sandboxMode` 仍是公佈已掛載執行器能否兌現該策略的能力事實，因此只有約束組合才暴露升級。seam 接受任何顯式策略；工具擁有工作階段解析和「僅更寬」的升級規則。非沙盒執行器誠實地保持無約束。

`ctx.sandboxPolicy.resolve()` 在執行器執行前蓋章完整執行策略——顯式升級模式 > 工作階段覆蓋 > 設定預設值，且 `SessionHeader.cwd` > 設定的後備根目錄。`SandboxBashExecutor.resolve()` 在 spec 上保留該策略，或為直接的無 agent 呼叫方提供部署後備值，使 `run()`/`start()` 永不讀取可變工作階段狀態。每行程包裝事實以返回的 `ShellProcess` 為鍵；`onProcessDone()` 會透過 stderr 分類之外的通道接收 spawn 失敗，並在 `done` 結帳前給該控制代碼蓋章，因此重疊行程各自保留自己的模式和 runner 方言。

當約束執行器被掛載時，`bash` 公佈配對的 `sandbox_permissions` 和 `justification` 欄位。schema 暴露完整的封閉升級詞彙，因為有效模式是按工作階段的；執行拒絕任何不嚴格寬於該呼叫有效模式的目標。批准在執行之前解析。`allowed-once` 僅將授權模式蓋章到該請求上，而 `rejected`、`cancelled`、`unavailable`、缺失的 approval 服務或缺失的 agent 都以各自不同的結果文字失敗關閉。授權不持久化。

升級是對被拒絕命令的同輪次重試，使用最窄的足夠 `sandbox_permissions` 和一個 `justification`；批准提示詞是同意步驟。它必須基於實際的拒絕，除非工作階段已觀察到相同的被拒絕訪問；停用或被拒絕的批准終結該命令。重試、批准決策和結果使用既有的工具和批准事件。`dsh-tool-bash` 擁有請求動作，因為執行器 Service Definition 既沒有 agent 也沒有使用者互動所需的 call id。

仍未決定：持久授權超出沙盒模式之外的作用域標識是什麼——確切呼叫、路徑、命令前綴、工作階段或時間視窗——這是公佈 `allow_always` 選項之前必須回答的問題。

#### 按工作階段模式：工作階段日誌即儲存

```
effective(session) = findLast(the session's knob events)?.value ?? the composition-config default
```

預設值是組合設定（`cordis.yml`）——由運維人員擁有、作用於整個行程。執行時期切換是工作階段範圍的覆蓋，以一條僅日誌事件記錄在該工作階段的日誌中。重新啟動後仍然有效以及多工作階段隔離均由重播自然保證，且不存在任何外部設定儲存。行程內 subagent 驅動程式器在委派時對父級的顯式覆蓋項取得快照，並在子 agent 選填的 fork 前綴之後預置一條帶來源標記的事件，因此委派無法回退到更寬的預設值（[決策](2026-07-25-subagent-policy-inheritance.md)）。

**每個旋鈕一種事件，由其領域擁有**——這是每個既有事件族已遵循的可合併擴充 `SessionEventMap` 慣用法（`dsh-user-approval` 中的 `approval/*`、hooks 包中的 `hook/*`）：

```ts
interface SessionEventMap {
  'sandbox/mode': { mode: 'read-only' | 'workspace-write' | 'danger-full-access' }
  'approval/policy': { policy: 'ask' | 'never' }
}
```

每個擁有者匯出相同的三件套：事件聲明、純 fold（`effectiveSandboxMode(events)` / `effectiveApprovalPolicy(events)`——一個 `findLast`，類型化到領域的封閉聯合），以及唯一的寫入路徑（`setSandboxMode(session, mode)` / `setApprovalPolicy(session, policy)`——切換即其事件；沒有任何東西在帶外修改狀態）。無需共享的歸屬服務、通用 facts map 或登錄檔：第三個設定項只需將約 40 行模式複製到自己的包中。執行在兩側都遵循 fold——bash 工具的按呼叫蓋章將其作為 § 升級機制優先級鏈的中間層讀取，approval seam 的 `'never'` 門控是[批准 Agent Note](2026-07-06-approval-seam.md) 同一模式的另一側。

每次擬議步驟之前，沙盒策略與批准策略都會渲染為一條目標策略上下文訊息中的有序貢獻。監聽器將該訊息與工作階段歷史、已領取批次及其待處理的 `next-step` inbox 條目協調。訊息一旦被領取並進入步驟，迴圈就會記錄完整且帶來源的 `user/message`；`'ask'` 與 `'never'` 都會明確寫入，因此兩個歸屬方都無需切換敘述或「上次告知」狀態。

**選填的 UI 介面**是 `PermissionPresetService`：一張部署定義的 preset 表，每個條目捆綁一個沙盒模式與一個批准策略。隨附的 `workspace-write` 和 `danger-full-access` preset 寫入兩個領域 setter；preset 表之外的旋鈕組合報告為 `custom`。UI 配接器可以把該表暴露為選擇器。僅面向自動化的 ACP 傳輸層不公佈任何設定選擇器，也不掛載權限 preset 服務。

**已提交的事件是提交邊界。** 執行時期切換在目標工作階段上記錄其 preset 和發生變化的旋鈕事件，之後每次能力解析都摺疊最後的值。選擇有效的工作階段追加邊界由配接器負責；ACP 傳輸層沒有執行時期切換路徑。（原先 ACP 的空閒切換錨定——將待定的空閒選擇保留到下一次提示詞提交——已隨該橋一並移除。）

#### 行程內工具

fs/web/todo 在行程內執行，因此它們的沙盒語義是各自能力邊界層面的策略。fs seam 現在透過沙盒提供方強制共享模式詞彙（`dsh-fs-sandbox` 按模式限制 write/edit；見[跨工具族 fs 沙盒 RFC](2026-07-14-cross-family-fs-sandbox.md)），因此 `read-only`/`workspace-write` 對檔案系統工具也是真實邊界，而非僅限 bash 的近似。web/todo 仍不受限制（web 的唯一效果是網路，不在文件效果模式詞彙內）。沒有通用的按工具沙盒執行時期：主機中介的工具僅透過返回主機驗證的聲明式效果來離開行程，那是一次重寫而非包裝層——後續設計選擇了一個共享策略歸屬 `ctx.sandboxPolicy`，由各能力強制，而不是統一包裝層。

### 測試

- **單元測試：** 固定平臺選擇和 profile、直接交接提供方返回的 argv、帶有無效 workdir 對照的 spawn 層失敗、runner 缺失／不可執行／解釋器缺失證據、格式錯誤 runner 陰性對照、受約束的 `BASH_ENV` 求值順序、結構化 runner 分類（包括只有部分強制執行通知的子行程結果、帶門控的致命證據、子行程退出碼 126／127，以及前臺／後臺一致性）、按呼叫的模式/根目錄解析、按行程事實、升級驗證和結果、權限 preset fold 和寫入透傳，以及執行時期上下文排序與具體化。
- **Keyless 真實 runner：** 在提供方和 bash 消費端層面對 bwrap、Landlock 和 Seatbelt 執行真實檔案系統效果測試；一個真實 Cordis 上下文透過已交付的 bash 和 fs 工具並行驅動程式兩個項目工作階段，證明在自身根目錄寫入成功、在兄弟根目錄寫入被拒絕。打包安裝測試會安裝當前 checkout 的原生 tarball，並證明 launcher 保持可執行且位元組完全一致。CI 拒絕靜默全跳過。
- **With-key：** 以只讀模式啟動真實 ACP 組合，讓模型驅動程式的 bash 寫入命中 runner 的拒絕標記，再透過已授權與被拒絕的 workspace-write 重試驅動程式 bridge 應答器和磁碟效果；不可用的憑證或 runner 自動跳過。
- **快照：** 固定原子化的當前策略上下文和兩個指令碼化的 approval 分支。一個真實 ACP 示例場景把工作階段放在使用者主目錄下，同時讓部署後備根目錄指向 `/tmp`，然後固定 workspace-write 執行時期上下文訊息與一次成功的、由部署選定的變更；這能區分工作階段根目錄解析與行程後備值，而不相依性 runner 特定的拒絕文字。一個模擬 Landlock 部分強制執行行為的 POSIX 提供方會在組裝後的應用中固定直接執行 bash `false` 時仍得到普通子行程結果，並固定提供方可執行文件缺失時在前臺／後臺均為基礎設施失敗。其他快照以無約束啟動，使無關 fixture（測試前置資料）保持平臺無關。

## 延遲階段

每個階段在開始實施時都會完成完整設計，並對照當時的程式碼驗證，同時在其涉及的層級配套單元測試、真實 API e2e 和快照覆蓋。

- **第二個消費端**——`subagent-acp` 選填地約束子 agent（按呼叫策略；默認無約束——子 agent 必須寫入自己的持久化）。
- **更多環境**——環境一致的能力組示例（如 bash+fs 對一個容器）。
- **Windows 鏈**——`PLATFORM_CHAINS.win32` 保留為空（失敗關閉）；填充它意味著來自 AppContainer/restricted-token 家族的約束 runner，由主倉庫在 `native/` 下按 `@deepseek-ai/node-addon-landlock-run` 範本交付，加上其 profile 方言、拒絕簽名和 runner 失敗規則。改為包裝第三方 landstrip runner 的方案[經考慮後已駁回](../../rejected/feature/2026-07-26-evaluate-landstrip-for-windows-sandbox-rung.md)——它所經受的實戰檢驗還不足以承載安全不變式。

## 曾考慮的替代方案

- **命令字串啟發式預檢**：否決。無法理解展開/子行程/符號連結；嚴格嘗試（執行它，讓核心決定）是唯一可信的拒絕訊號。
- **即使平臺僅有一個後端也功能性探測**：否決。探測用於在候選者之間仲裁；只有一個時無需決策，且探測開銷對每個工作階段的首次約束命令徵稅（對未來重量級後端而言代價過高）。runner 自身執行時的失敗關閉拒絕加結構化 `runnerFailureRules` 分類承載了安全屬性。
- **提交建置好的 launcher 二進位**：否決。diff 中的二進位不可審查且膨脹歷史；經審查的原始碼 + 原生 CI 建置 + 主倉庫的位元組固定發布演練使二進位遠離所有程式碼樹。
- **安裝時編譯 launcher**：否決。將 C 工具鏈強加給每個消費端；僅在碰巧有編譯器時才存在的備選不是備選。
- **從一個建置器交叉編譯兩種架構**：否決。僅為重建兩個約 70 KB 的二進位就需要攜帶一個固定的交叉工具鏈（rustup targets、zig 或容器映像檔）；每架構的原生 runner 已存在，各自建置自己的平臺包（`node-addon-require-builtin` 模式，由主倉庫的原生管線保留）。
- **無備選（bwrap 或失敗關閉）**：否決。將失敗集中在沙盒最重要的主機上，最終因放棄而降級到 `danger-full-access`。
- **將機制保留在 `dsh-bash-sandbox` 內部**：否決。阻塞既有的第二個消費端，使未來階段從一個 bash 外掛程式的設定中讀取模式，且無法表達升級。
- **提供方上的設定固定模式**：否決。每行程一個模式；無法服務具有不同策略的並行消費端，也無法表達一次性放寬重試。
- **一個介面同時覆蓋容器/VM**：否決。`confine(argv)` 預設共享檔案系統；環境隔離是作為一致組部署的能力兄弟後端。
- **通用 ToolRuntime 包裝任何工具**：否決。對行程內工具（閉包了 `ctx`）機械上不成立；聲明式效果重寫對 fs/web/todo 而言不合理。
- **在執行器內部（`dsh-bash-sandbox`）請求批准**：否決。沒有可路由的 `agent`，沒有可附加提示詞的 `callId`；新增它們會讓傳輸邊界瞭解工作階段和 UI——工具層持有兩者並擁有面向模型的詞彙。
- **同一工具呼叫內自動重試**：否決。日誌無法重建的隱藏重入：一個 `tool/call` 會產生兩次具有不同策略的執行——重試是一次新的帶有自身參數和結果事實的已記錄呼叫。
- **無條件公佈升級欄位**：否決。在 `dsh-bash-local` 下它們是死槓桿——公佈 harness 無法兌現的選項會製造註定失敗的授權；能力門控僅需註冊時一次讀取。
- **預設值相對的升級階梯（僅公佈比執行器註冊時預設值更寬的模式）**：否決。按工作階段覆蓋使預設值成為錯誤的基線——切換到比預設值更窄的工作階段恰恰失去它需要的槓桿，而在 `danger-full-access` 預設值下欄位完全消失，同時一個被覆蓋為 `read-only` 的工作階段仍處於約束中卻沒有升級路徑。枚舉固定封閉的目標詞彙；嚴格放寬是針對工作階段有效模式的按呼叫執行檢查。
- **按工作階段動態工具 schema**：否決。schema 設計上是登錄檔全域性的（一套 assembly 詞彙、固定 header 快照約定），按工作階段重新註冊只能買到執行時嚴格放寬檢查已保證的東西，代價是按工作階段的 schema 和每次切換的 header 變動。
- **將重試硬匹配到先前的拒絕**：否決。命令字串同一性脆弱（引號、`workdir`、env 前綴、作為失敗階段重試的管道）——要麼誤拒誠實的重試，要麼被輕易滿足；真正的邊界是人看到命令 + 理由。僅在 `allow_always` 授權儲存需要機器可檢查的範圍時才重新考慮。
- **通用 `env/state` facts map 加擁有者服務**：否決。approval 和沙盒獨立組合，因此任何一方的狀態都不應拖入第三個包；單鍵 fold 各自是一個 `findLast`，擁有者服務自然消解；沒有跨旋鈕的不變式，因此原子多鍵修補程式無收益。
- **透過 `agent.inject()` 加總線事件逐次敘述切換**：否決。獨立通知會暴露歸屬方順序和中間組合，而一次 pre-step 組合可以原子排隊完整的當前狀態。
- **在穩定系統提示詞中聲明沙盒模式**：先行交付，隨後根據線上證據移除：每次請求都帶有 `Bash commands run under the "read-only" file sandbox.` 時，模型會拒絕嘗試本可在被拒後升級的工作（首次人工工作階段的十二個輪次中有五個以零工具呼叫結束），使沙盒變成軟鎖死。拒絕標記會在相關時刻指出模式，升級欄位則承載復原路徑。[當前策略決策](2026-07-30-current-sandbox-policy-context.md)取代了省略策略的決策；這項測量和因果觀察仍是任何替代方案必須進行反證測試的依據。
- **用專門的簿記事件追蹤「上次告知」**：否決。工作階段歷史記錄模型看到的確切策略上下文，已領取批次與待處理 inbox 條目則表明正在進入或已經排隊的內容。重新計算目標訊息取代了第二條簿記流——事件僅在它們本身即為儲存時才需要。
- **相互獨立的沙盒與批准選擇器**：否決。一個部署定義的權限 preset 讓兩個策略旋鈕對暴露執行時期切換的 UI 用戶端保持一致。

## 後果

已交付並固定的內容——測試中的各層級分別保障：

- 被拒絕的命令以 `sandbox_permissions` + `justification` 重試時，透過組合的應答器鏈提示使用者；授權使該次呼叫在更寬模式下執行（結果事實如此報告），而其他所有呼叫保持各自的有效模式；每種非授權結果產生各自不同的錯誤文字且不執行任何內容。
- 升級欄位恰好在已掛載的執行器約束時存在；不嚴格寬於呼叫有效模式的請求以自身文字失敗關閉且不提示任何人；沒有 ApprovalService 的部署對升級呼叫失敗關閉，對普通呼叫不影響。
- 一條帶來源的策略上下文訊息會以原子方式聲明完整的當前沙盒策略與批准策略；整個互動——上下文訊息、header、旋鈕事件、批准通知、批准與結果——僅從工作階段日誌即可重建，除兩個旋鈕事件外沒有策略簿記事件。
- 一次 preset 選擇只記錄發生變化的旋鈕值，而無操作的選擇不記錄任何內容；下一次 pre-step 會原子 upsert 兩個當前值，已提交的沙盒切換由下一次呼叫的蓋章兌現。
- 復原工作階段的覆蓋項會進入其首條新策略上下文訊息，無需追趕狀態；行程停止期間變更的組合預設值也會出現在該訊息中。
- 兩個並行工作階段永遠看不到彼此的狀態或通知。
- 同一個 Cordis 上下文中的兩個並行項目工作階段解析各自獨立的工作區根目錄；bash 和 fs 寫入在呼叫方工作階段的 cwd 內成功，對其相鄰工作階段的 cwd 則失敗。
- 策略歸屬仍透過 `SessionEventMap` 合併、從 `agent/pre-step` 變更 inbox，以及由能力歸屬方擁有的解析留在外掛程式中；通用迴圈只領取並記錄最終進入步驟的批次。

代價與已接受的限制：

- **單一包裝層的幻覺被有意放棄。**`tools/pre-execute` 包裝層加提示詞約定無法解決沙盒批准——正確的設計需要結構化拒絕、原生 runner 探測、按呼叫策略承載和一致的跨工具族強制，本設計為此付出了代價。
- **`read-only` 透過後續設計成為跨工具族邊界。** 本 Agent Note 最初只交付 bash 強制；[跨工具族 fs 沙盒 RFC](2026-07-14-cross-family-fs-sandbox.md) 透過沙盒化的 `ctx.fs` 提供方把同一模式詞彙擴充到檔案系統工具，並將 mode/root 設定和 `sandbox/mode` 覆蓋遷移到 `ctx.sandboxPolicy`（§ 行程內工具）。
- **Windows 後端只提供部分強制執行。** 本 RFC 最初預留了一條空的、失敗關閉的 win32 鏈；後續的 [Windows ACL 沙盒決策](2026-08-08-windows-acl-restricted-token-sandbox.md)以受限權杖 runner 填充了它。其 Everyone 與硬連結缺口報告為 `enforcement: 'partial'`，絕不提升為完整承諾。
- **Seatbelt 層級相依性 Apple 已棄用但仍交付的 `sandbox-exec` CLI。** 作為 darwin 的唯一候選，它無需探測即被選中，因此在 workdir 可用時，未來移除會表現為可歸因於 runner 的 spawn 失敗，可執行文件拒絕則透過其致命簽名體現——兩者都會變為 `SANDBOX_UNAVAILABLE`，且命令絕不會執行；失敗關閉，絕不開放。
- **Landlock 約束的完整度取決於執行核心的 ABI。** 報告為 `enforcement: 'partial'` 而非拒絕——這是有意的權衡，使備選在舊核心主機上仍可用。
- **Runner 歸因使用帶內協議。** 退出狀態與 stderr 無法以密碼學方式識別寫入者，因此受限子行程可以模仿 runner 的致命診斷行和狀態，造成可用性或診斷誤歸因。多項證據的合取與精確通知排除減少了意外匹配；這不是沙盒繞過，因為子行程已經受到限制。
- **launcher 在原始碼中是 workspace 相依性，發布後是 NPM 相依性。** 主倉庫會在發布同一個包家族之前，一起測試經審查的 C 原始碼、原生 CI 建置和位元組固定的本機 tarball；真實核心 e2e 測試環節會驗證這些安裝位元組的實際行為。
- **模型可能過度請求。** 在沒有拒絕依據的情況下升級，或在 `workspace-write` 足夠時選擇 `danger-full-access`：描述引導且枚舉強制階梯，但人的提示詞是實際門控；`approval/asked` 原因使過度請求可審計，且 `prepend` 策略應答器可以自動拒絕部署永遠不想要的模式。
- **公佈的目標集是靜態的，而有效模式是按工作階段的**（schema 是登錄檔全域性的）——已處於最寬模式的工作階段仍被提供這些欄位。構造上無害：執行時的嚴格放寬檢查（而非枚舉）是安全邊界——非放寬請求以自身文字失敗且不提示任何人。
- **授權的升級不等於可工作的沙盒。** 不可用的後端即使對授權升級到約束模式也仍然失敗關閉——平臺沒有鏈或所有探測失敗時在 `confine()` 階段失敗，所選可執行文件無法啟動時透過 spawn 通道失敗，已啟動的 runner 拒絕時則透過結構化規則失敗——而授權的 `danger-full-access` 執行根本不觸及提供方：此時授權（而非探測）是權威。
- **執行時期上下文歷史僅附加。** 策略切換會在保留的歷史之後追加一份用於取代先前快照的完整快照，從而保留穩定的系統與對話前綴；狀態不變時不新增訊息。
- **舊策略快照仍保留在歷史中。** 每份完整快照都會明確取代更早的執行時期上下文快照，因此重播與壓縮（compaction）只需保留最新具體化的訊息。

## FAQ

- **一個命令返回了 `[sandbox: file access denied under read-only mode]`——它失敗了嗎？** 它執行了，核心拒絕了一個文件操作：拒絕是與退出碼正交的結果事實。相關指令禁止透過繞過限制來重試；唯一被認可的動作是以升級請求重試同一命令一次。
- **如何區分損壞的沙盒與失敗的命令？** 提供方 argv 的任何 spawn 拒絕都能證明受限啟動從未開始，但只有在呼叫方擁有的 workdir 可用，且 Node 為該 argv[0] 報告可歸因的 `ENOENT` 或 `EACCES` 時，才能據此判定 runner 損壞。沒有精確錯誤路徑的裸 `syscall: 'spawn'` 和其他所有拒絕仍是普通的命令啟動錯誤。行程啟動後，只有當 `runnerFailureRules` 中某一條目同時匹配其選填退出碼門控，以及排除整行精確資訊性行後的一行致命 stderr 診斷時，runner 失敗才會優先於拒絕。前臺失敗會拋出結構化的 `SANDBOX_UNAVAILABLE`，並附帶 spawn 錯誤或匹配行作為詳細資訊；遭非同步拒絕或已結帳的背景工作則蓋章 `sandbox.runnerFailed` 並渲染自己的標記。如果 `SubprocessRuntime` 同步拋出同樣帶有 runner 路徑的 `ENOENT`／`EACCES` 形態，後臺啟動會拋出該結構化錯誤；其他同步錯誤原樣傳播。Landlock 部分強制執行通知加上普通子行程失敗時，仍返回命令結果。
- **在沒有後端的平臺上會發生什麼——今天的 Windows？** `confine()` 拋出失敗關閉的 `SANDBOX_UNAVAILABLE`，命令永不 spawn；`win32` 是保留的空鏈，由測試固定為同樣失敗關閉，直到 Windows runner 填充它（§ 延遲階段）。
- **`bwrap` 已安裝在我的主機上但不可用（停用了非特權 userns、LSM 拒絕 `mount`）——會發生什麼？** 鏈探測是功能性的——它建置並強制一個真實 profile 而非檢查 `--version`——因此存在但不可用的 `bwrap` 探測失敗，選擇落到已打包的 Landlock launcher，結論在提供方生命週期內快取。
- **沙盒限制網路或行程可見性嗎？** 不——`SandboxMode` 僅聲稱文件操作；bwrap profile 刻意不 unshare pid，沒有後端聲稱網路。網路限制是否成為自己的旋鈕留在 § seam 中開放。
- **哪些工具實際在約束下執行？** 透過 `ctx.shell` 的 OS 子行程——bash 工具及傳遞性的掛鉤命令——再加上透過沙盒化 `ctx.fs` 提供方執行的檔案系統工具（`read`/`write`/`edit`，見[跨工具族 fs 沙盒 RFC](2026-07-14-cross-family-fs-sandbox.md)）：bash 透過 OS runner 約束，fs 透過行程內路徑圍欄約束，二者都以同一個 `ctx.sandboxPolicy` 模式為鍵。web/todo 仍在行程內且不受限制（web 的唯一效果是網路，不在文件效果模式詞彙內）。
- **授權的升級會持久化嗎？** 不會。授權由發起請求的確切前臺或後臺呼叫消費；每個相鄰呼叫保留自己的有效模式。後續的後臺拒絕透過 `job_output` 呈現，並且可以作為一次新的精確命令重試的依據。
- **執行時期模式切換何時生效？** 一旦其工作階段事件提交，下一次 pre-step 策略上下文協調與下一次能力解析都會摺疊新模式。帶來源的上下文訊息會記錄模型收到的內容，之後的任何拒絕都會在使用點命名同一策略。
- **重新啟動後什麼存活——如果運維人員在行程停止期間改了設定預設值呢？** 覆蓋從工作階段日誌重播（`effective = fold ?? config`），因此復原的工作階段以零追趕機制保持其模式；離線漂移的預設值會進入下一條完整策略上下文訊息。
- **結果上的 `enforcement: 'partial'` 是什麼意思？** 所選後端強制其核心 ABI 管控的子集——例如 ABI v3 之前的 Landlock 不管控路徑 truncate——並以結構化方式如此聲明而非拒絕主機；探測的報告行區分各種情況。bwrap 和 Seatbelt profile 構造上管控所有承諾的文件操作，因此始終報告 `full`。
