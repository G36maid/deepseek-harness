# Agent Note: 計畫審閱是一次決定，不是一道題

Status: implemented

[English](2026-07-30-plan-review-presentation-intent.md) | [简体中文](2026-07-30-plan-review-presentation-intent.zh.md) | 繁體中文

## 問題

`exit_plan_mode` 透過 `ctx.userQuestions.ask()` 把寫好的計畫交給使用者審閱，而這正是 `ask_user_question` 使用的同一個 seam。在 Web GUI 上，這導致計畫審閱渲染為[ask-question Web 呈現](2026-07-29-ask-question-web-presentation.md)裡的通用問題流程：一個 `1 / 1` 分頁器、計畫作為問題的補充說明、兩個裁決作為帶描述的編號單選行、一行「其他，請填寫自訂答案」，以及底部的 `跳过本题` / `提交`。

這些可互動元素對這個介面而言無一正確。審閱一份計畫是對一份文件做一次決定，而做題式的介面告訴使用者他正在被考試，而不是被請求批准一份工作 —— 實際回饋是「讓人很困惑以為在做題」。分頁控制元件在給只有一項的集合分頁。跳過並不是該工具接受的結果（它會摺疊成繼續規劃）。最糟的是，這個介面完全沒有暗示這就是計畫關口，而旁邊的等待審批接管早就具備了一次決定該有的形狀：一條帶色條帶說明正在決定什麼、主體是決定的對象、靠右對齊的操作行。

## 決策

一個問題可以聲明**呈現意圖（presentation intent）**，Web 輸入區把已聲明的意圖渲染為它自己的介面。`AskUserQuestionItem` 新增 `intent?: AskUserQuestionIntent`，這是一個帶標籤的聯合，目前唯一成員是 `{ kind: 'plan-review', approve: string }`；`plan-mode` 在審閱問題上設定它，並指明 `Approve` 是表示批准的標籤。

意圖只改變呈現。回答協議不變：遵循意圖的 UI 回答的仍是通用 UI 會發送的那些選項標籤，因此無論由哪個介面收集，`exit_plan_mode` 讀到的都是同一組回答欄位；而不認識某個標籤的 UI 渲染通用流程，除版面配置之外一無所失。

`approve` 指名肯定選項，而不相依性選項順序，因此沒有任何 UI 會從位置推斷裁決。意圖作出的兩項斷言超出類型的表達能力，`UserQuestionService.ask()` 都以 `BAD_INTENT` 在提問方一側拒絕：`approve` 未命中該問題自身的任一選項 —— 早於任何 UI 回答一個從未被提供過的選擇；以及意圖落在沒有 `detail` 的問題上，而 `detail` 正是它自稱在審閱的東西，那會讓使用者去批准一件看不見的事。在協定格式（wire format）上意圖是可辨識聯合，因此無法識別的標籤是被拒絕的幀，而不是靜默退回通用渲染。

`ui-user-questions` 把該意圖渲染為 `PlanReviewPanel`，沿用等待審批卡片的語言：琥珀色條帶寫著 `Plan review`，計畫是可滾動的 markdown 主體，決定行放三個操作 —— `Chat about it`、`Refuse`、`Approve`。問題文字成為卡片的無障礙名稱而非標題，因為按鈕已經說明瞭這次決定是什麼。Approve 與 Refuse 用提問方自己的選項標籤回答，並把提問方的描述保留為 tooltip；`Chat about it` 取消該請求，從而讓輸入區歸位，使用者直接說他想說的話即可。所有文案在既有 `question` 命名空間下雙語。

路由住在單一輸入區條目內部（由 `QuestionComposer` 選擇呈現），而不是第二個鏈式註冊；`planReviewOf` 僅在卡片能夠寄出該請求允許的每一個答案時才接管：只有一個問題且聲明瞭意圖、以 `detail` 承載計畫、提供了被指名的批准標籤，且是二元單選 —— 除批准外最多一個選項，且非多選。出現第三個選項或多選批次時，其答案是兩個按鈕無法表達的，通用流程保留它，也保留其他任何卡片渲染不了的請求。因此「只改變呈現」是字面意義上的：意圖絕不讓使用者失去一個可達的答案，而位於協議邊界下游的用戶端讓每個請求都保持可回答。

放棄審閱成為面向模型的獨立結果。`ASK_CANCELLED` 以前傳到模型的是「the user cancelled ask_user_question」，指名了一個它從未呼叫的工具；現在 `exit_plan_mode` 報告使用者放棄審閱是為了改用說話，並要求留在 plan mode 中等待。其餘每一種 ask 失敗 —— 輪次取消或提供方 teardown導致的中止，那裡並沒有使用者會來 —— 保留它們自己的訊息。

## 備選方案

**讓計畫審閱成為自己的待處理種類（`plan-review/requested`）。** 否決：對一個呈現問題來說尺寸不對。它換來的是誠實的回應形狀（approve / decline / discuss 而非一批迴答），代價是第三個 `PendingKind`、新的 requested/resolved 幀與 schema、一個 api-proxy 登錄檔與回應分支、用戶端工作階段與基線重放處理，以及為一個問題協議已能表達的決定新增一個三包能力 seam。只有當計畫審閱長出回答形狀承載不了的結果時才值得重新考慮。

**按問題的 `id` 或 `header`（`plan-review` / `Plan review`）路由卡片。** 否決：這是跨協議邊界嗅探另一個包的文案字串，任何措辭改動都會靜默破壞它。意圖纔是讓路由可讀的那個聲明。

**約定選項順序，讓卡片把第 0 個位置讀作批准。** 否決：這是包邊界上的位置約定，在類型和協議幀裡都看不見，也無法強制 —— 生產方一旦重排選項，就會顛倒使用者的裁決。指名標籤只花一個字串。

**為計畫卡片註冊第二個輸入區鏈條目。** 否決：兩個條目會對同一個待回答問題載體做選擇，使介面取決於鏈優先級、以及計畫包的用戶端半邊是否被組合。一個自己挑形狀的條目不會和自己搶，而通用流程正是內建的回退。

**把面板放在 `ui-plan` 裡、緊挨計畫狀態標籤。** 否決：面板的全部行為就是問題載體的回答編碼（`PendingQuestion`），那是 `ui-user-questions` 擁有的；意圖是問題協議的欄位，不是 plan-mode 的私有通道。渲染已聲明的意圖屬於擁有問題渲染的那個包，正如工具渲染意圖屬於工具渲染方。

**與 `ui-conversation` 的 `ApprovalPanel` 抽出共享的接管卡片。** 未做：兩個接管在 token 和幾何上一致，但內容不一致 —— 這邊的主體是可滾動 markdown，那邊是一行標題加一行命令 —— 共享外殼只會剩兩個元素寬。它們靠 token 保持一致，而不是靠元件。

**給 `Chat about it` 自己的協議結果。** 否決：放棄一個請求是通用流程已有的動詞（取消整批的 `×`）。把它提升為帶標籤的按鈕屬於呈現；為它發明第四種協議結果不屬於。

## 結果

問題協議從此帶有一個呈現軸。新增第二個意圖 = 聯合上的一個標籤、一個設定它的生產方、一個 schema 成員、一個面板 —— 不需要新的幀、服務或回答形狀。代價是問題約定從此知道「呈現」這件事存在，且 `ui-user-questions` 知道「plan」這個詞；兩者都是由單一條目擁有全部問題介面所要付的價錢。

計畫關口讀起來就像計畫關口：計畫是卡片的內容，裁決是兩個帶標籤的按鈕，把輪次拿回來是第三個。通用流程對其他每個問題都未受影響，其已提交的 golden 也沒有變動。

用戶端半邊早於本次改動的部署仍然顯示做題式版面配置 —— 正確、可回答、只是沒有專門樣式 —— 因為意圖是增量的，而回退就是通用流程。

## 測試

`ui-user-questions` 測試釘住收窄（單問題批、意圖存在、計畫作為 detail、被指名的批准標籤確實被提供、二元單選、只提供批准時 decline 缺席）與面板（條帶、markdown 計畫、無障礙名稱、不顯示分頁器、單選行、跳過項和自訂項、批准與拒絕用提問方的標籤回答、放棄觸發取消、一次性閉鎖，以及在回執被拒時重新武裝並給出訊息、tooltip 有與無、兩種語言）。`user-questions` 測試釘住兩種 `BAD_INTENT` 拒絕與意圖透傳；`plan-mode` 測試釘住已聲明的意圖與其自身選項清單的一致、以及兩條失敗訊息；apiproxy schema 測試釘住協議接受與未知標籤的拒絕。

`plan-review` Web e2e 通道錄制了 `/plan` 真實進入 plan mode、模型呼叫 `exit_plan_mode`、決定卡片接管輸入區（並斷言通用流程**沒有**接管該請求）、以及卡片自身的 Approve 完成該輪 —— 兩份無金鑰 golden：等待中的卡片與批准後的 transcript（文字記錄）。
