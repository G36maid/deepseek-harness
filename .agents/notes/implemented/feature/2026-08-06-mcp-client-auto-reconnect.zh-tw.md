# Agent Note: MCP client auto-reconnect with bounded backoff

Status: implemented

[English](2026-08-06-mcp-client-auto-reconnect.md) | [简体中文](2026-08-06-mcp-client-auto-reconnect.zh.md) | 繁體中文

## 問題

[MCP 用戶端](2026-07-07-mcp-client-plugin.md)在外掛程式載入時僅連線一次。stdio 伺服器崩潰或被終止後，其已註冊的工具仍然可見，但每次呼叫均以 `Not connected` 失敗，直到人工編輯設定觸發 HMR（熱模組替換）重載，或重新啟動 Host——v1 明確推遲了重連機制。長時間執行的 Host（ACP 自動化、Web）不能因為子行程死亡就被重新啟動；而對於 stdio 傳輸，harness 組合層是唯一能重新拉起子行程的一方。外部回饋將此升級為真實的運維缺口（issue #1746）。

## 決策

`packages/mcp/mcp-client/src/connection.ts` 擁有一個逐實例的連線監督器；`apply()` 收縮為設定解析加兩個副作用（`serverName` 預留和監督器的生命週期）。監督器負責管理 client/transport 代、活躍的工具註冊以及重連迴圈。

**觸發條件。** 監督器在每一代上掛載 `client.onclose`。SDK 在 stdio 子行程退出時觸發該回調，因此崩潰無需輪詢即可感知。`StreamableHTTPClientTransport` 僅在主動關閉時觸發 `onclose`——它內部擁有自己的 SSE（Server-Sent Events）流復原機制，並將請求失敗以逐呼叫方式暴露——因此 HTTP 伺服器實際上不在監督器的重新啟動範圍內；包 README 記錄了該限制。

**代隔離，無交錯。** 每次嘗試建置一個全新的 transport 和 `Client`（SDK 將一個 Protocol 綁定到一個 transport 上終身使用）。每個監督器內部有一個佇列將所有 `syncTools` 呼叫序列化——跨所有代的初始同步和 `list_changed` 再同步——`isCurrent` 柵欄使過時的代變為惰性，從而確保不會有兩次同步交錯執行 dispose 上一代/註冊下一代的切換（否則會對同一代執行兩次 dispose 並洩漏另一代）。該佇列還消除了一個先前存在的競態：兩次快速的 `list_changed` 通知同時觸發重新同步。嚴格啟動註冊由啟用嘗試本身顯式擁有，而非由首個入隊者擁有；提前到達的 `list_changed` 採用故障隔離的再同步語義，不能消費 `failOnStartupError`。失敗訊號按代冪等：一次連線拒絕與其自身 transport 關閉競態時，僅調度恰好一次重試。失敗嘗試只有在 `Client.close()` 結帳且 transport 報告 `onclose` 後才能進入退避；對 stdio 而言，`onclose` 證明子行程已退出；若關閉訊號始終未到，則在 SDK 的有界終止視窗結束後停止重連，而不是允許兩個伺服器行程重疊執行。dispose 使用同一個有界關閉訊號屏障；若關停未完成則予以報告，且絕不重新啟動。

**有界退避與故障預算。** 延遲從 `initialDelayMs` 起逐次翻倍，上限為 `maxDelayMs`。一次故障期間共享 `maxAttempts` 次連續失敗嘗試的預算；耗盡後註銷該伺服器的工具、以 error 等級記錄日誌並停止，直到 dispose 或重新載入。連線在存活超過穩定視窗——即 `maxDelayMs`，作為最長退避間隔從設定推導得出而非作為第五個獨立調參項——之後重設預算；因此偶爾崩潰的伺服器可無限復原，而連線短暫成功後立即再次崩潰的迴圈無法將其預算洗白為重新啟動風暴。

**設定與解析。** 兩種傳輸均接受 `reconnect { enabled, initialDelayMs, maxDelayMs, maxAttempts }` 設定，Schemastery 預設值為（啟用、500ms、30s、10）。`resolveReconnectPolicy()` 是顯式的解析步驟：它重新校驗每個邊界值和跨欄位約束，因為程序化構造可能繞過 Schemastery，設定錯誤在載入時即令外掛程式實例失敗。

**可觀測狀態。** 初始嘗試或重試嘗試失敗時記錄 `connection failed`，已建立的代結束時記錄 `connection lost`；重試的 warn 日誌包含嘗試次數和延遲，復原以 info 等級記錄，最終失敗和停用重連時的斷連以 error 等級記錄。故障期間，上一個正常代保持註冊，對其工具的呼叫返回失敗——確定性公開名稱意味著復原後未變化的工具清單會復現相同的定義，保持模型可見 schema 前綴穩定而非反覆抖動。設定 `reconnect.enabled: false` 後，斷連保持 v1 的手動復原行為。

**資源釋放。** dispose 翻轉柵欄、取消待執行的定時器、關閉當前 client，然後等待正在進行的嘗試和同步佇列完成後再註銷工具——完全靜止，而非僅寄出停止請求。重連定時器使用 unref，因此等待中的退避不會阻止行程正常退出。

## 曾考慮的替代方案

**連續失敗計數器，每次成功連線即重設。** 否決：連線短暫成功後立即崩潰的迴圈伺服器會在每個週期重設預算並永遠重新啟動——恰恰是失敗上限旨在防止的重新啟動風暴。基於執行時期間的重設能區分已復原的伺服器與迴圈崩潰的伺服器，無需新增設定。

**跨重連複用同一個 SDK `Client`。** Protocol 在關閉時清除其 transport，技術上可以再次連線，但 SDK 自身的指導方針是每個 Protocol 實例對應一次連線，且複用會將通知處理器和已協商的能力狀態帶入新的伺服器實例。每代建立全新 `Client` 加 `isCurrent` 柵欄的方式無歧義。

**斷連時立即註銷工具，復原時重新註冊。** 否決：短暫故障會使模型可見工具清單抖動（每次崩潰觸發兩次 schema 前綴失效），而無任何資訊增益；失敗的呼叫已足以標示故障，復原時的切換按代原子執行。工具僅在最終失敗時註銷，確保永久死亡的伺服器不會洩漏永久失效的工具。

**將 Streamable HTTP 請求失敗路由到監督器。** 暫不採納：HTTP 傳輸已使用自己的退避機制重連其 SSE 流，逐請求錯誤並不意味著伺服器已死，且 harness 沒有可重新拉起的子行程。transport 關閉仍是唯一觸發條件。

**透過 Loader/HMR 機制重新啟動，而非使用外掛程式內監督器。** 否決：Loader 負責設定驅動的重組合，而非執行時期健康管理。外掛程式透過 Loader 重新啟動自身會混淆設定代與連線代，並丟失逐故障預算。

## 測試

單元測試（`tests/reconnect.spec.ts`，mock SDK）：復原在不產生重複或洩漏的前提下切換代並服務復原後的呼叫、診斷區分初始或重試嘗試失敗與已建立連線丟失、嚴格啟動註冊在連線前收到 `list_changed` 通知後仍然生效、初始化失敗會等待舊代的關閉訊號，若該訊號始終未到則停止重連、dispose 同樣等待同一關閉訊號，並在有界等待到期時報告關停未完成、失敗上限註銷工具並停止、dispose 取消待執行的退避並使進行中的同步完全靜止、dispose 後的關閉不調度任何操作、停用模式保持 v1 行為、穩定視窗重設預算而崩潰迴圈耗盡預算、雙重失敗訊號僅調度一次重試、過時的代和處理器為惰性、`resolveReconnectPolicy` 拒絕每個無效邊界值。E2E（`tests/mcp-client.e2e.ts`，無需金鑰）：fixture 伺服器新增了一個 `crash` 工具（先回覆再退出）；真實行程測試證明 stdio 崩潰端到端復原，以及在故障期間解除安裝外掛程式能立即停止重連。快照：刻意不做，原因與原 Agent Note 相同——重連不引入新的展示形態，而在快照組閤中 spawn 崩潰伺服器會使重播相依性時序。

## 後果

- 崩潰的 stdio MCP 伺服器無需人工幹預即可復原：有界退避、重新發現、原子代切換。默認策略對一次故障大約重試 2.5 分鐘後放棄。
- 連線狀態確實比一次性連線更複雜——v1 刻意迴避的部分可用視窗現已存在（故障期間已註冊工具返回失敗），集中在一個模組中並命名了所有不變式。
- `reconnect` 是兩種傳輸上的新設定表面，穩定視窗刻意從 `maxDelayMs` 推導；將其設為獨立可調參數是相容的未來變更。
- 最終失敗後或停用重連時，外掛程式保持載入狀態但無（或失敗的）工具，直到重新載入——行為是刻意的且有日誌記錄，確保長期故障的伺服器不能永遠重新啟動。
