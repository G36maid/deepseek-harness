# Agent Note: 允許同時存在多個 `in_progress` todo

Status: implemented

[English](2026-07-26-todo-parallel-in-progress.md) | [简体中文](2026-07-26-todo-parallel-in-progress.zh.md) | 繁體中文

## 問題

[原始 `todo_write` 設計](2026-06-29-todo-write-tool.md)在 `execute` 和持久日誌不變式中都強制每個清單至多一個 `in_progress` 任務。該不變式假設工作是順序進行的，但 harness 會執行真正平行的工作（透過委派工具啟動的並行 subagent、後臺 bash 命令、工作流程扇出），而一個只能標出單個活躍任務的清單無法表示這種情況。模型被迫要麼把平行任務錯誤標記為 `pending`，要麼把它們合併成一個含糊的條目，導致 UI 進度清單少報了實際正在執行的工作。

## 決策

把單一 `in_progress` 上限從固定規則改為部署策略，並要求每個組合都作出選擇：

- `packages/todo/tool-todo/src/index.ts` 新增必填的 `Config.allowParallelInProgress` 欄位。為 `true` 時，`execute` 接受任意數量的活躍條目，描述指示模型把每個正在處理的任務標記為 `in_progress`（平行工作時可以有多個，順序工作時只有一個），並在仍有工作未完成時至少保留一個；為 `false` 時，描述要求恰好一個，`execute` 拒絕標記多個活躍條目的呼叫。
- `packages/todo/tool-todo/src/invariant.ts` 中的持久日誌不變式不再拒絕含多個活躍條目的快照，且不跟隨該設定，因此此前持久化的日誌不受影響，平行快照在任一策略下都能幹淨重播。

其餘編碼的不變式保持不變：`content` 去除首尾空白後非空且唯一、status 為合法枚舉值。本決定取代[原始設計的校驗決策](2026-06-29-todo-write-tool.md)中「至多一個活躍」的條款；該 Agent Note 的其餘部分（整清單替換、日誌支撐的狀態、單一所有者）依然成立。

## 為何用指引而非感知平行的不變式

編碼的不變式只能看到清單，看不到執行時期：兩個 `in_progress` 條目是否合理，取決於工作是否真的在並行執行，而這一點工具無法觀測。因此，恰恰在平行讓上限變得重要的場景裡，強制上限反而是錯的；任何替代方案（例如把活躍條目數限制為當前執行中的 subagent 數量）都會把工具耦合到它有意一無所知的執行時期上。把 `in_progress` 標記與真正並行的工作對應起來這一紀律，轉移到工具描述中，也就是排序與清單新鮮度已經所在的地方。

## 該策略是部署層的選擇

並行的活躍任務是否合理，取決於工具無法觀測的執行時期並行情況——但一個部署的 agent（代理）是否會並行展開工作，在組裝期就是可知的。因此該策略是必填的 `Config` 欄位，而非常數或預設值：每個 cordis.yml 組合都會有意設定 `allowParallelInProgress`，為可能平行展開工作的 agent 選擇 `true`，或為單活躍項紀律選擇 `false`。

該開關會同時改變面向模型的指令與接受的輸入。把兩者拆開纔是 bug：描述要求只保留一個活躍任務、而 `execute` 卻接受多個，等於教給模型一條工具並不遵守的規則；反過來則會拒絕描述所邀請的呼叫。描述中只有活躍狀態那一句會變化，因為這是該策略唯一改變的指令。

持久日誌不變式刻意**不**跟隨該開關。在允許平行時寫下的日誌，在部署收緊策略之後仍必須可重播，因此把 `invariant.ts` 綁定到當前設定會拒絕在寫入當時合法的歷史。不變式對活躍數量保持沉默；策略生效之處是工具，時機是寫入的那一刻。

## 曾考慮的替代方案

- **保留上限並增加一個顯式的平行 opt-in 標志**——為服務常見場景而給每次呼叫增加一個額外參數；這個標志對順序工作而言只是噪聲，而且仍然無法驗證。
- **把活躍條目限制在一個可設定的上限內**——任何固定數字都是任意的。這正是該設定欄位是布林策略開關而非數量的原因：「是否允許多個任務同時活躍」是部署的屬性，而「最多 N 個」憑空發明瞭一個無從論證的閾值。
- **把平行策略硬編碼**——本變更的第一版就是如此，這也是 `allowParallelInProgress` 之所以必要的原因：執行嚴格順序 agent 的部署沒有任何辦法回到它想要的紀律。

## 展示面是本次改動的一部分

解除上限使一種此前任何渲染器都不曾收到的清單形狀變得可達，因此本變更建置在 [web todo 展示](2026-07-23-web-todo-display.md)之上，而不是與之平行落地：兩者都改 `tool-todo`，而 GUI 正是平行計畫變得可見的地方。web 有兩處用 `todos.find(t => t.status === 'in_progress')` 推導單行摘要——摺疊態的計畫橫條表頭與 `todo_write` 工具行——在舊上限下這個 `find` 是完備的，因為最多隻能有一個條目匹配。一旦有多個活躍項，它會靜默丟掉除第一個之外的全部活躍條目：一個四條目、三個任務在跑的計畫摺疊後只顯示其中一個的名字，工具行讀作 `1/4 已完成 · <一个任务>`，而另外兩個仍在進行。展開態的清單始終正確（它遍歷每個條目），這也是兩個變更的測試都沒抓到它的原因——只有摺疊表頭與工具行丟失了資訊。面板重做把摺疊表頭的具名提示換成以 `·` 連線的各狀態計數（本機化後形如 `1 已完成 · 2 进行中 · 1 待处理`，計數為零的段落省略），它能正確報告平行工作，且不需要任何可被截斷的名字；工具行纔是本變更仍需修的那一處。

工具行改用 `toolviews/plan-summary.ts` 中的 `planSummary`。它給出第一個活躍條目，並計數其餘活躍項，因此工具行報告的是有多少任務在跑，而不是暗示只有一個。列出全部活躍條目被否決了：工具行是單行，無上界的拼接會溢位——在清單做不到的地方，計數能夠可預測地降級。該推導放在 toolviews 域內而非 `contract/`（域間共享面）：面板自行內聯計算其計數，與工具行不共享任何東西，因此放進 contract 會聲明一種已不存在的共享關係。

`planSummary` 把任務名與計數作為兩個獨立欄位返回，而不是一個拼好的字串，因為工具行用 `overflow: hidden` / `text-overflow: ellipsis` 截斷其摘要文字。計數接在任務名之後時位於可截斷文字的末端，於是恰恰是讓計數變得有意義的那些場景——窄視口、長任務名——會把它裁掉，讓平行計畫看起來與順序計畫無異。因此工具行把計數交給共享的 `ToolRow`，作為 `summarySuffix`——一個緊鄰被省略號截斷的摘要文字、且不會收縮的 slot；一個預先拼好的字串無法表達這個切分，而把計數放到任務名之前也被否決了：讀者首先要找的是任務名。

`summarySuffix` 是 `ToolRow` 上的 slot，而不是 todo 工具行自有的標記：每個 toolview 都經由這個共享元件渲染，而它的 `summary` 是一個會被省略號截斷的普通字串，容不下一個必須挺過截斷的片段。該後綴落在 `.summary` 規則之外，因此重複了該規則的 `font-size` 與 `line-height`——Web 外殼把正文字級留在瀏覽器預設值而非該行的 14px，所以未加樣式的 span 會明顯大於同一 24px 行內與之並列的文字。錯誤行會丟棄該後綴，因為它摺疊態的摘要是失敗行，而非任何由呼叫 args 推匯出的內容。

## 暫緩項

兩個已知缺口暫緩處理。`summarySuffix` 這個 span 沒有無障礙名稱，螢幕閱讀器讀出的數量缺少它所修飾的名詞（`… 实现 fixture 样本 +1`）；為它命名會引入帶自身測試約定的本機化文案，這屬於對整條 `ToolRow` 摘要行做的無障礙專項，而不屬於某一行。以及，當*第一個*活躍條目的 content 不可用時——缺失、類型不對、或 trim 後為空——行會連同數量一起丟掉活躍子句，於是平行計畫渲染成裸計數；向後跳到第一個可用活躍條目的方案被否決，因為呼叫 args 是一處明確未經校驗的邊界，模型給出的順序是該行唯一能遵循的順序，而只丟掉不可用的那個子句可以保住 `done`/`total` 計數——這兩個數無論如何都是可信的。

## 後果

現在 todo 清單可以忠實反映平行執行，並且每個展示面都能一次渲染多個活躍標記：計畫橫條的表頭會計數活躍條目，工具行則需要上述推導。設定 `allowParallelInProgress: true` 的組合不再拒絕一種此前無效的快照形狀；設定為 `false` 的組合仍保留舊的拒絕行為，而持久日誌不變式兩者都接受。面向模型的描述發生了變化，這重新記錄了 tool-catalog 頁面以及每個帶有 todo schema 的快照伴隨檔案。此處不記錄數量：該集合會隨每個新落地的 pin 場景成長。有效規則是：改動工具描述的分支必須刷新它分叉之後落地的那些伴隨檔案——包括固定 subagent 類工具的編號文件 `tool-schemas.<n>.expected.json`，其 schema 不被父場景覆蓋——`pnpm run test:snapshot:refresh` 可以無 key 地對整個語料完成刷新。web fixture（測試前置資料）的 todo 樣本現在有兩個條目處於 `in_progress`，因此兩個由 fixture 驅動的展示面渲染的都是平行計畫。`packages/client/ui-conversation/tests/todo-panel.client.spec.tsx` 在 src 上固定工具行摘要與計畫橫條，ACP（Agent Client Protocol）`todo-write` 場景錄制的是三條目、兩個活躍的計畫，而 `apps/web/tests/todo-row.snapshot.ts` 在組裝後的應用中固定這兩個面——它從建置產物 `packages/client/*/lib/client.js` 啟動，因此是唯一覆蓋 keyed 註冊與打包接線的地方。該文件把 `summary`、`suffix` 與橫條表頭記錄為獨立欄位，因此即便拼接後的文字讀起來一樣，把 `+N` 計數折回摘要字串也會改變預期輸出。
