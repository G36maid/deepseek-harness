# Agent Note: 刪除 Workspace 註冊記錄

Status: implemented

[English](2026-07-27-workspace-registration-deletion.md) | 繁體中文

## 問題

Workspace 註冊已有程式碼目錄，使 GUI 能夠為目錄命名，並對其工作階段排序。該記錄沒有說 Harness 建立或擁有該目錄，工作階段日誌也是獨立的持久化對象。若將行內 Delete 操作視為遞迴刪除原始碼或刪除工作階段，就會破壞該記錄所有權邊界之外的資料。

現有選單行只有視覺呈現，沒有實際功能，因此持久化順序、Workspace 表、Host 流、並行瀏覽器分頁標籤、重連基線，以及清單請求與變更並行時的刪除語義也沒有定義。

## 決策

`ctx.workspaceRegistry.delete(id)` 只刪除 Workspace 註冊記錄：其 id 會從持久化的 `workspaceIds` 中移除，`workspaces` 錶行與實體快取條目會消失，有序 `sessionIds` 帳本也隨該行一並消失。它絕不呼叫檔案系統移除操作或 `SessionPersistence`；目錄、所有使用者文件、所有即時工作階段和所有已持久化的工作階段日誌都會保留。側邊欄分組是所有存續 Workspace 帳本的補集，因此這些工作階段（包括當前工作階段）會立即出現在 Ungrouped 下。

未知 id 在領域約定處返回 `false`。`workspace.delete({ workspaceId })` 將該結果對映為 `workspace-not-found`；成功時返回 `{ deleted: true }`。`workspace.list` 仍是重連基線。

## 持久化提交與發布

登錄檔操作會序列執行建立與刪除。刪除時先寫入移除該 id 後的 Workspace 順序，再從快取中移除實體，最後刪除錶行。表刪除是通知提交點：只有快取停止發布該實體後，包不變數才接受該刪除；Host 也只根據這次已提交的刪除寄出 `host/workspace-removed`。表寫入失敗時，系統會復原快取和此前的持久化順序，且不會發布移除幀。

Host 流在前一筆全域性順序寫入期間繼續保留其已提交 id 集合，只在刪除錶行時移除該 id。因此，建立回滾不會發出錯誤的移除幀，而每個已連線分頁標籤都能收到從自身投影中刪除該記錄所需的準確 id。

建立與刪除會在記錄／順序對可能分叉之前寫入持久化的 `pendingMutation`。啟動時只補全該標記明確命名的操作，並清除標記；僅有一行孤立記錄無法確定哪個操作被中斷。因此，沒有標記的順序／表分叉仍會保持登錄檔原有的損壞直接失敗語義。如果刪除的表寫入已經提交、但標記清理失敗，操作仍會報告成功——所請求的狀態和移除幀都已經提交——下一次啟動會以冪等方式清除該標記。

## 用戶端收斂

`WorkspaceManager` 將 `host/workspace-changed` 與 `host/workspace-removed` 都視為有序增量，並在進行中的 `workspace.list` 回應之上重播。成功的一元刪除會立即移除行，無需等待本次操作自己的流回顯。移除操作具有冪等性；由於 Workspace id 永不複用，行程本機墓碑標記會拒絕延遲到達的 changed 幀或過時基線行。重連仍從 `workspace.list` 刷新；Workspace 增量絕不會剪除工作階段狀態。

刪除確認框會保持待處理，直到 React Workspace 投影已經提交目標 id 的移除，因此下一次 Workspace 操作不會看到過時清單幀，也不會以其為操作目標。

## 確認互動

現有 Workspace 行選單會在刪除前打開共享 `Modal`。文案明確說明三項後果：Workspace 會從清單中移除，資料夾和工作階段日誌會保留，相關工作階段會出現在 Ungrouped 下。請求待處理期間，確認與 Cancel 控制元件均被停用，重複確認會被忽略，Escape 或 Close 也無法關閉此次操作。失敗時 `Modal` 保持打開並顯示錯誤；提交前使用 Cancel、Escape 或 Close 絕不會觸發刪除。

選單、`Modal` 和按鈕保留現有結構與設計 token。工作階段刪除仍只有視覺呈現，沒有實際功能，不在本決策範圍內。

## 考慮過的替代方案

**級聯刪除工作階段。** 不予採納，因為 Workspace 註冊記錄不擁有工作階段持久化，且產品需求是將歷史記錄保留在 Ungrouped 下。工作階段刪除需要自己的生命週期、執行狀態檢查、後代對象的處理語義和明確 UI。

**將資料夾移到廢紙簍。** 不予採納，因為該記錄無法證明目錄所有權。未來的破壞性檔案系統操作必須使用單獨名稱、單獨確認，並實施明確的安全邊界。

**先刪除錶行，之後再修復順序。** 不予採納，因為崩潰或寫入失敗會使已初始化登錄檔的順序與表不一致。登錄檔會在同一序列操作內更新二者，並在表操作失敗時復原此前順序。

**啟動時刪除所有未引用錶行。** 不予採納，因為來源不明的順序損壞也會呈現相同形狀；靜默丟棄可能損失 Workspace 元資料和 Session 帳本。復原必須相依性擁有該變更的操作預先寫入的明確待處理標記。

**成功後重新拉取兩個清單。** 不予採納，因為已提交的移除幀與即時一元回顯已足夠，既能保留當前工作階段對象，也避免將區域性變更擴大為兩次清單請求。重連基線仍是修復路徑。

## 驗證

Workspace 包測試固定了僅刪除元資料的成功路徑、同路徑重新註冊、未知 id 的冪等行為、表操作失敗回滾、明確標記的重新啟動復原、來源不明損壞的拒絕，以及快取／表不變數行為。Apiproxy 與載體測試固定了 schema、處理器、`workspace-not-found`、保留工作階段／資料夾、使用新 id 重新註冊，以及已提交的 `host/workspace-removed` 幀。用戶端測試固定了一元直接回顯、重複移除、延遲到達的 changed 幀，以及刪除與進行中基線並行的行為。元件測試固定了確認互動、投影穩定後關閉、成功幀先於一元回應、失敗、Cancel、Escape 與 Close。瀏覽器場景會在為不同目錄複用已刪除名稱時，觀測每一次瞬時 alert、slot error、console error 與 page error。

組裝後的無金鑰 Web 場景會註冊一個已有臨時項目目錄，將持久化工作階段計入帳本，把該工作階段設為當前工作階段，在 Chromium 中確認刪除，並驗證 Workspace 分組消失，而 Ungrouped 保留當前工作階段。該場景在刪除前後檢查使用者文件和 JSONL 日誌，並在刷新後重複驗證 UI、目錄與日誌。

## 後果

刪除 Workspace 後仍可使用新 id 重新註冊同一目錄，因此該操作有意設計為可逆；但此前的手動工作階段順序會丟失，重新註冊後，系統也不會在 bootstrap 結束後自動重新收編現有工作階段。該操作放棄一鍵清理工作階段歷史或原始碼目錄，以換取與記錄實際所有權一致的刪除邊界。
