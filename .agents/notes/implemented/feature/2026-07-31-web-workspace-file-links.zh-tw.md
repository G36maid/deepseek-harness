# Agent Note: 從 web UI 打開產出的文件

Status: implemented

[English](2026-07-31-web-workspace-file-links.md) | [简体中文](2026-07-31-web-workspace-file-links.zh.md) | 繁體中文

> 範圍：完成的輪次以其產出文件收尾的那一行、讀得出是連結的檔案路徑連結，以及 Host 打開器對瀏覽器可渲染文件優先選用預設瀏覽器。經決定不在範圍內：以 HTTP 提供工作區文件，以及為不在 Host 機器上的用戶端提供預覽。

## 問題

一個產出了文件的 web 工作階段，沒有辦法看到那個文件。agent（代理）寫出了 `deepseek-homepage.html` 並如實告知，而使用者唯一的辦法是把 `/private/tmp/dsh-client-hotplug.ygPvsm/workspaces/plugin-hotplug/deepseek-homepage.html` 這樣的絕對路徑複製進終端機。

這背後是兩個不同的缺陷。transcript（文字記錄）從不說明一個輪次產出了什麼：`ToolCallView.locations`——文件工具早已填好的跟隨文件詞彙——在用戶端沒有任何消費端，因此讀者對產出的唯一交代，就是收尾訊息恰好拼出來的那點內容。而已經存在的那個互動是隱形的：`ToolRow` 早已把改寫行或讀取行的路徑渲染成一個接到 `host.openPath` 的真按鈕，但它的樣式與周圍正文一模一樣、只有懸停纔有底線，於是沒人發現。所報告的「做完了打不開」，是一個可發現性失敗疊在一項本就可用的能力之上。

## 決策

**完成的一輪以它產出的文件收尾。** 該行是獨立外掛程式 `@deepseek-ai/dsh-client-ui-deliverables`，註冊進 chat 檢視表在收尾訊息正文與其 IconActions 之間渲染的 `conversation.chat.turnTail` 空位——ui-conversation 擁有空位與 owner 通貨（節點、收尾 seq、`openFile`），外掛程式擁有全部策略。`producedForClosing` 從改寫工具自身的跟隨文件 `locations` 中讀出路徑——diff 卡片，或 `kind` 為 `edit` 的 generic 卡片（即 `str_replace_editor` 的 insert 所呈現的形狀）——因此無論收尾訊息是否點名，這一輪的產出都會被列出；新的改寫工具靠聲明自己做了什麼加入，而不是靠被加進某張名單。read、刪除與失敗的呼叫不貢獻任何條目；同一路徑在一輪內按首見順序只出現一次；累積在 turn 邊界重設，因此一輪若先改寫文件、隨後沒有正文內容就結束，不會溢進下一輪的行裡。單行 lane 會測量 chip 和本機化剩餘計數，再顯示能放下的最大前綴（至多六個）及 `+ N 个文件`。cordis.yml 中的一行即可把該互動面組合進來或去掉；未註冊的空位什麼也不渲染。

**路徑連結讀得出是連結。** 靜止狀態下就帶底線，而不只在懸停時。這是本次改動中更小的那一半，卻是修復中更大的那一半。

**打開仍然是 Host 的職責，並且優先選用預設瀏覽器。** `host.openPath` 把路徑交給作業系統，得到的是真實瀏覽器裡的一份 `file://` 文件：頁面能力完整，且夠不到 `/api`——因為 `file://` 文件與它並不同源。在所報告的那份產物上實測：`localStorage` 可用、主題切換生效、tabs 可切換，而對 API 的 `fetch` 失敗。對瀏覽器能渲染的文件——`.html`、`.htm`、`.xhtml`、`.svg`——平臺能夠確定預設瀏覽器時，打開器解析的是默認**瀏覽器**而非該類型的默認應用，因為把 `.html` 綁給編輯器的開發者，否則點開一個產出的頁面得到的會是原始碼。macOS 讀取 LaunchServices 的 `https` 處理程序，桌面 Linux 讀取 `$BROWSER`；無法確定瀏覽器時，兩者都會回退到默認應用。Windows 使用其註冊的文件關聯，WSL 則先轉換路徑，再使用同一 Windows 交接。存在隱藏文件時，**在資料夾中顯示**會把 `.` 經由同一 owner `openFile` 傳遞；它只在 loopback 頁面的當前 `host.describe.canOpenPath` 允許原生打開時出現。其他部署會省略它；桌面探測誤報時可設定 `nativeOpen: false`。

**以 HTTP 提供工作區文件不在範圍內，非本機用戶端亦然。** 由 harness 自己提供文件——與 `/api` 同源、置於 `CSP: sandbox` 之後、或交給一個以自身埠給所服務文件獨立源的第二監聽器——隨產品範圍一並否決：不為「瀏覽器不在 Host 機器上」的場景提供預覽，因此 Host 打開器完整回答受支持的場景，而那套 HTTP 機制只會回答不受支持的那個。

## 考慮過的替代方案

- **由 harness 提供 `/f/<sessionId>/<segments…>`**——已經實作並可用，包含雙 `realpath` 路徑約束、瀏覽器信任 fence、流式讀取，以及一個以自身埠給所服務文件獨立源的監聽器。它是唯一能把預覽呈現給另一臺機器上用戶端的設計，而那恰恰是被判出範圍的場景。因此退役，而不是因為它失敗了；它的代價是一個帶自身生命週期的第二 socket、一個注入頁面的埠，以及一份跨兩個包共享的 URL 形狀約定。
- **同源 HTTP 提供且不加隔離**——經實測不安全，記錄在此以免有人重試：與 `/api` 並排提供的文件把 `settings.describe` 打到 `200` 並拿到完整資料，把 `session.list` 打到包含所有工作階段 transcript 的 35 KB，而這個頁面根本不必由 agent 撰寫（一條 read 行就讓 clone 下來的倉庫裡任何文件變得可打開）。
- **在那套同源提供之上加 `Content-Security-Policy: sandbox`**——它以剝奪文件的源來堵住這個洞，而這經實測會破壞本功能存在的意義所在的那類頁面：所報告的產物在載入時拋 `SecurityError`，又因為未捕獲例外會中止其 `<script>` 的其餘部分，該行之後聲明的所有監聽器——主題切換、行動裝置選單、模型 tabs——統統不會綁定。報告者工作區裡四份產物有兩份在它之下是死頁面，而且它們渲染得完美無缺，所以這種破壞是看不見的。
- **把路徑在助手的收尾訊息裡連結化**——這是使用者開口要的形狀（「在結尾附上鍊接」），但它讓渲染取決於模型是否把路徑拼寫得可識別。工具呼叫已經把 `locations` 作為結構化事實攜帶，產出文件行消費的正是它。
- **讓文件 chip 橫向滾動**——這樣會把每個文件都留在 DOM 中，卻使隱藏的尾部難以發現，在 transcript 內增加一層橫向手勢，也無法精確說明視口外還有什麼。經過測量的一行和穩定的剩餘計數既保留回答的縱向節奏，也明確呈現省略量。
- **桌面端外殼中的內嵌 WebView**——可得到的最強隔離，因為那時預覽跑在產品自己擁有的容器裡，而不是使用者的瀏覽器裡。它屬於桌面端外殼自身的設計，而非本互動面，記錄在此作為未來預覽能力應走的方向。

## 後果

現有的每一處文件互動都同時改變了：write、edit、read 與通用單文件卡片都匯到 `openFile`，因此連結修復與瀏覽器優先策略無需逐行改動。組裝層 Web 測試覆蓋溢位幾何和單次點擊的 Host 交接，且不會啟動原生應用。產出的 `file://` 文件無法 `fetch` 同級文件（但 `<script src>`、`<img>` 和 CSS `@import` 可用），這是 HTTP 提供曾有、而此處沒有的能力。遠端用戶端保留 chip，但省略資料夾操作；每個 chip 的 `title` 仍保留完整路徑。Markdown 仍由平臺的 `.md` 應用打開；產品內渲染屬於另一項工作。
