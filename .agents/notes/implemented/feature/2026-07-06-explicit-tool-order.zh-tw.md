# Agent Note: 顯式的模型側工具順序

Status: implemented

[English](2026-07-06-explicit-tool-order.md) | [简体中文](2026-07-06-explicit-tool-order.zh.md) | 繁體中文

## 問題

模型側的工具順序此前跟隨外掛程式註冊順序，而註冊順序取決於相互獨立的外掛程式的並行模組載入。這種競態在 CI 和快照錄制中產生了不同的請求標頭。由於順序影響請求位元組、快取和持久化的請求標頭，因此需要一個顯式的確定性策略。

## 決策

系統提示詞組裝邏輯負責權威定義模型側工具順序，正如它已經負責權威定義 section 順序一樣。`dsh-system-prompt` 上的 `toolOrder?: string[]` 是選填的顯式策略：

- 清單中已註冊的工具按清單位置排列。
- 清單中的名稱沒有對應的已註冊工具，屬於設定錯誤。形狀錯誤（缺少 rest 條目或名稱重複）在服務構造器中快速失敗；未註冊的名稱則會導致每次 `assemble()` 呼叫被拒絕——這是已註冊工具集存在並可供檢查的最早時刻（工具外掛程式在服務構造之後才註冊），也是唯一的通用時刻（註冊隨時可能變化；Cordis 沒有「所有外掛程式已載入」事件）。在已交付的 agent loop（代理循環）下，第一個輪次在寄出任何模型請求之前就會失敗——確切的影響範圍見下文「後果」。
- 已註冊但不在清單中的工具，插入到 `'<unlisted-tools>'` rest 條目（`TOOL_ORDER_REST`）的位置，與其他未列出的工具按名稱字典序排列。
- 任何已收集的工具不得使用 `TOOL_ORDER_REST` 作為其 `ToolSchema.name`；組裝邏輯在排序之前就會拒絕這個保留名稱。
- 清單必須恰好包含一個 rest 條目，且不得有重複名稱。
- 當 `toolOrder` 未設定時，權威順序為純字典序（code-unit 比較，與 locale 無關），因此無需設定即可保證確定性。

`assemble()` 在 `system-prompt/assemble` waterfall（瀑布式事件）之前將提供方工具歸一為權威順序，從源頭消除註冊順序的差異。waterfall 從這個確定性清單開始；不變的順序隨後流入請求標頭、凍結的請求和重建檢查，無需 loop 特有的排序邏輯。

範圍刻意收窄：本 Agent Note 修復的是註冊順序競態，而非外掛程式行為。`system-prompt/assemble` 的監聽器仍然可以新增、移除或重排工具——正如它可以在 section 排序之後編輯 section——並對自身輸出的確定性負責；waterfall 約定已經要求監聽器是確定性的（可重建性不變式會捕獲在建置與重播之間行為不一致的監聽器）。

設定傳遞沿用 `persona` 的先例，`toolOrder` 與之並列：TUI、Headless 和 ACP 應用設定接受該鍵，並透過 `dsh-agent-spine-demo`（其 schema 是各所有者 schema 的交集）轉發給 `SystemPrompt` 子服務。有一個 schemastery 細節至關重要：schemastery 陣列預設為 `[]`，但省略的 `toolOrder` 必須保持 ABSENT（= 字典序），而不是變成一個顯式設定的空清單（無效——缺少 rest 條目），因此鏈路上每個 schema 都將預設值強制為 `undefined`。

## 曾考慮的替代方案

- **註冊順序（現狀）**：並行匯入競態，相依性宿主環境（上述 CI 抖動），評審中不可見。
- **外掛程式相依性圖的線性化**：該關係是偏序的，獨立的工具外掛程式不可比較；抖動發生時偏序已完全滿足。
- **每個外掛程式在其工具貢獻上標注 `weight`**：將順序分散到各外掛程式中，仍需一個無人擁有的全域性編號約定（section 的 `order` 分段已經展示了這種協調成本需要手工承擔）。
- **在 `ToolRuntime.schemas()` 中排序（登錄檔層）**：同樣確定，但登錄檔是一個成員儲存，被組裝之外的多方消費；排序是提示詞組合的關注點，而組裝邏輯已經擁有 section 的組合策略。
- **在 `LlmRuntime` 上加設定 + `orderTools()` 方法，由 loop 在記錄 header 前呼叫**：可行，但僅為在遠處應用一個策略就增加了一個公開服務方法和一處 loop 改動；每個未來的請求組合者都必須記得呼叫。在清單誕生處進行規範化使得無序清單不可表示，且零新增介面。
- **在 `llm.stream()` 內部規範化**：在 header 事件已記錄之後才執行（抖動仍然存在），且需要重建深度凍結的請求封裝對象，靜默地解除了重建不變式。
- **窮舉清單（無 rest 條目）**：每個新載入的工具外掛程式都會導致啟動失敗；強制的 rest 條目使未列出的工具保持確定性，且其位置是顯式的。
- **啟動時校驗（由 `dsh-app-boot` 在 `loader.await()` 之後呼叫 `SystemPrompt.assertToolOrderSatisfied()`）**：能將錯誤設定變為啟動時死亡而非首輪失敗，但代價是一個公開服務方法加上通用啟動膠水對單個服務的結構耦合，且無法替代組裝時檢查（嵌入式呼叫者從不執行 app boot；註冊在 boot 之後仍會變化）。也沒有現成事件可以承載該檢查：Cordis v4 沒有 ready 類事件，`loader/entry-init`/`internal/status` 在載入中途觸發（與工具註冊存在競態——正是本 Agent Note 要消除的熵源），而 agent 生命週期事件不會早於組裝。經權衡，選擇只在 `assemble()` 設定一個校驗點，值得為此接受失敗時刻較晚的代價。

## 後果

- 每個由登錄檔建置的組裝在任何宿主上都以確定性工具順序開始；在沒有專家監聽器刻意改變的情況下，每個 `request/header` 事件和模型請求都繼承該順序。CI 與本機之間的註冊順序翻轉從結構上被消除，預設為字典序。
- 初始 `PromptAssembly.tools` 是權威的，因此 waterfall 監聽器從模型側順序開始；提供方註冊順序在該協作擴充點之前無處可觀測。
- 快照套件中唯一鎖定請求標頭的 fixture（測試前置資料）為 `text-turn`，其攜帶新的權威工具順序；按照鎖定請求標頭的設計，其他 ACP 快照仍將大段 header 替換為 `{{system}}`/`{{tools}}`。
- 步驟之間的純工具重排與其他 header 變更一樣記錄：一份原因是 `'change'` 的完整 `request/header` 快照。穩定的權威順序會防止註冊時序在普通路徑上製造這類變化。
- `toolOrder` 鍵沿 app → `agent-core` → `SystemPrompt` 的轉發鏈傳遞，因此部署時將其放在 app 設定中 `persona` 旁邊即可；`dsh-llm` 和 agent loop 無需改動。
- `toolOrder` 中拼錯或未載入的工具名稱在提示詞組裝時使輪次失敗，而非啟動時：loop 在輪次內部組裝（`turn/start` 之後、`step/start` 之前），因此該拒絕會進入輪次的外層 catch——輪次以攜帶該訊息的 `error` 原因完整結束，`agent/error` 也攜帶該訊息，不打開步驟，不記錄 `request/header`，不向配接器寄出請求，agent 回到空閒狀態。每個輪次都以相同方式失敗，直到設定被修正；行程本身保持執行（符合倉庫規則：顯式設定引用不得被靜默忽略——校驗點設在組裝階段，因為不存在更早的通用時刻）。
- 工具提供方返回保留的 rest 條目名稱時，其提示詞組裝失敗形態與未知的已列名稱相同。這防止哨兵值變成一個歧義的真實工具，並保持「從不丟棄工具」的排序約定。

## 測試

系統提示詞測試覆蓋：字典序默認順序、清單/rest 位置、提供方順序無關性、共享名稱、無效清單、未知或保留名稱、waterfall 前的權威清單，以及監聽器新增的工具不被重新排序的規則。Loop 測試鎖定：在不同註冊順序下，已記錄與已分發的順序一致、設定透過 agent-core 和兩個 app 轉發、請求經過深度凍結，以及在設定了未知名稱時的平衡輪次失敗（無步驟、無 header、無配接器呼叫）。快照重播僅在固定的 `text-turn` header 中保留完整的權威清單；其他 fixture 繼續使用 `{{tools}}`。
