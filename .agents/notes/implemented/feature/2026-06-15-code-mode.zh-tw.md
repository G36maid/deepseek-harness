# Agent Note: Code Mode——模型針對工具登錄檔編寫 TypeScript

Status: implemented

[English](2026-06-15-code-mode.md) | [简体中文](2026-06-15-code-mode.zh.md) | 繁體中文

## 問題

在登錄檔的原生呈現方式下，agent loop（代理循環）將每個可見能力以 JSON Schema 函式定義的形式通告給模型。`ToolRuntime` 將其 schema 貢獻給系統提示詞組裝，組裝結果中的 `tools` 落到協定格式（wire format）上（也記錄在請求標頭日誌中），模型每步呼叫一個 `tool-call` 塊，而在本 note 寫作時，迴圈透過 `ctx.tools.execute()` **逐個**分發每次呼叫（平行工具執行當時還是 open TODO；此後有界的平行分發已經交付——見[平行工具呼叫 note](2026-07-10-parallel-tool-call-execution.md)，以及 [docs/architecture.md](../../../../docs/architecture.md) 中的 rolling pool）——且**每一個**中間 `tool-result` 都會在下一次請求時重新進入模型上下文。

對於多步工具操作，這種方式 token 開銷大且序列。模型無法組合工具——遍歷結果集、根據中間值分支、扇出、後處理——每次呼叫都需要一次完整的模型往返，而每次往返都會把完整的中間結果拖回上下文，不管模型是否需要。

Cloudflare 的 [Code Mode](https://blog.cloudflare.com/code-mode/) 提出了一種替代方案，基於一個簡單的觀察：LLM（大型語言模型）編寫程式碼的能力優於寄出工具呼叫，因為它們見過數百萬行真實程式碼，而人為構造的工具呼叫 trace 相對很少。模型不再每步寄出一次工具呼叫，而是針對工具生成的 API 編寫一段 TypeScript 程序，程序在沙盒執行時期中執行，模型只篩選返回的內容——僅限它 print 或 return 的部分——而非所有中間結果。

工具呈現屬於掌管工具可見性的登錄檔：如果把第二種呈現方式實作為事後的 waterfall（瀑布式事件）變換，正確性將相依性監聽器順序，並與[可重建請求](../architecture/2026-07-05-reconstructable-requests.md)衝突。執行基底同樣屬於基礎設施而非佔位實作：Node `worker_threads` 提供獨立 isolate、空環境、堆上限以及對熱同步迴圈的終止能力，同時契合 harness 既有的信任模型（§信任姿態）。

## 決策

三項決策，各自在下方獨立小節中展開：

1. **Code Mode 是 `ToolRuntime`（`dsh-tools`）的一等呈現模式**，透過經校驗的 `mode` 設定選擇：`'native'`（默認，貢獻可見能力 schema）、`'code'`（登錄檔僅貢獻其保留的 `run_code` 傳輸通道加一份生成的 SDK `.d.ts` 到系統提示詞中）或 `'both'`（原生 schema 加傳輸通道 + SDK）。登錄檔在源頭建置其規範貢獻；協作式提示詞組裝的結果仍具權威性，記錄在日誌中的請求標頭精確反映該返回的呈現。
2. **程式碼執行是一個能力 seam**——`packages/code-runtime/` 包含 Service Definition 包 `@deepseek-ai/dsh-code-runtime`，擁有 `ctx.codeRuntime`（[能力 seam](../architecture/2026-06-13-capability-seams.md)；消費端 = `dsh-tools`，core 消費 seam 的先例見 `agent-loop` → `dsh-llm`）。執行時期對工具一無所知：它接收一段程序和命名的非同步綁定，執行程序，報告 `{ value, logs, error? }`。語言和基底是後端屬性，因此未來的 Python 或容器後端只是另一個 Service Provider 包，而非重新設計。
3. **交付的實作是 `@deepseek-ai/dsh-code-runtime-worker-thread`**：每次執行 spawn 一個全新的 Node worker 執行緒，對模型的 TypeScript 進行 type-strip 後執行，綁定透過訊息埠橋接，環境為空，堆/輸出/時間上限可設定，並支持硬終止。其信任姿態在設計上等同於 bash——無需 unsafe-acknowledgement flag——因為 harness 已經交付了 `dsh-bash-local`，後者以嚴格*更高*的環境權限執行模型編寫的任意 shell 命令。

本說明負責定義 Code Mode 的呈現、組合、隔離與結帳基礎。後續的[類型化工具回傳值 Agent Note](2026-07-20-code-mode-typed-tool-returns.md)負責定義生成的輸出對映、規範綁定值、`ToolCallError` 和無損外層輸出邊界。

### 登錄檔擁有模式

`ToolRuntime` 獲得一個經 schemastery 校驗的設定（`static Config`），這是它的第一個設定：`mode: 'native' | 'code' | 'both'`，默認 `'native'`。部署透過 `cordis.yml` 翻轉模式（`tools: { mode: code }`），無需改程式碼，遵循 no-hardcoded-tunables 約定。

**協議工具清單。** 登錄檔在 `'native'` 下貢獻可見能力，在 `'code'` 下僅貢獻 `run_code`，在 `'both'` 下兩者都貢獻。最終的 `PromptAssembly.tools` 清單記錄在請求標頭中。`run_code` 是一個保留的呈現傳輸通道，位於註冊和限制層之外；直接提示詞提供方和組裝 waterfall 仍各自負責自己的貢獻。

**與 `toolOrder` 的互動：** 如果設定的 `systemPrompt.toolOrder` 引用了原生能力名稱，在 `mode: 'code'` 下會拒絕所有組裝，因為那些名稱不在該模式的協議校驗範圍內。這是正確行為而非 bug：使用 Code Mode 的部署需要更新其 order 設定或移除它。

**SDK 提示詞段。** 在 `'code'` 和 `'both'` 下，tool-guidance order band 中的惰性 `tools:sdk` 段為當前 scope 的可見能力渲染所載入執行時期語言的聲明加固定的使用說明（默認 TypeScript；[語言分發 note](2026-07-31-code-mode-language-dispatch.md) 加入了 Python 與按 `ctx.codeRuntime.language` 選擇的渲染器表）。它共享尋找和執行可見性，排除 `run_code`，並按字典序排列工具以獲得位元組穩定的輸出。

**組裝所有權。** `run_code` 和 `tools:sdk` 作為正常的組裝輸入進入受信任的 `system-prompt/assemble` waterfall。一個 scoped 的 `tools:sdk` 段可以在分發前遮蔽全域性預設值，監聽器也可以移除或替換任一貢獻。waterfall 返回的組裝結果是最終的，因此修改這些輸入的人有責任在部署期望 Code Mode 可用時保持協議面的完整性；沒有復原 pass 會覆蓋有意的組合。

**程式碼生成。** `jsonSchemaToTs()` 將 `defineTool` 的 JSON Schema 子集對映為 TypeScript，將 schema 描述帶入 JSDoc，不支持的構造降級為 `unknown`。SDK 將工具暴露為帶引號的對象鍵，支持任意名稱而無需別名或衝突處理。類型是建議性的，因為執行時期在執行前會剝離類型。

### run_code 工具與分發橋

在 `'code'` 和 `'both'` 下，登錄檔擁有 `run_code` 作為保留的呈現傳輸通道，帶兩個必需參數 `{ code: string; description: string }`（description 為 UI 標注該呼叫，沿用 bash 的先例）。它由一個正常的 `ToolDefinition` 表示以供分發，但位於可過濾的能力層之外，因此限制規則不會意外移除 Code Mode 的唯一入口。呼叫遍歷完整的工具管線——`tools/pre-execute` → 單調性守衛 → `tools/execute` 包裹分發 → `tools/post-execute` → 由定義擁有的選填 `finalizeContent` → 不可變的 `tools/result` 通知——與原生呼叫完全一致；權限外掛程式可以在程序執行前檢查程序文字，最終結果觀察者看到的是規範化的外層結果。其 `execute(args, exec)`：

1. **建置綁定。** 一個 run 等級的 signal 跟隨外層取消，並在 run 結帳時被 abort。每個可見工具綁定都會對無損 JSON 參數建立快照，進入原生約定的分發池（調度設計由[即時平行 Agent Note](2026-07-26-code-mode-live-parallel-dispatch.md) 負責），以確定性的 call id 和外層 token 作為 `parent` 執行，透過外層 execution 延後返回的上下文，並記錄 `tool/code-dispatch-start`/`tool/code-dispatch` 事件對，其中結帳側攜帶完整渲染後的結果內容。成功時返回工具最終的規範 JSON 值；失敗則變為程序可見的 `ToolCallError`。每個子呼叫保留自己不可變的執行標識，並遍歷完整的工具管線。
2. **執行程序**：`ctx.codeRuntime.run({ program: args.code, bindings: [{ global: 'tools', functions }], signal: runController.signal })`。執行時期接收的是 run 等級的 signal 而非僅呼叫方的外層 signal，因此外層 run 以任何方式結帳都會同時 abort 執行時期內部的工作。
3. **完全靜止後結帳。** 執行時期結帳後，橋 abort 未完成的工作並排空分發佇列後再返回。成功時返回捕獲的日誌和完成值，將其作為規範輸出；登錄檔再把該值渲染為持久化的 `tool/result.content`，供結果卡片直接讀取。執行時期失敗變為 `CodeRunFailedError`；後端拒絕使用登錄檔的正常錯誤邊界。兩者都產生結構化的錯誤結果，且 `run_code` 結帳後不允許子呼叫追加。

**子呼叫上下文透過父呼叫延後。** 在 `run_code` 內部注入會破壞父呼叫/結果的相鄰性，因此 `ToolRunContext.deferContext()` 按分發順序收集每個子結果的 `additionalContexts` 條目。即使程序後來拋出例外，登錄檔仍攜帶該陣列；迴圈只在外層結果與步驟中所有兄弟結果之後追加每個條目。外層 post-execute 阻止會丟棄工具延後的條目，只暴露阻止 decision 顯式附加的上下文。

**並行是有界的，而非被序列化。** 每次 run 擁有一個分發佇列，嚴格按提交順序啟動呼叫，並透過 `registry.executionMode` 對每個呼叫分類——與原生迴圈所用的 fail-closed `isConcurrencySafe` 約定相同。連續的 parallel 類呼叫最多重疊 `maxParallelSubCalls` 個（默認 10；設為 `1` 復原序列分發）；exclusive 類呼叫會排空池並單獨執行。結帳時放棄尚未開始的排隊呼叫。本 note 交付的是被序列化的佔位實作；取代它的調度器由[即時平行 Agent Note](2026-07-26-code-mode-live-parallel-dispatch.md) 負責。

**呈現。** `run_code` 的 render intent 按[呈現意圖 Agent Note](../architecture/2026-07-02-tool-render-intent-union.md)在此決定：`presentCall` 建立一個 `generic` 卡片，`kind: 'execute'`，以程序文字作為標題，並將同一程序文字作為 `rawInput`；`run_code` 有意不聲明 `presentResult`，因此 TUI 和宿主/用戶端執行時期（Web）會透過通用原始內容回退機制，使用最終持久化的 `tool/result.content` 補全該卡片，其中包括捕獲的日誌，以及回傳值、失敗資訊或 post-policy spill 預覽。這不是 `terminal` 卡片：該卡片的語義是「工作目錄中的 shell 命令」，程序不是。參見[結果卡片完整性說明](../../archived/bug-fix/2026-07-20-code-mode-result-card-completeness.md)。

### 可觀測性：`tool/code-dispatch`

每次子分發在進入分發池時追加一個僅日誌的 `tool/code-dispatch-start` 事件，並以一個 `tool/code-dispatch` 結帳事件收尾，後者包含父子 call id、工具標識、規範化參數以及完整渲染後的 `content`/`isError` 結果。它不進入模型歷史，但可供持久化和 UI 使用。追加發生在開放的 `run_code` 輪次內。沒有 agent 的直接執行仍然執行，但無法記錄該事件。

### code-runtime seam

`packages/code-runtime/code-runtime/`——`@deepseek-ai/dsh-code-runtime`，僅相依性 `cordis`。一個抽象的 `CodeRuntime extends Service`（`super(ctx, 'codeRuntime')`）加上詞彙：

- `CodeRunRequest = { program: string; bindings: CodeBindingNamespace[]; signal?: AbortSignal }`
- `CodeBindingNamespace = { global: string; functions: Record<string, (args: unknown) => Promise<CodeJsonValue>>; errorClass?: { name: string; memberNameProperty: string } }`——執行時期將每個命名空間作為程序內部的全域性非同步函式對象暴露；選填描述符要求執行時期注入真正的、程序可見的 reject 類，而無需讓 seam 獲知消費端專用名稱。`CodeJsonValue` 是這個低相依性 seam 的結構化無損 JSON 類型，因此綁定參數與回傳值可以完整跨越實作的序列化邊界。
- `CodeRunResult = { value?: CodeJsonValue; logs: string[]; error?: CodeRunFailure }`——程序執行失敗時，執行 promise 仍會 fulfill，並透過 `error` 欄位返回失敗結果。只有呼叫方/seam 誤用（例如重複的綁定命名空間）時，`run()` 才會 reject；消費端仍在自己的錯誤邊界處理不合規後端的拒絕。
- `CodeRunFailure = { kind: 'exception' | 'timeout' | 'abort' | 'worker-exit' | 'invalid-output' | 'output-limit'; message: string }`——按[防禦性模式](../../../../docs/defensive-patterns.md)獨立報告的正交結果；逾時的 run 不是例外，abort 不是逾時，有損完成值不是溢位，基底退出也與上述情況相互獨立。
- 兩個只讀的後端描述符，僅供資訊參考而非閘門判定：`language`（程序必須使用的語言——首個後端為 `'typescript'`；Python 後端聲明 `'python'`，並在呈現側配對自己的 SDK 生成器）和 `isolation`（交付的後端為 `'worker-thread'`；未來可為 `'process'`、`'container'` 等）。`dsh-tools` 接受任何註冊了 SDK 渲染器與 `run_code` flavor 的 `language`（TypeScript 與 Python 已交付；見[語言分發 note](2026-07-31-code-mode-language-dispatch.md)），否則組裝會顯式失敗，與 `toolOrder` 違規時的設定錯誤慣用法相同（如 `mode` 為非 native 但根本沒有載入 `ctx.codeRuntime`）。

請求包含所有執行時期輸入；實作方擁有經校驗的逾時和上限預設值。登錄檔僅在組裝 Code Mode 時尋找選填的執行時期，因此 native 模式不相依性它。缺失或語言不相容的執行時期會顯式失敗。替代基底或語言可以在同一 seam 背後替換實作，配對相應的 SDK 生成器。

### worker-thread 執行時期

`@deepseek-ai/dsh-code-runtime-worker-thread`，`packages/code-runtime/` 組的第二個包。每次 `run()`：

1. **宿主側 type-strip**，使用 Node 內建的 `stripTypeScriptTypes`（`node:module`；在本倉庫的整個引擎範圍 `^22.19.0 || >=24.0.0` 內可用，且會保留原始碼位置，因此執行時期錯誤行號與模型原始碼一致）。僅剝離模式拒絕不可擦除的文法（`enum`、namespaces）——該拒絕以 `error.kind: 'exception'` 加 Node 的訊息返回，SDK 說明寫明「僅限可擦除 TypeScript」，模型像處理其他程序錯誤一樣自我修正。文法級失敗不會 spawn worker。
2. **每次 run spawn 一個全新 `Worker`**，來自包自身的 bootstrap 模組：`env: {}`（真正為空——比 spawn 命令的 scrubbed-env 規則更嚴格），`resourceLimits` 來自設定，`stdout`/`stderr` 捕獲到 `logs` 而非繼承。不做池化，不跨 run 保留狀態：程序的世界隨 worker 消亡，這使得 run 僅從日誌即可重建，狀態洩漏不可表達。
3. **在 bootstrap 中執行**：剝離後的程序成為一個 `AsyncFunction` 的函式體，其參數是綁定全域性變數、消費端聲明的 reject 類和一個捕獲式 `console` shim，因此頂層 `await` 和 `return` 可用。Code Mode 聲明 `ToolCallError`，成員屬性為 `toolName`；執行時期無需硬編碼工具即可實體化真正的構造函式。無損 JSON 完成值會精確跨越邊界；`undefined` 仍表示缺席，有損值產生 `invalid-output`，過大的外層結果產生 `output-limit`，而不會退化為檢查格式化後的字串替代品。
4. **透過訊息埠橋接綁定**：worker 中的每個綁定函式傳送 `{ id, global, name, args }` 並等待回覆；宿主根據請求的綁定校驗名稱、呼叫、並回覆 `{ id, ok, value }` 或 `{ id, ok: false, message }`（宿主側綁定拒絕變為程序側 rejection）。worker 側的命名空間對象透過 `defineProperty` 建置為 null-prototype，因此名為 `__proto__`、`constructor` 或 `toString` 的綁定是普通自有屬性，而非原型鏈碰撞。未知名稱、重複 id 和結帳後訊息被拒絕或忽略——埠協議假設對端是惡意的，因為對端執行的是模型程式碼。
5. **強制獨立預算。** `computeMs` 計量 worker 忙碌時間，允許慢速的 awaited 工具而不放過熱迴圈。`maxWallMs` 約束總經過時間，包括未解析的等待。`maxOutputBytes` 只約束序列化後的外層日誌、完成值或診斷的組合；中間綁定值沒有位元組數上限。到期、取消和完成都終止 worker，堆退出或外層溢位會作為顯式失敗報告。
6. **dispose（資源釋放）至完全靜止**：服務自身的 dispose 終止進行中的 worker 並*等待*其退出後再 resolve，遵循[防禦性模式](../../../../docs/defensive-patterns.md)。

### 信任姿態

worker 執行時期只能約束程序的執行，而不構成安全邊界：模型程式碼可以訪問 Node API，權限與 bash 工具相當。`worker.terminate()` 停止執行緒但不停止它 spawn 的 OS 行程。Code Mode 使用與 bash 相同的 `tools/pre-execute` 策略閘門，並額外提供空環境、堆限制、獨立 isolate 和對程序本身的硬終止。需要硬多租戶邊界的部署需要為程式碼和 bash 都使用容器級後端；執行時期的 isolation 描述符讓它們能區分該後端。

### 模型看到的內容

SDK 指示模型編寫一個所載入執行時期語言的非同步函式體（默認可擦除 TypeScript；Python 執行時期下為 Python `async` 函式體——見[語言分發 note](2026-07-31-code-mode-language-dispatch.md)），透過 `await tools.name(args)` 呼叫工具，在需要時捕獲被拒絕的工具呼叫，並僅 return 或 log 應重新進入上下文的輸出。兩種 flavor 用各自的原語陳述同一約定：相互獨立的只讀呼叫可以（MAY）在 `Promise.all`（TypeScript）或 `asyncio.gather`（Python）下重疊，有副作用的呼叫按提交順序單獨執行，有相依性的工作用 `await` 排序。聲明前綴可能與原生 schema 一樣大，尤其在 `'both'` 下，但對提供方快取保持穩定。

傳輸自身的 `description` 與兩種 flavor 的 SDK 說明都以點名 `code` 和 `description` 這兩個必填參數開頭。把該呼叫描述成「傳入一個程序」的散文會讓第二個參數只能從參數 schema 中發現，而只發出 `{code}` 的模型會因 `INVALID_ARGS` 被拒，連同已寫好的整個程序一起丟失。

## 後果

切換到 `'code'` 的部署必須更新任何僅限 native 的 `toolOrder`。組裝監聽器有責任維護任何被重寫的協議訊息的完整性。子分發在有界的重疊池下按提交順序啟動，而每次呼叫的上下文會透過外層結果保留其 source、信封與元資料。

## 測試

- **Worker 執行時期：** 真實 worker 測試覆蓋類型化的綁定值與失敗、每一種無損 JSON 根類型的完成值、無效和超限輸出、精確的組合帳本邊界、compute 和 wall 預算、惡意綁定流量、空環境以及 dispose 至完全靜止。一個建置後包測試在純 Node 下執行 worker 入口。
- **登錄檔整合：** 測試覆蓋程式碼生成、所有呈現模式、保留名稱和限制規則、scoped 可見性、權威組裝重寫、`toolOrder`、執行時期相容性失敗、完整管線子分發、parent-token 關聯、序列化、取消和佇列排空、JSON 規範化、錯誤傳播、日誌事件、成功與失敗程序中的有序上下文延後、外層阻止抑制以及 HMR（熱模組替換）清理。
- **帶金鑰 e2e：** 真實模型在一個程序中組合兩次 bash 呼叫；另一個模型透過 Code Mode fs 分發發現巢狀的工作區指令。測試驗證摺疊的請求標頭、關聯的分發事件、結果文件、延後上下文和模型行為。
- **快照：** `code-mode-turn`、`both-mode-turn` 和 `code-mode-workspace-context` fixture（測試前置資料）固定 SDK 文字、請求標頭工具清單、分發事件、延後上下文和結果卡片。

## 曾考慮的替代方案

**一個零核心改動的附加消費端外掛程式。** 否決，因為 `agent/request` 在[可重建請求](../architecture/2026-07-05-reconstructable-requests.md)下僅限 call-config，而變換已組裝的工具清單需要在不擁有其設定的情況下撤銷 `toolOrder` 規範化，並相依性監聽器順序。向模型提供哪些工具、以何種表示形式提供，是登錄檔的單一關注點：原生 schema 和 SDK 是同一個可見儲存的兩種投影。

**`node:vm` 作為參考執行時期，加固推遲。** 否決：`node:vm` 不是隔離（原型鏈逃逸可達宿主 realm）且無法中斷熱迴圈。worker 執行緒提供獨立 isolate、空環境、`resourceLimits` 和可靠的 `terminate()`，信任等級等同於 bash，因此參考實作和生產實作是同一個包，無需 unsafe-acknowledgement 儀式。

**在原生工具呼叫上做結果省略/摘要。** 僅解決問題中上下文膨脹這一半：裁剪舊 `tool-result` 作為可重建請求下的日誌化表面替換成本低，但仍需每次呼叫一次模型往返，且無法表達迴圈、分支或匯合。互補而非競爭；它可以在 Code Mode 下為殘餘的原生呼叫分層。

**迴圈中的平行原生分發。** 決策當時對往返成本的另一個答案；它被並行安全元資料阻塞，且無論如何都不提供組合能力——它平行化的是模型在一步中已經決定的呼叫。Code Mode 的佇列決策保持了兩者相容，兩者後來都已交付：元資料即 `isConcurrencySafe`（見[平行工具呼叫 note](2026-07-10-parallel-tool-call-execution.md)），原生 rolling-pool 分發加每工具綁定平行化則基於同一個分類器。

**始終排他（忠於 Cloudflare，無模式）。** 否決，因為本 SDK 的主要消費端是編碼 agent：其日常的單次呼叫（`bash`、`read`、`edit`）作為原生呼叫已經是最優的，強制每次編輯都透過程序會給常見場景增加負擔。mode 設定讓忠實形式（`'code'`）只需一行設定即可啟用，而不強加於人。

**每工具可見性分層（此工具 native，彼工具 code-only）。** 推遲：它需要每工具元資料和 `'native' | 'code' | 'both'` 不提供的呈現拆分，且其設計取決於模型在 `'both'` 下如何分配使用的證據。

**SDK 中的清潔化識別符號別名**（`my-tool` → `my_tool`，Cloudflare 的做法）。否決：`declare const` 上的帶引號鍵使每個名稱可達，零別名碰撞邏輯；模型能正常處理 `tools["my-tool"](…)`。

**REPL 風格的持久核心**（狀態跨 `run_code` 呼叫存活）。在 MVP 中否決：跨呼叫狀態對工作階段日誌不可見，破壞了「每個請求是日誌的純函式」這一可重建性保證；每次 run 均使用全新實例則維持了這一保證。核心風格的後端在未來仍可透過同一 seam 表達，配合自己的日誌方案。

## 風險

**Worker 不是硬安全邊界。** 有意為之且已文件化（§信任姿態）：姿態等同於既有的 bash 工具，約束能力強於它，閘門使用相同的審批與沙盒策略。需要更強隔離的部署需要未來的 `isolation: 'container'` 後端——作為 seam 設計中預留的擴充進行跟蹤，而非本設計的 TODO。

**`stripTypeScriptTypes` 標記為 experimental。** 它與 Node 自身原生 `.ts` 執行背後的引擎（amaro/swc）相同，在本倉庫的整個引擎範圍內作為 API 暴露。緩解措施：執行時期的單元測試套件會檢查位置保持和可擦除限制拒絕訊息中的必需部分；呼叫位於一個私有函式之後，且 `amaro`/`sucrase` 可在 API 變化時直接替換它。僅可擦除子集是面向模型的輸入限制，錯誤訊息會告訴模型如何修正程序。

**SDK 的提示詞成本，尤其在 `'both'` 下。** `.d.ts` 可能與它補充的原生 schema 體量相當；`'both'` 攜帶兩種表示。前綴穩定性 + 提供方快取攤銷了每工作階段成本；mode 按部署設定；本 Agent Note 不做無條件節省的聲明。何時優先使用哪種模式的量化指導明確屬於上線後學習。

**登錄檔 scope 成長。** `dsh-tools` 吸收了程式碼生成、一個工具、一個橋和一個事件。包內模組把這些職責分開（`ts-types.ts`、`code-mode.ts` 與 `schema.ts`、`json-schema.ts`、`presentation.ts` 並列），所有 code-runtime 專用實作都由 `ctx.codeRuntime` 提供。

**大型無損 JSON 值可能耗盡記憶體。** 工具綁定會在分發前對無損 JSON 建立快照，並完整返回規範 JSON 回傳值。執行時期會校驗 worker 埠兩側，但不對單次綁定設定位元組數上限；結構化克隆成本以及行程或 worker 記憶體構成實際邊界。只有包含日誌、完成值和失敗診斷的組合外層輸出帳本受位元組數上限約束。

**子分發的重疊由工具自身的安全聲明限定，而非由呼叫方決定。** 程序裡的 `Promise.all` 或 `asyncio.gather` 只在工具自己分類為並行安全的呼叫之間換來掛鐘平行性；一串 exclusive 呼叫仍要按順序付出各自的往返開銷，模型可能過度期望。兩種 flavor 的 SDK 說明都陳述了真實約定。本 note 交付的是使該風險絕對化的序列化佔位實作；調度器及其重疊上限由[即時平行 Agent Note](2026-07-26-code-mode-live-parallel-dispatch.md) 負責。

**預算計量讀取事件迴圈，而非 flag。** 忙碌時間輪詢（`eventLoopUtilization()`）比精確 CPU 計量更粗糙——預算到期最多延遲一個輪詢間隔——且其正確性聲明（「pending 的分發不能暫停它」）是抵禦惡意程序的關鍵。兩種情況均有單元測試（帶 pending 誘餌分發的熱迴圈會在耗盡 `computeMs` 預算時終止；等待慢速綁定的空閒程序則會持續執行至 `maxWallMs`），輪詢間隔是內部常數而非設定——部署無法將其誤調為繞過手段。`maxWallMs` 是設定項，且會傳入 `setTimeout`，後者會把超過 `MAX_TIMER_DELAY_MS`（2^31-1 ms）的延遲夾到 1 ms；因此僅有正數校驗會放行一個 25 天的上限，它在第一個 tick 就到期，使每次執行都逾時。worker 執行時期正因如此在載入時對該欄位做範圍校驗。`computeMs` 不需要上界，因為它對照的是實測佔用率，而不是交給定時器。
