# Agent Note: 逐提供方請求重試策略

Status: implemented

[English](2026-07-24-provider-retry-policies.md) | [简体中文](2026-07-24-provider-retry-policies.zh.md) | 繁體中文

## 問題

同一行程可能把模型請求路由到可靠性和成本約束各不相同的提供方。單一的瞬態錯誤分類器與有限重試預算無法表達這種部署需求：大多數提供方只需有界復原，但其中一個提供方必須持續重試每次模型請求失敗，直到請求成功或呼叫方取消。

提供方策略必須跟隨實際失敗的請求，包括 `agent/request` 選擇的路由，而不能跟隨 agent（代理）的初始選項。無界策略也不能把 JavaScript `Infinity` 存入持久工作階段事件；提供方錯誤文字與丟棄的部分輸出都不得進入下一次模型請求。

## 決策

每個具體配接器都在其提供方設定中接受選填的 `retryPolicy`。配接器負責校驗並解析策略，`ctx.llm` 則在該特定提供方路由註冊時捕獲策略。當呼叫進入最終配接器邊界時，`ctx.llm` 會把實際提供服務的註冊項所持不可變策略綁定到該呼叫；即使路由在請求進行期間被 dispose（資源釋放）或替換，agent loop（代理循環）仍會把該策略傳給已關閉步驟復原。`@deepseek-ai/dsh-llm-retry` 會把綁定到該呼叫的策略與失敗步驟的持久化提供方標識結合起來。未到達最終配接器的呼叫沒有實際提供服務的策略，因而會委託後續處理。未設定 `retryPolicy` 的提供方使用 normal 預設值。

```yaml
providers:
  - provider: deepseek
    retryPolicy:
      mode: normal
      maxRetries: 2
      retryableCodes: [EMPTY_RESPONSE, RATE_LIMIT, SERVER, TIMEOUT, TRANSPORT]
      backoff:
        initialDelayMs: 500
        maxDelayMs: 10000
        jitterRatio: 0.1
  - provider: internal
    retryPolicy:
      mode: always
      backoff:
        initialDelayMs: 1000
        maxDelayMs: 30000
        jitterRatio: 0.2
```

監聽器從失敗步驟關閉時生效的持久化 `request/header` 讀取提供方，後續復原產生的改動不參與選擇，但絕不會從可變的提供方登錄檔重新解析策略。它會根據已解析的實際服務策略的所有欄位生成規範鍵；由於是否可重試是按集合成員關係判斷的，生成時會對 `retryableCodes` 排序。重試歷史只會對同一提供方和同一規範鍵延續。因此，即使模式未變，只要路由替換後的次數上限、錯誤程式碼成員或退避不同，重試計數與初始延遲都會重新開始。normal 模式保留有界瞬態錯誤處理行為：它重試設定的錯誤程式碼，次數不超過 `maxRetries`；其他情況委託後續處理。

always 模式先請求下游復原，使上下文溢位壓縮（compaction）之類的專用策略有機會取得進展。下游若決定重試，則以該決定為準。下游若決定失敗或復原過程拋出錯誤，則回退為無界重試同一提供方請求；拋出的錯誤會寫入日誌。重試監聽器會持有並排空已委託的復原，輪次取消或外掛程式 dispose 只能在其結束後完成；隨後監聽器會執行相應的中止操作，而不會採用遲到的下游決定。成功、輪次取消和外掛程式 dispose 是僅有的終止路徑。

兩種模式的本機延遲都按指數成長，從 `initialDelayMs` 增至 `maxDelayMs`。`jitterRatio` 用 `[1 - jitterRatio, 1 + jitterRatio]` 區間內的均勻隨機樣本乘以每次目標值，再應用上限。提供方給出的正數 `Retry-After` 若未超過上限，則保持精確且不加抖動。若提供方延遲超過上限，normal 模式會委託後續處理；always 模式則改用設定的本機退避，以維持無限重試保證。

每次安排重試都會追加一條不進入表層的 `llm/retry` 事件，其中包含失敗的提供方、策略模式、已解析策略的規範鍵、提供方策略內的重試編號、延遲和失敗事實。normal 事件包含有限的 `maxRetries`；always 事件省略該欄位，UI 將上限渲染為 `∞`。該事件與失敗的 `assistant/chunk` 記錄都不會生成表層訊息，因此除非其他復原策略有意改變表層，否則下一次請求包含的派生上下文與失敗請求相同。

## 曾考慮的替代方案

**單一全域性 `always` 開關**：不予採納，因為它無法把無界成本與延遲風險限制在確有需要的提供方，還可能在執行時期重新路由後悄然生效。

**在 `dsh-llm-retry` 上維護單獨的指定提供方清單**：不予採納，因為它會在所屬配接器設定之外重複提供方路由名稱，並讓提供方註冊與復原策略發生偏差。

**設定很大的有限重試次數**：不予採納，因為它最終仍會違反持續重試的約定，並把任意選取的運維上限序列化成看似有意義的數值。

**使用提供方 SDK 重試**：不予採納，因為隱藏嘗試會疊加 agent 層預算，無法利用已關閉步驟的持久性邊界，還可能在沒有可重建重試記錄的情況下拼接或丟棄流式輸出。

**把錯誤放入模型上下文**：不予採納，因為傳輸或提供方診斷資訊屬於運維狀態，而非對話內容。它可能暴露敏感的提供方細節，並會改變重試請求，無法重複原本失敗的請求。

## 驗證

配接器測試會在提供方載入時校驗巢狀策略，證明註冊流程會捕獲已設定策略和默認策略，並證明請求進行期間替換路由後仍會保留實際提供服務的策略。單元測試根據失敗請求實際使用的註冊項選擇策略、分離不同提供方和策略變更後的重試歷史、驗證 always 模式可越過 normal 預算、固定抖動和延遲上限、證明下游復原順序、證明取消與 dispose 會先排空已委託的復原再達到完全靜止，並證明二者都會停止正在進行的退避等待。請求級覆蓋會比較失敗嘗試與重試嘗試的完整訊息，並排除提供方錯誤文字和丟棄的部分輸出。一個無金鑰 headless `stream-json` 快照會透過組裝後的應用執行失敗、重試與成功流程，固定完整的 `llm/retry` 記錄，並拒絕各次嘗試之間出現任何模型訊息變化。JSONL 與 SQLite 測試會往返讀寫不含 `Infinity` 的 always 事件；不變式測試會將提供方標識綁定到請求標頭、校驗失敗事實和各模式的計時器邊界，並將重試編號綁定到提供方策略鍵；TUI 測試會渲染有限和無限上限。

## 後果

normal 模式仍是有限的默認策略；顯式的 always 策略可能在永久性的身分驗證、配額、無效請求、協議或上下文錯誤上耗費無限次請求和無限時間。運維方必須為 always 模式配備可取消的呼叫方和針對提供方的成本控制。重試狀態保持可觀察且會持久化，但不會對模型可見；捕獲實際提供服務的註冊項，也能防止配接器生命週期變化反過來改變進行中請求的復原約定。

本決策擴充了[瞬態 LLM（大型語言模型）請求失敗的有界復原](../architecture/2026-06-21-bounded-llm-request-recovery.md)中確定的已關閉步驟復原、單次可見配接器嘗試、結構化失敗與持久化狀態設計。
