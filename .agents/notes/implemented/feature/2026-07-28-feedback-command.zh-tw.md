# Agent Note: `/feedback` 命令

Status: implemented

[English](2026-07-28-feedback-command.md) | [简体中文](2026-07-28-feedback-command.zh.md) | 繁體中文

## 問題

使用者在工作階段中途發現問題時，沒有地方記下這個觀察。告訴模型會浪費一個輪次、改變使用者原本進行的對話，並把這條評論埋進派生歷史，使後續讀者無法找到它。寫到工作階段之外則會丟失讓它有意義的上下文：屬於哪個工作階段、處於哪個時點、針對哪項工作。

採集介面必須能在使用者產生不滿的那一刻使用，因此任何需要使用者離開互動式用戶端的方案都不可行；它還不能擾動正在進行的執行：不消耗模型 token、不產生工作輪次、不改變使用者正在等待的請求。

## 決策

位於 `packages/feedback/command-feedback/` 的 `@deepseek-ai/dsh-command-feedback` 透過 `ctx.commands` 註冊一個全域性 `feedback` 命令。`/feedback <text>` 在確認文字中包含接收回饋的工作階段 id 與 harness home 的共享匿名使用者 id；空輸入或僅含空白的輸入返回直接用法錯誤。處理器是同步的，只注入 `commands`，且沒有任何設定。[共享 id 決策](../architecture/2026-08-07-shared-feedback-telemetry-user-id.md)說明瞭回饋與 OpenTelemetry 為何使用同一個 `$DSH_HOME/.anonymous-user-id` 值。

本包聲明僅寫入日誌的 `feedback/record { text }` 工作階段事件，並匯出 `recordFeedback(session, text)`，作為不相依性命令的生產方。該生產方丟棄前後空白，拒絕空結果，並且恰好追加一個事件。`/feedback` 委託給它，因此其他 UI、掛鉤或 host 整合無需構造斜槓命令也能記錄同一個領域事實。

`dsh-commands` 仍會圍繞 `/feedback` 寫入 `command/run` / `command/done` 生命週期配對，但該命令設定了 `recordInput: false`。因此，它的 `command/run` 攜帶命令標識與來源，但不攜帶 `args`；回饋文字只存在於 `feedback/record` 中，而 `command/done` 攜帶確認結果。三個記錄都僅寫入日誌且非 surface。它們的追加會進入持久化的常規有界寫入路徑；沒有任何環節強制 flush，因此確認文字報告的是回饋已進入日誌，而非已經落盤。

採集對正在執行的 agent（代理）與模型仍不產生後續動作。選填的 OTel 遙測包後續增加了一個基礎設施消費端：它在 `FEEDBACK_ONLY` 模式下將 `feedback/record` 作為釋放觸發器，在 `DISABLED` 模式下將其作為僅限本機的警告觸發器，且不改變回饋事件或命令路徑。見[回饋門控的工作階段遙測](2026-08-05-feedback-gated-session-telemetry.md)與[確認文字中的共享披露](2026-08-07-feedback-acknowledgement-sharing-disclosure.md)。

### 為何回饋擁有自己的事件

回饋是領域事實，而 `/feedback` 是一種觸發方式。只把載荷保存在 `feedback/record` 中，既讓後續觸發方式可以使用同一個事件，也讓消費端無需相依性命令名或解析命令生命週期記錄即可篩選回饋。在該定義中省略 `command/run.args`，可避免同一條人類評價出現兩個看起來都具有權威性的副本。

### 為何模型永不看到它

回饋是關於工作階段的，而不是工作階段的輸入。將其作為 user 訊息注入會改變下一次模型請求，與「記錄不得擾動執行」的要求相衝突，也會讓該評論成為它所評論的那段對話的一部分。`command/run` 與 `command/done` 不屬於 `SurfaceEventType`，因此即便出錯也無法獲得 `surfaceOp` 或進入派生歷史。

### 原樣文字

前後空白會被丟棄，但除此之外不做解析。`/feedback /plan felt slow` 記錄 `/plan felt slow`；開頭的 `/plan` 是內容，而非巢狀命令。若採用 `/goal` 那樣的控制詞文法，對應的字面回饋將無法表達，這與採集介面的目的正好相反。

### 一個新的分組

`packages/feedback/` 是新分組，因為現有分組都不擁有此職責：`goal/` 負責目標狀態，`session-title/` 負責標題，`core/` 是產品主幹。該分組只包含一個生產方包；跨領域的消費端留在各自所屬的分組，而不是迫使這個分組不斷膨脹。

## 考慮過的替代方案

**使用 `command/run` 作為回饋記錄。** 已否決，因為這會將回饋與一種觸發方式耦合，消費端還必須透過命令名識別領域事實。非命令生產方若不偽裝成執行命令，就無法建立相同記錄。

**同時在 `feedback/record` 與 `command/run.args` 中儲存文字。** 已否決，因為同一行為會產生兩個沒有實質區別的載荷副本。`recordInput: false` 保留通用生命週期，同時讓領域事件保持權威性。

**透過 `agent.inject()` 將回饋作為 user 訊息注入。** 無需新增事件類型，並複用 `/goal` 變更所走的路徑。已否決：它會讓回饋對模型可見，從而進入下一次請求、改變正被評論的那次執行並消耗 token——與「不得擾動」要求的三個方面全部衝突。

**讓 `/feedback` 成為真正的空操作，什麼都不記錄。** 這是對「什麼都不做」最字面的理解。已否決：這會使命令失去意義——明確的要求是讓這條評論進入工作階段日誌。

**在現有包中註冊該命令**，例如 `packages/interaction/commands`。可省去新分組及其雙語 README。已否決：`ctx.commands` 是登錄檔，而不是任意命令實作的歸屬地；且請求者明確要求獨立的包。

**從文字中解析結構**（類別前綴、嚴重程度標記）。已否決，屬於投機設計：沒有消費端需要該結構，而任何控制詞文法都會讓對應的字面回饋無法記錄。原樣文字是未來消費端可以收窄的最寬介面；而已被解析的介面無法事後放寬。

**改為提供面向模型的工具。** 已否決：回饋是人類的直接觀察。經由模型會消耗一個輪次、讓模型改寫使用者的原話，並使記錄取決於模型是否選擇呼叫該工具。

## 後果

隨附的 `dsh` 基礎組合無條件掛載該命令：沒有設定，也不相依性 goal 棧。Web 用戶端透過命令配接器暴露該命令。無頭模式、ACP（Agent Client Protocol）和 JSON-RPC 不提供命令配接器，因此 `/feedback` 在那裡不可用。對於某個 harness home，首次接受回饋時可能建立 `$DSH_HOME/.anonymous-user-id`；被拒絕的空輸入不會取得或建立 id。

本包擁有一個獨立的僅附加事件，不存在跨事件關係或可變資料關係可供不變式伴生外掛程式檢查。該事件遵循工作階段日誌現有的重播、fork、持久化和崩潰尾部行為。

延期事項：沒有產品或模型消費端；沒有結構化欄位；不支持修改或撤回，因為日誌僅附加且本包不新增 tombstone；且沒有顯式持久化屏障，因此緊臨崩潰前記錄的條目可能與其他未 flush 的尾部一同丟失。選填的遙測消費端只將該事件作為匯出策略觸發器。

本次變更按請求者的明確指示不附帶無金鑰 transcript（文字記錄）快照。包測試、基於 `cordis.yml` 的真實 Loader 組合測試，以及隨附的 Web 組合測試覆蓋註冊、採集、模型排除和產品組裝。
