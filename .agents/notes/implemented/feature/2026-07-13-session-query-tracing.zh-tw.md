# Agent Note: 工作階段查詢關係追蹤

Status: implemented

[English](2026-07-13-session-query-tracing.md) | [简体中文](2026-07-13-session-query-tracing.zh.md) | 繁體中文

## 問題

工作階段關係分散編碼在不可變 header、位置式表面操作和已記錄的來源事件 seq 引用陣列中。消費端如果直接重建這些關係，就必須重複實作語料優先級、表面摺疊、格式錯誤日誌的處理、確定性的譜系順序和克隆。位置替換關係與來源事件引用關係表示不同含義，因此把兩者合併為一種通用邊類型也會丟失含義。

## 決策

`ctx.sessionQuery` 除精確讀取外，還公開 `traceSession(sessionId)` 和 `traceEvent({ sessionId, seq })`。兩者都是基於現有「即時資料優先」語料的一次性檢視表：工作階段追蹤讀取一次完整語料清單，事件追蹤讀取一份邏輯日誌並執行一次規範表面摺疊。服務在呼叫結束後不會保留譜系、反向索引或替換狀態。

`SessionLineageTrace` 返回目標、按從直接父級到外層父級排序的已知父級，以及遞迴的後代樹；同級節點先按建立時間排序，再按 session id 排序。`complete: true` 會攜帶已知根節點；`complete: false` 會攜帶第一個無法解析的父級 id。與目標相連的環會以 `SESSION_QUERY_INVALID_LINEAGE` 失敗。

`SessionEventTrace` 將位置替換與來源事件引用關係分開保留。`replacedBy` 是直接的位置替換者，`replacementChain` 沿替換者追蹤至最終節點，`replacedEventSeqs` 則列出目標直接移除的真實表面節點。`sourceEventSeqs` 保留日誌中直接來源的順序，而 `derivedEventSeqs` 按日誌順序列出後續的直接反向引用。查詢不會沿被引用的來源事件繼續向上追蹤。

## 校驗邊界

事件追蹤會在分析表面之前檢查目標是否存在。隨後，事件清單與追蹤都會使用 `dsh-session` 的單遍表面摺疊，對載入的日誌整體進行接受或拒絕：事件 seq 從零開始且連續；表面標記符合事件類型的適用範圍；只有表面事件類型可以引用來源事件 seq；存在的陣列必須非空且沒有重複項；每個來源必須是更早的 seq；每次位置替換必須指明並引用它所移除的全部表面節點。任何約定違例都使用 `SESSION_QUERY_INVALID_SURFACE`；系統不存在只用於分類、要求更弱的表面標準。

所有返回的記錄與陣列都與內部狀態分離。已知的即時事件追蹤絕不查詢持久化；來自持久化資料的事件追蹤保留精確讀取所要求的清單／載入一致性檢查。工作階段譜系必然屬於跨語料操作，因此也保留跨語料的持久化失敗語義。

## 考慮過的替代方案

- **公開獨立的追蹤輔助函式**：不予採納，因為源優先級與狀態分離邊界屬於 `ctx.sessionQuery`；公開輔助函式會誘使呼叫方繞過該邊界。
- **合併替換邊與來源事件引用邊**：不予採納，因為位置替換可以遮蔽表面節點，同時引用不在表面上的構造輸入，而消費端需要區分這兩種含義。
- **返回所有傳遞引用的來源事件**：不予採納，因為這會掩蓋日誌中直接記錄的證據、增大結果，並讓一條遙遠的格式錯誤邊改變原本區域性的輸出。
- **對格式錯誤的來源事件清單返回盡力而為的追蹤結果**：不予採納，因為結構上看似合理的區域性結果會顯得具有權威性。當規範的關係約定損壞時，精確檢查會明確報錯。

## 後果

消費端無需快取或引入第二份語料，即可獲得確定性的關係檢視表。事件追蹤每次呼叫都會執行全日誌校驗和分配，而譜系追蹤每次呼叫都會列出完整的邏輯語料。這些成本讓真源保持明確，並且與承載內容的全文搜尋及過濾 API 相互獨立。

該功能具備單元測試和服務層測試覆蓋，但沒有快照或端到端 fixture（測試前置資料），因為它沒有引入面向模型的消費端、transcript（文字記錄）變更或跨行程協議。
