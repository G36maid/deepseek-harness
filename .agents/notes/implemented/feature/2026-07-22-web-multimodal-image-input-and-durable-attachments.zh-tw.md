# Agent Note: Web 多模態圖片輸入與持久附件

Status: implemented

[English](2026-07-22-web-multimodal-image-input-and-durable-attachments.md) | [简体中文](2026-07-22-web-multimodal-image-input-and-durable-attachments.zh.md) | 繁體中文

## 問題

在此變更之前，Web 輸入區僅接受文字：`InputBar` 接收字串草稿，`ConversationController.send()` 建立文字內容，宿主再把該內容轉發給 agent（代理）。使用者無法貼上圖片、在傳送前查看圖片、提交僅含圖片的提示詞，也無法從歷史記錄中復原已傳送圖片。

這不只是輸入區功能缺失。核心層需要持久圖片內容區塊，提供方需要明確處理模態，工作階段日誌則必須重建模型可見的全部內容。[此前移除圖片塊的決策](../../implemented/simplification/2026-07-04-drop-image-content-block.md)否決了可能靜默丟失圖片或將其展平的不完整設計。瀏覽器對象 URL、本機路徑、提供方 URL 或 base64 資料都不能成為規範工作階段內容。

[Web 用戶端架構](../../implemented/architecture/2026-07-19-gui-web-client-architecture.md)要求元件保持純粹，並將每個工作階段的輸入區狀態放在 `ctx.conversation` 中；[GUI 分層與 RPC 協議](../../implemented/architecture/2026-07-19-gui-layering-and-rpc-protocol.md)則要求持久事件成為即時渲染與歷史重播的共同真源。因此，圖片接收、持久化、提供方轉換和渲染需要遵循同一個明確的生命週期。

同類產品普遍在編輯器上方設定附件欄，但儲存方案各不相同。諸如 `/var/folders/.../codex-clipboard-*.png` 的 Codex 式路徑適合作為接收輸入時的暫存位置，卻不能作為持久訊息身份：作業系統可能刪除檔案，另一臺宿主無法讀取文件，復原後的工作階段也不能相依性文件仍然存在。

## 決策

貼上或拖放的光柵圖片是 Web 輸入區對持久附件能力的首個應用場景。未傳送文件仍是由用戶端持有的臨時草稿狀態。宿主在追加相應訊息事件前，校驗並持久提交每張已接受的使用者圖片。生成結構化圖片輸出的提供方配接器在追加相應助手塊前，也必須持久提交輸出。規範使用者內容與助手內容只包含角色無關的 `ImageBlock` 引用。

第一版支持貼上和拖放 PNG、JPEG、WebP 與 GIF，支持僅圖片或混合提示詞，支持渲染歷史使用者圖片與助手圖片，並支持單擊預覽原圖（展示與互動細節部分由[附件展示對齊 Note](2026-08-11-web-attachment-display-alignment.md)取代）。文件選擇、通用文件、PDF、音訊、影片、圖片複製和自訂上下文選單仍分別作為後續工作。

### 產品行為

- 貼上或拖放一張或多張受支持的圖片後，文字方塊上方會按順序顯示縮略圖，但不會插入佔位文字。文件拖入輸入區時會高亮放置目標。
- 同一個常駐 `InputBar` 會在空白工作階段 Hero 和活躍工作階段版面配置中渲染附件欄。附件欄為空時隱藏，透過橫向滾動避免撐寬輸入區。
- 每個縮略圖為 64 × 64 畫素，移除按鈕位於卡片內部、懸停時顯示；單擊打開草稿原圖，溢位用兩端箭頭翻頁而非可見捲軸。
- 提示詞可同時包含文字與圖片，也可僅包含圖片。貼上純文字時保持瀏覽器原生行為；貼上混合的剪貼簿內容時，文字會正常插入，文件則同時新增到附件欄；僅貼上文件時才阻止瀏覽器的默認處理。在輸入區放置文件時總會阻止瀏覽器導覽，並在本機報告不受支持的文件。
- 傳送失敗時復原完整的文字與圖片草稿，但不會覆蓋請求飛行期間新增的文字或圖片。移除、傳送成功、工作階段 scope 釋放、已渲染歷史記錄釋放和應用釋放都會撤銷各自持有的對象 URL。
- 歷史使用者圖片與助手圖片共用一個 `MessageImage` 控制元件。行內圖片保持固有寬高比、不放大，並限制在 240 × 240 畫素的邊界框內。
- 單擊訊息圖片會在不超出視口的模態對話框中打開儲存的原圖。按 Escape、啟用關閉控制元件或啟用背景區域都會關閉模態對話框並復原焦點。
- 第一版不覆蓋瀏覽器上下文選單，也不提供明確的圖片複製操作。

### 儲存生命週期與歸屬

持久化邊界是訊息被接受，而不是圖片被貼上：

| 狀態 | 允許的表示 | 持久性與順序 |
| --- | --- | --- |
| 未傳送的使用者草稿 | 瀏覽器 `File` 加對象 URL；原生用戶端可以使用 `/var/...` 等作業系統暫存檔 | 臨時且由用戶端持有。它可能在重載或行程退出後消失，絕不出現在工作階段事件中。 |
| 已接受的使用者圖片 | `DSH_HOME` 下的不可變對象加 `ImageAttachmentRef` | 在 `agent.send()` 或 `agent.steer()` 能夠追加所屬使用者事件前，宿主提交每張圖片。 |
| 結構化模型圖片輸出 | `DSH_HOME` 下的不可變對象加 `ImageAttachmentRef` | 提供方配接器在寄出已完成的圖片塊或助手訊息事件前提交位元組。事件中禁止出現臨時 URL、路徑和 base64。 |

每個工作階段的 `InputMachine` 狀態在即時草稿旁保存僅限執行時期的有序附件識別符號。框架持有的 chat store 只接收草稿的純文字持久化映像檔，`ConversationController` 則持有相應的瀏覽器專用 `File` 與對象 URL 登錄檔：

```ts
import type { Branded } from '@deepseek-ai/dsh-brand'

type DraftAttachmentId = Branded<'DraftAttachmentId'>

interface ChatStoreState {
  selection: object | null
  draft: string
  view: string | null
}

interface InputState {
  draft: string
  imageIds: readonly DraftAttachmentId[]
}

interface ComposerAttachment {
  kind: 'image'
  id: DraftAttachmentId
  file: File
  previewUrl: string
}
```

這一拆分把工作階段 provide 通道的輸入 hook 與 actions 用作即時輸入區狀態的唯一訂閱路徑，同時避免把不可序列化的瀏覽器對象寫進持久 JSON。只有純文字草稿映像檔使用 `localStorage`；附件識別符號、瀏覽器 `File` 對象和對象 URL 都限定在即時工作階段輸入外殼的 scope 內。未傳送圖片因此無法跨重載或工作階段 scope 釋放保留。切換 Workspace 時，只有目標外殼接受完整圖片批次，圖文混合草稿才會移動；拒絕時，文字和圖片都留在來源外殼。原生用戶端可以在作業系統臨時目錄中暫存輸入，但必須像對待瀏覽器對象 URL 一樣對待該路徑：不再需要時刪除，並在訊息被接受前把位元組複製進持久儲存。

本機附件後端依次解析顯式 `dshHome`、`$DSH_HOME` 和 `~/.dsh`。它把內容尋址物件儲存在 `$DSH_HOME/attachments/v1/objects/<prefix>/<sha256>` 下，並為目錄和文件設定僅所有者可訪問的權限。每個行程首次為某個 home 保存對象時，都會建立該 home，並逐級同步每個祖先目錄項直至檔案系統根目錄；不能把存在視為持久性，因為另一個行程可能仍處於 `mkdir` 與父目錄 `fsync` 之間。隨後，服務寫入並同步暫存檔，再以原子方式發布，並對發布路徑執行目錄同步使其持久（POSIX；Windows 相依性檔案系統元資料日誌），之後才返回引用。內容摘要編碼在不透明的 `sha256:<digest>` 識別符號中。寫入准入與讀取都會完整解碼受支持的光柵圖片，之後才接受其格式和尺寸；每次讀取還會校驗摘要、位元組長度和已記錄的元資料。

第一版不對儲存執行自動刪除。已傳送的使用者圖片和模型生成圖片會一直保留，以供歷史記錄、復原和 fork 使用。按引用感知的垃圾回收需要單獨設計，因為僅按時間清理可能刪除仍被持久工作階段引用的資料。部署的位元組和畫素限制是寫入時的准入策略；讀取時會校驗摘要和已記錄的元資料，但不重新應用當前准入限制，因此收緊策略不會導致舊歷史記錄失效。

### 持久內容與提示詞協議

附件 seam公開不可變圖片寫入和經過校驗的讀取操作。規範元資料刻意比通用文件記錄更窄：

```ts
import type { Branded } from '@deepseek-ai/dsh-brand'

type AttachmentId = Branded<'AttachmentId'>

interface ImageAttachmentRef {
  attachmentId: AttachmentId
  mediaType: 'image/png' | 'image/jpeg' | 'image/webp' | 'image/gif'
  bytes: number
  width: number
  height: number
  name?: string
}

interface ImageBlock {
  type: 'image'
  attachment: ImageAttachmentRef
}
```

`ImageBlock` 加入可合併擴充的核心 `ContentBlockMap`，在使用者內容和助手內容中都有效。它絕不攜帶 base64、對象 URL、檔案系統路徑或提供方持有的定位符。因此，工作階段事件與不可變物件儲存足以共同重建模型可見的確切圖片。LLM 詞彙由此僅在類型層面相依性附件 seam；提供方執行時期相依性仍由各配接器持有。

瀏覽器無法生成持久引用，因此 `session.prompt` 接受範圍狹窄的接收聯合類型，而不是規範 `ContentBlock[]`：

```ts
export {}

type PromptInputPart =
  | { type: 'text'; text: string }
  | {
      type: 'image'
      mediaType: 'image/png' | 'image/jpeg' | 'image/webp' | 'image/gif'
      data: string
      name?: string
    }
```

Base64 只跨越一次 JSON-RPC，並在持久化後丟棄。宿主會校驗規範 base64、圖片數量、總位元組數、單張圖片位元組數、聲明的 MIME 與完整解碼後的光柵圖片是否一致、固有尺寸和解碼畫素數。它會在保存任何成員之前，等待seam 上不觸碰儲存的 `validateImage` 完成對每個批次成員的校驗，因此一張畸形圖片不會把批次中的有效成員留成無引用對象。隨後按提交順序執行儲存提交，以限制完整光柵解碼器的記憶體佔用。如果後續儲存 I/O 操作失敗，宿主不會追加使用者事件，但先前的不可變內容尋址對象可能保持無引用狀態；第一版將清理留給未來按引用感知的垃圾回收，而不向去重儲存新增破壞性回滾。只有每張圖片都成功後，宿主才會用規範化文字和按提交順序排列的持久圖片塊呼叫 agent。失敗時不公開任何附件路徑或原始位元組。

`session.attachment` 是隻讀且限定於工作階段作用域的端點。只有該工作階段中的持久事件引用了所請求的附件識別符號，宿主才提供位元組。工作階段處於渲染狀態時，用戶端會按工作階段和附件識別符號對載入操作去重；已渲染工作階段釋放時會撤銷已解析的 URL，並在分配對象 URL 前拒絕已失效的延遲載入，以免已解除安裝的工作階段或已釋放的服務重新寫入快取。

### 模型能力與提供方行為

模型目錄項增加選填且可合併擴充的輸入模態聲明。缺少聲明表示未知；聲明存在但不含 `image`，則明確表示不支持圖片。

宿主是權威的前置檢查邊界。它會解析工作階段最新路由到的提供方和模型，並在缺失時依次回退到 agent 選項和宿主預設值；如果該模型明確排除圖片輸入，宿主會在寫入任何附件或事件前拒絕提示詞，用戶端則復原草稿。包含圖片的提示詞准入與模型選擇共用一個逐 agent 的序列邊界，而且已經出隊的提示詞在其持久訊息事件發布前仍保持待發布狀態（[順序決策](../bug-fix/2026-07-29-atomic-web-image-admission.md)）；steering 載體則從入隊起就參與門檻，直到其 `steering/message` 事件發布為止，堵住了從不進入排隊映像檔的 outbox 視窗。當圖片正等待發布或仍存在於工作階段當前的派生歷史中時，模型選擇會拒絕純文字目標。壓縮（compaction）可以移除舊圖片，使之後選擇純文字目標變得有效；未發布任何事件即轉入空閒時，已認領的 queued 載體會被釋放，而保留在 outbox 中的 steering 在發布或丟棄前始終受門檻約束。`session.updateQueue` 的編輯只接受文字內容，因此佇列編輯無法繞過該准入邊界注入圖片。能力未知時繼續進入配接器強制檢查，使未收錄的模型識別符號仍然可用。瀏覽器會在分配預覽 URL 前拒絕聲明不支持的圖片媒體類型，但不會為部署限制或模型能力保留快照：握手快照無法表達 `session.selectModel` 之後工作階段的當前目標，部署策略也可能獨立變化。宿主會根據當前的單張位元組數、圖片數量、總位元組數、媒體類型、尺寸、畫素數和路由模型策略校驗整個批次，再寫入任何附件或事件；其拒絕透過 composer 的短時 toast 播報。

Pi-AI 配接器是首條視覺輸入路徑：它在請求時解析 `ctx.attachments`，遞迴轉換每個持久圖片引用，包括巢狀在工具結果中的引用，並且僅為聲明支持圖片輸入的模型生成提供方原生圖片內容。交付的組合會同時註冊 Pi-AI OpenAI、Anthropic 路由和僅支持文字的默認 DeepSeek 路由；選擇當前提供方／模型仍由宿主組合或設定承擔，而不是圖片輸入 CLI（命令列介面）的功能。在請求時解析服務，可避免 Cordis 載入順序將選填附件服務的可用性固化。手寫 DeepSeek 配接器遇到請求中任何位置的圖片時都會拋出類型化的 `UNSUPPORTED_CONTENT` 錯誤，包括巢狀工具結果中的圖片。任何配接器都不得將圖片展平或跳過。

核心層支持結構化助手圖片塊，但當前沒有任何生產提供方路徑透過圖片輸出認證。未來任何支持輸出的配接器都必須在有界的大小和時間策略下取得提供方位元組，透過同一個附件服務校驗並持久化位元組，之後才能以原子方式發布 `ImageBlock`。助手 Markdown 中的 URL 仍是文字，絕不自動下載。

提供方無關的 token 估算不會根據圖片尺寸猜測視覺定價；提供方返回的用量仍是權威值。在 ACP（Agent Client Protocol）介面原生支持圖片前，ACP 會渲染明確的圖片標記，而不是靜默省略該塊。

壓縮會把選定的工作階段前綴（包含圖片引用）重播到已設定的摘要生成路徑中。支持視覺的路徑會透過配接器解析這些引用；僅文字路徑會明確失敗，而不是靜默丟棄視覺上下文。合成的檢查點仍僅包含文字，`compaction-basic` 會以 `UNSUPPORTED_CONTENT` 拒絕包含圖片的摘要輸出。

### 歷史渲染與原圖預覽

歷史記錄摺疊會在使用者訊息和助手訊息中保留 `ImageBlock`。使用者圖片在文字上方靠尾端對齊；助手圖片則保留在靠前端敘述流中的原內容區塊位置。`MessageImage` 根據記錄的尺寸派生穩定的行內邊界框，透過工作階段授權載入器解析位元組，使用 `object-fit: contain`，並將對象缺失或損壞轉換為可重試的錯誤控制元件。

輸入區縮略圖和每個 `MessageImage` 各自持有臨時原圖預覽狀態，並呼叫同一個純 `ImageLightbox`。模態對話框使用已經解析的原始對象 URL，只限制顯示尺寸；它會聚焦關閉控制元件，並在關閉時把焦點復原到先前的目標。

### 限制與信任邊界

第一版僅接受 PNG、JPEG、WebP 和 GIF。不接受 SVG 和遠端 URL。默認限制為每張圖片 5 MiB、每則訊息 20 張圖片和 100 MiB 圖片總位元組數，以及每張圖片 4,000 萬個固有畫素。這些隨部署變化的限制屬於經過校驗的後端設定，並由宿主在持久化前強制執行。用戶端連線載體為每個 API 請求設定獨立且可設定的 `maxRequestBodyBytes` 上限（默認 160 MiB）；如果該上限無法容納附件服務的圖片總量限制經 base64 和請求封裝膨脹後的大小，載入就會失敗。因此，降低圖片策略絕不會靜默降低有效文字或其他 RPC 的載體上限。未聲明長度的請求體在越過上限的瞬間即被拒絕，而不是先讀完再拒。

格式錯誤的 base64、不支持或不匹配的媒體、截斷的圖片資料、超出位元組限制、超出圖片數量、超出畫素限制、對象缺失和完整性不匹配都會返回穩定的結構化錯誤。原始檔名只保留用於顯示的末段，控制字元會被移除，並且任何本機路徑都不會寫入日誌或返回瀏覽器。

| `packages/host/apiproxy` 和 `packages/bundle/base` | 範圍狹窄的上傳協議、先持久化再追加事件的順序、工作階段授權讀取、限制和模型前置檢查，以及默認 profile 組合。 |
| `packages/client/connection` 和 `packages/client/runtime` | 有界請求緩衝、協議類型、fixture（測試前置資料）圖片、提示詞上傳、附件讀取和持久引用摺疊。 |
| `packages/client/ui-conversation` | 每個工作階段的草稿圖片、附件欄、使用者與助手圖片控制元件和原圖預覽。 |
| `packages/acp/acp` | 圖片塊的明確兜底渲染。 |

附件包構成一個能力 seam 的介面與實作側。輸入區行為留在工作階段對象層，提供方轉換留在配接器中，無需修改 `agent-loop`。

### 實作

已實作的範圍包括附件 seam、角色無關的圖片塊、Pi-AI 輸入轉換、DeepSeek 拒絕、宿主持久化順序、Web 上傳與讀取協議、當前圖片限制執行、大小受限的 Web 請求體、記憶體草稿圖片、貼上與拖放附件欄、使用者與助手歷史圖片渲染、單擊預覽、壓縮處理，以及組裝後無需金鑰的 Web 覆蓋。

預發布提示詞協議不需要相容包裝層；引入相應切片時會同時修改所有呼叫點和 fixture。

## 曾考慮的替代方案

### 將每張貼上圖片保留在 `/var` 或其他臨時目錄中

臨時儲存適合在傳送前使用，也適合透過作業系統接收剪貼簿文件的原生用戶端。但它不適合在訊息被接受後繼續使用：清理不在 harness 的控制範圍內，路徑因宿主而異，復原或 fork 後的工作階段也可能比文件存在得更久。提案允許臨時暫存，但會在追加事件前將已接受的位元組複製進 `DSH_HOME`。

### 貼上或拖放後立即持久化

立即持久化可以讓草稿在重載後繼續存在，但會在工作階段或訊息持有對象前就建立持久對象，因此必須定義配額、殘留對象生命週期和清理策略。第一版保持未傳送草稿為臨時狀態，並把傳送被接受作為持久性邊界。

### 在訊息與工作階段日誌中內聯 base64

這種方式會在 RPC、事件、歷史分頁、fork、壓縮和瀏覽器儲存中複製二進位資料，還會誘使 token 計量把編碼文字當成模型文字。單一不可變對象配合小型引用，可以讓持久表示保持有界。

### 使用瀏覽器對象 URL、本機路徑或提供方 URL 作為規範內容

對象 URL 會隨文件失效，本機路徑不可移植，提供方 URL 則可能過期、跟蹤查看者或暴露憑據。它們只能作為臨時傳輸或預覽細節存在。

### 用一個通用 `AttachmentBlock` 表示圖片、文件、音訊和影片

輸入區展示可以使用通用附件欄，但提供方語義取決於具體模態。圖片是原生多模態輸入；PDF 可能是提供方文件或提取後的文字；影片可能由模型原生支持、抽幀處理或不受支持。特定的 `ImageBlock` 會迫使每個消費端明確處理或拒絕該模態。

### 相依性 UI 能力檢查或靜默過濾圖片

UI 狀態可能過時，也無法保護直接 SDK、ACP、重播或未收錄模型的路徑。靜默過濾會改變使用者意圖。提供方強制檢查仍是必需項，UI 檢查則是選填的提前回饋。

## 測試

- 儲存測試覆蓋內容尋址去重、私有權限、准入失敗、對象損壞或缺失時的失敗，以及收緊部署限制後讀取歷史資料。
- 宿主與協議測試覆蓋先持久化再追加事件的順序、日誌中不含 base64、工作階段作用域授權、能力拒絕、上傳限制、大小受限的 HTTP 請求體、圖片准入與模型選擇的競態（排隊與 steering 兩種放置）、待發布狀態、未發布即空閒時的門檻釋放、僅文字的佇列編輯，以及壓縮後依據當前派生歷史進行的選擇。
- 用戶端單元測試覆蓋貼上與拖放、混合剪貼簿文字、僅圖片傳送、草稿復原、順序、草稿、工作階段作用域和應用層級的對象 URL 清理，以及一項在釋放後才完成的延遲歷史讀取；keyless 的組裝後建置產物通道（`apps/web/tests/image-display.snapshot.ts`，`DSH_EXAMPLE_MODE=lib pnpm run test:snapshot`）覆蓋經授權附件路由渲染的歷史使用者與助手圖片畫廊、原圖 lightbox，以及 composer 貼上縮略圖條。
- 配接器與壓縮測試覆蓋 Pi-AI 原生圖片轉換、後置附件服務組合、僅文字拒絕、遞迴巢狀在工具結果中的圖片、保留摘要輸入，以及明確拒絕圖片輸出。
- 需要憑據的實際 API 測試會透過 Anthropic `claude-opus-4-8` 路徑傳送一張 PNG，並要求模型識別其中的QR Code。
- 當前生產配接器集合沒有經過認證的圖片輸出路由；輸出提供方認證仍不在第一版範圍內。

## 後果

- 持久儲存會在沒有垃圾回收時持續成長。第一版選擇重播安全，而不是過早刪除。
- 對象缺失或損壞會讓模型請求無法精確重建。明確失敗可以保持完整性，但在修復前可能阻止該工作階段繼續執行。
- JSON-RPC base64 會增加上傳記憶體，並帶來約三分之一的編碼開銷。第一版的限制可以約束開銷；更大的媒體需要流式傳輸或二進位傳輸協議。
- 未傳送圖片無法跨重載保留。持久草稿需要配額和殘留對象清理，而不是隱式複用訊息儲存。
- 原圖預覽解碼的畫素多於行內控制元件顯示的畫素。畫素限制、一次只打開一個預覽和對象 URL 釋放可以約束但無法消除瀏覽器瞬時記憶體佔用。
- 能力元資料可能缺失或過時。宿主前置檢查可以改善回饋，配接器強制檢查仍是權威結果。
- 未來輸出提供方可能需要經過身份認證的下載，助手圖片才能完成，這會增加延遲與新的故障點。先持久化再追加事件的順序優先保障重播完整性。
- 文件選擇、通用文件與 PDF、音訊與影片、持久草稿暫存、圖片複製、自訂上下文選單、輸出提供方認證和按引用感知的垃圾回收仍是相互獨立的設計。
