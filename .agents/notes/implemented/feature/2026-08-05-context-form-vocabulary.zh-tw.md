# Agent Note: 由生產方聲明的上下文形態

Status: implemented

[English](2026-08-05-context-form-vocabulary.md) | [简体中文](2026-08-05-context-form-vocabulary.zh.md) | 繁體中文

## 問題

每一條已記錄的非使用者 `user/message` 都透過同一個內容區渲染：把整則訊息序列化成內聯 JSON。讀者展開一行，看到的是 `{ "content": [ { "type": "text", "text": "…\n\n…" } ], "source": { … } }`——轉義把唯一值得讀的東西（面向模型的散文）壓成了一行，生產者欄位也放在同一個 JSON 對象中。

在標題欄寫出生產者（[來源與 steer 標識決策](2026-08-04-web-context-source-and-steer-marks.md)）解決了「這是誰加的」。它解決不了「加進來的是什麼東西」，因為日誌裡根本沒有這項資訊。注入上下文不是一種形狀：對帳後的 `AGENTS.md`、可用 skill（技能）的目錄、執行時期策略快照、subagent 的彙報，彼此之間的差別不亞於終端機卡片與 diff 卡片，然而這四者呈現出來是同一堵轉義 JSON 的牆。

工具呈現層早就解決過同一個形狀問題。`ToolCallView` 只有三種卡片，而不是每個工具一種，由工具自己聲明本次呼叫屬於哪一種。上下文沒有對應物：既沒有形狀詞彙表，生產方也無從聲明自己寄出的是哪一種。

## 決策

`MessageSource` 新增一個選填、由生產方聲明的 `form: ContextForm`——一份關於資訊**形狀**的小型帶標籤詞彙表，與 `kind` 相互獨立：

- `kind` 回答**由誰產生**，不攜帶呈現選擇。
- `form` 回答**這是何種形態的資訊**。多個生產方可以共用一種形態，一個生產方在一次工作階段中也可以寄出多種。

該詞彙表是語義的，絕不涉及視覺。取值只陳述「內容是某個文件的指令」或「是一份可用項的目錄」；顏色、圖示、排序、默認摺疊狀態歸消費端管，不得進入這個聯合類型。它隨生產方補齊各自形態所需的結構化欄位而逐個成長。已聲明的形態：

**`instructions`**——從工作區文件中讀出的指令。`agent-instructions` 在啟動基線與後續增量上都聲明它；其既有的 `changes[]` 已經攜帶了呈現所需的路徑、動作與 digest，因此沒有新增欄位。內容區在正文之上列出對帳過的文件，並原樣保留 `<system-reminder>` 包裝：那層包裝本就是模型讀到的一部分，隱藏它會歪曲這次請求。

**`catalog`**——本工作階段可用項的目錄，隨變化重新發布。`dsh-tool-skill` 從共享的 `plugin` kind 遷到自有的 `skill-catalog` 來源，攜帶 `entries`（本次發布的 `name`／`description` 對）以及替換時的 `update`，後者由內容區渲染成替換提示。內容區直接列出這些條目，不再從散文裡反解 `<available_skills>` 塊。

條目記錄的是**未轉義**的發布事實。偽 XML 轉義屬於 `<available_skills>` 這層為模型而設的框架，因此只在渲染該框架時施加、從不儲存；否則消費端要正確展示含 `<` 的描述就得知道框架的編碼方式，本決策剛移除的框架知識會換一種形式洩漏回來。`escapeText` 確定且單射，故對未轉義條目取 digest 與此前完全等價，重新發布語義不變，面向模型的文字逐位元組不變。

這次遷移同時挪動了目錄的**身份**：重新發布用的 digest 現在覆蓋持久條目而非渲染文字，於是面向模型的包裝再也無法左右是否需要重新發布，那段從已記錄訊息裡切出條目的文字切分邏輯也隨之刪除。若復原的工作階段中最新目錄早於本次改動，會重新發布一次——預發布立場允許這樣做。有一種情形不會自愈：當那份舊格式目錄是唯一的一份、且當前檢視表沒有任何 skill 時，外掛程式看不到已發布目錄，也就不會發出 tombstone，模型手裡會留著一份無人替換的過時目錄。預發布立場（「後端拒絕舊的磁碟格式」）允許這一點；此處如實記錄，而不是隻寫樂觀路徑。

**`snapshot`**——會被同一生產方後續快照取代的當前狀態。執行時期快照、`time-context`、`tmux-context` 聲明它。`renderContextSections()` 暴露出裝配時的具名貢獻——`renderContextSnapshot()` 本來就是把它們拼給模型的——因此內容區能把每一段歸屬到產生它的子系統，而不必去切分已經拼好的散文。兩個單貢獻生產方各記錄一段。執行時期快照的「已清空」標記沒有任何貢獻可歸屬，因此不聲明形態。

**`notice`**——剛剛發生了什麼的一次性說明。`tool-jobs`、`tool-goal` 收尾、`plan-mode` 切換與 `repeat-tool-reminder` 提醒都帶 `summary` 聲明它，而該摘要出現在**摺疊態**行上：notice 的全部意義就是不展開也能讀完。摘要在其輸入是呼叫方文字時自行封頂（任務的 label 與狀態 detail 本身沒有長度約束）。Goal 狀態變更仍是由領域層持有的 `goal/change` 事件，而非模型上下文，因此不聲明 form。

**`relay`**——另一個 agent（代理）發給本 agent 的訊息。兩個 subagent 定向來源都聲明它；傳送方以來源已記錄的不透明工作階段 id 呈現，因為本用戶端無法把它解析成標題。

**`recall`**——從另一個工作階段日誌搬來的材料。`session-reference` 聲明它，且不需要新增欄位：其 references 已經記錄了標籤、保留與省略條數、截斷標記，內容區把這些放在最前面——召回上下文在進入時是有界的，隱藏省略條數的卡片會誇大模型實際收到的內容。

兩個讀取器都是**全有或全無**：一條不可讀的條目即判定整條記錄不可用，而不是把它丟掉——會替換掉面向模型文字的內容區，不得給出自信但殘缺的「模型讀到了什麼」。行上的形態標記報告的是實際渲染出的形態，而非聲明的形態。

生產方一側對同一份持久資料採取同樣的姿態。`catalogHistory` 從 `agent.session.events` 讀 `source.entries`，而復原或 fork 時它來自 JSONL／SQLite 種子，種子驗證只保證來源是帶非空 `kind` 的對象，不校驗任何 kind 特有欄位。因此不可讀的目錄被當作「不是本外掛程式的記錄」跳過——正是被替換掉的內容 digest 原有的姿態；在那裡拋錯會讓該工作階段此後每一步都在最晚、最難定位的點失敗。

其餘一切——包括本 UI 版本不呈現的形態、來源未聲明形態、以及條目不可用的 `catalog`——一律渲染 **opaque** 內容區：按真實換行展示面向模型的文字，其後把剩餘來源資料列成欄位。opaque 是文件規定的默認；約定要求這些不支持的情況使用它。復原的、fork 的、外部寫入的日誌，無論其生產方是否掛載在此處都必須渲染得出來——這同樣是分類資訊必須落在持久來源裡、而不是落在用戶端以生產方為鍵的表裡的原因。

## 為什麼不做 presenter 登錄檔

工具呈現約定把它的詞彙表與 `presentCall(args)` 配對，那是每個工具在 host 側實作的純函式。上下文刻意不設對應物，因為輸入的歸屬不同：工具的 `args` 由**模型**按面向模型的 schema 生成，翻譯步驟無法迴避；而上下文的 `source` 由**生產方外掛程式**自己構造，不受任何外部約束，完全可以直接記錄呈現所需的事實。加一層登錄檔買到的是一次沒人需要的翻譯，代價卻是一個 host 計算點、每條上下文訊息一個 wire 欄位、以及每個生產方包都要出瀏覽器 bundle（用戶端純度閘門禁止 host 包貢獻元件）。

## 考慮過的替代方案

**在用戶端把來源 kind 對映到渲染器。** 寫起來最省，也不用改格式，但它把生產方知識放回了用戶端：此後每新增一個 kind 都要用戶端發版才能渲染成 opaque 以外的東西，而外部日誌根本無法分類。它還會重新引入[來源與 steer 標識決策](2026-08-04-web-context-source-and-steer-marks.md)剛為名稱去掉的那種耦合。

**複用 `kind` 充當形態。** 單一判別欄位更簡單，`agent-instructions` 本來也與它的形態一一對應。但多個生產方共享同一形態時，這種設計無法保留完整資訊：今天有三個生產方寄出執行時期快照，把它們並成一個 kind 後，將無法分辨每則訊息由哪個生產方提供。獨立的 `kind` 和 `form` 欄位會記錄生產方，同時允許多個生產方共用一種呈現方式。

**讓用戶端解析面向模型的散文。** 條目與文件分節在文字裡確實有可見結構。解析它們會把呈現耦合到提示詞措辭上，於是每改一次文案就會悄悄破壞一張卡片——這也正是目錄身份從文字上遷走的原因。

**把 instructions 渲染成 Markdown。** 正文本來就是 Markdown 文件，渲染出來更好讀。但文字同時攜帶 `<system-reminder>` 包裝，Markdown 渲染器會把它當原始 HTML 丟棄，於是 Markdown 內容區會悄悄隱藏模型讀到的一部分。推遲到生產方按文件結構化記錄內容之後再做。

## 測試

- `packages/client/runtime` 釘住形態投影，包括必須降級為 opaque 的未知值、空值、類型不符與缺失。
- `packages/client/ui-conversation` 逐個釘住內容區：opaque 的換行留存與來源欄位、instructions 的文件清單與原樣包裝、catalog 的條目清單，以及條目不可用的 catalog 回落到 opaque。
- `packages/skill/tool-skill` 釘住首次發布與替換時的新來源、由持久條目驅動的重新發布行為，以及畸形持久目錄不打斷步驟觀察。
- 無金鑰的組裝 Web seeded-history 場景在 Chromium 中展開一條真實的 `instructions` 上下文，斷言其文件清單、原樣包裝與未改動的展開項幾何。`catalog` 沒有組裝態覆蓋：隔離腳手架不發布任何 skill，因此沒有目錄能進入瀏覽器場景。

## 後果

- 讀者不展開就能知道加進來的是什麼，展開之後讀到的也不再是轉義 JSON。
- 持久 `MessageSource` 現在會在生產者 kind 及其欄位之外記錄內容形狀。這條邊界是承重的：只放事實與形狀，絕不放呈現。生產方若想獲得更好的卡片，就應記錄更好的事實。
- 目錄身份不再相依性面向模型的散文，刪掉了那條可能把「改了措辭」誤判為「改了內容」的文字切分路徑。
- 除兩個掛鉤橋接外，每個已發布的生產方現在都聲明瞭形態。橋接按設計保持 opaque：其內容是外部程序列印出來的任意文字，無法承諾任何形狀。未知 kind 與不可讀記錄同樣落在這裡。
- `ContextFormed` 按 `form` 判別，因此生產方無法在缺少該形態所需事實的情況下聲明它——沒有 summary 的 `notice`、沒有 sections 的 `snapshot`，都會編譯失敗。
