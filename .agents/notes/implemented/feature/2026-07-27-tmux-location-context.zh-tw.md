# Agent Note: tmux 位置上下文

Status: implemented

[English](2026-07-27-tmux-location-context.md) | [简体中文](2026-07-27-tmux-location-context.zh.md) | 繁體中文

## 問題

執行在 tmux 內的 agent（代理）無法告訴模型自己身在何處：行程佔據哪個 session、window、pane，以及 window 如何版面配置。當用戶操作多個 pane 時，希望模型能對自身位置有所定位，從而讓「下方的 pane」「這個 window」之類的指令得以解析。位置必須以持久、可重建的上下文形式送達模型，而非在原地被改寫的系統提示值，並且當位置未變化時不產生任何成本。

tmux 無需守護行程即可暴露這些資訊：`$TMUX_PANE` 標識行程所在 pane，`tmux display-message -t "$TMUX_PANE" -p '<format>'` 可列印任意 pane/window/session 欄位。待決問題在於如何觀測——在每次準備時拉取，還是由 tmux hook 推送——以及如何避免逐步驟 token 成本與隱藏的行程內狀態。

## 決策

`@deepseek-ai/dsh-tmux-context` 是位於 `packages/context/tmux-context/` 的選填啟用型函式外掛程式，與其他既不定義工具也不定義服務的有界請求上下文增強並列。已交付的 TUI 會掛載它，因為終端機複用器上下文是該介面特有的；`dsh-agent-spine-demo` 與 Web／無頭介面保持沉默。

**在每輪的第一個步驟拉取，而非 tmux 推送。** 外掛程式前置註冊一個 `agent/pre-step` 監聽器，僅在 `step === 1` 時動作。拉取模型無需後臺行程、無需在使用者的 tmux 中安裝 hook、也無需清理；它每輪重新讀取當前狀態，因此被移動、改名或重新版面配置的 pane 都會被自然感知。以第一個步驟為門檻使讀數按輪次生成：位置在一輪內是穩定的，逐步驟重複查詢只會增加成本而不帶來新資訊。輪次中途移動的 pane 會在下一輪反映，這是換取更簡單設計所接受的取捨。

**透過 `ctx.shell` seam 讀取，絕不用裸 `child_process`。** 監聽器透過 `ctx.shell` 執行 tmux／`ps` 只讀命令，從而應用部署方的沙盒與策略，外掛程式不擁有任何子行程程式碼。`ctx.shell` 缺失、tmux 環境缺失、欄位數不符或 pane id 為空，都會使本次嘗試成為空操作，與 `agent-instructions` 在無 `fs` 提供方時的空操作一致。

**以 tty 判定真實 pane，而非僅憑 `$TMUX_PANE`。** `$TMUX_PANE` 會被繼承：從 tmux shell 啟動的終端機（VS Code 整合終端機、桌面啟動器）會從該祖先進程帶上 `$TMUX`／`$TMUX_PANE`，即使行程並不位於那個 pane 中，否則就會注入一個過時且錯誤的位置。命令用 `ps -o tty= -p <pid>`（在行程內傳入 agent 自身的 pid）解析本行程的控制終端機，並與 pane 的 `#{pane_tty}` 比較；只有匹配時才輸出欄位。真正的 pane 擁有本行程的 tty；繼承而來的環境指向的是另一個 pane 的 tty，因而被讀作「不在 tmux 中」。改為檢查 `$TMUX` 也無濟於事——它同樣會被繼承。這是決定性的判別依據，且無需維護終端機模擬器名單。

**僅自身位置與版面配置。** 查詢欄位為 session name、window index/name、pane index/id、window/pane 活動標志以及 `window_layout`。省略 pane 與 window 畫素尺寸（版面配置樹已傳達結構；尺寸嘈雜且每次終端機縮放都會變化）。從不採集相鄰 pane 內容（`capture-pane`），使讀數保持小巧，並避免抓取無關、可能敏感的輸出。

**僅在變化時注入，並可選間隔下限。** 需要時，外掛程式呼叫 `agent.inject()` 注入一條來源為 `{ kind: 'plugin', plugin: 'tmux-context' }` 的 `user/message`。變化抑制將渲染出的狀態塊（輪次前綴行之後的全部內容）與該來源的最近一次注入比較，後者透過掃描原始持久工作階段事件獲得——因此調度可跨壓縮（compaction）與行程復原存續，無需行程內快取。選填的 `refreshIntervalMs`（在外掛程式載入時手動校驗為非負安全整數）會額外抑制距最近一次注入不足該視窗的注入。

### 文字

```text
tmux location (turn <turn>):
session <session>, window <index> "<name>", pane <index> <pane-id>
window active=<0|1>, pane active=<0|1>, layout <window-layout>
```

輪次前綴是易變的首行；其下的兩行狀態塊纔是變化抑制所比較的單元，因此重新注入由 tmux 狀態驅動程式，而非迴圈位置。

### 持久性與請求重建

每條讀數在被壓縮遮蔽前都是普通表層節點；外掛程式對系統提示裝配毫無貢獻，`request/header` 也不攜帶任何 tmux-context 文字。讀數記錄的是一次準備嘗試，而非已提交的步驟：由於前置監聽器最先執行，當後續 `agent/pre-step` 監聽器取消該嘗試或導致其失敗時其追加可能仍會保留，只追加的日誌不做回滾。

發布的 `./invariant` 伴生外掛程式不註冊任何執行時期檢查：讀數是外部 tmux 狀態的按輪快照，工作階段中不存在需要校驗的跨事件關係，調度與格式由本包的管線測試固定。

## 後果

啟動於 tmux 內的 agent 現在會以持久、帶來源標記的上下文收到自身的 session/window/pane 位置及 window 版面配置，並在位置變化時按輪次更新。已交付的 TUI 選擇啟用；自訂部署可直接組合該外掛程式。在真實 tmux pane 之外——包括僅繼承了 `$TMUX`／`$TMUX_PANE` 的終端機——或沒有 `ctx.shell` 執行器時，外掛程式保持惰性且不報錯，因此在任何地方組合它都安全。由於讀數是一條持久的 `user/message`，它作為普通歷史經受壓縮，對系統提示裝配與請求標頭毫無貢獻，且每個位置發生變化的輪次至多增加一條兩行訊息。拉取模型在每個到期輪次的第一個步驟增加一次 `tmux display-message` 子行程（經沙盒化的 bash seam）。選填的間隔下限在查詢之前檢查，因此同時抑制查詢與注入；而位置未變化只能透過比較查詢返回的狀態得知，因此它只抑制注入，查詢開銷仍會付出。

## 測試

單元測試固定了：首個步驟的注入及來源／表層元資料；以 `$TMUX_PANE` 為鍵的命令（含其 `#{pane_tty}` 與 `ps -o tty=` 的比對守衛）；步驟門檻；跨輪次的變化抑制與 pane 移動時的重新注入；正間隔抑制與閾值；每條空操作路徑（無 bash、非零退出、欄位數不符、pane id 為空、訊號已取消，以及 `resolve()` 或 `run()` 拋出的執行器拒絕被兜住並記錄警告而非使該輪失敗）；前置排序先於普通 `agent/pre-step` 監聽器；對損壞的歷史讀數（非文字塊、單行文字）的容錯；以及設定對負值與非整數間隔的拒絕。逐文件覆蓋率為 100%。

## 考慮過的替代方案

- **由 tmux hook／後臺監視器推送**——否決：需要在使用者的 tmux 中安裝 hook，並引入帶清理的後臺行程，只為換取按輪次上下文並不需要的步內新鮮度。
- **每個步驟都執行**——否決：位置在一輪內穩定；重複查詢只增加 token 成本而無新資訊。以 `step === 1` 為門檻得到按輪次讀數。
- **裸 `child_process`**——否決：繞過沙盒策略路徑，並手寫 `ctx.shell` 執行器已擁有的子行程程式碼。
- **包含 pane/window 畫素尺寸**——否決：尺寸每次縮放都變動、徒增噪聲；版面配置樹已傳達結構。
- **用 `capture-pane` 抓取相鄰 pane**——否決：龐大、嘈雜且涉及隱私；超出「自身位置」範圍。
- **動態系統提示區塊**——否決：替換某個值會抹去支撐先前推理的歷史讀數且不可重建；單條持久且帶來源的訊息在每個位置變得可見時予以記錄。
- **信任 `$TMUX_PANE`（或 `$TMUX`）存在即可**——否決：兩者都會被從 tmux shell 啟動的終端機（VS Code 整合終端機）繼承，於是非 pane 行程會注入過時位置。pane 的 `#{pane_tty}` 與本行程控制終端機的比對纔是決定性檢查。
- **對已知終端機模擬器設黑名單（如 `TERM_PROGRAM=vscode`）**——否決：名單不完整且會不斷成長，仍會漏掉其他啟動器；tty 比對精確且與啟動器無關。
- **用執行時期 invariant 校驗每條讀數的輪次、位置與格式**——最初隨包發布，隨後移除：它從日誌中重新推導生產者自身的調度，並對同一個包剛剛渲染出的文字斷言正則，因此只是重述 `apply()`，而非檢查一條獨立關係。它能報出的每種失敗都必須先修改本包，而這些本包的管線測試已經覆蓋。僅當出現外掛程式自身並不計算的關係時才重新引入伴生檢查——例如讀數將來具備可被其他包破壞的跨輪次順序或包裹義務。
