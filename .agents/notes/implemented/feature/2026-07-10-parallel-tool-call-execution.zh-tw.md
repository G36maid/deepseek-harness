# Agent Note: 按單次呼叫安全性平行執行工具呼叫

Status: implemented

[English](2026-07-10-parallel-tool-call-execution.md) | [简体中文](2026-07-10-parallel-tool-call-execution.zh.md) | 繁體中文

## 問題

一條 assistant 訊息可以包含多個並列的 `tool-call` 塊。儘管模型已經同時請求了這些呼叫，序列執行仍會疊加各個獨立讀取和 Web 請求的延遲。

並行屬於宿主調度範疇，不是面向模型的工具元資料。迴圈需要在不硬編碼工具名稱、不向 JSON Schema 暴露調度策略的前提下，判斷哪些呼叫可以重疊執行。

工作階段日誌仍是權威記錄：每個已啟動的呼叫都有審計事件，正常完成和取消都會使呼叫與結果配對；無論完成順序如何，模型歷史都按原始呼叫順序觀察已提交的結果。

## 決策

每個工具都可以提供選填的 `isConcurrencySafe(args)` 分類器。該分類器必須是同步純函式：它只檢查當前呼叫已解析的參數，不執行 I/O 或任何變更。只有顯式返回 `true` 才表示選擇平行；分類器缺失、參數無效、分類器拋錯或返回任何其他值，都會使該呼叫按獨佔方式執行。規範類型約定見[工具資料結構](../../../../docs/subsystems/tools.md)。

分類器有意設計為一元函式。返回 `true` 表示工具承諾：此呼叫可以與任何同樣返回 `true` 的並列呼叫重疊執行。調度器不會比較呼叫，也不會證明它們的資源訪問相容。

這個一元分類器仍然可以感知輸入。工具可以將只讀操作分類為平行，將變更操作分類為獨佔。該介面無法表達「僅當路徑不同時，這些寫入才安全」之類的關係規則，因此，安全性相依性並列呼叫的呼叫仍按獨佔方式執行。

`defineTool()` 先驗證參數，再呼叫類型化分類器。無效參數會被歸為獨佔，且只有該呼叫真正執行時才會產生常規參數錯誤。`ctx.tools.executionMode(exec)` 會解析當前有效的工具定義，並返回帶標籤的 `parallel` 或 `exclusive` 模式；未知工具將按安全側原則歸為獨佔。

使用帶標籤的模式，而不是公開布林型調度器 API，使得以後可以表達感知資源的變體，無需改變分類器約定。

## 調度與順序

迴圈會等待完整的 assistant 訊息，對每個呼叫只解析一次，為每個呼叫建立獨立的 `ToolExecution`，再按模型順序掃描。連續的平行呼叫組成一組；每個獨佔呼叫單獨組成一組，並構成順序屏障。各組按順序執行。分類採用惰性方式：每經過一個屏障，調度器都會解析下一個呼叫；補充平行池之前，還會重新分類每個後續呼叫。如果登錄檔變更使該呼叫變為獨佔，當前池會先完全排空，然後該呼叫才作為下一個屏障啟動。

例如：

```text
[parallel read(A), parallel read(B), exclusive write(A), parallel read(C)]

→ [read(A), read(B)]
→ [write(A)]
→ [read(C)]
```

`read(A)` 和 `read(B)` 可以重疊執行。`write(A)` 要等兩者都完成後才啟動，`read(C)` 則要等寫入完成後才啟動。

每組都使用一個由 `maxParallelToolCalls` 限制上限的滾動池：迴圈先按模型順序啟動呼叫，直到達到上限；每有一個呼叫結帳，就再啟動一個。獨佔組是容量為 1 的池。將上限設為 `1` 可保持序列執行。

只有派發和工具主體會重疊執行。`tools/pre-execute` 和 `tools/post-execute` 按模型順序執行，因為中介軟體可能維護對順序敏感的狀態。`tools/execute` 包裝層會包裹並行派發過程，因此必須能在不同執行之間重入。

每個已啟動的呼叫都會在進入 pre-execute 閘門之前立即追加 `tool/call`。已完成的派發佔據模型順序的槽位；提交遊標只有在下一個槽位就緒時，才會追加 `tool/result` 並收集 `additionalContexts`。即時介面可以顯示多個待處理呼叫，但結果和工具執行後的上下文仍按模型順序排列。

如果在一組啟動前中止，系統不會記錄該組的任何呼叫。如果在一組執行期間中止，系統會停止補充池，等待已啟動的呼叫，按順序提交其結果，在這些結果之後排空已接受的批次上下文，然後透過現有中止路徑結束該步驟。從未啟動的呼叫沒有審計事件。調度器發生意外故障時，會停止新的派發，等待每項已啟動的派發結帳，並重新拋出第一個故障。由於該故障是內部終態，而非工具結果，迴圈不會為被拒絕或未提交的呼叫虛構工具結果。

Code Mode 仍不使用此調度器，因為模型只會寄出一個原生 `run_code` 呼叫。`run_code` 及其內部派發佇列仍按序列方式執行；`mode: 'both'` 中的原生並列呼叫使用常規調度器。

## 安全約定

工具返回 `true` 即承諾：其主體可以與其他平行呼叫同時執行。它不得直接變更父工作階段或其他由父級擁有的狀態；它將輸出返回給迴圈，由迴圈按模型順序提交。

執行期間觸及的任何共享狀態都必須支持並行。這也包括工具包裝層和提供方：它們可以在內部序列化，也可以實施自身容量限制，但必須在並行派發時不破壞狀態。

## 設定與聲明

`maxParallelToolCalls` 是 AgentLoop 的正整數部署上限，由工廠建立的所有 agent（代理）共享。預設值為 `10`；`1` 保持序列執行。欄位和預設值的精確定義見生成的[設定目錄](../../../../docs/config-catalog.md)。

當前實作中的聲明保持保守。Web 搜尋、Web 取得、檔案系統讀取、工作階段查詢的 trace/read 工具和 subagent 委派選擇平行；委派之所以平行，是因為子 agent 在自己的工作階段中工作，其執行絕不變更父工作階段，並列委派間的工作區協調由模型負責（[平行 subagent Agent Note](2026-08-09-parallel-subagent-delegations.md)）。檔案系統寫入與編輯、bash 工具、工作階段查詢的 search 工具、工作流程、使用者互動、todo 變更、Code Mode 以及 Cordis 變更工具仍按獨佔方式執行。Bash 沒有已證明的輸入敏感分類器，因此仍按獨佔方式執行。

檔案系統讀取相依性一個範圍很窄的記錄器例外：其同步觀察更新可以不按順序結帳，但寫入和編輯在變更前會重新檢查已觀察的版本，因此過時狀態只會導致 `FS_STALE_VERSION`。

## 驗證

單元測試固定了按安全側原則進行的分類、類型化參數驗證、分組、屏障、登錄檔替換後的執行時期重新分類、滾動上限、獨立執行對象、中介軟體順序、有序結果與上下文、中止排空，以及調度器故障後的完全靜止。第一方測試固定了每項平行聲明。

快照測試固定了可見的多呼叫 transcript（文字記錄）：待處理呼叫可以重疊執行，已完成結果仍按模型順序排列。Code Mode 測試固定了其序列邊界。此調度屬於確定性迴圈行為，因此無需相依性提供方的 e2e 測試。

## 備選方案

**保持序列執行。** 這可以避免新的順序和中止情形，但會保留獨立並列呼叫所產生的不必要延遲。

**使用一個工具級布林值。** 固定的 `supportsParallelToolCalls` 標志更簡潔，但無法區分同一工具的只讀操作和變更操作。感知參數的分類器保留了這項區分。

**使用有狀態的分類。** 向分類器提供執行中的 agent、登錄檔或 I/O 訪問，會使決策相依性分類器的執行時期機，並在分類與派發之間留下缺口。可變授權和過時狀態檢查仍屬於執行時職責。

**使用感知並列呼叫或感知資源的分類。** 調度器可以成對比較呼叫，或讓每個呼叫聲明資源讀寫要求。這樣可以平行化不衝突的寫入，卻要求不相關工具共享資源標識和衝突語義。一元約定選擇放棄這部分並行性，並在安全性取決於呼叫間關係時按安全側原則處理。

**平行執行完整的工具管線。** 這樣可以讓迴圈繼續使用公開的單呼叫 API，但會並行執行 pre-execute 和 post-execute 中介軟體。現有防護和掛鉤橋可能承載有序狀態，因此只允許派發重疊。

**公開分階段方法或調度 waterfall（瀑布式事件）。** 公開的 `prepare` / `dispatch` / `finalize` 方法或 `tools/execution-mode` 事件，會在另一個消費端需要它之前擴大擴充介面。迴圈使用內部調度器檢視表，而 `executionMode(exec)` 為策略掛鉤保留了插入點。

**將調度器故障轉換為工具結果。** AgentLoop 無法判斷被拒絕的派發是否已呼叫工具主體；ToolRuntime 負責工具主體呼叫狀態和類型化工具結果。因此，內部調度器故障保持為終態，而不會被重新分類為 `ABORTED` 結果。

**在模型流式輸出時啟動呼叫。** 這可能進一步降低延遲，但會改變 assistant 訊息的權威性、重播以及呼叫/結果配對。調度器只在 assistant 訊息完成後才啟動。

**使用固定大小的視窗。** 如果在啟動下一個視窗前等待當前視窗的每個呼叫，一個緩慢呼叫就會使容量閒置。滾動池在保持上限的同時避免了這項延遲。

**向模型暴露並行元資料。** 模型已可以寄出並列呼叫。宿主調度元資料會擴大請求，卻無助於工具選擇。

## 影響

該設計遵循安全側原則，對工具作者而言也很簡單，但無法利用必須透過比較並列呼叫才能確認安全的並行性。工具過於寬泛地選擇平行，可能暴露潛在的共享狀態競態。

在某些情形下，平行呼叫會先行啟動，而序列執行原本會在輪到這些呼叫之前中止。因此，調度器只記錄已啟動的呼叫，在中止時將其排空，且取消後絕不啟動替換呼叫。

有序提交可能會讓快速結果等待較慢的早期並列呼叫。這保留了重播和模型歷史順序，同時即時介面仍可顯示待處理進度。

並行外部呼叫可能會爭用配額或行程容量。提供方負責自身容量控制；迴圈上限只限制一個 agent 步驟中的呼叫數量。

工具註冊是調度邊界。調度器會在每個屏障之後以及每次補充池之前重新分類，因此登錄檔變更會影響尚未啟動的呼叫。已啟動的呼叫保留它們進入池時所依據的調度決策。

終態調度器故障可能會在故障步驟關閉前留下已記錄但沒有結果的呼叫。等待仍在執行的派發可確保完全靜止，而不會將這些內部故障誤報為工具結果。
