# Agent Note: Web 終端機卡片：bash 渲染意圖抵達瀏覽器

Status: implemented

[English](2026-07-28-web-terminal-card.md) | 繁體中文

## 問題

bash 工具的呼叫與結果都聲明 `card: 'terminal'`（[渲染意圖聯合類型](../architecture/2026-07-02-tool-render-intent-union.md)）：呼叫檢視表攜帶命令、一段選填的模型撰寫描述以及工作目錄，結果檢視表攜帶輸出、退出碼與終止訊號。該檢視表早已抵達瀏覽器——host、connection 與 runtime 把它投遞到 `ConversationSnapshot` 的 `callView`/`resultView` 上——原 TUI 曾把它渲染為帶 `$` 提示符的卡片，附退出行與首尾高度上限。

Web client 卻對它視而不見。`packages/client/ui-tool/src/client/tool/models/tool-call-model.ts` 僅從原始工具參數推導每一行，`skeleton/DetailsPanel.tsx` 則把所有工具的內容區塊壓平進一個 `<pre>`，樣式為 `white-space: pre-wrap; word-break: break-word`。軟換行加上沒有高度約束，帶來兩個缺陷：多列輸出（`ls`、表格、框線圖）被折成一段文字，丟掉了這類輸出賴以存在的列對齊；而單列的長清單會把詳情面板拉長到與清單等長。

## 決策

`TerminalBlock` 是 `ui-primitives` 中把 shell 命令渲染為終端機表面的元件，bash 呼叫在 Web 側的兩個渲染點都經由它消費 terminal 渲染意圖：聊天工具行展開後的正文，以及詳情面板的 Output 區。`packages/client/ui-tool/src/client/tool/models/terminal-card-model.ts` 是把快照上的 `callView`/`resultView` 這一對轉換為該元件 props 的唯一位置，因此兩個渲染點不可能在命令、cwd 或退出狀態上產生分歧。當兩側都不聲明 `card: 'terminal'` 時它返回 null，即走 generic 路徑——包括本 client 版本不認識的 `card` 取值；當一個已落定呼叫的結果檢視表是 generic 時同樣返回 null，這正是 bash 工具的執行錯誤與後臺啟動得以保持既有渲染的方式。渲染意圖約定交給 UI 橋接層的兩項職責也落在這裡，而不在工具側：已落定結果的 `title` **替換**待定標題；工作目錄針對工作階段 workspace 解析——檢視表給出的絕對路徑原樣使用，相對路徑在 workspace 之下拼接，省略則**就是** workspace，而這正是不帶 `workdir` 的 bash 呼叫的常見情形。純 presenter 看不到工作階段 cwd，因此該解析屬於這個 UI 橋接層；兩個渲染點各自從工作階段清單行取出 cwd 傳入。只有**存在**的呼叫檢視表才能表示「省略了 cwd，因此取 workspace」：當分頁視窗丟掉呼叫頭時，任何地方都不再有 cwd——結果檢視表並不攜帶它——而原呼叫完全可能使用過一個顯式 workdir，因此提示行繪製一個裸 `$`，而不是命名一個它無法知曉的目錄。解析後的路徑還會歸一化其 `.`／`..` 段，因為 bash 執行器在執行前就已解析 workdir：相對 `/w/app` 的 `..` 實際執行在 `/w`，因此提示標籤必須讀作 `w` 而不是 `..`。UNC 路徑的 `server` 與 `share` 屬於其根，而非可彈出的路徑段，因為 Windows 無法越過一個共享向上。呼叫檢視表的 `description` 走同一處推導，因為約定把它渲染在卡片上方，且它必須優先於該行由參數推匯出的摘要。三個渲染點都會繪製它：兩種聊天行形態與詳情面板。展開後的行自行繪製它，因為一行處於展開態時其摺疊摘要是隱藏的——否則該描述將只在摺疊時可見，這與「位於卡片上方」的含義正好相反。

該元件的約定：

- **提示符行，每條命令列一行。** 命令的每一行各佔一行：標籤，其後原樣跟隨該行。因此一個在兩行上承載兩條 shell 命令的 `command` 就讀作它本身的兩條命令，而不是被壓成一行並省略號截斷。標籤取 cwd 的最後一段路徑，當 cwd 等於 `home` prop 時取 `~`——瀏覽器沒有 `$HOME`，因此由呼叫方提供絕對家目錄，不提供時該摺疊不生效。檢視表不帶 cwd 時渲染一個純 `$`。末尾換行是終止符，不是一條空的末命令。只有**第一行**攜帶該標籤：檢視表只知道一個工作目錄——呼叫開始處的那個——而後面的行完全可能在別處執行，命令裡一個 `cd` 就足以改變它。把標籤在各行重複，等於陳述一個此處無人知曉的逐行目錄，這與執行狀態點只出現一次是同一個理由。其餘行保留一個裸 `$`，因此它們仍讀作提示符。
- **整次呼叫一枚執行狀態點，位於第一行。** 它是 `StateDot` 四種狀態中的三種：執行期間為追逐動畫，會渲染狀態徽章的退出狀態為紅色，乾淨落定為綠色——與工具行行首圖示使用同一個指示器，因此一行與其自身的卡片不可能對同一條命令產生分歧。該狀態點存在的理由是：讀者對一條 shell 命令的第一個問題就是它是否仍在執行；沒有它時，這一點只能從「沒有輸出」推斷，而一條落定後無輸出的命令看起來也一樣。它以脫離文件流的方式落在卡片以**自身左內邊距**預留的落區裡，因此既不會縮排其命令，也不相依性命令自身的文字度量來與之對齊。該預留用 padding 而非 margin，是因為每個渲染點都會整條重寫 `margin` 來設定自己的縮排——那會靜默取消基於 margin 的落區，並讓容器把狀態點裁掉。無論有多少行，都只有一枚：檢視表攜帶的退出狀態屬於整次呼叫，而 bash 不報告逐條命令的狀態，因此每行一枚狀態點就等於在斷言——一條在失敗呼叫中其實成功了的命令列自身失敗了。那一處視覺隱藏的文字標籤具有相同的作用域，因為 `StateDot` 是 `aria-hidden`，而每行一個標籤會被輔助技術讀成好幾個各自獨立的結果。
- **不軟換行。** 輸出行使用 `white-space: pre`，置於橫向滾動的容器內。列對齊得以保留；長行滾動，而非折行。
- **高度上限與展開控制元件。** 輸出超過 `DEFAULT_TERMINAL_MAX_LINES`（16）行時，顯示 `ceil(max/2)` 行首部加餘下的尾部行數，中間是一個按鈕，報告被隱藏的行數並可展開。計數針對的是剝除輸出末尾終止符之後解析出的行，因此以換行結尾的 N 行輸出就是 N 行。切分演算法保留原 TUI transcript（文字記錄）摺疊卡片的行為，因此既有的首尾選擇保持穩定。
- **ANSI 顏色。** `anser` 切分 SGR 分段；`ui-primitives/src/ansi.ts` 把每段解析為內聯樣式，渲染成 React span。只設前景色的分段把基本 16 色對映到 `--dsw-*` 主題 token，使作者指定的顏色在兩種主題下都可讀；自行繪製背景的分段則前後景都保留 anser 給出的字面 rgb，以保住它意圖中的對比度，256 色板、truecolor 以及本設計系統沒有對應 token 的兩種基本色同樣如此。不承載顏色的轉義序列（OSC 串、非 CSI 轉義、無顯示意義的 C0 控制符）在解析前被剝除，因此絕不會以字面字元抵達 DOM。遊標移動在該剝除之前先行結帳，且落在逐行的列緩衝裡而不是靠字串手術，因為回車與退格**只移動**遊標——兩者都不擦除任何東西，所以讀者看到的就是每一列最後被寫入的內容。`100%` 後接回車再接 `OK` 顯示為 `OK0%`，因為這次重繪比它下面的幀更短；末尾 `abc` 加一個退格仍顯示 `abc`，因為沒有任何東西覆蓋過那個 `c`；`abc` 加兩個退格再接 `XY` 顯示 `aXY`。這些語義與真實終端機一致；「截斷加刪除」的近似看起來是對的，實際並不對。SGR 狀態按列打戳，與終端機按單元格儲存顏色的方式一致，因此部分覆蓋會保留每個存活字元自身的顏色：紅色 `bad`、三個退格、再寫 `ok`，顯示為 `okd` 且那個 `d` 仍是紅的。CSI 序列不佔列，只改變後續寫入被打上的狀態——這也正是回車不會重設顏色的原因，以及 SGR 狀態會從一行延續到下一行、而不是在每個換行處關閉的原因。行內擦除屬於同一次重放，因為 `\r\x1b[K` 是每個 spinner 與進度列都會寫的同一個慣用法——只建模 `\r` 會讓上一幀的尾巴留在原處，那是終端機從未顯示過的文字。只有 `m` 會累加進單元格樣式；遊標或擦除序列不能累加，否則狀態串會隨每次重繪線性成長，並行出 anser 只能丟棄的邊界。SGR 按單元格以**歸一化記錄**保存（前景、背景、屬性集合），而不是序列歷史：累積原始序列會讓每個狀態邊界重新發射整條鏈，因此不做完整 reset 的換色輸出會發射 O(n^2) 個字元——3200 個這樣的單元格產生 25 MB，並最終觸發 `RangeError`，遠低於 bash 自身的輸出上限。該記錄也讓所有 chalk 系工具寫出的屬性閉合碼（`39`、`49`、`22`、`24` 等）真正閉合其屬性，且每個邊界只為它開啟的狀態發射一條規範序列。一個分段也必須**收束**：重放收斂到掃描結束時的狀態，而不是最後一個被寫入單元格的狀態——因為最後一次寫入之後的 reset 不改變任何單元格，卻結束了該分段；沒有這一步，以 `\x1b[0m` 結尾的行會把顏色洩漏到其後所有行。遊標按終端機列推進，因此製表符前進到下一個 8 列製表位、寬字元佔兩列（其續列在首列被覆蓋後變為空白而非合攏），組合標記不佔列。寬度依據 emoji **presentation** 而非 U+2600–U+27BF 整個區塊：`\u2713`——每條進度行都會寫的對勾——只佔一列，把該區塊整體當作雙寬恰好會錯位這張卡片賴以存在的那類輸出。寫入寬字元對的任一半都會把另一半清成空白，因為終端機無法讓一個雙格字形只留下一格：`a\tb` 之後用 `XY` 重繪顯示為 `XY      b`，因為兩個字元的重繪到不了第 8 列。
- **退出狀態與複製。** 非零退出碼或訊號渲染一枚狀態徽章，與 bash 工具自身渲染器所作的退出狀態區分一致；乾淨退出不渲染徽章，落定後的空輸出渲染一處變暗的佔位文字——該判定讀的是卡片實際渲染的解析行，而非原始文字，因為只含轉義或控制位元組的輸出能透過 `trim()` 卻解析不出任何可見內容，否則就會畫出一片空行外加一個把不可見位元組寫進剪貼簿的複製控制元件。複製控制元件複製的是原始輸出文字而非渲染後的樹，因此提示符行與徽章不會進入剪貼簿。

幾何尺寸、圓角與字體沿用 `CodeBlock`，因此終端機卡片與圍欄程式碼區塊在視覺上一致；`white-space: pre` 加橫向滾動是有意的分歧。兩個元件都需要的剪貼簿寫入從 `CodeBlock` 中提取到包內部的 `src/clipboard.ts`，不對外匯出，因此它仍是這兩個塊的實作細節。

### 聊天行內嵌輸出推翻了一條既有約定

`packages/client/ui-tool/src/client/tool/components/ToolRow.tsx` 與 `packages/client/ui-tool/src/client/tool/models/tool-call-model.ts` 都斷言過「絕不內嵌輸出——完整結果在詳情面板」。在行內顯示終端機塊推翻了這一點，依據是 owner 的明確決定。

這次推翻成立的理由：對 shell 命令而言，輸出**就是**使用者要讀的結果，把它專門收進面板會讓最常見的情形變成兩步互動。行內一個有界、限高、不換行的終端機塊，正是讓 bash 密集的 transcript 一遍讀完的條件。舊規則真正擔心的是行高不受輸出長度約束，而高度上限加展開控制元件正是防止其復現的機制。

餘下的約束：行內上限為 `CHAT_TERMINAL_MAX_LINES`（8），是元件預設值的一半，而面板沿用預設值——訊息流是跨多次呼叫閱讀的摘要表面，面板纔是單次呼叫的閱讀表面。只有 terminal 意圖內嵌渲染；generic 工具的內容依舊只在面板中。

這一劃分的一個前提此後被削弱了：[工具行已不再是詳情面板的點擊目標](2026-07-28-tool-call-file-open-in-os.md)，且沒有任何手勢接替它，因此該面板在組裝後的應用中當前不可達。於是行內上限成為讀者實際擁有的唯一長輸出表面，由展開控制元件承擔。復原面板入口屬於那次改動的後續，而非本次改動——但在它落地之前，「面板仍是查看完整輸出的地方」並不成立，行內的展開控制元件獨自承擔了這一職責。

## 考慮過的替代方案

**只在詳情面板渲染終端機塊。** 這樣保留既有的「不內嵌輸出」約定，也不需要記錄任何推翻。已被 owner 的明確決定否決：shell 命令的輸出正是使用者來讀的東西，把它挪到一次點擊之外，代價高於該約定帶來的收益。此處記錄的是 owner 的裁決，而非從程式碼庫推匯出的結論。

**複用 `CodeBlock` 並傳入 `console` 語言，而不新建元件。** 已否決：`CodeBlock` 會軟換行，而軟換行正是本次要修的缺陷，且它沒有退出狀態、沒有 cwd 提示符行、沒有高度上限、也不處理 ANSI。把四項終端機專屬關注點加進共享的程式碼圍欄元件，等於把它們強加給每一個 markdown 圍欄。兩個元件改為共享幾何與字體 token，那是唯一一處「一套實作對兩者都正確」的部分。

**手寫 SGR 解析器。** 已否決：SGR 解析器恰是[優先採用維護良好的相依性而非手寫](../process/2026-07-26-dependencies-over-hand-rolling.md)所指明不該自持的那類實作——它的邊界情形（256 色板與 truecolor 形式、`reverse`、多參數分段、未終止的序列）各自只在沒人會寫進測試的輸出上失效，因此手寫版本會在很長時間內一直微妙地出錯。對照那條策略的門檻：`anser` **並未**刪除任何既有自持程式碼。它是一次能力增補，而那條 Agent Note 把這與淨刪除式的簡化區分開來；它達到的是健康度與邊界契合這兩方面的門檻。`anser` 未覆蓋而仍由我們手寫的部分是：主題 token 的顏色對映、非 CSI 序列的剝除、回車重繪，以及供高度上限切片的逐行 span 摺疊。

## 後果

`anser` 成為 `packages/client/ui-primitives` 的一項新執行時期相依性，因此該包的每個消費端都為它付款一次。Web 聊天中的 bash 行現在承載輸出，相比只有摘要的行，這是有意提高的資訊密度；上限是維持其有界的機制，而調緊上限是改一個 prop，不是重新設計。

`TerminalBlock` 只讀取 terminal 檢視表攜帶的欄位，因此它始終是渲染意圖內容的純函式——不查工作階段狀態，與產出該檢視表的 presenter 一樣可安全重播。不具備終端機能力的 UI 仍從橋接層拿到圍欄式回退；工具的結果形態未作任何改動。

在當前已交付的 wire 上，`run_code` 子派發不會得到終端機卡片：`session.ts` 把 `tool/code-dispatch(-start)` 摺疊為 `callView: null`／`resultView: null`，而 host 的 `viewFor` 只呈現頂層的 `tool/call`／`tool/result`，因此巢狀的 bash 呼叫保持通用的壓平形式。兩條分支都已釘住——注入檢視表後的解析路徑，以及 wire 實際投遞的無檢視表形態——因此這個缺口是被記錄下來的，而非暗含的。把 presenter 檢視表貫穿 code-dispatch wire 屬於該邊界自身的改動。

內嵌渲染的許可僅授予 terminal 意圖。將來想要內嵌的意圖需要有自己的邊界與自己的決定，且需針對此處記錄的理由來論證，而不是僅針對「只在面板」這條約定本身。

## 測試

`packages/client/ui-primitives/tests/ansi.client.spec.ts` 固定解析層：基本色的 token 對映、無對應 token 取值的字面 rgb、帶背景分段的前後景配對、每一項裝飾以及其中兩項之間的 `textDecoration` 衝突、OSC 串與非 CSI 轉義及無顯示意義控制符的剝除、遊標重放（較短重繪讓上一幀尾巴留存、末尾退格不擦除任何東西、行內擦除的全部三種參數形式、製表位、寬字元、SGR 跨行延續，以及遊標／擦除序列絕不進入單元格樣式），以及 CRLF 的保留。每一條重放用例都先對照真實終端機核實過。`packages/client/ui-primitives/tests/terminal-block.client.spec.tsx` 固定元件：cwd 縮短、執行中／空／已落定三條分支、訊號優先於退出碼、末尾終止符規則、首尾高度上限及其 `aria-expanded` 開關、執行狀態點全部三種可達狀態及其位於提示符標籤之前的位置、每條命令列一行的提示區及其位於第一行的單枚狀態點，以及複製控制元件在剪貼簿接受與拒絕兩條路徑上都斷言原始輸出，另有對 `writeClipboard` 的直接固定。

`packages/client/ui-tool/tests/terminal-card.client.spec.tsx` 固定每個渲染點上的接線：`terminalCardModel` 的推導及其每一處 null 分支、結果標題替換待定標題、cwd 針對工作階段 workspace 解析的全部四種情形、切換選中呼叫時面板重設卡片展開態、對話行受展開控制的輸出體與面板的全高輸出體的對比、`BashRow` 的常駐卡片及其與自身摘要行狀態點的一致性，以及面板 Output 區段（含 run_code 子派發與超出視窗的呼叫頭）。該文件在沒有閘門壓力的情況下寫成——`packages/client/ui-tool/src/*` 位於 `vitest.config.ts` 的覆蓋率 `exclude` 清單中，因此覆蓋率執行不會統計其中任何文件。

`apps/web/tests/terminal-card.snapshot.ts` 在建置後的用戶端產物上固定組裝完整的應用：同一渲染意圖在兩個對話渲染點、以及兩種對話行形態下的表現——因為 bash 呼叫只有經由帶鍵的 `BashRow` 註冊纔得到常駐卡片，而其他任何聲明 terminal 的工具名都落到渲染點兜底行上，其輸出體受展開控制。fixture 第 65 輪名為 `bash`、第 60 輪保持 `fx-bash`，於是一份 fixture 覆蓋兩種形態，而第 60 輪的命令為兩行，使建置產物快照釘住逐行提示區及其單枚狀態點（`dotsPerPromptRow: [1, 0]`）。該終端機輪有意排在 todo 輪**之前**：站立計畫會在下一次 `turn/start` 時退役，若追加在其後就會讓 dock 的計畫條變空，並連帶毀掉 todo 表面自身的覆蓋；該輪還承載第 60 輪兩個提示行無法覆蓋的部分——解析到 `--dsw-*` token 的 SGR 分段、超出對話上限的輸出、巢狀 cwd，以及在樣本旁另行標注的非零退出碼。樣本正文有意**不含** `[exit code: N]` 行：真實的 bash presenter 正是因為卡片以徽章單獨呈現退出狀態，才把該標記從正文中消費掉；若保留它，釘住的將是一幀把退出狀態顯示兩次的畫面——而產品路徑產不出這一幀。

`apps/web/tests/navigation-panes.e2e.ts` 在其既有的 `echo NAVIGATION_OK` bash 呼叫上新增真實瀏覽器場景，斷言 jsdom 無法計算的部分：把輸出面板擠壓到窄於內容寬度後，行仍保持單行且面板產生橫向溢位；執行狀態點解析為綠色的 success token，而不是字面顏色（沒有真實主題樣式表時，`--dsw-*` 變數根本不產生計算值），且它位於卡片盒之內、提示標籤之左——這正是那道 gutter 內邊距所擁有的不變數；複製控制元件走的是頁面自身的非同步 Clipboard API，而非 `execCommand` 兜底路徑。其 `terminal-card.expected.md` 基準記錄了提示行中已解析的 workspace——這正是不帶 `workdir` 的 bash 呼叫應當顯示的內容，而非一個裸 `$`。
