# Agent Note: Plugin configuration in the web settings page

Status: implemented

[English](2026-08-10-web-plugin-configuration.md) | [简体中文](2026-08-10-web-plugin-configuration.zh.md) | 繁體中文

## 問題

外掛程式的一切可設定項都只存在於 `cordis.yml`。想要更長的 shell 逾時、不同的搜尋端點或更少的平行工具呼叫，使用者必須找到組裝文件、瞭解它的形狀，然後重新啟動——而 Models 頁幾個月來一直在證明：settings 命名空間可以在瀏覽器裡編輯並立即生效。

支撐 Models 頁的那條 seam 本就是通用的：任何外掛程式都可以註冊命名空間，`settings.describe` 會提供它的 schema、分層與 revision。缺的是兩端。除 LLM 配接器與權限服務外，沒有外掛程式註冊過命名空間；而對於非模型提供方的命名空間，也沒有任何表層。

## 決策

三個宿主平面外掛程式各自註冊 settings 命名空間，一個瀏覽器側“外掛程式”分區聚合由各功能持有的分頁標籤。它的“可設定”分頁標籤渲染該部署所暴露的一切可編輯設定。

**分層不變。** 一個分節按 schema 預設值 → 外掛程式的組裝條目 → 使用者層解析。每個外掛程式把自己的 `cordis.yml` 條目作為 `base` 傳入，並透過 source thunk 讀取設定，因此儲存的變更會作用於下一次使用，而脫離的 settings 提供方會讓組裝條目繼續執行。schema 無法表達的約束——正有限、`graceMs` 的定時器上界、平行上限必須是正整數——成為分節的校驗器，因此錯誤的值在寫入時被拒絕，而不是到下一條命令時才失敗。

**shell 命名空間命名的是能力，而非某個實作。** `SHELL_SETTINGS_NAMESPACE` 由 `@deepseek-ai/dsh-shell` 匯出，因為一個宿主只組裝一個 `ctx.shell` 提供方：win32 層會把 POSIX 行換成 pwsh 行，而同時掛載兩者會因服務重複註冊在載入期失敗。因此兩個家族都能用自己的 schema 與條目註冊同一個命名空間而永不相撞；在平臺間攜帶的 `settings.yaml` 也能在兩邊繼續解析——schemastery 對象會保留當前 schema 未聲明的鍵。

**當外掛程式設定大於使用者所擁有的部分時，分節就是一個子集。** `agent-loop` 只暴露 `maxParallelToolCalls`；它的 `agents` 陣列在服務啟動時被消費一次，所以儲存在那裡的變更只會看起來生效。

**提供方按次投影，而不是固化。** `web-search-deepseek` 交給提供方的是一個 thunk 而非 options 值，因此端點或模型的變更無需重新註冊提供方即可作用於下一次搜尋——重新註冊會讓 web seam 的提供方選擇以閃斷的形式被使用者看到。

**暴露仍是 Host 的白名單。** 這三個命名空間加入 `WEB_SETTINGS_NAMESPACES`；僅有註冊依然不會跨越傳輸邊界，而不在該名單中的命名空間會與未註冊的命名空間得到完全相同的 `settings-not-exposed`。

**“可設定”分頁標籤不認識任何命名空間。** `dsh-client-ui-settings-plugins` 擁有“外掛程式”分區，透過 `settings.plugins.tab` 貢獻自己的 `configurable` 頁面，並在其中聲明巢狀的 `settings.plugin.item` slot。它渲染註冊進這個巢狀 slot 的卡片，因此帶瀏覽器半側的外掛程式擁有自己的卡片與控制元件。每張卡片透過用戶端 settings scope 綁定其命名空間，而該 scope 補上了表單所需的兩樣東西：原始 `user` 層——鍵的**存在**才標記欄位被覆蓋——以及把單個欄位清回組裝層的 `unset`。命名空間不可用時卡片什麼都不渲染，因此未組裝該外掛程式的部署不會顯示它的任何痕跡。

**卡片暫存修改，保存時才寫入。** 控制元件不持有自己的草稿：暫存文字歸卡片的表單所有，所有控制元件渲染的都是它，只有**保存**才把它變成文件變更。settings 寫入是持久且帶 revision 柵欄的，因此「失焦即提交」的控制元件會為使用者尚未決定儲存、也無從預覽的值花掉一個 revision；重設同樣只是暫存組裝預設值。schema 表達不了的約束歸 Host 的校驗器所有，所以表單在寫入後回讀分節、報告沒有落盤的保存，而不是自行預測結果，並保留這些草稿供使用者修改。金鑰控制元件雖然經由 credentials 領域寫入，也和其餘欄位一起暫存，因此一次保存覆蓋卡片上的全部內容。

## 備選方案

- **用註冊期的暴露聲明取代白名單。** 這纔是誠實的形狀——命名空間的擁有方聲明自己的暴露，在本倉庫之外分發的外掛程式也無需改動 `packages/host/apiproxy` 就能呈現自己的設定。之所以暫緩，是因為它會同時改變 seam 契約、全部現有註冊點與防枚舉語義；而且外掛程式要暴露任意 schema，還得先有 fail-closed 的脫敏路徑：目前只能經由 union 或 transform 抵達的 secret 會被原樣返回。
- **通用 schema 驅動程式的表單渲染器。** 再次否決，理由與 [web-config-plane 筆記](../architecture/2026-07-30-web-config-plane.md)所記一致：沒有呈現詞彙的欄位真值產出的是無法使用的卡片。三個外掛程式的手寫控制元件成本相當而可讀性更好，且該 slot 讓第四個外掛程式無需與本包協商。
- **在本頁編輯 preset 掛載的外掛程式。** 超出範圍，而且不只是「尚未實作」：preset 的行把設定內聯在 `agent.cordis.yml` 中，且根本無法註冊 settings 命名空間——同一 preset 掛載第二個工作階段時會因重複註冊而失敗。跨 preset 共享的使用者層還會覆蓋 preset 用來定義其 agent 身份的欄位——人設文字、委派接線——而這些欄位按設計就是各 preset 各自的。
- **按執行器包各取一個命名空間，而非按能力命名的 `bash`。** 否決，因為被組裝的執行器隨平臺不同，而設定文件不隨平臺不同：在 macOS 上設過逾時的使用者，到 Windows 上會悄無聲息地失去它。
- **把搜尋金鑰寫進 settings 分節。** 否決，因為那樣字面值就必須搭乘 `describe` 回應才能被渲染。卡片只報告是否已設定金鑰，並按分節所命名的引用經由 credentials 領域寫入。
- **每個控制元件失焦即提交，不設保存。** 最初就是這麼做的，後被替換：失焦不是決定。它每個控制元件花掉一個命名空間 revision，寫入前不給使用者任何預覽或撤銷的餘地，還會把無效草稿悄悄丟棄——被 Host 校驗器拒絕的值只是彈回原樣，不給任何理由。每張卡片一個保存，才讓寫入成為使用者執行的動作。
- **讓提供方按屬性逐次讀取 options。** 最初為了不改動讀取點而在每個使用處讀 thunk，這悄悄違背了構造函式自己聲明的契約：`search()` 先 await 憑據解析，之後才讀端點、模型與預算，因此落在那段 await 裡的設定寫入會把按舊分節解析出的金鑰發往新分節命名的端點。現在每次操作在入口只快照一次，並把該快照傳進憑據解析。
- **在瀏覽器端校驗欄位，好讓保存誠實。** 否決：這些約束住在擁有方外掛程式的分節校驗器裡，在這裡重述一遍就會讓同一條規則有兩個家，且可能隨版本各說各話。卡片只判斷自己的控制元件能判斷的事——數字草稿是不是數字——其餘交給 Host 回答，這正是保存要回讀分節的原因。

## 影響

使用者可以在設定頁編輯 shell 的命令逾時與輸出上限、agent 迴圈的平行工具呼叫上限，以及搜尋提供方的金鑰、端點與單次請求預算，每個欄位都標注是否由自己設定，並提供重設。

有兩項真實代價。加入第四個外掛程式仍需要在 apiproxy 白名單裡添一條，因此本頁的覆蓋面是 Host 的決定而非外掛程式的決定。而 web 部署移入 agent 平面的那些外掛程式——文件工具、技能、壓縮、todo 工具——在這裡一個都不出現，而它們恰恰是使用者最可能期待找到的；它們的設定仍歸 preset 編輯器。

bash 與 pwsh 執行器現在把 `config` 暴露為 source thunk 之上的 getter，而不再是 readonly 欄位。所有讀取點本就是按次讀取，因此別無變化；但若某個子類在構造期捕獲 `this.config`，就會悄然把組裝條目釘死。

`verify-cordis-config` 新增一項檢查，代價由本分付款過：合併 master 對用戶端清單欄位的重新命名（`dshClient` → `dsh.client`）後，本包仍聲明舊名，於是整個分區從瀏覽器上消失，且任何地方都不報錯——行照常組裝、空的 node 半側照常啟用，只是瀏覽器 roster 掃描永遠匹配不到它。這一點無從被既有閘門發現，因為組裝文件區分不了 surface 外掛程式與 Host 外掛程式：差別在清單裡。現在閘門要求 `packages/client` 包的 `./client` 匯出與 `dsh.client` 聲明雙向一致。之所以只限這一組：Host 包的 `./client` 匯出是給瀏覽器消費端 import 的類型化 wire face，不是 roster 要服務的外掛程式。
