# Agent Note: 每個 LLM 請求都可從工作階段日誌重建

Status: implemented

[English](2026-07-05-reconstructable-requests.md) | [简体中文](2026-07-05-reconstructable-requests.zh.md) | 繁體中文

## 問題

請求管線未能保證前綴穩定性以利用提供方快取，工作階段日誌也無法重建模型實際看到的內容。日誌遺漏了模型、系統提示詞和工具 schema，同時允許逐次呼叫的請求改寫。因此快取行為和重播等價性取決於碰巧載入了哪些外掛程式。

快樂路徑的參考形態是 MiniCode 的 `LLMClient`：一個有狀態的對話用戶端，隨對話推進只做追加而不重建，僅在系統提示詞、工具集或壓縮（compaction）真正改變了模型需要看到的內容時才重設。本 Agent Note 回答的設計問題是：如何在不放棄事件溯源的前提下獲得這種紀律。

## 決策

### 原則

**模型可見 ⟺ 已持久引用。** 凡到達模型請求的內容都必須能從工作階段日誌及其引用的不可變內容尋址對象中重建。可檢查的推論：任何人持有日誌、日誌引用的附件對象和固定程式碼版本，即可逐位元組重建迴圈的每個請求。純文字 `GenerateOptions` 仍是日誌的純函式；含圖片請求還會在配接器序列化期間透過 `ctx.attachments` 解析 `ImageAttachmentRef` 位元組，其中對內容摘要及已記錄元資料的校驗使對象尋找具有確定性，並在資料缺失或損壞時明確失敗。直接的一次性呼叫（壓縮的 summarize 呼叫）記錄其信封標量（`compaction/summary.{provider, model, maxTokens}`），其輸入是對日誌區域及這些引用對象的確定性程式碼運算——由於只有迴圈會標記請求歸屬，因此它們不在不變式內。

前綴快取穩定性是推論 #1，而非標題：一個僅附加的日誌經逐節點純函式投影，在 header 不變時自然產出前一請求的追加擴充——穩定性是湧現的，不是管理出來的。位元組精確的審計/重播是推論 #2；帶*可歸因*漂移的復原與 fork 是推論 #3。

### 機制

**訊息。** `Session.deriveMessages()` 帶快取：每個 surface 條目在首次出現時透過公開的逐事件函式 `deriveEventMessage(event)` 精確投影一次；surface 重寫（壓縮的 `replace`，即 `SurfaceManager.replaceGeneration`）觸發重建。呼叫方每次獲得一個新陣列，底層是共享的深度凍結訊息：透過投影變異已記錄的歷史是不可表達的（會拋例外），取代了舊的逐次呼叫克隆隔離。外部重建器對日誌前綴摺疊同一個公開函式，因此不可能有兩條路徑產生分歧。

`EpochHeader` 記錄請求的非歷史狀態：呼叫設定、渲染後的系統提示詞和工具 schema，空值規範化為缺失。`request/header` 始終寫入完整快照：首個迴圈實例使用 reason `initial`，後續實例使用 `resume`，實例內變更使用 `change`。`foldRequestHeader` 選擇最新快照。舊的 `request/header-delta` 事件和已移除的 `fallback` reason 在追加或載入時都會被拒絕。

每個擬議步驟先領取其 inbox 批次，再執行 `agent/pre-step`。reject 不打開步驟；enter 打開 `step/start`，並把最終訊息批次記錄為 `user/message` 事件。隨後步驟組裝系統提示詞與工具，`agent/request` 只能替換凍結的呼叫設定種子。迴圈記錄所需的完整 header 快照，從派生訊息與該 header 建置 `GenerateOptions`，對其深度凍結但保持 `AbortSignal` 活躍。首次呼叫設定從顯式的 `AgentOptions` 出發，保留 fork 覆蓋和復原重設定；後續呼叫從摺疊後的 header 出發。

**已打開步驟是重建邊界。** 進入步驟的 `user/message` 批次與任何新寫入的 `request/header` 都位於請求分派之前。原子領取後發生的注入加入後續請求；必須影響本次請求的監聽器則透過 `agent/pre-step` 返回訊息。header 重建選擇該步驟的 `request/header`，或在無新 header 寫入時沿用前一個快照。

**強制執行。** `dsh-agent-loop/invariant` 配套外掛程式向 `ctx.invariants` 註冊，並在被選用時透過一個全新的 `Session` 獨立重建每個迴圈請求，使活躍快取無法為自身背書，然後在 `llm/stream` 處比較訊息和摺疊後的 header 欄位。迴圈透過 `dsh-llm` 的 `markAgentLoopRequest()` 記錄精確的凍結請求；這一行程內標識讓配套外掛程式和其他請求觀察者識別對話工作，而直接的一次性呼叫無論其凍結形狀或工作階段 id 如何都保持排除。正確性相依性於序列有界的重建，而非監聽器順序。帶金鑰的 e2e 要求首次請求之後有正值的 cache-read token；逐步驟用量是生產訊號，header 變更或壓縮表現為下一步驟的 cache-read 下降。

### MiniCode 形態：採納，以事件日誌為真源

與 MiniCode 相同，對話僅附加推進，僅在模型可見狀態變更時重設。與 MiniCode 不同，事件日誌仍是真源，因為它同時擁有持久化、復原、邊界、工具配對，並記錄派生事件到其輸入事件的關聯。`Session` 快取從日誌推導的訊息和 header 摺疊結果，使每個請求都可獨立檢查。

## 曾考慮的替代方案

- **用戶端作為真源**（照搬 MiniCode）：在日誌之外多出一個執行時期真相——兩者漂移而無人察覺；見上節。
- **映像檔日誌的有狀態傳輸用戶端**：重複對話狀態，需要圍繞監聽器做回滾，留下未記錄的編輯路徑，且仍無法重建請求 header。Session 擁有的快取加已記錄的 header 避免了這些分裂的真相。
- **逐次呼叫的請求標量**（一個可自由變異的設定傳給每次 `agent/request` 分發）：監聽器可以零記帳地逐次切換模型，悄然放棄本設計旨在保護的提供方快取。設定是逐對話的已記錄狀態；waterfall（瀑布式事件）提議，日誌記錄。
- **偵測並報告**（比較連續請求，發散時告警）：事後捕獲違規；違規請求仍可構造並行出。因違規必須在介面層面不可表達而否決。
- **事件驅動組裝**（僅在變更訊號時重新渲染）：存在漏訊號的 bug 類別——工作階段中途註冊的工具寄出 `tools/change` 而非 `system-prompt/change`，第三方提供方可能什麼都不發。逐步驟渲染加值比較在零訊號紀律下即可穩健工作。
- **自訂 header-delta 編解碼器**（系統行編輯、按名稱鍵控的工具編輯、完整設定/前綴替換）：減少了重複位元組，卻複製了表示及其 diff/apply/fallback 機制。完整快照只保留一種重播表示。
- **Header 快照上的敘事性變更欄位清單**：可以透過比較連續快照推導。`reason` 仍保留，因為實例邊界無法從快照值推導。

## 後果

- 一個日誌無法解釋的請求不可能被意外構造——無論是迴圈還是監聽器；變異已建置的請求會拋例外；每個 header 變更都是持久的、可 diff 的日誌事件。
- 模型可見上下文使用已記錄訊息通道。`agent.inject()` 與工具 `additionalContexts` 進入 inbox，等待後續領取；必須與當前已領取批次一起結帳的上下文由 `agent/pre-step` 返回。每個進入步驟的值都是帶來源的持久 `user/message`，只付出一次代價並在後續成為可快取前綴，代價是會在歷史中累積直至壓縮。
- 在提供方處仍需全價計算的內容是固有的且已記錄的：壓縮（其 `compaction/*` 事件和替換條目）、真正的提示詞、工具或設定變更（reason 為 `change` 的 `request/header`），或帶漂移的行程邊界（不同的 `resume` 快照）。提供方自身的 reasoning-content 排除由伺服器端管理。
- `agent/pre-step` 是當前請求的訊息通道；直接修改 inbox 則是最終進入後續請求的通道。
- 工具結果裁剪無需新機制：一個已記錄的單條目 surface replace（`start === end`），攜帶同一 `callId` 下裁剪後的 `tool/result`——屬壓縮家族，重播正確，快取失效由相同的壓力邏輯批次處理。
- 工作階段日誌每個迴圈實例成長一個 `request/header` 快照，並在真正變更時增加快照。它比 delta 編解碼器更大，但相對區塊密集型日誌仍然很小，並只保留一種重播表示。`SESSION_FORMAT_VERSION` 保持 `0`；舊的 delta 事件被拒絕而非遷移。
- 快照預期輸出變更一次（每個 transcript（文字記錄）增加其 header 事件）；寫入檔案系統的 fixture（測試前置資料）以規範化的撰寫形式儲存，工具參數使用 cwd 相對路徑，因為重播只對 cwd 無關的參數路徑做往返。
