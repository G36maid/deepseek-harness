# Agent Note: 重播式 token 計量服務

Status: implemented

[English](2026-07-15-replay-token-meter-service.md) | 繁體中文

## 問題

上下文壓力並不只對壓縮（compaction）有用。壓縮後端、溢位保護或未來的請求策略外掛程式都可能需要回答同一個問題：持久請求消耗了多少 token？如果把該摺疊邏輯留在 `dsh-compaction-basic` 內部，就會重複實作重播邏輯，使未載入壓縮的呼叫方無法使用計量，並誘使呼叫方複用過時的覈算結果。

提供方 usage 也不是完整答案。它只描述某個精確請求信封下的一次成功呼叫，而當前表層之後還可能成長、縮小或被替換。工作階段也可能切換提供方與模型，舊日誌可能缺少構成 assistant 訊息的區塊 seq，usage 欄位還會分別報告輸入、快取讀取、快取寫入、輸出與推理計數。因此，可用的服務必須把最新精確錨點與保守的啟發式重新定價結合起來，並公開每個結果已經消費的日誌修訂號。

## 決策

### 一個具體的 LLM（大型語言模型）家族服務

`@deepseek-ai/dsh-token-meter` 是 `packages/llm/` 下的單個具體包，並註冊 `ctx.tokenMeter`。在第二種實作出現之前，它不會被拆成介面與後端。`TokenMeter` 本身公開 `measure(session, requestHeader?)` 與 `estimateMessage(message)`；消費端直接呼叫這個單例服務。

服務沒有設定。估算採用固定的每 token 四個字元啟發式規則，並加上結構開銷。服務不提供模型 profile、容量設定、密度設定、分詞器後端或語言專用策略。對精確提供方/模型容量的查詢由配接器單獨負責，具體見[路由模型上下文與壓縮策略 Agent Note](2026-07-20-routed-model-context-and-compaction-policy.md)。

### 逐工作階段重播摺疊

每個工作階段都有一個隔離的增量摺疊。活躍摺疊透過 `session/event` 前進；每次讀取都會追到持久日誌尾部，因此監聽器順序、種子工作階段與服務重載不會改變答案。摺疊跟蹤規範的完整請求標頭快照、步驟邊界、表層追加與替換、assistant usage，以及每條 assistant 訊息引用的區塊 seq。下一個畸形事件會以交易方式失敗並保持未讀，不會讓狀態只修改一半。

`measure(session, requestHeader?)` 只同步一次摺疊，並在返回標量壓力的同時給出逐位置節點價格。`totalTokens` 仍表示請求與回應壓力；`surfaceTokens` 是僅針對表層的啟發式總量，並等於 `nodes[].tokens` 之和。`requestHeader` 覆蓋只改變壓力定價，表層欄位始終描述當前工作階段。`estimateMessage(message)` 不相依性工作階段狀態，直接應用固定啟發式規則。每個結果都是一個分離且深度不可變的快照，只攜帶一個 `logRevision`。每次計量都會複製當前節點，因此成本為 O(surface)。

只有當待計量的規範請求信封等於最近一次成功呼叫的錨點時，服務才複用提供方 usage。提供方、模型、系統提示詞、前綴、工具或呼叫設定任一變化都會觸發完整的啟發式重新定價。表層變化相對匹配錨點保留有符號增量，包括縮小替換後的負值。後續成功請求會替換先前錨點，提供方或模型切換時也一樣。

Usage 會對互不重疊的輸入、快取讀取、快取寫入與輸出 bucket 求和，不會再次加入推理計數。每次成功模型呼叫都會記錄 `assistant/message`，包括無內容呼叫與達到 token 上限的呼叫，並帶上精確的更早區塊 seq。顯式的空 `sourceEventSeqs` 清單表示已知為空的提供方流；舊日誌中缺失的清單則保守地把持久 assistant 輸出視為提供方輸出。

### compaction-basic 消費計量，但不擁有計量

`dsh-compaction-basic` 要求 `ctx.tokenMeter`；`CompactionEngine` 不增加 token 方法或類型。設定、區域交易與摘要分別保留在獨立模組中，服務自身註冊自動監聽器，而 `summarize()` 仍是唯一的子類掛鉤。單例計量器一致用於壓力、保留、被遮蔽內容、引用的源事件以及非縮小摘要拒絕的定價。

自動壓縮的每次閾值與保留聯合決策只使用一次統一計量。區域交易會在追加持久 `compaction/start` 鎖後執行計量，在非同步摘要完成後再次計量，隨後比較分離的表層節點向量。期間發生的表層變更會阻止替換；`logRevision` 可以因無關的純日誌事實而推進，而不會使未變的選定範圍失效。

壓縮策略採用服務級預設值：閾值比例 `0.8`、保留尾部比例 `0.16`、`summarizationProvider: ''`、`summarizationModel: ''`、`maxTokens: 8192`、`compactionRetries: 1`、`maxOverflowRetries: 1` 與 `auto: true`。頂層欄位適用於每個路由目標；`modelPolicies` 中的精確提供方/模型項可以部分覆蓋這些欄位。壓力檢查以所屬配接器解析的容量為基準換算這些比例，`retainTokens` 可以替代 `retainRatio`；保留值必須小於最終閾值。摘要提供方與模型必須同時設定或同時為空；空組合先解析最近記錄的請求目標，再使用 `AgentOptions` 中的組合。

自動壓力檢查在請求派生前執行於 `agent/pre-step`，並計量前一個 `agent/request` 實際所選提供方/模型產生的規範持久信封。沒有請求標頭的工作階段尚無已完成的路由請求可供判斷，因此不執行工作；任意路由目標都可使用這個單例估算器。規範的溢位復原流程使用同一計量結果強制選擇範圍，並且只有在表層替換得到證明後才重試。

## 測試

單元測試覆蓋固定估算、信封失效與錨點替換、重播邊界、不可變快照、已路由壓力、收斂、溢位 generation 證明與回滾。真實 Loader/Include fixture（測試前置資料）驗證零設定 token-meter 與 compaction-basic 按相依性順序載入的路徑。

## 考慮過的替代方案

- **把估算保留在 `CompactionEngine` 內**——不予採納，因為計量擁有獨立於壓縮的消費端與重播語義；它還會強迫每個壓縮器暴露同一套無關 API。
- **立即把 token meter 拆成介面與啟發式後端**——不予採納，因為目前只有一種實作。單個具體服務保留未來的 seam，同時避免推測性的包與設定。
- **把模型鍵控視窗與密度 profile 放進 meter**——不予採納，因為重播估算不擁有模型路由或容量事實。路由所屬配接器公開容量，compaction-basic 則擁有消費端專用的閾值與保留策略。
- **保留獨立的標量與表層計量**——不予採納，因為消費端必須為一次決策執行兩次讀取並匹配修訂號。僅讀取標量可以避免在低於閾值時複製節點，但拆分 API 會在消費端引入競態視窗；統一快照接受 O(surface) 複製成本，以換取結果一致性。
- **在不同信封之間移用提供方 usage**——不予採納，因為模型、工具、前綴與呼叫設定都是請求事實。不匹配時會重新定價完整當前請求。

## 後果

- Token 壓力擁有一個可供壓縮與未來外掛程式共享的重播感知所有者。
- 預設值讓 meter 成為零設定組合項；部署時在各個路由所屬配接器上設定容量，並在 compaction-basic 上設定選填策略覆蓋。
- 固定啟發式定價仍然只是提供方行為的估計，並不是精確分詞器或請求序列化器。
- 每次計量都會複製當前帶位置資訊的表層，因此成本為 O(surface)，低於閾值即可結束的壓力檢查也不例外。
- 遇到畸形持久邊界時，計量會明確失敗。這會把損壞的重播轉化為具名整合錯誤，而不是讓壓力靜默漂移。
- 步驟後壓力檢查讀取精確記錄的路由、工具與前綴邊界；對於在成功 usage 錨點出現前就被拒絕的請求，提供方溢位分類仍是由配接器維護的兜底路徑。
