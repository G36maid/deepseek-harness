# Agent Note: 按項目分組的工作階段目錄

Status: implemented

[English](2026-07-24-project-session-directories.md) | [简体中文](2026-07-24-project-session-directories.zh.md) | 繁體中文

## 問題

持久化根目錄可以只供一個項目使用，也可以由多個項目共享，還可以是臨時目錄或集中式目錄。對 cwd 進行雜湊得到的分桶目錄能適用於所有這些部署方式，但開發者無法從目錄名辨認項目，因此共享根目錄難以瀏覽。

每個 JSONL 工作階段也直接以單個文件的形式放在項目分桶目錄中。這種版面配置沒有為元資料、附件、溢寫文件或協調狀態等其他工作階段產物提供歸屬目錄。

## 決策

JSONL 後端按可讀的項目鍵儲存工作階段，並為每個工作階段提供獨立目錄：

```text
<configured-root>/
  --<normalized-cwd>--/
    <encoded-session-id>/
      session.jsonl.zstd
```

原始模式使用 `session.jsonl`，沒有 cwd 的工作階段使用 `_no-cwd`。檔案系統路徑分隔符和驅動器分隔符會轉換為 `-`，不安全的程式碼單元使用 `~XXXX`，可讀名稱則限制長度，以確保目錄項不超過檔案系統限制。

項目鍵有意不帶雜湊後綴。這遵循 coding agent（代理）常用的易讀約定，使規範化後的項目路徑本身就是完整的目錄名。規範化過程有損：`/a/b-c` 與 `/a-b/c` 等路徑，或者保留前綴相同的長路徑，會共用同一個項目目錄。不同的工作階段 id 仍會選擇不同的工作階段目錄；複用相同的工作階段 id 仍構成儲存衝突，系統會予以拒絕。

在不區分大小寫的檔案系統上，大小寫不同的項目鍵也可能指向同一個物理目錄。只有當檔案系統路徑規範化將已發現的路徑和預期路徑解析為同一個 transcript（文字記錄）時，身分驗證才接受這種拼寫變體。規範化後的路徑如果不同，仍視為儲存損壞，因此，即使存在大小寫別名，在區分大小寫的儲存上也不會放寬同一 id 的衝突檢查。

根目錄由部署設定決定。這種版面配置既不選擇全域性根目錄，也不要求項目共享根目錄。部署選擇集中儲存時，目錄名仍能讓項目路徑易於辨認；使用項目本機根目錄時，也採用同樣的確定性結構。

編碼後的工作階段 id 用於命名歸屬目錄，而不是 transcript 文件本身。`SessionPersistence.locate()` 仍返回固定的 transcript 路徑，從而保持掛鉤 `transcript_path` 和 `DSH_SESSION_JSONL` 的語義不變。發現過程會忽略工作階段目錄中的其他條目，因此後端以後新增工作階段自有產物時無需再次改變版面配置。

延遲物化仍以 transcript 為界：`create()` 不執行檔案系統 I/O，首次追加會先建立項目目錄和工作階段目錄，再以無衝突方式發布 transcript。空目錄不會被列為工作階段。後端會顯式報告版面配置錯誤並拒絕扁平的 `<project>/<id>.jsonl*` 產物；預發布格式不提供自動資料遷移。

## 考慮過的替代方案

**保留不透明的 cwd 雜湊。** 這可以保持目錄名簡短，但當多個項目共享一個持久化根目錄時，無法滿足按項目路徑瀏覽的需求。

**把工作階段文件直接放入各項目目錄。** 這與 Claude Code 和 pi 的基本文件組織一致，但沒有為未來產物提供工作階段級歸屬邊界。

**新增防衝突的雜湊後綴。** 這種方式能區分規範化形式相同的路徑，但會使目錄名不再只是規範化後的項目路徑。所選約定接受有損的項目分組，以換取更簡單、易於辨認的名稱。

**強制使用集中式根目錄。** 不予採納，因為儲存位置屬於部署設定。項目分組在根目錄共享時有用，在不共享時也沒有負面影響。

**同時載入扁平版面配置和目錄版面配置。** 按照預發布階段不提供相容性的原則，不予採納。只接受一種版面配置，可以讓身份檢查和發現過程保持確定性。

## 後果

共享儲存可以透過易於辨認的項目名進行瀏覽，本機根目錄和自訂根目錄則繼續保有現有的設定自由。每個工作階段都有一個可供後端未來存放自有產物的目錄，而現有 transcript 消費端仍會收到檔案路徑。

項目目錄名比原先由 12 個十六進位字元組成的 cwd 雜湊更長。路徑很長時，目錄名只顯示長度受限的前綴。移動項目通常會選擇不同的目錄，但按設計，不同的 cwd 字串如果規範化成相同名稱，就會共用同一個項目目錄。
