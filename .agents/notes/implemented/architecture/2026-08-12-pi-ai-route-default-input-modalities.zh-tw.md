# Agent Note：pi-ai 模型自行聲明輸入模態，未聲明即為文字

Status: implemented

[English](2026-08-12-pi-ai-route-default-input-modalities.md) | [简体中文](2026-08-12-pi-ai-route-default-input-modalities.zh.md) | 繁體中文

## 問題

`settings.yaml` 裡沒有任何寫法能把一個手寫的 pi-ai 模型描述成接受圖片，而配接器對已安裝 pi-ai catalog 未描述的每個模型都假定純文字。部署透過 Web UI 的“新增自訂提供商”卡片新增的模型統統屬於這一類，因此一個提供視覺模型的 OpenAI 相容閘道，無論實際提供什麼，報出來的都是 `inputModalities: ['text']`。

Harness 把缺失的模態當作否定能力，並有三個准入點在構造任何請求之前就依據它行動：模型選擇拒絕切換進已含圖片的工作階段，prompt 准入拒絕圖片，`read_image` 拒絕讀取。它們的診斷讓使用者去選一個支持圖片的模型——這條建議沒有可達的指向對象，因為沒有任何設定鍵能讓手寫模型變得支持圖片。這條路封死在元資料上而非能力上：請求轉接器和每種 pi-ai 線路協議都能攜帶圖片，`llm-pi-ai` 自身的流前置檢查纔是唯一會攔下它的東西。

原始碼中把這一假定論證為配接器的真實能力而非部署選擇，而 [[2026-08-03-pi-ai-declared-provider-catalog]] 在決定設定面公開哪些 `Model` 欄位時記錄了同一套論證（「沒有任何讀取方：…… `context.ts` 只保留文字塊」）。該論證描述的是 DeepSeek chat-completions 配接器——它的序列化器確實拒絕 image block——對 pi-ai 路由從來就不成立。本 note 僅在模態一項上取代那一條；定價在那裡依然因其自身、仍然成立的理由保持關閉。

## 決策

**模態的解析順序是：條目的 `input` → 已安裝 catalog 條目 → 路由的 `defaultInput`，後者自身預設為 `[text]`。** 這與 `contextWindow`、`maxTokens` 已經在用的鏈條逐欄位一致。pi-ai 把 `Model.input` 定義為必填且按模型給出，因此條目欄位直接映像檔上游：一條路由可以讓視覺模型與純文字模型並存，而 override 可以修正那些閘道實際提供的模態與 catalog 記錄不符的模型。路由欄位則讓那些**未被 catalog 描述的**模型全都接受圖片的閘道，不必在每個條目上重複一遍。

**路由值是回退值而非覆蓋值——catalog 的優先級更高。** 這採用的是 `default*` 的順序而非 `compat` 的，兩者不可互換：`compat` 之所以蓋住 catalog，是因為路由級的協議改指會整體作廢 catalog 關於推理分派的事實；而模態是按模型的屬性，對 catalog 自己出貨的那些模型，它記錄得準確無誤。讓路由值獲勝就意味著 `defaultInput: [text]` 會悄悄剝掉該路由上每一個 catalog 視覺模型的圖片能力——一個沒有對應收益的坑，因為收窄其中某個模型正是該模型自己的 `input` 要做的事。

**未聲明即 `[text]`，而這是「尚未聲明」，不是對端點的猜測。** 沒有任何環節能去詢問閘道的模態——沒有任何 OpenAI 相容的清單端點會報告它們——因此唯一誠實的底線是每個受支持協議都確定攜帶的那個模態。這也正是模態回退值與容量回退值分道揚鑣之處：262,144 只是個說得過去的數字，且兩個方向都會錯（閘道只給 8k 會溢位，給 1M 則被浪費），而 text 在一個方向上是安全的。兩種猜錯的代價同樣並不對等。少聲明會在圖片被附加之前就拒絕並點名該模型，補救辦法是一行有文件可依的設定。多聲明會接納一張圖片、再由提供方在輪次中途拒絕——而此時 prompt 准入**早已**把訊息持久化提交，於是工作階段會不斷重發一個不可能成功的請求，且模型選擇拒絕切換到任何純文字模型。在最早可解析點付出一次廉價的拒絕，勝過在最晚點付出一次昂貴的。

**條目的空清單與預設同義；路由的空清單則被拒絕。** `[]` 描述的是一個什麼都不接受、無法服務任何請求的模型，因此不作答，解析繼續往下走。這個讀法不是修辭：設定 schema 會為預設陣列物化出 `[]`，把它當作“什麼都不接受”，會悄悄剝掉 `models` 清單恰好點到的每一個 catalog 視覺模型的圖片能力。而路由值下面沒有可以代為作答的層級，因此它的空清單在寫入處即被拒絕。路由的 `models` 清單出於同樣的理由，早已用同一種方式解析預設與空。

**沒有任何設定介面編輯 `input`。** 它和 `compat`、`reasoningEfforts`、`thinkingBudgets`、`headers` 一樣是 settings 文件欄位，而模型清單編輯器仍是一張只覆蓋 id、名稱和兩個容量的手寫表單。這不會帶來持久代價，因為那張卡片本來就是按“承載自己並不編輯的欄位”建造的：它的行 patch 會先展開已儲存的行再應用改動，而採納候選時已有行優先於重新發現的候選，因此手寫的 `input` 在兩條路徑上都能存活。

DeepSeek chat-completions 配接器保持不動。它的 `['text']` 是關於其序列化器的事實，而不是一處缺失的聲明，它繼續在傳送前拒絕。

## 備選方案

- **樂觀的 `[text, image]` 預設值** —— 讓觸發本次變更的場景零設定即可工作；而且網頁表單不會寫入任何模態，因此保守預設值會把補救辦法留在一個純 Web 使用者沒有理由打開的文件裡。被否決的理由是猜錯時的嚴重程度：被拒絕的附件是一個有文件可依的減速帶，而提供方拒絕會毒化整個工作階段、表現為一次無從解釋的反覆失敗，且只能靠換模型或重開會話脫身。把補救辦法寫進設定模型頁即可補上可發現性的缺口；而毒化的工作階段沒有任何東西能補。
- **讓路由值蓋住 catalog**（`compat` 的順序：條目 → 路由 → catalog）—— 可以讓把 catalog 路由改指到自家閘道的部署，一句話聲明「這裡沒有視覺能力」。被否決是因為同一句話也會在有人照著容量欄位類比寫下它的路由上，悄悄停用每一個 catalog 視覺模型；而那個正當場景由該模型自己的 `input` 承擔。覆蓋值還必須在路由級改名叫 `input`，因為在兩個貨真價實的回退值旁邊把它叫作 `default*` 是名不副實。
- **完全不要路由欄位，只要條目欄位** —— 最貼近上游（上游沒有路由級概念）。被否決的理由是產品自身流程會產生的批次場景：「取得可用模型」一次採納三十個不帶模態的 id，全是視覺模型的閘道就得逐個手寫 `input`。
- **只要路由級 `defaultInput`，不要條目欄位** —— 無法在一條路由上混合模態，也無法修正單個 catalog 模型，唯一的變通辦法只剩「把該提供方拆成兩個路由鍵」，代價是多一個永久的 provider id 和每個模型選擇器裡的一項重複。
- **探測端點的模態** —— 沒有任何 OpenAI 相容的清單端點會報告它們。
- **從模型 id 推斷**（`*-vision`、`*-vl`）—— 命名約定不是能力，閘道可以隨意改名。
- **繼續拒絕，只改進診斷** —— 那則訊息對狀態的描述本來就準確，對補救辦法則毫無用處；缺的正是補救辦法。

## 影響

自訂提供方下的視覺模型只需在 settings 文件裡寫一行 `input: [text, image]`——或者當該路由列出的模型全都接受圖片時，在路由上寫一行。這就是修復的全部：三個准入點隨即接納它上面的圖片，`read_image` 也可用。什麼都不寫的部署保持原有行為完全不變，因此沒有任何既有路由改變它報出的內容。

圖片准入閘門在各處都保住了自己的意義，因為它讀到的每一個模態，如今要麼由已安裝 catalog 記錄，要麼由人寫下。沒有任何環節會替部署宣稱一項能力。

聲明瞭端點並不提供的圖片能力的模型不會在本機被攔下——該斷言不經驗證——而由此產生的失敗代價高昂。prompt 准入在構造請求之前就把使用者訊息持久化提交（`agent/inbox/spliced`），因此被拒絕的圖片會留在工作階段日誌裡：該模型會不斷重發它，而模型選擇拒絕切換到任何純文字模型。復原途徑是選擇一個確實提供圖片能力的模型、fork 到圖片之前，或者開啟新工作階段。讓這次失敗不具破壞性——傳送失敗時把尚未消費的圖片訊息從日誌中回滾出去——纔是能讓樂觀預設值重新可考慮的那項改動，本次未做嘗試。

## 測試

`packages/llm/llm-pi-ai/tests/catalog.spec.ts` 在 resolver 層覆蓋了這條鏈的每一級以及空清單的兩種讀法：一條路由上未聲明的模型與條目聲明的純文字、視覺模型並存，路由預設值為未聲明的模型作答而條目仍然壓過它，catalog 視覺模型在更窄的路由預設值下保住自身模態，條目的 `[]` 走繼承而非清空，以及路由的 `[]` 被拒絕。另有一條用例把每一級端到端複驗一遍——寫入的 settings 段、外掛程式自身的註冊、以及 `ctx.llm.listModels` / `resolveModelInfo`——因此文件與 `LlmModelInfo` 之間若有斷點無法矇混過關。

`config.spec.ts` 負責 schema 邊界：兩個層級上的未知模態拒絕、路由空清單被 schema 接受而由 settings seam 真正執行的命名空間校驗器拒絕，以及繼承規則所倚賴的「預設陣列物化為 `[]`」這一事實。

沒有任何無金鑰 snapshot 通道會跑 pi-ai 路由：snapshot 示例驅動的是 `dsh-llm-replay`，它在自己的設定裡直接聲明模態，而 pi-ai 路由需要一個真實端點，其埠是靜態 `cordis.yml` 無法寫出的。本次變更所供給的那些准入點已經透過該提供方在那裡得到覆蓋（`examples/acp-agent/image.cordis.snapshot.yml` 與 `image-text-route.cordis.snapshot.yml`）且不受影響——改變的是某個配接器報告什麼，而非閘門如何讀取它。
