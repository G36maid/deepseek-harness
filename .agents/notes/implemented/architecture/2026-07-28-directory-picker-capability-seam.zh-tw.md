# Agent Note: web GUI 宿主的能力可辨識目錄選擇 seam

Status: implemented

[English](2026-07-28-directory-picker-capability-seam.md) | [简体中文](2026-07-28-directory-picker-capability-seam.zh.md) | 繁體中文

## 問題

web GUI 的「打開本機資料夾」流程被焊死在一種互動上：`host.pickDirectory` 呼叫編譯進 `dsh-host-apiproxy` 的原生 OS 選擇器（私有模組，僅測試注入點）。這個形態服務不了遠端部署——沒有任何 OS 對話框能彈到另一臺機器的瀏覽器裡——而應用內目錄瀏覽器（Figma `Harness` 802-56979）需要列舉／建立原語，那是**另一種互動約定**，不是同一約定的另一種實作。想換互動只能改閘道原始碼，違背倉庫「一切皆外掛程式」的立場。

## 決策

在 `packages/host/` 落一個三包能力 seam——`directory-picker`（Service Definition）、`directory-picker-native`、`directory-picker-browse`（後端）——唯一約定方法 `capability()` 返回**可辨識聯合**：`{ kind: 'native', pick(signal) }` 或 `{ kind: 'browse', list(path?), createDirectory(path, name) }`。閘道（`dsh-host-apiproxy`）注入 `directoryPicker`，提供對應的 RPC，另一種 kind 的呼叫以 `directory-picker-unavailable` 應答。聯合之所以可辨識，是因為後端差異在**互動形態**——壓平成統一方法集會逼每個後端偽裝另一方的形態。

**client 側靠 slot 組合，而非按廣播分支。** ui-workspace 的兩個觸發表層各自聲明一個 `single` 目錄流洞（`conversation.hero.workspace.directoryFlow`／`sidebar.workspaces.directoryFlow`；之所以是兩個 key，是因為一個洞只有一個聲明它的 slot entry——owner 約定相同、佔用者相同）。後端包是**雙麪包**：瀏覽器一側把匹配的互動註冊進兩個洞——`-native` 是驅動程式 `host.pickDirectory` 的無渲染佔用者，`-browse` 是應用內的選擇工作區目錄對話框。洞的 owner 工作階段（`open`/`busy`/`onPicked`/`onCancel`/`onError`）承載整個交換：ui-workspace 保留觸發（選單入口僅在洞被佔用時渲染）與接納（`createWorkspace({path})`、可重試的錯誤對話框、重新選擇），佔用者持有從 `open` 到所選路徑之間的一切。因此一行 `cordis.yml` 同時切換宿主能力與 client 流程；錯配在構造上不可能，同時掛兩個流程包會在 client 載入期失敗（`single` 洞）。早先的 `host.describe.directoryPicker` 廣播與用戶端 kind 分支被刪除——組合已經接好兩側後，供用戶端分支用的 wire 事實不再有任何消費者。洞登錄檔（`ctx.slots.entries`）取而代之，成為每次打開選單的佔用讀取。

並入本決策的位置與策略裁決：

- **不用 `ctx.fs` seam。** `packages/fs/` 是面向模型／工作階段的儲存棧（policy 事件、沙盒可換後端）。騎上去會把 GUI 瀏覽耦合進模型的限制後端——為模型換 `fs-sandbox` 絕不能改變 GUI 行為——而 OS 事實（home 錨定、隱藏約定）也不是儲存原語。picker seam 保持無展示、無模型；`packages/host/` 是它消費端域的家。
- **相依性調研（手寫 vs 引入）。** Node 標準庫本身就是維護中的跨平臺 OS 層（`readdir(withFileTypes)`、`homedir`、路徑語義）；調研過的替代品都過不了相依性門檻——文件管理器包（`node-file-manager`、`files-and-folders`、Syncfusion 的提供方）是整套 HTTP 應用（契合度不過），盤符工具（原生擴充 `drivelist`、約七年未更的 `windows-drive-letters`）健康度／比例失當。browse 後端是標準庫上的薄配接器。
- **隱藏條目：返回並打標。** 宿主標注 `hidden`（POSIX 點前綴約定）並返回全部條目；用戶端過濾。展示策略留在用戶端，「顯示隱藏」開關正是作為這一純用戶端改動落地：標籤固定的 footer 開關，其狀態由按下態呈現承載（`aria-pressed` + 勾選符號）；以點開頭的路徑草稿前綴會顯出它所指名的隱藏條目；當前選中項則不受隱藏與前綴兩種過濾影響（它錨定著雙欄檢視表）。Windows 的 `FILE_ATTRIBUTE_HIDDEN` 不被 dirent 暴露——記為限制，直到原生探測的收益抵得上其成本。
- **路徑編輯器的取消範圍：對話框卡片。** browse 用戶端的路徑編輯器在按 Escape 與焦點離開卡片時取消，兩者都在卡片範圍的包裝層而非輸入框上監聽——Tab 把焦點停到某個過濾命中的行之後，輸入框已不在事件路徑上，但 Escape 仍須收起編輯器（而非對話框），其後的焦點離開也仍須取消。不取消的豁免：視窗／分頁標籤失焦、卡片內焦點移動，以及指針路徑（編輯期間行與開關在 mousedown 時抑制焦點奪取）。預填與草稿末段過濾所用的分隔符從 `listing.home` 推斷；下文的線上欄位替代方案記錄了被延期的權威形態。編輯器與其過濾的清單之間的 combobox 語義（`aria-expanded`／`aria-controls`／active-descendant、結果播報）同樣被延期——目前二者在輔助技術看來是彼此獨立的控制元件。
- **路徑編輯器自我點明，各欄跟隨草稿。** 點擊即編輯的區域不再是隱形的：欄右端坐著一枚鉛筆圖示，懸停／聚焦時**整條欄**以編輯器自身的那隻框亮起——輪廓與內邊距在兩種模式下都由欄承載，於是懸停預覽的正是點擊後出現的那隻輸入框，區域與輸入框互換時也沒有任何尺寸變化。編輯器打開期間，各欄跟隨草稿，而不是停在它打開那一刻恰好列出的層級——末段對其目錄部分所指的層級做前綴過濾，無一匹配的末段解除過濾（還在拼寫中的名字不該把正在拼寫它的那一欄清空），而其餘任何目錄部分都會在停頓 250ms 後被掃描，並經由每次導覽共用的那套以選中項為錨的雙欄落地落定，於是鍵入路徑移動 Miller 檢視表的方式與 crumb 跳轉完全一致——繼續鍵入即下潛、刪掉末段即上退——全程不必離開編輯器。**分欄個數纔是不變數**：最後一欄永遠是路徑所指的那一層，其上一層在它旁邊，只有展示根會獨佔一欄。「只要任意一欄碰巧列出了該目錄就跳過掃描」是更省事、也是錯的規則——刪掉一段之後，正在鍵入的那一層會留在左欄，而它自己的子欄仍立在右邊，於是兩欄不再讀作「我在哪兒、我從哪兒來」。只有最後一欄自己的末段不需要掃描。一種落地形態、兩個呼叫方：提交的路徑關閉編輯器並呈現失敗，草稿跟隨掃描則兩者都不做。該掃描是推測性的——鍵入到一半的目錄多數時候讀不出來——因此失敗時保留最後一次可讀的分欄並保持沉默。Enter 仍是權威提交：自取交至落地由它獨佔檢視表（同一批按鍵武裝的防抖計時器會被扣住，而不是頂掉這次導覽；提交被拒後仍扣住，直到下一次編輯），也只有它把失敗呈現出來。有兩點是刻意為之。等待以草稿為鍵，而非以它指名的目錄部分為鍵，於是頂掉在飛掃描的那次按鍵會重新武裝等待，被拒提交之後的編輯也能釋放那道扣留；而它讀取的分欄是 ref 而非相依性，否則落地會重新武裝等待，遇到以不同拼寫作答的宿主便會永遠掃描下去。以及，走過的路不回退：關閉編輯器——包括取消——都把分欄留在草稿帶到的地方，由麵包屑導覽指明、Open 的兜底目標隨之而動，因為操作者親眼看著它們移動。若落地解除安裝了鍵盤操作者 Tab 停留的那一行，焦點會被重新停回編輯器——Modal 並沒有焦點陷阱。另有兩條規則保證一次按鍵只讓檢視表移動一次：這段行走會**等齊兩程**，而不套用提交導覽的等待上限（推測性掃描沒有任何東西在等它，先落單欄再升級恰恰就是它要避免的那次閃動，而且一旦末段按鍵中止了緩慢的父層級這一程，雙欄檢視表就會永久丟失）；末段也只過濾**最後一欄**——去收窄一個草稿已經走開的分欄，會讓檢視表先因收窄動一次、再因它自己的落地動一次。此外，層級會持續應答產生它的那段目錄文字（`scanned`），因為宿主會解析它收到的東西：`..` 段與 Windows 的正斜槓都會抵達一個自身路徑拼寫不同的層級；沒有這份記憶，這類草稿會每敲一鍵就重掃一次，而且永遠過濾不了。
- **導覽以選中項為錨、安靜且有界地落地。** 在展示根之外（與 crumb 頭部渲染的是同一塌縮，因此 crumb 與分欄形態永不相左），落地即雙欄：重新選中目標在父層級中的實際條目（Windows 上按平臺慣例摺疊大小寫），右側展示其子項，因此 crumb 跳轉讀作後退一欄，而不是塌縮成單列。父層級這一程在 200ms 等待上限內落定時，目標與父層級兩程以**同一幀**落地——在此之前過時檢視表持續渲染，導覽換欄時因此沒有中間的單欄閃現——超出該上限則目標即刻單獨提交（Enter 提交的導覽絕不會被滯塞的父層級扣作人質），遲到的父層級這一程再就地升級這次落地。父層級這一程在落地的 supersession 範圍下執行，任何較新的意圖都會線上上將其中止（因此在落地視窗內按 Escape 即撤回整次導覽）；父層級這一程失敗，或被截斷的父視窗缺少目標時，都保留單欄落地——升級的存在正是為了錨定選中項，絕不能反而讓它懸空。載入指示器遵循同一安靜規則：它浮於內容右下角（絕不是會挪動版面配置的一行；截斷／錯誤行佔據左下角，並在掃描期間持續渲染），且僅在掃描超出 300ms 靜默視窗後纔出現，因此本機列舉切換時什麼也不顯示。行選取被刻意豁免於同一幀規則：選取後立即分欄本身就是其選中態回饋（aria-current、crumb 跟隨），而導覽除了換欄本身沒有任何東西可確認這次點擊。三個時序常數——200ms 父層級上限、300ms 靜默視窗，以及編輯器的 250ms 草稿停頓——都按本機列舉校準；遠端部署（每層級一次 RPC，通常 100–400ms）會落在靜默視窗之內、crumb 上卻沒有按下態，而且要先付停頓再付 RPC 分欄纔跟上——待遠端消費端落地時，三者一並重新審視。
- **符號連結：為可進入性而跟隨。** 用 `stat` 探測符號連結（斷鏈／迴圈→跳過）；麵包屑導覽保留操作者導覽的邏輯路徑，`workspace.create` 在接納時本就做 realpath 規範化。
- **列舉層級有上限，且流式處理。** 單次 `list` 至多返回 `maxEntries` 行（設定項，默認 1000——GitHub 網頁端目錄列舉的同一上限）。層級經 `opendir` 流入一個按名排序、容量 `maxEntries + 1` 的候選視窗，記憶體保持 O(maxEntries)，可進入性探測只觸及視窗內候選；線上 `DirectoryListing` 攜帶必填的 `truncated` 標志，讓用戶端明示不完整而不是靜默缺尾。視窗內的斷鏈符號連結不從視窗外回填——發生過驅逐本身已把層級標記為截斷。視窗插入使用二分尋找、滿窗尾部單次比較即拒絕（超大層級不能為每個 dirent 付出一次全窗掃描），且 `list(path, signal)` 透傳載體的請求訊號，滯塞網路目錄的掃描不會在呼叫方斷連後繼續存活——掃描中的每個 await（打開、每次讀取、每次符號連結探測）都與訊號賽跑，中止路徑放棄而非等待 close（Node 會把 close 排在在飛讀取之後），被放棄的 settlement 全部吞掉，清理不會以未處理拒絕的形式冒出。無上限的層級對超大或惡意構造的目錄就是記憶體／回應性漏洞。
- **整個檔案系統均可瀏覽，不做 roots 設定。** `workspace.create` 接受任意路徑且 API 本就提供驅動程式 bash 的方法，瀏覽根只會是 UX 範圍而非邊界；沒有消費端的可設定性過不了證據門檻。等到有部署需要再做。
- **native 後端保留。** 外掛程式化正是目的：多個提供方都能提供該 seam（Electron 殼可以經自己的對話框 API 提供 `native` 互動）。kind 命名：最初選了 `dialog` 後被放棄——browse 互動同樣以對話框呈現（應用內彈出視窗），這個詞起不到判別作用；`native` 命名的是選擇器執行的位置。

## 曾考慮的替代方案

- **給 `ctx.fs` 增加瀏覽方法。** 否決：上述權限域耦合；且面向展示的列舉約定（hidden 標志、麵包屑導覽、home 錨點）不屬於儲存 seam。
- **統一的 Service Definition 方法集（`pick(): path`）。** 否決：應用內瀏覽器無法藏在一次宿主側呼叫後面——瀏覽迴圈在用戶端，需要協議上的原語；而原生選擇器實作不了原語。互動差異不可約，故用判別標籤。
- **apiproxy 裡直接調標準庫（不建 seam）。** 否決：換裝點仍是改閘道原始碼，失去 fixture（測試前置資料）／測試後端，與促成這項工作的外掛程式教義相悖。
- **引入文件管理器／盤符枚舉相依性。** 按上文調研否決；相依性政策要求記錄於此。
- **動作標籤隨狀態翻轉的「顯示隱藏」開關（「隱藏隱藏文件」）。** 否決：會翻轉的動作標籤在狀態與動作之間有歧義，還把否定疊了兩層；固定標籤加按下態呈現一次說清兩者。
- **純 relatedTarget 失焦取消（不做 mousedown 抑制）。** 否決：Safari 在指針按下時不給按鈕聚焦，點擊觸發的 focusout 因而攜帶空 `relatedTarget`，會在點擊落地前就取消編輯器；編輯期作用的 mousedown 抑制加上錨定卡片的 relatedTarget 守衛才能同時覆蓋指針與鍵盤路徑。
- **在 Miller 檢視表上方常駐一個路徑輸入框。** 否決：麵包屑導覽本就在回答「我在哪兒」，再常駐一個欄位是重複回答，還要從 500px 卡片裡挪走一行——那是列需要的高度。圖示加懸停亮起的區域，把這個入口放在了已經回答該問題的那一欄上。
- **每敲一個鍵就掃描草稿，或只在 Enter 時掃描。** 每鍵掃描：走完一段路徑就是每個字元一次列舉，其中多數目錄操作者只是路過而非停留。只在 Enter 時掃描（最初落地的行為）：整個編輯過程中各欄與所鍵入文字各說各話——正是本條所回應的抱怨。250ms 的停頓把掃描收斂為「鍵入真正停下來的每個目錄一次」。
- **前綴無一匹配時清空該欄（最初落地的行為）。** 否決：名字敲到一半時「無匹配」纔是常態，於是恰恰在操作者需要它確認名字時把欄清空了；解除過濾保住了層級的可讀性，代價只是短暫的寬鬆。
- **在 `DirectoryListing` 上增設線上 `separator` 欄位（宿主標注 `path.sep`）。** 延期而非否決：它纔是權威形態——含反斜槓的 POSIX 家目錄會擊穿 `listing.home` 啟發式——但它觸及 Service Definition 類型與每個後端；browse 用戶端的 `separatorOf` 掛著指向本方案的 TODO，直到下次安排線上變更。

## 後果

- `cordis.yml` 決定互動形態；`apps/cli` 掛 [`-auto` 選擇器](../feature/2026-07-29-directory-picker-adaptive-default.md)，它在啟動時判定宿主處境並自行掛載 `-native` 或 `-browse`，一行仍同時切換後端與 UI；直接組合某個後端行即固定互動。
- 協議新增 `host.listDirectory`／`host.createDirectory` 與四個錯誤碼；connection fixture 提供確定性瀏覽樹與確定性 `pickDirectory` 路徑供無金鑰組裝測試使用。
- 未來的新互動（或提供 `native` 互動的 Electron 提供方）只是一個雙面後端包——無需閘道手術，也不動 ui-workspace。
- `ApiProxyDefaults.pickDirectory`（僅測試注入）刪除；測試像提供其他服務一樣提供 stub `ctx.directoryPicker`。
