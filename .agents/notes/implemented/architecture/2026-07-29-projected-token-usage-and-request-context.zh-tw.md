# Agent Note: token 用量投影與上下文佔用率

Status: implemented

[English](2026-07-29-projected-token-usage-and-request-context.md) | 繁體中文

## 問題

Web 統計行原先從當前已載入的工作階段節點推導 token 總量。該視窗是分頁的，因此滾動會改變總量；壓縮（compaction）又會替換可見內容，而不保留其背後的計費用量。持久的提供方計費用量需要一個能同時經受這兩者的資料源。

上下文佔用率需要一個分子和一個分母，而這兩者都不曾由任何既有介面送達瀏覽器：最新一個請求的提示詞規模，以及該請求所用路由的容量。

## 決策

這兩個值都是普通的持久工作階段投影狀態。當 `ctx.sessionProjections` 存在時，`@deepseek-ai/dsh-token-meter` 會註冊兩個單元。

`tokenUsage` 將完整持久日誌歸並為未快取輸入、輸出、快取讀取和快取寫入四類計數項。即使後續請求失敗，`assistant/chunk` 用量樣本仍會保留；同一 `(turn, step)` 的 `assistant/message` 用量值會替換先前樣本，不會重複計數。推理（reasoning）仍是輸出的細分項。壓縮和表層替換不會抹除先前的計費用量。

`contextPressure` 攜帶選填的 `pressureTokens`（提供方報告的最新提示詞規模，為未快取輸入加快取讀取與寫入之和，不含輸出），以及來自最新一條 `request/context` 記錄的選填 `contextWindow`。在各自來源出現前，兩個欄位都不會被合成。

`request/context` 是新增的僅入日誌工作階段事件，記錄請求所解析到的路由的、綁定註冊項的元資料。AgentLoop 在步驟內緊隨 `request/header` 追加它，資料取自 `prepareCall()` 現在與已解析設定一並返回的上下文元資料：正是那次已經校驗過推理的、綁定註冊項的查詢，因此不會發生第二次解析。當提供方、模型和容量都與上一條記錄相同時會跳過。配接器不公佈容量的路由會以缺失 `contextWindow` 的形式記錄，從而清除較早路由的分母。

容量刻意不進入 `EpochHeader`。該類型是重建約定，即請求由什麼建置而成，而 `headerEquals` 會逐欄位比較它，以判定某個快照是否真的是一次 `change`。容量是描述路由的配接器元資料，把它放進去會讓容量變化偽裝成請求封裝的變化，還會把它拖進 AgentLoop 的重建不變式。

兩個單元都沿用標準投影生命週期：歷史尾頁基線、`session/projection` 即時幀、seq 高者勝的用戶端儲存、JSON 檢查點、快取復原和單元解除安裝。系統沒有任何 token 專用的歷史欄位、mux 幀、投影器、修訂計數器或用戶端柵欄。

Web `StatsLine` 透過標準 `useProjection` 席位讀取兩者。視窗內節點仍提供輪次和步驟計數，以及 LLM（大型語言模型）與工具的牆鐘時間：它們回答的是「螢幕上有什麼」，按視窗作用域正是正確的。壓縮使可見 assistant 步驟歸零後，持久 token 與上下文分組仍會保留。快取寫入會計入計費輸入和快取命中率分母。未部署 token-meter 時會去掉 token 分組；只有壓力與容量都已知時才顯示佔用率。

## 上下文佔用率是近似值，而這正是決策本身

`pressureTokens` 與 `contextWindow` 是兩個各自後者勝的獨立欄位，不是一次原子觀測。切換模型時，新容量會與上一路由的壓力配對，直到下一個請求報告用量為止；分子描述的是最後一個請求，而不是此刻的表層。

這是刻意接受的結果。佔用率百分比是面向使用者的參考數字：harness 中沒有任何環節依據它做決策，壓縮改為直接讀取 `measure()`。TUI 狀態行一直以這種方式計算佔用率，即用 `measure()` 總量除以為所選模型單獨解析出的容量；因此在這裡做成原子版本纔是異類，而不是常態。

這種非原子性是有意為之，不是缺陷。確實需要同一邊界精確數字的消費端，應在自己的請求邊界呼叫 `ctx.tokenMeter.measure()`，那裡兩個值同時可得，而不是讀取該投影。

## 備選方案

**以臨時 mux 幀交付請求邊界上的原子快照（已實作，隨後否決）。** 較早的一個修訂版會發出 `session/model-request`：一個不可重播的幀，攜帶在同一個 `agent/model-request` 邊界測得的 `contextTokens` 與 `contextWindow`。真正讓它失效的，是它成了 mux 流上唯一的不可重播類別。Host 流與 mux 流是兩條獨立的 SSE（Server-Sent Events）流，彼此之間沒有順序保證：在移除之前寄出的請求可能在 `host/session-removed` 之後纔到達，讓一個已死工作階段的遙測資料復活；而複用同一 id 的新生命週期的合法請求，又可能被一條遲到的移除攔下。`session/subscribed` 不能證明生命週期：它只說明某個佇列開始訂閱某個 id，而不說明新的記憶體工作階段替換了較早的工作階段；`lastSeq` 則是兩個生命週期可以共用的持久水位線。正確的修法需要在幀上、訂閱上和移除上都帶一個單調遞增的生命週期代次，再加上一次用戶端水位線比較。

這份代價換來的是更差的顯示：佔用率在每次重連後變為空白，而且工作階段成長期間從不移動。它還把 ApiProxy 變成一個測量點，每個請求都要呼叫 O(surface) 的 `measure()`，並透過一個 UI 必須特殊處理的、連線打開時的合成 `cancelled` 錯誤來表達重連狀態。

**在 React 中歸並已載入的節點視窗。** 無法跨分頁或壓縮保留資料，還會迫使展示包重建日誌語義。

**僅隨最終 assistant 訊息發布用量。** 如果請求報告一個用量區塊後失敗，就會丟失自己的計費用量。

**在 token-meter 內部解析容量。** 該包自述與模型路由無關，且在其他方面是一個從不向日誌追加內容的純讀取方。AgentLoop 在寫入請求標頭的位置已經持有已解析的元資料。

**為 `session.models` RPC 增加容量欄位。** 其處理器已經解析出容量又將其丟棄，因此這個欄位幾乎是免費的；但 `StatsLine` 位於 `ui-conversation`，模型目錄位於 `ui-model-selection`，而 `ui-conversation` 不能相依性 `ui-model-selection`。要送達它，就得增加第二個 dock 條目、把一行文字拆到兩個外掛程式裡，或者做一次跨外掛程式的 store 寫入。

**在模型選擇器旁增加上下文圓環。** 該位置會讓人以為這是所選模型的狀態。統計行可以承載該數字，無需引入重複的 UI 或資料路徑。

## 後果

token 總量在分頁、壓縮、重播、重新啟動和重連期間保持穩定，因為它們是透過通用路徑復原的普通持久投影狀態。跨流重排序競態從構造上就不存在，而不是被柵欄擋住。

佔用率在上文記錄的意義上是近似值。由於兩個欄位都是持久的，它在復原或重連後立即可用；代價是它描述的是最後一條已記錄的請求，而不是精確的當前邊界。

每個工作階段日誌會為每次路由或已公佈容量變化增加一條小型 `request/context` 記錄。token-meter 投影是持久工作階段投影用量語義的正典所有方；TUI 未掛載通用投影 seam，因此保留自己的即時逐步驟 map，而獨立瀏覽器 fixture（測試前置資料）會映像檔該單元。ApiProxy 不攜帶任何 token 專用程式碼，不擁有逐工作階段指標快取，也不執行測量。瀏覽器只保留兩個通用投影值，不保留連線本機的遙測資料；流式文字增量仍不會迫使統計行重新計算。
