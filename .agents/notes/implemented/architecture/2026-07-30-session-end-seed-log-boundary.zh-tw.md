# Agent Note: 種子結束日誌邊界

Status: implemented

[English](2026-07-30-session-end-seed-log-boundary.md) | [简体中文](2026-07-30-session-end-seed-log-boundary.zh.md) | 繁體中文

## 問題

在工作階段日誌中擁有獨立開／閉括號的外掛程式無法區分一個已死的標記和一個存活的標記。`compaction/start` … `compaction/end` 就是已發布的實例：當接手一份日誌、而它最後的壓縮（compaction）事件是一個未配對的 `compaction/start` 時，「上一個寫入方在壓縮中途死掉了」與「此刻正有一次壓縮在執行」在儲存歷史中是逐位元組相同的。該括號所有方只能二選一：拒絕壓縮一份其實空閒的日誌（把工作階段卡死），或者在一份確實繁忙的日誌上繼續壓縮。

日誌中沒有任何東西標出繼承歷史在哪裡結束。`session/created`、`session/disposed` 與 `session/flush` 是 Cordis 執行時期訊號，不是日誌事件；`agent/session-start` 只發射不落盤。`Session.firstLiveSeq` 本來就精確地持有這個答案——本生命週期第一次自有寫入的 seq——但只存在於記憶體中，因此讀取儲存位元組的消費端看不到它。

崩潰修復既沒有填上這個缺口，也不應該去填：`interruptedTurnClosers` 合成輪次、步驟與工具邊界，是因為核心擁有那套詞彙表，而 `compaction/*` 屬於壓縮 seam。一個會關閉外掛程式括號的核心修復流程，等於把每個外掛程式的括號語義都搬進核心。

## 決策

`Session` 的構造函式緊接顯式傳入的構造種子（包括空種子）之後追加僅日誌事件 `session/end-seed`，作為帶種子工作階段的第一次自有寫入，位置正是 `firstLiveSeq` 指出的 seq。該事件是那個欄位的持久投影：`firstLiveSeq` 為持有對象的消費端回答本生命週期的寫入從哪裡開始，`session/end-seed` 則為只持有儲存位元組的消費端回答同一問題。它的 payload 為空——位置與 `time` 承載全部含義——並且不是 `SurfaceEventType`，因此不產生訊息，也無法擾動派生歷史。這個 seq-0 標記把從空日誌復原的工作階段與真正的全新工作階段區分開來，從而防止復原期間應用新工作階段預設值。

括號所有方按位置讀取它：在 `session/end-seed` 之前的未配對開啟標記具有更小的 seq，來自構造種子，並且屬於一個已結束的生命週期。核心寫入該邊界但不從中讀取任何內容；每個括號的詞彙表仍歸其所屬外掛程式，因此在沒有消費端來塑形之前，核心不會先發布謂詞輔助函式。

選擇構造函式，是因為它是每一個帶種子工作階段都必經的唯一收窄處。全部六個入口都會到達它：`agents.resume()`、在已持久化 id 上的設定驅動程式啟動（`restoreOrCreateConfigured`）、`sessions.fork()`、subagent fork 子工作階段、`coordinator.adopt()` 的即時前綴路徑，以及裸的 `sessions.create(id, {seed})`。在持久化載入時寫入的邊界會漏掉兩條 fork 路徑——而一個繼承了仍在執行的父工作階段開放 `compaction/start` 的 fork 子工作階段，恰恰是必須可判定的場景。在 loop 啟動時寫入的邊界會漏掉 `fork()` 與 `adopt()`，並且不得不在 `SessionStartSource: 'startup'` 上觸發——那正是 fork 子工作階段發布的取值，於是該欄位將不再具有區分力。

兩條守衛讓這個標記保持精確。省略種子時不寫入任何內容，因為這是全新工作階段。種子本身已以該事件結尾時不會重複標記，這讓寫入具備冪等性。冪等性是承重的，而不是為了整潔：每次綁定到 Agent 的冷工作階段接手都會經過 `agentFor()`；沒有這條守衛，重複的控制操作即使沒有執行任何工作，也會讓日誌成長。只執行檢查的 `session.history` 與 `session.fork` 源端路徑不會在源工作階段中建立這條邊界。

## 持久化無需任何改動

構造函式中的 append 發生在 `enter()` 之前，因此工作階段尚無 store attachment：該標記不會在 `session/event` 上發布，與它之前的種子事件完全一樣。它屬於 `initFor` 捕獲的那份建立種子，並透過普通的種子路徑落盤——`onCreated` 的 `createCore` + `appendCore`，或無主認領的後綴寫入。因此監聽 firehose 的消費端永遠看不到這條邊界，必須從日誌中讀取它。

對 seam 的影響：`load()` 仍是純讀取，沒有 revision 遞增，對平衡日誌不走 `commitRepair`，被拒絕的 `append` 也不留下持久標記。但**接手不是純讀取**——如今一次拾起會在此前完全無寫入的路徑上產生寫入，因此只讀儲存或磁碟寫滿會在 `session/created` 處報錯，而不是在第一個真實輪次處。這是本放置方式新增的唯一成本，並且比載入路徑方案的成本更窄（後者會讓載入本身失敗）。

若崩潰發生在種子寫入到達磁碟之前，邊界會丟失，而這沒有代價：待處理批次按序寫入，所以丟掉一個邊界意味著它之後的每個事件也一起丟掉。下一次接手讀到的位元組與上一次相同，會追加自己的邊界，並對括號作出完全相同的判定。行程內消費端應優先使用 `firstLiveSeq`，它在任何寫入之前就是精確的。

## 保證的適用範圍

該謂詞對*本*工作階段繼承的括號成立，而不是關於其他寫入方的存活訊號。一個並行存活的工作階段可能在同一段儲存歷史上持有開放括號，而它自己的邊界在別處。必須容忍並行寫入方的消費端需要日誌之外的存活訊號，不能僅憑這個事件就省掉它。

## 曾考慮的替代方案

**由持久化協調器的冷載入路徑寫入邊界。** 較早的一版迭代寫入的是 `session/resumed` 邊界；它落選，一是因為完全覆蓋不到 fork——而 fork 恰恰是繼承括號的所有方可能仍然存活的那一種情形——二是因為在載入時鑄造的標記必須在學取路徑上做持久寫入，這把成本鋪開到整個 seam：每次冷載入都遞增 revision、對一份無需修復的平衡日誌也要走 `commitRepair`、需要一個已儲存時間下限來維持鉗制的單調性，以及載入在只讀儲存上會失敗。

**在 loop 啟動時追加邊界。** loop 呼叫 `resumeWith`，因此覆蓋復原路徑，但完全漏掉 `fork()` 與 `adopt()`，而且事件不得不在 `'startup'` 上觸發——那是 fork 子工作階段發布的來源——於是 `SessionStartSource` 將不再具有區分力。它還會在追加標記之前就發布工作階段，因此 `session/created` 監聽方可能觀察到一份沒有邊界的帶種子日誌。

**複用 `header.seedLength`。** 它是持久的 *fork 血緣*邊界，並且刻意在復原時保留原始 fork 取值——而復原時構造種子是整份儲存日誌。這兩個事實並不相同，混同會同時失去兩者。

**讓崩潰修復連同輪次邊界一起關閉 `compaction/*`。** 否決：這會把每個外掛程式的括號語義搬進核心的修復流程，而核心無法知道關閉另一個包的括號應該記錄什麼。

## 後果

買到的：一條邊界，在一處寫入，對全部六條帶種子啟動路徑都正確——包括持久化層方案觸及不到的 fork 缺口。持久化各包保留純讀取路徑。`firstLiveSeq` 獲得一個持久孿生體，而不是關於同一邊界的第二套彼此競爭的概念。

代價：帶種子工作階段的日誌長了一個事件，空日誌復原也包括在內。seq 期望會隨這條邊界移動。兩處更新是承重的而非機械的：telemetry 的接管測試斷言該邊界*會*被匯出，因為它是本生命週期的自有寫入；屬性測試套件的重播不變式則是「種子逐位元組復現，外加一個僅日誌邊界」，並把冪等性作為獨立屬性。

`session/end-seed` 加入了落盤詞彙表。在預發布立場下（`SESSION_FORMAT_VERSION` 固定為 `0`，不作相容承諾），更舊的日誌只是沒有它，而沒有邊界的日誌會正確地判定沒有任何內容屬於構造種子歷史。

[排隊手動壓縮決策](../feature/2026-07-30-queued-manual-compaction.md)如今提供了第一個消費端。其尾部掃描會分別尋找未匹配的 `compaction/start` 與最新 end-seed，只把位於該邊界之後的 start 視為存活，並在同一個重播轉換上清除不變數追蹤狀態。該謂詞仍位於壓縮功能所在的包中，不會成為通用核心輔助函式。
