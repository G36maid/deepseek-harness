# Agent Note: 發布前可複用的 Session 準備階段

Status: implemented

[English](2026-08-05-session-preparation.md) | [简体中文](2026-08-05-session-preparation.zh.md) | 繁體中文

## 問題

冷歷史檢查和 agent（代理）復原會分別實體化同一份持久工作階段日誌。對於大型壓縮日誌，每次操作都會重新完整讀取、解壓縮、解析、驗證、凍結並構造 Session。因此，歷史分頁可能反覆承擔冷讀成本；如果改為由歷史查詢啟用 agent，讀取生命週期又會與缺少自然退出時機的即時 agent 耦合。

新建和持久化復原也透過不同構造流程抵達相同的發布邊界。這使一項關鍵不變數不夠清楚：設定必須基於一個未發布的 Session 完成，之後系統才能同時公開這個精確 Session 及其 agent。

## 決策

`SessionPreparation` 持有一個精確的未發布 `Session`，直至發布或回滾。它屬於 Session 生命週期，不屬於 agent 生命週期或啟用機制。新建流程包裝 `SessionStore.prepare()` 的結果；持久化復原則從 `SessionPersistence.prepare()` 取得準備對象。

agent loop（代理循環）透過同一條設定與發布管線消費這兩種形式：先取得準備對象，圍繞 `preparation.session` 建置私有 agent 上下文，等待選填設定完成，再發布該精確 Session 和 agent，並在所有退出路徑上對準備對象執行 dispose（資源釋放）。發布後，即時生命週期由現有 Session 與 agent 儲存接管；`SessionPreparation` 本身不負責任何 agent 行為。

該機制細化了 [agent 生命週期與所有權決策](2026-06-18-agent-lifecycle-and-ownership-contracts.md)中的發布邊界，但不替換其所有權模型。

## 持久化準備生命週期

使用協調器的持久化實作會將一個冷源載入為準備完成的 Session。後端轉移新鮮、彼此無別名的元資料和事件，以及標識這些精確值的來源限定 revision；Session 復原路徑直接驗證並凍結這些對象圖，不再複製。協調器計算中斷輪次的 closer，並且只構造一次精確的未發布 Session。其不可變 header 與已配平的邏輯事件日誌構成讀取方借用的 `SessionInspection`，revision 則保留在持久化內部。

`inspect(id, signal?)` 不修改儲存。合成 closer 只存在於準備完成的記憶體檢視表中，撕裂的物理尾部保持不變。同 id 呼叫方共享進行中的冷讀。準備完成後，該對象可以進入每個協調器自己的 LRU；第一方後端可設定容量，默認保留五個。協調器複用保留源之前會讀取該 id 的當前 revision；如果不匹配，就淘汰處於就緒階段的源並重新完成冷實體化。已經進入提交或為復原而預留的源仍由其所有者獨佔，因此並行檢查會借用該不可變檢視表，直至發布或釋放。

`prepare(id, signal?)` 獨佔預留準備完成的 Session。它先確認保留的 revision，再提交撕裂尾部和中斷輪次修復、建立持久遊標，最後返回可 dispose 的準備對象。過時源會被丟棄並重新讀取，不會參與修復或發布。修復成功後也會丟棄修復前的源，並在預留前重新實體化已提交日誌，以免把較新的 revision 關聯到較舊的事件對象圖。同 id 的另一個準備請求會等待當前預留發布或釋放。發布只接受精確的預留 Session，並直接附接已提交遊標，無需重建歷史。設定失敗或取消時，未發生變化的未發布 Session 會返回 LRU；發生變更或完成附接後，系統會消費該預留。

存量 `load(id)` API 使用相同的準備和修復機制，隨後丟棄其預留並返回不可變邏輯檢視表。它保留為相容 API，不承擔歷史到復原的複用路徑。該生命週期擴充了[共享持久化協調器](2026-06-18-shared-persistence-write-coordinator.md)，同時繼續遵循[工作階段持久化決策](2026-06-14-session-persistence.md)所規定的儲存與復原規則。

## 歷史與復原複用

歷史讀取使用 `inspect()`，因此重複分頁可以借用同一份不可變準備狀態，而不會啟用 agent。後續復原呼叫 `prepare()`，直接取得檢查階段保留的精確 Session；系統不會再次完整讀取、解壓縮、解析、複製、驗證或凍結日誌。

如果持久日誌在檢查後發生變化，其 revision 也會變化。下一次歷史讀取或復原會丟棄保留且處於就緒階段的 Session，並實體化新日誌，因此舊事件對象圖不會被關聯到較新的快照 revision。已經由進行中復原操作取得的源不會被淘汰：其獨佔所有者會持有它直至發布或釋放，並行歷史讀取可以借用同一個不可變檢視表。

冷 continuable subagent 訪問沿用同一路徑。系統先檢查子工作階段並完成 descriptor 授權，再由 `ctx.agents.resume()` 預留並行布保留的 Session。這樣既遵循 [continuable subagent 工作階段決策](../feature/2026-07-28-continuable-subagent-conversations.md)中的生命週期與授權規則，也消除了重複冷讀。

## 邊界

- `readFrom()` 仍是脫離的物理後綴 API。它不會建立或消費準備對象，不會合成邏輯 closer，也不會進入 LRU。
- HMR（熱模組替換）接管繼續以即時 Session 為權威，並直接讀取已儲存前綴。它可以截斷撕裂的物理碎片，但絕不把即時開放輪次關閉為中斷狀態。
- 快取屬於單個持久化協調器，而不是行程全域性 Session map。即時 Session 由現有儲存持有，絕不佔用準備容量。
- 新建流程絕不認領相同 id 的冷持久化準備對象。持久化衝突仍會被拒絕。
- 第三方持久化實作繼續獲得透過 `load()` 實作的抽象 `prepare()` 回退。它們使用相同發布介面，但只有覆蓋準備流程後才能複用精確對象。
- Revision 校驗在複用點和修復提交點建立新鮮度，但不會為後端增加跨行程 writer 排他。持久日誌在一次讀取與複核往返內保持不變後，重試才能收斂，因此持續的外部寫入可能延遲準備。

## 驗證

共享持久化約定規定冷檢查不得修改儲存且須保持配平，並覆蓋後續修復。`persistence.spec.ts` 與 `preparations.spec.ts` 覆蓋同 id 進行中讀取共享、檢查與準備之間的精確 Session 複用、在歷史讀取與復原前由 revision 觸發刷新、修復只提交一次、獨佔預留、設定失敗後釋放、就緒項 LRU 淘汰、預留期間拒絕 append，以及只允許發布預留 Session。後端測試覆蓋完整讀取與輕量讀取使用同一 revision 身份。agent loop 與 continuable subagent 測試覆蓋統一發布管線，以及取消和清理期間從檢查到復原的路徑。

## 考慮過的替代方案

**由歷史讀取啟用 agent。** 不採用，因為分頁會使僅用於查詢的 agent 長期保持即時狀態，並把快取退出問題轉移到 agent 生命週期。

**只快取 `{ meta, events }`。** 不採用，因為復原仍需從快取值重新構造、驗證、凍結並複製 Session。真正可複用的單元是精確的未發布 Session。

**維護行程全域性 Session map。** 不採用，因為它會跨越後端和執行時期所有權邊界，無界保留身份，並與即時 Session 儲存重複。

**在 agent loop 中增加復原交易或協調器。** 不採用，因為冷讀、修復、預留和遊標附接都屬於持久化與 Session 職責。agent loop 只需要統一的 `SessionPreparation` 所有權邊界。

**把 `readFrom()` 改成邏輯準備流程。** 不採用，因為水位消費端需要脫離的物理後綴；對於可尋址後端，還需要限制實際讀取範圍。復原平衡與完整 Session 複用具有不同語義。

## 後果

一次冷實體化可以同時服務歷史分頁、subagent descriptor 檢查和後續復原。所有權轉移去除了復原階段的冗餘複製；每個協調器的有界 LRU 限制記憶體佔用，也避免查詢建立即時 agent。新建和復原共享同一發布協議，同時保持 agent 與 Session 職責分離。

首次冷檢查需要承擔完整驗證與 Session 構造成本，並可能保留該未發布 Session 直至淘汰。持久化層必須協調預留、append、修復和發布；呼叫方必須把檢查結果視為借用的不可變狀態。相依性默認 `prepare()` 的後端仍然正確，但無法獲得複用最佳化。
