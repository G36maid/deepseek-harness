# Agent Note: 憑據邊界、按整份快照發起的請求與原子路由註冊

Status: implemented

[English](2026-07-30-credential-boundaries-and-atomic-registration.md) | [简体中文](2026-07-30-credential-boundaries-and-atomic-registration.zh.md) | 繁體中文

> 範圍：加固[請求級 LLM（大型語言模型）設定邊界](2026-07-29-request-level-llm-config-credentials.md)——存下來的憑據落在哪裡、誰能讀到它，一次請求所用的事實如何保持在同一代，以及一組路由如何在不留空窗的前提下更換。本 note 與 [settings 寫路徑 note](2026-07-30-settings-write-path-integrity.md) 配套：它把那篇 note 的提供方修復套用到 `credentials-local`，並把其中的寫鎖提升進 `dsh-atomic-write`。

## 問題

憑據路徑越過它自己劃下的邊界發生了洩漏。已交付的各個面在 Cordis 啟動之前就把 `$DSH_HOME/.env` 提升進了 `process.env`，於是下一次執行時期，`credentials-local` 會把它自己存下的每個鍵都判成來自環境的只讀啟動覆蓋：`describe()` 報告 `source: 'env'` 且 `writable: false`，`set`/`unset` 以被遮蔽為由拒絕，從 web 頁面或 TUI 存入的金鑰既無法輪換也無法刪除，而配接器還在繼續使用啟動時捕獲的那個值。

儲存自身的寫路徑重演了 settings 寫路徑 note 在 settings-file 修掉的那些缺陷（兩條相互獨立的鏈、從過時快取渲染整份文件），還疊加了編輯器自己的缺陷：另一個鍵的帶引號多行值內部的一條物理行會被讀成賦值，CRLF 行尾會退化成 LF，多行條目報告 `writable: true` 而 `set` 總是拋錯，`credentials/updated` 又在提交之後裸發，於是一個出錯的觀察者就能讓一次已經落盤的寫入看起來失敗。

在學取一側，文件的 `0600` 權限擋得住其他 OS 使用者，卻擋不住模型：它的 bash 與檔案系統工具就以同一個使用者身份執行。

與之並排的還有兩個請求路徑缺陷。DeepSeek 分別解析連線事實與憑據事實，因此被 resolver 拒絕的那一代設定仍可能把自己的憑據選擇與上一代的端點配在一起。設定了 `apiKeyEnv` 卻解析不到值時，pi-ai 會把 `undefined` 交給 SDK，讓 pi-ai 自己的環境發現拿一個毫不相干的提供方金鑰完成鑒權——那是另一個租戶，帳單還悄悄記在它頭上。而且它的路由替換是先 dispose（資源釋放）舊註冊、再建立新註冊：只要有一條路由已被別的配接器佔有，現有路由就會被全部丟掉，此後事實快取可能與登錄檔中的事實相等，於是把設定改回可用狀態也不會重新生效。

## 決策

**憑據文件只歸憑據提供方所有。**沒有任何一個面會把它載入進 `process.env`。當時該文件是 `$DSH_HOME/.env`；[憑據文件拆分](2026-08-04-credentials-yaml-and-user-environment-layer.md)後來把它移到 `$DSH_HOME/.credentials.yaml`，因此如今被載入的正是那條舊路徑——作為使用者的普通環境層，其中不含任何提供方管理的金鑰。真正的啟動環境，以及呼叫目錄中由 bin 載入的 `.env`，仍然是那一層只讀的環境來源，因此不掛載該提供方的組合，解析金鑰的方式與從前完全一致，而存下的金鑰跨重新啟動仍然來源於文件、仍然可寫——這一點由 loader 組閤中的一次真實重新啟動來證明，而不是靠對 `describe()` 的單元斷言。

**存下的憑據對模型沒有邊界，而 README 就是這麼寫的。**`0700` 目錄下的 `0600` 擋得住其他 OS 使用者；模型的 bash 與檔案系統工具正是以同一使用者身份執行，而已交付的預設配置不提供任何約束。harness 真正守住的邊界更窄，文件也嚴格按這一範圍表述：沒有任何一個面會把該文件提升進 `process.env`，模型也從不會拿到它的解析後路徑，因此要拿到這個值，需要刻意去讀一條並未交給它的路徑。OS 鑰匙串（keychain）提供方——一個模型的行程根本讀不到的儲存——被記錄為真正的答案，而不是靠一個殘缺的方案去暗示它。

**一次請求，一代設定。**DeepSeek 解析出的快照在端點旁一並攜帶憑據引用，`resolveApiKey` 接收這份快照，而不再重新讀取設定。被拒絕的那一代如今完全不再貢獻任何東西。只有當一個 profile 完全沒有點名憑據時，pi-ai 才交給提供方原生的發現流程；設定了引用卻解析不到，就以 `MISSING_CREDENTIAL` 失敗，並點名該路由與該引用。啟動時的憑據探測被刪除：它可能在憑據服務掛載之前就執行，並把每一種失敗都報成金鑰缺失，而第一次請求本就會給出準確的錯誤。

**路由替換是登錄檔的操作，不是呼叫方的一串步驟。**`registerAdapter` 返回一個攜帶 `replace(providers)` 的控制代碼：候選集合先被完整校驗（衝突、名稱、提供方元資料），再在一個同步區段內完成替換。被拒絕的替換會讓先前的路由保持註冊並繼續服務，而呼叫方的事實快取只有在登錄檔確實持有新集合之後才會推進，因此改回可用設定時會重新生效。pi-ai 的註冊事實按提供方排序，因此僅僅調換鍵順序的設定文件不再算作路由變更。

**已提交的憑據寫入採用收容式發布。**`CredentialProvider.notifyUpdated` 逐個監聽器扇出 `credentials/updated`；同步拋錯與非同步 rejection 都只記日誌，不改變已提交操作的結果，而帶 `INVARIANT` 程式碼的失敗會在每個監聽器都執行完之後重拋——與 settings seam 處理 `settings/updated` 的形狀相同。`installSettingsSection` 的清理現在會區分它的兩個觸發來源：提供方脫離時仍回退到組合的 entry 設定並重新推導，而消費端自身解除安裝時立即返回，不再在拆卸過程中重新註冊路由。

## 曾考慮的替代方案

- **用沙盒點名拒讀 `$DSH_HOME/.env`**——已按 `readDenyPaths` 策略欄位實作過（末尾一條 SBPL `deny file-read* file-write*`、一條 `/dev/null` 的 bwrap bind），又被它自己的證據推翻。bwrap 必須在自己 profile 已經置為只讀的目錄樹內部建立該 bind 的掛載點，因此只要父目錄不存在，它就會拒絕整次約束——那是每一臺還沒有存過憑據的主機，包括全新安裝；Landlock 無法從它自己對 `/` 的讀取授權中減去任何東西，於是每一次受限呼叫都會為一個它其實從未藏起的文件報 `partial`。一項在生效之處破壞約束、在不生效之處誤報的保護，比一條寫明的「沒有保護」更糟。至於拒掉整個 harness home，早先另有理由被否：它同時覆蓋 `sessions/`，而 `DSH_SESSION_JSONL` 是一項成文的、模型可見的能力。
- **把 `DSH_HOME` 從模型的 bash 環境中移除**——作為縱深防禦考慮過，最終按「有真實代價的表演」不予採納：默認 home 是 agent（代理）能自行重建的成文約定，而這個變數正是正當工具鏈定位 harness 狀態的途徑。這裡並不存在一條需要它來補強的邊界，藏起指針只會讓這種缺失更難被看見。
- **現在就交付 OS 鑰匙串提供方**——只有這個設計能讓模型的行程真正讀不到機密，而它是一個帶三種平臺後端的兄弟包。把它與其餘這些修復放在一起評估體量，會拖慢其他每一項；它被記錄為那個延後的答案，而不是一個「也許」。
- **做成 `replaceRegistration(previous, next)` 服務方法**——不予採納：它要求呼叫方自行攜帶上一個控制代碼，也允許它傳入一個不匹配的控制代碼。把 `replace` 掛在註冊控制代碼上，讓歸屬關係變成結構性的：只有持有路由的那一項註冊才能替換它們。

## 後果

與 `update()` 相關的行為多了成文的失敗模式：憑據寫入現在可能因鎖截止時間到期、或磁碟文件無法解析而失敗，`describe()` 對它不會改寫的多行條目報告 `writable: false`。`LlmAdapter` 的註冊方無需改動即可繼續工作（控制代碼本身仍可當作釋放器呼叫），`DeepSeekConnectionOptions` 則新增了憑據欄位，因此以程式設計方式構造該配接器必須提供 `apiKeyEnv`。延後事項：OS 鑰匙串憑據提供方，以及針對兩個寫方編輯同一引用的逐值修訂號檢查（後寫勝出仍是成文的解決方式）。
