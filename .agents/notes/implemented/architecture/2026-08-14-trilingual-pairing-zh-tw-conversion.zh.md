# Agent Note: 三语文档配对与 zh-TW 转换流水线

Status: implemented

[English](2026-08-14-trilingual-pairing-zh-tw-conversion.md) | 简体中文

## 问题

本仓库的文档与 Web UI 只提供英文与简体中文，所有配对门禁、网站投影、语言注册表与翻译提示词都硬编码为两种语言。新增台湾繁体中文（zh-TW）因此触及每一层：配对记录格式、语料发现、合并驱动、站点语言模型、客户端语言集与机器翻译契约。zh-TW 侧无法像 zh-CN 那样从英文人工翻译——语料约一千篇文档，且 zh-TW 由 zh-CN 派生而非由英文派生，因此机械转换流水线加人工复核是唯一可行的生产路径。

## 决策

**配对模型是语言映射，而非固定双槽记录。** `PAIRED_LANGUAGES = ['en', 'zh', 'zh-TW']`，每种语言有对应的文件后缀（`.md`、`.zh.md`、`.zh-tw.md`），`.i18n.yaml` 记录每种语言的一个 git blob hash。门禁、合并驱动与 `--write` 流程都遍历语言集而非硬编码中文侧；今后新增第四种语言只需改一行注册表。

**zh-TW 由 zh-CN 机械派生，再对照英文复核。** 转换工具（`scripts/convert-zh-tw.ts`）运行 zhtw-js——一个约 3.1 万词的词汇优先台湾转换器，叠加来自 `docs/i18n/terminology-zh-tw.md` 的自定义词典——然后对 zhtw-js 遗漏的字做 OpenCC s2t 字形兜底，最后经配对门禁重新记录。复核时对照英文源，因为纯 zh→zh-TW 转换会继承 zh 译文的任何漂移。术语文件的机械陷阱表记录了必须修正的 OpenCC 输出（权限 → 許可權 是错的；權限 才对）。

**zh-TW 门禁报告简体字残留，而非词汇偏好。** `scripts/verify-zh-tw.ts` 用 OpenCC s2t 过滤 zhtw-js 检查结果：只有仍含简体字的片段才算失败。词汇建议（聲明 → 宣告、綁定 → 繫結）留给复核，因为两种形式在台湾都是合法用法。

**每个已发布层都携带第三语言。** 浏览器客户端语言集为 `['zh', 'zh-TW', 'en']`，浏览器侦测使用 script 子标签（`zh-Hant-TW` → zh-TW）；每个语言命名空间都注册 zh-TW 字典；网站投影 `/zh-TW/` 路由，含自己的侧栏与搜索标签；翻译提示词接受 `Chinese-TW` 目标用于 zh→zh-TW 转写。

**冻结的归档三件套永不新增 zh-TW 侧。** `.agents/notes/archived/` 从转换发现与配对中排除；转换器跳过该目录树，归档验证器继续封存既有的 en+zh 三件套。

## 后果

配对门禁在全部 936 个范围内配对上都已变绿，每个配对视对记录三个 hash。转换语料为 934 个 zh-TW 文件（docs/i18n/ 下的两个契约文件先存在）；`verify-zh-tw --all` 报告 14 个简体字残留，全部集中在 面包/游程 这类边界词汇——其中 面/游 有合法的传统读法，转换器无法消歧。网站以三种语言构建（`pnpm run docs:build`），客户端测试套件在第三语言下全绿（`pnpm run test:gui`）；基础 tsconfig 增加了 `customConditions: ['node']`，让 TypeScript 能解析 zhtw-js 的条件导出（该包只有 `node`/`browser` 导出条件，没有顶层 `types`）。

## 考虑过的替代方案

- **以 OpenCC s2twp 作为转换引擎**——在语料上产生 5094 个残留发现，因为其台湾短语表比 zhtw-js 薄，且误转 权限 → 許可權（术语表须再修）。zhtw-js 将同一语料转换到 14 个残留。其词汇优先设计也让仓库术语表可充当自定义词典，使 打包 在打包语境保持 打包 而非变成 外帶。
- **双槽记录加硬编码 zh-TW 字段**——避免泛化门禁，但每种未来语言（zh-HK、ja）都会重复同样的改动；映射现在花费相同成本，以后免费。
- **从英文人工翻译 zh-TW**——在约一千篇文档的规模下不可行，且与 zh 译文重复；机械转换加复核把人力成本放在质量上，而非转录上。
- **将归档三件套视为可转换**——违反冻结；归档验证器会拒绝第四个文件，且配对契约承诺永不重写归档内容。
