# Agent Note: 背景工作執行時期（`ctx.jobs`）與通用任務控制工具

Status: implemented

[English](2026-06-20-generic-long-running-tool-runtime.md) | [简体中文](2026-06-20-generic-long-running-tool-runtime.zh.md) | 繁體中文

## 問題

後臺 bash 原本兼有兩項職責：bash 執行器既執行行程，又管理 job id、所有權、增量讀取、取消、完成監聽器和麵向模型的控制工具。新增後臺 subagent 需要相同的生命週期與互動約定。如果每種長時間執行能力都獨立實作該約定，就會重複隔離、清理、通知和提示詞行為，還會讓模型為每種生產方學習不同的收集與停止協議。

任務登錄檔、控制工具與完成通知共同構成一項 harness 能力。bash 和 subagent 只提供執行專屬的掛鉤，不擁有通用任務行為。

## 決策

`jobs/` 包組擁有後臺任務語義：

- `@deepseek-ai/dsh-jobs` 將執行中的工作註冊為 `ctx.jobs`，並擁有 job id、授權、快照、讀取、取消、等待、完成監聽器與清理。
- `@deepseek-ai/dsh-tool-jobs` 暴露 `job_output`、`job_list` 和 `job_kill`，注入完成通知，並提供背景工作的系統提示詞指導。

長時間執行工具是生產方。`dsh-tool-bash` 將 `ShellProcess` 適配為增量輸出與行程取消；`dsh-tool-subagent` 將子執行適配為最終輸出與子執行釋放。bash 與 subagent 能力 seam 保持獨立，不相依性工作階段或任務登錄檔。

`JobRegistry` 是 `@deepseek-ai/dsh-jobs` 中的 Service Definition；行程內 Service Provider 是 `@deepseek-ai/dsh-jobs-local` 中的 `LocalJobRegistry`（該拆分記錄在[任務登錄檔約定 Agent Note](2026-07-26-job-registry-seam.md)中）。

## 執行時期約定

字面類型見[任務子系統頁面](../../../../docs/subsystems/jobs.md)。生產方呼叫 `ctx.jobs.start()`，傳入 kind、label、選填的所屬 `Agent`、選填的正數 `outputLimitBytes` 與一個 `run()` 函式。執行時期會在呼叫 `run()` 前完成所有可能失敗的預檢工作，並且只調用一次。`run()` 返回掛鉤後，註冊過程不會再執行可能失敗的步驟而直接提交；生產方無法啟動沒有可收集 job id 的工作。

行程內 Service Provider 還擁有有界准入，其理由記錄在[有界背景工作準入決策](../bug-fix/2026-08-11-bounded-background-job-admission.md)中。它的 `maxConcurrentJobsPerOwner` 設定必須是正的安全整數，預設值為 `10`；`start()` 從 `running` 與 `stopping` 記錄派生每個確切 `Agent` 對象的活動數量，而全部無 owner 任務共享一個服務級桶。容量拒絕發生在 `run()` 與 id 分配之前，處於 stopping 的任務只有在生產方 `done` 結帳時才釋放名額。Service Provider 不排隊或搶佔任務，也不保留第二份可變計數。

`outputLimitBytes` 是生產方擁有的呈現策略，而非登錄檔緩衝區。登錄檔校驗該值，並將其原樣投影到 `JobSnapshot`；通用任務控制器新增自身的狀態或通知元資料後，再將該上限應用於完整的面向模型輸出。省略該值時保持現有控制器行為，因此執行時期不會向無關的生產方類別施加隱式預設值。

面向模型的生產方會在規範成功值中暴露已提交的 id，通常為 `{ kind: 'background', jobId }`；Native 渲染仍可保留便於人類閱讀的行文。預先被中止的後臺呼叫會失敗，而不是返回空操作，因為不存在可履行所承諾控制代碼的任務。一旦註冊過程發布 id，取消就歸任務自身的控制器與任務執行時期所有：隨後取消生產工具呼叫不得終止已發布的任務。`job_kill`、所有者資源釋放和服務拆除會請求取消；前臺執行仍與呼叫的 `exec.signal` 耦合。

生產方掛鉤定義三項職責：

- `cancel(reason?)` 同步請求終止，具備冪等性，並且必須使 `done` 完成。
- `done` 從不拒絕，並且僅在生產方釋放任務資源後完成。
- 選填的 `readOutput()` 返回下一個消費式輸出增量。省略該掛鉤即聲明這是最終輸出任務，其終止結果來自 `JobOutcome.output`。

狀態包括 `running`、`stopping`、`completed`、`killed` 和 `failed`。退出碼或停止原因等生產方專屬資訊放在 `detail` 中，登錄檔不解釋這些資訊。任務 kind 構成可合併擴充的字串聯合；job id 帶品牌，並按 `<kind>-N` 生成，每個 kind 各有一個計數器。

執行時期為 `done` 附加一個 continuation，記錄第一個終止結果、使等待方完成等待，並逐個呼叫完成監聽器，同時隔離每個監聽器的錯誤。首次結果優先的結帳在資源銷毀期間至關重要：如果 `cancel` 拋出，執行時期會強制將記錄標為失敗，並警告工作可能殘留，而不是永遠等待一個可能永不完成的 promise。後續生產方結果不能覆蓋該診斷，也不能重複通知。`cancel` 返回後如果最終未使 `done` 完成，仍會阻塞資源銷毀，因為執行時期無法區分這種情況與緩慢但有效的停止。

任務註冊不是生產方工具 fiber 的 effect。因此，重新載入工具或控制器外掛程式不會終止由 agent（代理）和後端擁有的工作。任務服務自身釋放時會取消所有尚未終止的任務，並等待遵守約定的生產方。

## 授權與所有者生命週期

job id 在執行時期全域性可見且可預測，因此登錄檔會授權每次訪問。`get`、`read`、`wait` 和 `kill` 接受呼叫方 `Agent`；`list` 僅返回該呼叫方可見的任務。有所有者的任務僅允許對應的確切工作階段訪問。無所有者任務向非 agent 呼叫方開放，並隨任務服務一起終止。

快照儲存所有者的品牌化 `SessionId` 以供授權，生命週期操作則保留確切的存活 `Agent` 實例。這兩種身份用途不同：工作階段相等性授予訪問權，精確對象身份決定清理和完成通知的接收方。複用 agent 或工作階段 id，不能將舊作用域的清理或通知重定向到替代實例。

某個所有者的第一個任務會向 `owner.ctx` 附加一個非同步 effect。agent 作用域釋放時會取消該所有者尚未終止的任務、等待其終止記錄，並移除其快照。該 effect 可跨生產方重載存續，並加入 agent 現有的完全靜止邊界。任務服務保留 effect disposer，使服務重載可以在全域性資源銷毀後，從仍然存活的 agent 作用域中分離回呼。

對於遵守約定的生產方，`AgentHandle.dispose()` 只在所屬後臺工作停止後完成。需要比 agent 存活更久的工作必須以無所有者方式啟動；要跨執行時期重新啟動存續，則需另行設計持久任務。

## 服務 API

`JobRegistry` 提供：

- `start(spec)`：經過預檢與 Service Provider 准入的原子註冊。
- `get(id, caller?)` 和 `list(caller?)`：非消費式快照。
- `read(id, caller?)`：消費式流增量或冪等的最終結果。
- `kill(id, caller?, reason?)`：取消。
- `wait(id, timeoutMs, caller?, signal?)`：有界的終止等待。
- `onJobDone(listener)`：effect 作用域內的觀察，具有精確所有者投遞和監聽器隔離。
- `attachController(name)`：任務控制器可用性防線。

`wait` 在任務完成時返回終止快照，在等待逾時時返回當前快照。中止一次等待只取消該次等待。如果結帳已經將終止投遞分配給該等待方，終止快照仍然優先。等待方在中止時同步註銷，因此同一 tick 內發生結帳時，不會代表一個實際未收到任何內容的讀取方壓制完成通知。

如果生產方載入時沒有任何任務控制器，呼叫方就能啟動無法收集或停止的工作。因此，`dsh-tool-jobs` 在其整個生命週期內呼叫 `attachController()`；沒有附加控制器時，`start()` 會在生產方開始執行前失敗。該檢查發生在啟動時而非外掛程式載入時，因為兄弟外掛程式可能並行啟用。自訂的非模型控制器可以自行附加，無需讓登錄檔瞭解工具名稱。

## 面向模型的控制 API

`dsh-tool-jobs` 註冊三個與 kind 無關的工具，並使用通用 UI 卡片：

- `job_output(job_id, wait?, timeout_ms?)` 讀取輸出，並始終追加 `[status: ...]`。流式任務只返回上次讀取以來的輸出；最終輸出任務在結帳後返回結果。除非指定 `wait: true`，否則讀取不會阻塞；等待逾時由外掛程式設定提供預設值並限定上限。等待逾時會報告仍在執行的狀態，不會停止任務。
- `job_list()` 將呼叫方可見的任務返回為 `<id> [<kind>] <status> — <label>`，沒有任務時返回 `(no background jobs)`。
- `job_kill(job_id, reason?)` 立即請求取消。選填的已記錄原因會轉發給生產方。終止任務報告現有狀態；生產方的取消操作若拋出，呼叫便會失敗，任務保持執行。

流式讀取共享一個任務作用域內的消費遊標，因為所屬模型是預期讀取方。UI 或多個獨立讀取方需要單獨的非消費式觀察 API；共享該遊標會讓讀取方彼此消費對方的輸出。

系統提示詞要求模型保留 job id、在後臺工作執行時期繼續處理獨立工作而非忙輪詢或重複啟動同一任務、在給出最終答案前收集相關任務，並終止不再重要的工作。完成時，系統會向確切所有者的工作階段交付一條已記錄的訊息：繁忙的所有者走注入，空閒的所有者會被喚醒，其有界策略由[空閒所有者喚醒決策](../feature/2026-08-11-background-job-completion-wakes-an-idle-owner.md)負責。

當讀取或等待交付終止任務、尚在等待的等待方在結帳時認領了投遞，或模型顯式終止任務時，執行時期將終止任務標為 `reported`。已報告的任務不會注入冗餘的完成通知。監聽器失敗會獨立記錄，不會阻止後續監聽器，也不會被等待方或資源銷毀過程等待。當快照攜帶 `outputLimitBytes` 時，`dsh-tool-jobs` 會保持 UTF-8 邊界，並複用生產方已有的截斷標記，而不會重複新增。讀取會為狀態後綴預留空間並保留輸出尾部；完成通知會先為穩定的 `background job <id>` 前綴與 `job_output` 指令預留空間，再截斷可變的 kind、label、status、detail，乃至截斷標記本身，因此 PTY 的最小上限仍能標識需要收集的任務。任務控制器在策略有機會拒絕或短路分發之前，於最先執行的 pre-execute 監聽器中解析呼叫方可見的生產方上限；隨後透過任務定義最後一道的 `finalizeContent` 回呼應用該上限，使規範化的工具錯誤、外層管線失敗與單文字策略結果都無法繞過該邊界；經特意結構化的多塊策略結果仍由策略擁有其形狀與大小。

## 生產方顯式啟用

每個生產方透過帶預設值的設定，自行決定其 schema 是否暴露 `run_in_background`。`dsh-tool-bash`、`dsh-tool-terminal` 和每個 `dsh-tool-subagent` 實例都使用 `enableRunInBackground`，預設值為 true。停用的實例會省略該參數；由於通用參數校驗器允許未聲明的鍵，它還會在執行時拒絕強制傳入的後臺參數。省略 schema 用於聲明能力不可用；執行檢查負責強制該約束。

`ctx.jobs` 不改寫生產方 schema。bundle 只轉發其所擁有的生產方的設定。如果後臺呼叫在沒有附加控制器的情況下到達 `start()`，執行時期防線會在執行前使其失敗。

## 生產方整合

bash seam 暴露 `resolve`、`run` 和 `start`。`start(spec)` 返回一個 `ShellProcess`，提供增量讀取、取消、退出事實以及不拒絕的完全靜止 promise。本機執行器只為自身釋放時能終止並等待行程而保留活動行程的控制代碼。前臺呼叫方繼續直接使用 `resolve` 和 `run`。

對於後臺 bash，`dsh-tool-bash` 將呼叫方 agent 註冊為所有者。其掛鉤將 `kill()` 對映為取消，將 `done` 對映為 completed 或 killed 的 `JobOutcome`，並將 `readOutput()` 對映為行程的有界增量輸出，以及 spill 與沙盒通知。通用任務工具擁有 id、狀態行、清單、等待和完成通知。

對於後臺 subagent，`dsh-tool-subagent` 建立由任務擁有的 `AbortController`，並在任務 starter 內啟動提供方。無論提供方發布前後，取消都會中止同一個 signal。`done` 同時等待子執行結果和子執行釋放，將已完成輸出對映為最終結果，將中止對映為 `killed`，並將其他停止原因或基礎設施失敗對映為 `failed`。中間子歷史保留在子工作階段中，不透過 `readOutput()` 暴露。

## 備選方案

### 按能力劃分控制工具

為 bash 與 subagent 分別提供輸出/停止工具，會重複 id、隔離、清理、通知和指導，並增加模型的 schema 與協議負擔。統一執行時期將執行專屬行為保留在生產方中，而無需複製任務生命週期。

### 立即抽象任務執行時期後端

當前 `JobStart.run()` 約定傳入行程內回呼與確切的 `Agent` 對象。持久化後端會改變身份、重新啟動、所有權與觀察語義，因此在引入之時登錄檔保持為單一具體服務，而非固化錯誤的邊界。[任務登錄檔約定 Agent Note](2026-07-26-job-registry-seam.md)後來在不改變這些行程內語義的前提下，將約定與行程內實作分離。

### 由消費端負責授權或清理事件

由消費端負責檢查，會使每個新介面的隔離實作不一致或遺漏。廣播清理事件會迫使每個監聽器過濾所有 agent，且不提供註冊 disposer。集中授權加一個所有者作用域內的 effect，為每個消費端提供相同防線，以及可等待、可移除的生命週期掛鉤。

### 阻塞輸出或單獨的等待工具

默認阻塞會在後臺工作執行時期序列化父任務。只等待而不讀取會增加一次不返回有用資訊的模型呼叫和 schema。`job_output(wait: true)` 顯式表達阻塞，並將其與結果交付合併。

等待使用共享的 deadline 原語，而不使用通用工具逾時策略。等待逾時是一次成功的觀察，會返回 `[status: running]`；通用策略會將它替換為逾時錯誤。任務返回 job id 後，沒有任何工具呼叫逾時會控制任務生命週期。

### 由執行時期擁有輸出接收端

推送式接收端可以集中緩衝，但 bash 已經在執行器 seam 後擁有有界緩衝、截斷與 spill 文件。拉取格式化增量能夠保留這一所有權。擁有儲存的持久化後端可能足以支持重新審視生產方介面。

### 隨機 id、提升或生命週期工作階段事件

授權而非不可猜測性纔是訪問邊界，並且 id 不用於派生檔案系統路徑；順序生成的品牌化 id 可保持 transcript（文字記錄）易讀。將前臺任務提升為背景工作需要 SDK 並未規定的使用者互動約定。啟動、讀取和通知已作為工具與上下文事件記錄，因此專用任務工作階段事件會重複面向模型的事實。

## 測試

單元覆蓋固定預檢原子性、按 kind 分配的 id、按確切 owner 與無 owner 桶執行的准入、`stopping` 佔位、終態釋放、輸出上限的校驗與投影、完整結果的 UTF-8 位元組上限、流式與最終讀取、等待逾時與中止競態、取消、首次結果優先的結帳、監聽器隔離、通知壓制、所有者隔離、過時的所有者實例、所有者清理、服務資源銷毀和無控制器防線。生產方測試覆蓋 bash 行程對映、subagent 啟動取消、終止對映與釋放。快照覆蓋固定控制工具 schema、提示詞指導，以及一條組合完整的 ACP 路徑：設定上限會拒絕第二個真實後臺 Bash 任務，並給出 `job_kill` 復原動作。

## 後果

bash 命令與 subagent 共享一套 id 詞彙、清單、通知格式、提示詞習慣和控制工具。新的長時間執行生產方只需實作執行掛鉤，而不必再實作一套登錄檔與工具族。[工具實作手冊](../../../../docs/cookbook/adding-a-tool.md)將生產方指向本約定。

單個確切 owner 無法再無限增加行程內由 Task 承載的工作，另一個 owner 也不會消耗它的額度。取消請求會繼續佔用容量，直到生產方真正釋放資源，因此用新工作替換緩慢停止的任務不會突破已設定的即時資源預算。

有所屬後臺 bash 會隨其 agent 一起停止，不再比 agent 存活更久。後臺行程沒有執行器逾時；呼叫方必須終止無關工作，或相依性所有者/服務釋放。流式讀取只支持一個消費端；生產方的 `cancel` 返回後如果未使 `done` 完成，仍可能阻塞資源銷毀。持久任務、獨立觀察遊標和前臺提升仍屬於單獨設計。
