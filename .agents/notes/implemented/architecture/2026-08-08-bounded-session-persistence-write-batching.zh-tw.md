# Agent Note: 為工作階段持久化寫入批次處理設定上界

Status: implemented

[English](2026-08-08-bounded-session-persistence-write-batching.md) | [简体中文](2026-08-08-bounded-session-persistence-write-batching.zh.md) | 繁體中文

## 問題

流式回應可能會在短時間內寄出大量 `assistant/chunk` 事件。此前，只要空閒佇列收到一個事件，持久化協調器就會立即調度一次後端追加。該追加仍在進行時到達的事件會共用一個後續批次，但如果後端速度很快，仍可能產生大量小規模的持久化追加。每次 JSONL 追加都會建立並同步一個 Zstandard 幀或原始格式後綴，而每次 SQLite 追加都會打開並提交一個事務，同時遞增工作階段修訂版本。

丟棄區塊事件或用組裝後的訊息替代它們可以減少邏輯儲存量，但也會改變事件日誌、重播、序列號、時間戳，以及助手訊息引用的區塊 seq。寫放大問題不要求採取這項語義變化更大的方案。

### 量化基線

倉庫 fixture（測試前置資料）讓邏輯資料量有了具體依據。對當前 [`goal-multi-turn-actions`](../../../../apps/web/tests/snapshots/goal-multi-turn-actions/session.jsonl) 中的打包行進行解碼，可得到 2,098 個事件，其中 2,017 個是區塊（96.1%）。這些區塊解包後的 JSONL 行共 332,647 位元組，佔全部事件 379,225 位元組的 87.7%；區塊打包則把倉庫中的已提交文件縮小到 89,176 位元組和 182 個儲存行，其中包括 23 個打包區塊行。[`permission-policy-context`](../../../../apps/web/tests/snapshots/permission-policy-context/session.jsonl) 可得到 813 個事件，其中 746 個是區塊（91.8%）；這些區塊解包後的 JSONL 行共 118,935 位元組，佔全部事件 184,821 位元組的 64.4%。其打包文件為 84,917 位元組，共 123 個儲存行，其中包括 14 個打包行。這些是納入版本控制的確定性 fixture，不代表生產工作負載分佈；但它們說明瞭刪除區塊為何會降低邏輯資料量，也說明現有打包行版面配置已經消除了大量 JSON 包裝開銷。

SQLite 每個邏輯事件儲存一行，因此同樣的邏輯日誌會分別保留 2,098 和 813 個事件行；批次處理不會改變這些數量。JSONL 每個持久化追加批次會寫入一個 Zstandard 幀並執行一次 fsync，SQLite 每個批次會執行一次交易並遞增一次工作階段修訂版本。執行時期文件不記錄原有追加邊界，因此不能把 fixture 的儲存行數當作 fsync 或交易次數。

調度上界是確定的。當寫入端會立即完成每次操作時，原來的即時控制器可能對每個在前一次追加完成後到達的事件分別發起一次追加。一個控制器測試以 10 ms 的間隔接納 20 個事件：200 ms 固定視窗會把全部 20 個事件交給一次追加。對於這種到達節奏，追加次數從 20 次降至 1 次，但這不是普遍比例。稀疏事件、強制 flush、較慢的前序寫入和不同到達速率都會產生不同的批次大小。

## 決策

第一方 JSONL 與 SQLite 外掛程式公開 `writeBatchMaxDelayMs`，其值必須是一個不超過 Node 計時器上限的正整數，預設值為 `200`。每個外掛程式都會在載入時解析該值，再傳給 `PersistenceCoordinator`；批次處理行為仍只由協調器負責。

每個活躍的工作階段都有一個包私有 `SessionWriteBehind`。當其待處理佇列從空變為非空時，控制器會啟動一個固定視窗。後續事件加入該批次但不會重設截止時間：這屬於有界合併，而不是防抖。截止時間到達後，控制器會把完整的待處理前綴交給現有的按 id 序列化機制，並沿 `appendBatch` 路徑寫入。同一工作階段同時最多有一個活躍寫入。該寫入期間接納的事件會形成新的待處理前綴，並擁有自己的固定截止時間；如果該截止時間在活躍寫入完成前到期，新前綴會在前一次寫入完成後立即開始寫入。

`writeBatchMaxDelayMs` 只限制控制器為批次處理而主動等待的時間。事件迴圈調度、初始化、此前的序列化操作和後端 I/O 都可能延後持久化完成時間，因此該選項並不對 fsync 完成時間或崩潰資料丟失提供硬性 SLA。

`session/flush` 會取消剩餘等待，並充當共享的完全靜止屏障。它會在完成前等待活躍寫入嘗試，並排空屏障執行期間接納的每個事件。工作階段退役與後端 dispose（資源釋放）共用該屏障，因此生命週期 teardown 絕不會等待批次處理計時器。檢查點策略仍會在模型請求與頂層工具副作用之前設定強制屏障。

每個事件仍會按原有順序和形態持久化。控制器會在接納時複製每個事件；任何 `assistant/chunk`、`seq`、`time`、surface 元資料或儲存記錄都不會被刪除或重寫。因此，JSONL 可以在一個追加幀中編碼更多事件，SQLite 可以在一個事務中插入更多事件行，而無需改變任一種磁碟格式或 schema 版本。

後臺追加失敗後，控制器會把完整批次復原到所有較新的待處理事件之前，報告一次該失敗，並暫停自動重試。隨後新接納的第一個事件會開啟新的固定視窗；顯式 flush、退役或 dispose 會立即重試，如果故障再次發生，則會向呼叫方暴露該故障。這可以避免計時器驅動程式的失敗迴圈，同時保留現有可復原的 flush 邊界。

本決策僅取代[將即時持久化歸並到單個刷新控制器](../simplification/2026-07-23-collapse-persistence-flush-state.md)中的即時調度節奏。對於每個活躍工作階段使用一個控制器、保留失敗批次、按 id 序列化、退役和完全靜止的 dispose，原 Agent Note 仍是權威記錄。後端掛鉤邊界仍由[共享持久化協調器](2026-06-18-shared-persistence-write-coordinator.md)定義。

## 備選方案

**不持久化流式區塊事件。** 這裡不採納：這會改變事件溯源的權威地位及復原語義，而不只是改變物理寫入節奏。在無資訊損失的替代方案獨立定義重播、fork、引用源事件的關聯、序列和崩潰行為之前，現有的[拒絕僅保留組裝訊息的決策](../../rejected/simplification/2026-06-20-assembled-assistant-messages-only.md)仍是防護規則。[打包行決策](2026-07-26-packed-chunk-rows-by-default.md)仍是配套的 JSONL 儲存體積最佳化。

**僅在語義檢查點寫入。** 不採納：此方案會最大化批次處理，卻讓普通的崩潰丟失視窗取決於另行掛載的策略。有界後臺寫入會在檢查點之間持久化進度，而強制 flush 繼續提供更強的順序約定。

**按最新事件重設防抖視窗。** 不採納：持續不斷的流式回應可能無限期推遲首次寫入。由第一個待處理事件啟動的固定視窗，為主動合併等待提供了真正的上界。

**分別在 JSONL 與 SQLite 中實作計時器。** 不採納：調度、失敗保留、flush 競態和 teardown 都是後端無關的生命週期問題。重複實作這些機制會重新引入 `PersistenceCoordinator` 已消除的實作漂移。

## 驗證

控制器測試使用假時鐘證明固定且不會重設的 200 ms 視窗、即時且可共享的 flush 屏障、屏障執行期間接納的事件、在活躍寫入之後已超過視窗時限的尾部批次、有序保留失敗批次、暫停自動重試，以及對重疊發生的後臺失敗進行顯式重試。協調器測試會在工作階段通知、退役、衝突回收和 teardown 路徑中驗證該控制器。JSONL 與 SQLite 測試套件繼續覆蓋儲存格式、交易、復原和共享持久化約定。

## 後果

高頻事件突發通常會減少持久化追加操作，同時保持邏輯事件數量完全不變。減少幅度取決於事件到達速率和後端延遲：位於同一 200 ms 視窗內的突發事件會成為一個批次，而強制 flush 與稀疏事件仍可能產生小批次。

本決策不會限制因後端緩慢而積壓的待處理事件數量或位元組數，也不會減少 SQLite 行數或解碼後的邏輯日誌。若要建立經過驗證的記憶體上界或邏輯保留策略，就必須為其另行定義失敗與重播約定，而不是再引入一條隱式計時器規則。

接納後的事件在設定視窗內可能只存在於記憶體中，此後在等待調度或後端工作完成期間也可能如此。部署可以選擇較小的值以縮短普通丟失視窗，也可以選擇較大的值以加強批次處理。顯式持久性邊界保持不變，並會繞過等待。

新的 deep 模組統一負責計時器、活躍寫入、待處理前綴、重試暫停和屏障。`PersistenceCoordinator` 繼續負責初始化和按標識序列化；後端仍只負責持久儲存原語。`SESSION_FORMAT_VERSION` 與 SQLite `SCHEMA_VERSION` 均不變。
