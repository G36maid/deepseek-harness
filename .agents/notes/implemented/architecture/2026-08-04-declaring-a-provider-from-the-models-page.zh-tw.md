# Agent Note: 在 Models 頁上聲明一個提供方

Status: implemented

[English](2026-08-04-declaring-a-provider-from-the-models-page.md) | [简体中文](2026-08-04-declaring-a-provider-from-the-models-page.zh.md) | 繁體中文

## Problem

下面兩層已經讓 pi-ai 路由變成[一份聲明](2026-08-03-pi-ai-declared-provider-catalog.md)，並給了 host [詢問草稿端點](2026-08-04-draft-provider-endpoint-interrogation.md)的能力。但兩者都沒有抵達不編輯 YAML 的人：Models 頁仍然只為每個提供方提供一個 API 金鑰輸入框和一個裝著 API 地址的摺疊區，因此接入一個閘道意味著打開 `$DSH_HOME/settings.yaml` 並知道 profile 的形狀，更正一個過時的上下文視窗也是如此。能力已經存在，介面卻沒有暴露它。

缺的是兩件事，而它們的形狀並不相同。編輯既有路由的模型，是一張已經存在的卡片上的一個*欄位*；聲明一條路由則是一次*建立*：路由 id 正在此處被選定，而在選定之前根本沒有可編輯的 settings 地址。

## Decision

模型清單是兩條流程共用的元件；建立則是它自己的卡片。

`ModelListEditor` 編輯 profile 的 `models` 陣列——一行一個模型，含 id、顯示名稱、上下文視窗與輸出上限——並持有取得動作。空清單意味著「使用該路由的內建 catalog」，因此每一行都只會被刻意新增；清空某個選填欄位會丟棄它，而不是存入一個 schema 會拒絕的值，不是正整數的容量則根本不會被存下。

取得會詢問表單**當前顯示**的端點——已修改但未保存的 API 地址、已鍵入但未儲存的金鑰——因此新增一個提供方是一趟走完，而不是「先保存再回來」。回覆會打開一個選擇框而不是直接寫入：已設定過的候選默認不勾選，因此採納一次選擇絕不會覆蓋使用者已更正的容量。無法被詢問的提供方只是繞路而非死路；配接器自己的訊息會出現在各行旁邊，而這些行仍可手工編輯。

`CustomProviderCard` 聲明 pi-ai 未提供的路由。它之所以是獨立卡片，正因為路由 id 是在這裡選定的：一次 `settings.mutate` 在 `providers.<route>` 上設定整個 profile，金鑰則經 `credentials.set` 單獨傳遞，使用與既有提供方相同的 `<ROUTE>_API_KEY` 派生。手工聲明的路由無法默認的三件事——端點、協議、至少一個模型——會門控建立按鈕，因此失敗會在使用者仍看著該欄位時點名它。

協議選項來自該 namespace **自己的 schema**，經頁面本就會取得的 settings 描述符讀出（`providers.*.api` 是配接器 `supportedProtocols()` 的一個 union）。沒有新增 wire 欄位，用戶端裡沒有常數，提供的選項也無從與被接受的集合發生漂移。

對於目錄報告為**已聲明**的路由，編輯器夠得著它為自己命名的那兩個欄位——顯示名稱與該協議。建立卡片索要一個編輯器改不了的欄位，等於把該欄位留在只有 `settings.yaml` 才能觸及的位置，而那正是本記錄要終結的姿態。兩者都渲染在摺疊區裡、緊挨著端點，協議讀的是同一份 schema。清空名稱即取消設定，而路由退回的是該欄位所編輯層之下的那一層——`cordis.yml` 可以為目錄未提供的路由釘一個名稱，因此佔位符讀組合層，只有沒人釘名稱時才報路由 id。協議沒有可退回的兜底。既然一次保存現在可以改名，保存回執便按刷新後的目錄來點名這條路由，而不是按卡片打開時捕獲的 target。內建目錄路由兩個都不給：它的名稱由目錄條目兜底，它的每個模型各自帶著自己的協議，路由級協議只可能把它們全部覆蓋掉。

**Provider ID** 是建立卡片上唯一保持固定的欄位，原因不是沒做控制元件。它是 `providers.<route>` 這個字典鍵，因此改它是一次搬移而非一次編輯，而編輯器正是由那次搬移會作廢的 `settingsPath` 尋址的。它還被本 namespace 之外引用——`agent-default-model` 存著一個 `provider` 字串，每條工作階段日誌裡的每個 `request/header` 也都已經記下了一個——因此重新命名會悄悄抽空這個頁面看不見的那些引用。它同時是派生憑據引用的詞幹：頁面寫得了金鑰卻永遠讀不回來，因此無法把 `OLD_API_KEY` 搬到 `NEW_API_KEY`，重新命名要麼讓已存金鑰成為孤兒，要麼讓 profile 指向一個仍帶舊名的引用。聲明新路由再刪掉舊的，把這三件事都顯式做了一遍，而頁面本就提供這兩半。

## Alternatives considered

**在 `ProviderEditor` 上加欄位來聲明提供方。** 兩張卡片變一張，但編輯器由 `settingsPath` 尋址，而正在被命名的路由還沒有路徑。逐次按鍵重算路徑會讓卡片重新掛載並丟掉草稿；推遲計算則意味著編輯器的整條寫入路徑不再描述它正在編輯的東西。

**為協議清單新增一個協議欄位。** 顯式。但 settings schema 本來就會跨越協議層、本來就含有那個 union，因此第二份副本可能與第一份不一致——而配接器強制執行的是 schema 那一份。

**開放 Provider ID 編輯，由頁面來完成這次搬移。** 卡片可以在一次 `settings.mutate` 裡取消舊鍵、設定新 profile，剩下的就只是改名。但憑據沒法跟著走——頁面手裡只有脫敏描述符，從來沒有值——而其他 namespace 與已記錄工作階段裡的引用根本沒有重新命名通路，因此這個功能誠實的版本，就是頁面已經具備的「先建後刪」。

**給每條 pi-ai 路由都提供協議，並附一個「繼承」選項。** 與緊挨著的 API 地址對稱，而且把內建目錄路由指向講另一種協議的閘道確實是有人會想要的事。但目前沒有消費端提出這個訴求，一次選錯就會靜默地把該路由上每個模型都重指，而「繼承」選項還會成為把已聲明路由寫成配接器拒絕的 profile 的唯一途徑。真要這麼做的部署，`settings.yaml` 仍然表達得了。

**針對已存 profile 而非即時表單發起取得。** 對尚未保存的提供方來說，金鑰就不會離開表單。但最需要取得的恰恰是「什麼都還沒存」的那條流程，而端點已修改的表單會悄悄去詢問舊地址。

**把採納的候選直接寫進清單。** 點擊更少，但一次取得就會覆蓋使用者已更正的容量，而只公佈 id 的清單會把真實數字替換成空。

## Consequences

閘道、自建服務，或比已安裝 catalog 更新的模型，如今無需離開瀏覽器就能設定，而模型 id 在端點能提供時由端點自己給出。頁面多了兩個元件和一個共用的清單編輯器；編輯卡片的 pi-ai 摺疊區從兩個欄位長成了一個清單，已聲明路由上還多了一個名稱輸入框和一個協議選擇框。

代價是：只有 pi-ai 路由可以手工聲明，因為 `llm-pi-ai` 是唯一一個其 profile 描述整個提供方的 namespace——`llm-deepseek` 路由仍是組合面的事實。詢問只覆蓋 OpenAI 相容端點，因此講其他協議的閘道會報告自己無法被詢問，其模型需手工鍵入。另外，頁面在一次取得期間會把金鑰保存在元件狀態裡，這與 `credentials.set` 已有的暴露面相同，且不長於卡片的存活時間。

## Testing

`packages/client/ui-settings-models/tests/provider-form.client.spec.tsx` 在指令碼化的協議面之上驅動渲染後的頁面：新增、編輯與移除行；被清空的選填欄位離開 profile、非整數容量從不進入；詢問攜帶已修改的端點、未保存的金鑰，以及 profile 自身的協議；選擇框的默認選中、勾選切換、取消，以及「採納保留已調優的行」；空清單、被拒、傳輸被拒三條路徑；建立寫入一份 profile 加其憑據；建立按鈕上的每一道門控；以及只讀姿態。`protocolChoices` 針對「聲明瞭該 union」與「沒有聲明」兩種 schema 都有覆蓋。樣式 gate 讀取本包自己的原始碼，任何只取 `.input` 而不取 `.selectInput` 的 `<select>` 都會失敗——否則它保留的系統箭頭會緊貼 `select.input` 所設 240px 上限的右邊緣。編輯器自身的欄位清單按路由種類各有斷言——內建目錄路由止於金鑰與端點，已聲明路由還帶著協議——同時覆蓋協議改動只以單條 `api` path op 傳出、改名只以單條 `displayName` path op 傳出、清空名稱是取消設定而不是存入配接器會拒絕的空串，以及不寫協議的已聲明 profile 什麼都不選中、而非選中第一個候選。`apps/web/tests/models-settings.e2e.ts` 經真實協議層重新打開這條已聲明路由，捕獲該卡片，並斷言選定的協議與新名稱都抵達了 `settings.yaml`、該行也以新名重新註冊。
