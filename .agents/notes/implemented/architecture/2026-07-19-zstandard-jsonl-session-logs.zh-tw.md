# Agent Note: Zstandard JSONL 工作階段日誌

Status: implemented

[English](2026-07-19-zstandard-jsonl-session-logs.md) | [简体中文](2026-07-19-zstandard-jsonl-session-logs.zh.md) | 繁體中文

## 問題

JSONL 持久化後端會逐字保留每個 `SessionEvent`，其中包括數量龐大的 `assistant/chunk` 記錄。原始文字便於檢查，但重複的 JSON 鍵和模型文字會增加儲存與 I/O 開銷。壓縮編碼必須保留既有的 append/fsync 提交邊界、首次物化時的無衝突發布、崩潰修復以及僅元資料列舉；如果每輪都重寫整個壓縮文件，就會失去這些屬性。

編碼還必須在部署邊界上保持顯式。快照 fixture（測試前置資料）與外部逐行讀取器需要原始 JSONL，而後端無法在同一根目錄中安全猜測壓縮產物與原始產物，也不能靜默遷移預發布工作階段資料。

## 決策

### 設定與後綴歸屬

`dsh-session-persistence-jsonl` 接受 `compression?: 'zstd' | 'none'`，並將省略值顯式解析為 `'zstd'`。Zstandard 產物使用 `.jsonl.zstd` 後綴；`'none'` 保留原有的換行分隔 UTF-8 `.jsonl` 表示。`SessionLocation.kind` 仍為 `'jsonl'`，因為兩種編碼承載同一邏輯記錄格式；按照倉庫的預發布拒絕且不遷移策略，`SESSION_FORMAT_VERSION` 仍為 `0`。

每個持久化根目錄只歸屬於一種編碼。一次性的發現預檢會拒絕任何相反後綴，而針對性的載入、活躍採用、列舉與物化路徑會在最初空目錄預檢之後再次執行對應後綴檢查。錯誤會指出不相容產物，並要求部署選擇匹配設定或單獨根目錄。系統不提供遷移、雙重讀取、雙重寫入或基於擴充名的兜底。

### 幀與寫入路徑

壓縮產物是標準獨立 [Zstandard 幀](https://datatracker.ietf.org/doc/html/rfc8878)的串聯：第一個帶校驗和的幀只包含頭部行，後續每個持久追加批次各佔一個帶校驗和的幀。正常 agent loop（代理循環）批次就是輪次提交，因此幀邊界保留既有持久化檢查點，同時不讓儲存層相依性輪次事件類型。

壓縮使用 Node 內建的 [`zstdCompress` 與 `zstdDecompress`](https://nodejs.org/download/release/v22.19.0/docs/api/zlib.html)，倉庫最低支持的 Node 22.19 已提供這些 API。後端啟用 `ZSTD_c_checksumFlag`，其餘採用 Node 預設值，不公開壓縮等級調節項，也不增加相依性。Node 將該 API 標記為實驗性，因此 Node 22.19、24 與 26 相容性閘門會執行同一個輔助實作。

首次物化會在打開暫存檔之前壓縮兩個初始幀，然後寫入該文件並執行 `fsync`。POSIX 透過避免衝突的硬連結和目錄 `fsync` 發布該文件；Windows 透過 `MoveFileExW(..., MOVEFILE_WRITE_THROUGH)` 在不替換目標文件的情況下發布。後續批次也會先壓縮，再打開目標並在 EOF 追加。捕獲到寫入或文件同步失敗時，後端會關閉追加控制代碼，以讀寫方式重新打開日誌，截斷到原有位元組長度，同步回滾結果，再重新拋出錯誤，讓協調器能夠在兩個平臺上重試未變化的批次。

### 讀取、列舉與當機復原

幀邊界掃描器會讀取標準魔數、可變頭欄位、塊頭與負載長度，以及選填校驗和尾部，但不會解釋壓縮塊。完整幀會獨立驗證校驗和，再進入[大型工作階段復原管線](2026-08-05-large-session-jsonl-restore-pipeline.md)；該管線負責複用解碼器、協作式讓出事件迴圈和增量掃描 JSONL。任何完整幀的校驗和或解壓縮失敗、完整幀中畸形的 JSONL 尾部，或者無效幀結構都屬於損壞並拒絕載入。

列舉只按有界區塊讀取到第一個完整幀可用為止，驗證並解壓縮該頭部幀，絕不讀取事件幀。因此，即使工作階段日誌很大，專用頭部幀仍能維持僅元資料列舉。

最終幀內部遇到 EOF 屬於可復原的撕裂尾部。掃描器確定該邊界後，專用前綴解碼器會使用 `finishFlush: ZSTD_e_flush`，使 Node 不必等到幀結束或讀到完整校驗和就能產出已有明文；其中每個完整且以換行結束的事件都會保留。修復從該幀起始位元組截斷，再追加一個新的帶校驗和幀，其中依次包含復原出的完整事件，以及協調器生成的工具、步驟與輪次閉合事件。如果撕裂位置尚不足以解碼任何完整事件，修復會丟棄該不完整幀並保留此前全部完整幀。

### 消費端與驗證

CLI（命令列介面）、ACP（Agent Client Protocol）與 stdio 應用包公開對稱的 `persistenceCompression` 透傳設定。web 宿主裝配與普通應用組合省略該選項並使用壓縮預設值。快照錄制與重播組合顯式選擇 `'none'`，因為提交的 fixture 是重播與規範化過程使用的原始 JSONL 輸入。

共享持久化約定與協調器約定會針對兩種編碼執行。後端測試覆蓋標準幀與校驗和互操作性、僅頭部列舉、追加回滾、編碼不匹配拒絕、完整幀損壞，以及橫跨頭部、塊和校驗和尾部的最終幀撕裂。默認執行時期、建置後二進位、headless、ACP 與 Python 冒煙測試會斷言壓縮後綴與 Zstandard 魔數，或解碼頭部；讀取原始內容的測試則顯式退出壓縮。

## 考慮過的替代方案

- **每條 JSONL 記錄一個幀**——不予採納，因為它會讓大量區塊事件各自承擔幀頭與校驗和開銷，並讓物理邊界脫離持久追加批次。
- **每次追加都重寫一個完整壓縮流**——不予採納，因為成本會隨日誌大小成長，而且替換操作會放棄追加/fsync 回滾和既有的無衝突物化機制。
- **跨追加使用流式壓縮器**——不予採納，因為編碼器狀態中斷後不會留下可獨立校驗的追加單元，從而使有界列舉與按幀起點修復更複雜。
- **增加外部原生 Zstandard 相依性**——不予採納，因為受支持的 Node 最低版本已經提供所需編解碼器；另一個原生產物會增加安裝與可執行文件打包風險，卻不增加必需行為。
- **公開壓縮等級或繼續默認使用原始 JSONL**——不予採納，因為沒有部署證據支持第二種調節策略，而 `'none'` 已為需要逐行讀取的 fixture 與整合保留路徑。

## 後果

- 普通工作階段根目錄儲存 `.jsonl.zstd`，並保留僅附加、fsync、回滾與中斷輪次復原語義。
- 原始 JSONL 仍是顯式設定，但切換編碼需要使用全新或單獨根目錄，或者選擇與既有產物匹配的模式。
- 每個持久批次一個幀會增加有界的幀與校驗和開銷，同時支持僅頭部列舉和從精確追加邊界開始修復。
- 外部工具必須理解串聯的 Zstandard 幀，或者消費原始模式產物；Node 通用的一次性解壓縮只讀取第一個獨立幀，因此後端讀取會透過[復原管線](2026-08-05-large-session-jsonl-restore-pipeline.md)遍歷各幀。
- 實作相依性 Node 的實驗性內建 Zstandard API，但不增加 NPM 相依性；受支持版本相容性閘門會暴露 API 漂移。
