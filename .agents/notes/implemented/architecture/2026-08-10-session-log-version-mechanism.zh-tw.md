# Agent Note: Session log 版本機制：單調整數、升級器鏈、逐事件可忽略標記

Status: implemented

[English](2026-08-10-session-log-version-mechanism.md) | [简体中文](2026-08-10-session-log-version-mechanism.zh.md) | 繁體中文

## 問題

Session log 在發布後必須能升級格式，而最先發布的執行時期決定了此後一切的下限：第一個發布版的讀取器缺少哪種拒絕和降級行為，使用者手裡已經裝上的副本就永遠補不上。發布 issue #1901 的最低要求是老執行時期讀到新 Session 格式時明確報不支持，而不是讀錯。改動前的讀取器在兩個方向上都做反了：`assertVersion` 對任何版本不匹配拋出同一條不區分方向的訊息；JSONL 解碼器把不認識的事件類型原樣放行，重建時靜默跳過，復原出一個內容殘缺的工作階段且沒有任何診斷。

## 決定

**一個單調遞增的整數，不分大小版本。**某一步能不能自動升級是那一步自己的屬性，由它的升級器存在與否表達，不該由兩級編號方案提前承諾（設計時很少能預知下一個變更算不算"大"）。這與 SQLite 後端 `SCHEMA_VERSION` 的先例一致。

**升不升版本由寫入方決定，與讀取方能力無關。**當且僅當老執行時期無法在語義上完全正確地處理新日誌時才必須升版本。"解析不報錯"不是標準：靜默跳過影響重建的內容就是讀錯。只有結構性變更夠得上這條線：header 形狀、事件信封、核心事件語義、surface 機制（`SurfaceEventType` 集合、`SurfaceOp` 變體）。拿不準就升：近似恆等的升級器幾乎沒有成本，漏升一次會讓老讀取器靜默讀壞。

**讀取規則按方向區分。**版本相等：正常讀。比讀取器新：拒絕，說明方向（"由更新的 harness 寫入，請升級"），並給出原始日誌文件的路徑，使用者仍能看到文字（`SessionFormatUnsupportedError`，與 `SessionPersistenceCorruptionError` 區分，因為資料沒有損壞）。比讀取器舊：查看時經 n→n+1 升級器鏈在記憶體中逐級轉換；只有工作階段真正被繼續時才把轉換落盤（暫存檔原子替換，原文件留備份）。寫不出升級器的那一步留空，這會切斷該步及更早所有版本的升級路徑，它們降級為只能看原文。

**逐事件的 `ignorable` 標記吸收詞彙表成長，普通的新增事件永遠不用升版本。**事件詞彙表由掛載了哪些外掛程式決定，單個版本整數描述不了它。讀取器遇到不認識的事件類型時拒絕解讀日誌，除非該事件的信封帶 `ignorable: true`。預設為必需：忘寫標記的後果是把一個本可復原的工作階段拒絕過頭（體驗問題），而默認可忽略會讓同樣的疏忽靜默復原出殘缺工作階段（安全事故）。架構保證了這條規則成立：模型可見內容只經三種帶 `surfaceOp` 標記的 surface 事件加 `request/header`、`request/context` 摺疊進入重建，危險的未知事件恰好是那些不進 surface 但改變日誌其餘部分解讀方式的事件（`session/end-seed` 是現存例子）。

## 影響

v0（0812 發布）交付的內容：分方向的拒絕並帶原始日誌路徑；基於生成的已知詞彙清單（`KNOWN_SESSION_EVENT_TYPES`，由 `gen-persistence-catalog` 從所有 `SessionEventMap` 聲明合併生成，`verify-persistence-catalog` 保證新鮮）的未知事件守衛；`ignorable` 信封欄位被種子校驗、兩個後端（SQLite 專用列，`SCHEMA_VERSION` 升到 15）和 BFF 線上 schema 接受。升級器鏈本身推遲到第一個真實的 v0→v1 變更出現、有真實對象可測時再建；寫入側目前不寫 `ignorable`（還沒有生產者需要它），`Session.append` 的這一表面隨第一個使用者一起落地。在註冊表面出現之前，倉庫外外掛程式的事件在第一方讀取器下無法復原工作階段，預發布立場接受這一點，而且拒絕是顯式的而非靜默的。未知類型守衛只在學取側生效：`appendCore` 繼續拒絕已淘汰的 legacy 形狀，但不對新類型做詞彙檢查，因為寫入時拒絕會讓活躍工作階段的持久化中途停擺，代價大於下次載入時的顯式拒絕。JSONL 後端還會在校驗當前 header 形狀、解碼任何事件行之前，直接從原始 header 行拒絕外來版本，因此結構完全不同的未來格式仍會報告升級方向而不是"損壞"；SQLite 則先由自己的 `SCHEMA_VERSION` pragma 把關整個文件的結構。

## 曾考慮的替代方案

- **大小兩級版本號**：能否轉換這一位資訊屬於每一步的升級器，把它預先固化進編號形狀會做出錯誤承諾。
- **未知事件默認可忽略**：把忘寫標記的後果從可見的過度拒絕反轉成靜默損壞。
- **查看時自動遷移落盤**：打開即改寫把讀操作變成破壞性寫操作，轉接器的 bug 會在瀏覽時損壞日誌，同目錄的舊版本執行時期也會因為新版本只是看了一眼就失去訪問能力。
- **外掛程式執行時期註冊已知事件類型**：會讓已知集相依性外掛程式組合，同版本的精簡組合會拒絕完整組合寫出的日誌。生成的全倉庫清單保證同版本讀取行為一致；倉庫外外掛程式的事件按構造就在清單之外，為它們提供註冊表面推遲到真有這樣的消費者時再做。
