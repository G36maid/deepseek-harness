# Agent Note: 路由模型上下文與壓縮策略

Status: implemented

[English](2026-07-20-routed-model-context-and-compaction-policy.md) | [简体中文](2026-07-20-routed-model-context-and-compaction-policy.zh.md) | 繁體中文

## 問題

當一個行程把請求路由到不同容量的模型時，壓縮（compaction）不能安全地應用同一個全域性上下文視窗。相同模型 id 也可能存在於多個提供方下，配接器還可能接受不在建議目錄中的動態 id。錯誤容量要麼讓壓縮觸發過晚並造成原本可避免的溢位，要麼讓壓縮觸發過早並丟棄有用上下文。

兩個直觀的設定歸屬方都無法獨立解決問題。Compact-basic 是選填外掛程式，不知道配接器接受哪些模型。LLM（大型語言模型）配接器擁有模型路由，但不能相依性選填壓縮外掛程式，也不應吸收消費端專用的閾值、保留、摘要器與重試策略。該設計既需要權威容量事實和選填的逐目標壓縮策略，又不能建立第二套模型登錄檔。

## 決策

### 配接器擁有精確路由容量

`LlmAdapter.resolveModel(provider, model, signal?)` 返回一條精確路由的聚合元資料，其中選填的 `LlmModelContext` 位於 `context` 欄位下。`LlmRuntime.resolveModelInfo()` 選擇已註冊的路由所屬方，驗證 `contextWindow` 為正整數，並返回與配接器內部狀態分離的元資料。該查詢獨立於 `listModels()`：不在目錄中的動態模型也可以擁有容量元資料，而缺少 `context` 只表示配接器無法描述容量。

手寫 DeepSeek 配接器允許每個已設定模型提供選填 `contextWindow`，並支持配接器級 `defaultContextWindow`。精確模型容量優先；未提供容量的模型項與未列出的透傳 id 會繼承配接器預設值，若預設值也不存在則省略 `context`。兩個內建模型項都公開精確的 256,000 token 容量。pi-ai 配接器從同一個目錄描述符解析容量，該描述符也用於權威解析請求模型。

### Token 計量保持模型無關

`dsh-token-meter` 沒有設定，也沒有模型 profile。它擁有一個固定重播摺疊，並返回絕對估算 token 壓力，以及按位置排列的表層節點 token 估值。移除全域性容量後，未載入 compaction-basic 時仍可複用計量，同時避免讓重播覈算變成另一套模型登錄檔。

### Compact-basic 解析目標規格

Compact-basic 擁有消費端策略。頂層欄位定義預設值；`modelPolicies` 包含以精確 `{ provider, model }` 組合為鍵的部分覆蓋。重複目標、未知欄位或無效欄位都會讓外掛程式載入失敗。`thresholdRatio` 預設為 `0.8`，保留策略預設為 `retainRatio: 0.16`；呼叫方也可以改用絕對 `retainTokens`，但兩種保留形式互斥。完成繼承後，如果保留比例不小於閾值比例，外掛程式也會載入失敗，因為任何模型容量都無法讓該策略有效。

對於主動壓力檢查，compaction-basic 讀取最新持久請求路由，解析其配接器容量與精確目標策略，再把比例縮放為 `ResolvedCompactSpec`。每次檢查都會重新解析，因此同一工作階段切換提供方或模型後，容量與策略會立即變化。若絕對保留預算不小於縮放後的閾值，系統會在目標容量首次允許比較兩者時失敗。

同一精確目標覆蓋還可以選擇摘要提供方/模型、摘要輸出上限、收斂重試次數與溢位重試上限。這些都屬於壓縮問題，不會進入任何 LLM 提供方。

### 目標專用壓力錯誤仍保留選填組合

缺少容量元資料的配接器仍是有效 LLM 路由。手動主動壓力檢查會返回目標專用設定錯誤；自動監聽器按精確路由只警告一次，並繼續保留完整歷史。當已解析容量暴露出無效的絕對保留預算時，系統也按路由抑制重複警告；其他執行故障仍會各自對外可見。提供方已經確認的規範化溢位不需要容量元資料：它繞過主動閾值與普通保留預算，嘗試一次最大且平衡的縮減，並在替換無法證明進展時保留原始提供方錯誤。

## 測試

服務測試覆蓋與配接器內部狀態分離的上下文元資料、無效配接器輸出、目錄獨立性與默認缺失行為。配接器測試覆蓋 DeepSeek 的精確容量、默認容量、未列出模型解析及無效容量，以及 pi-ai 的精確描述符解析。壓縮測試覆蓋比例縮放、精確提供方/模型覆蓋、載入期拒絕無效合併比例、執行時期校驗絕對預算、相同模型 id 的提供方切換、目標專用警告抑制與不相依性容量的溢位復原。Loader fixture（測試前置資料）會拒絕已經移除的 token-meter 容量設定，示例則在配接器上設定容量。

## 考慮過的替代方案

- **把容量與所有策略都放進 compaction-basic**——不予採納，因為 compaction-basic 會複製配接器的模型知識，未列出的動態模型需要平行註冊，而且未安裝壓縮時容量也會消失。
- **把壓縮策略放進各個 LLM 配接器**——不予採納，因為配接器必須獨立於選填消費端，而摘要與重試策略也不是提供方事實。
- **讓 `listModels()` 成為權威來源**——不予採納，因為發現能力只是建議資訊，一些配接器有意接受動態 id。正確性元資料不能把選擇器成員關係變成路由白名單。
- **給 token-meter 增加逐模型摺疊**——不予採納，因為重播演算法可以共享，變化的只有容量與消費端策略。多個摺疊會重複狀態，卻不會改善估算。
- **建立獨立模型上下文登錄檔**——不予採納，因為配接器已經擁有權威路由解析。第二套登錄檔會引入生命週期順序、重複鍵與漂移問題，卻沒有獨立後端。

## 後果

- 容量在提供方約定上擁有唯一權威歸屬方，而壓縮策略留在選填消費外掛程式中。
- 同一個 compaction-basic 實例無需查詢發現元資料，就能安全處理不同視窗、提供方切換，以及不同提供方下的相同模型 id。
- 僅 LLM 與僅 meter 的組合仍然有效；載入 compaction-basic 不會讓配接器產生反向相依性。
- DeepSeek 部署可以設定精確的逐模型容量，也可以讓未提供容量的模型項與未列出的透傳 id 使用 `defaultContextWindow`。
- 比例預設值會隨模型自然縮放，同時仍可按精確目標使用絕對保留值，以滿足部署專用行為。
