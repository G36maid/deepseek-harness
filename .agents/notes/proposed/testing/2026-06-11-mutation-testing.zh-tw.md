# Agent Note: 變異測試作為覆蓋率的制衡手段

Status: proposed

[English](2026-06-11-mutation-testing.md) | 繁體中文

## 問題

逐文件 100% 覆蓋率閘門（[品質閘門決策](../../implemented/process/2026-06-11-quality-gates.md)）證明每一行程式碼在測試中都被*執行*了，但不能證明如果該行出錯，任何斷言會注意到。在 agent（代理）編寫測試的場景下，覆蓋率壓力可能產出「執行但不斷言」的測試。變異測試衡量的正是覆蓋率無法衡量的：測試套件是否能*殺死*被刻意注入的缺陷。

## 提案

使用 Stryker（`@stryker-mutator/vitest-runner`）對 `packages/*/src` 執行變異測試：

- **PR（Pull Request）範圍的增量執行**（僅變更文件），作為一個 CI job。調優後速度足以作為合併閘門。
- **每夜全量執行**，跟蹤變異分數；先記錄基線，再將閾值設為觀測到的基線並只升不降（與覆蓋率策略一致：閾值只收緊）。
- 存活的變異體是待辦項：agent 選取一個存活體、編寫殺死它的測試、迴圈往復——一個適合自主執行的閉環。
- 等價變異體（可證明不改變行為的）加註釋排除並附理由，與 `/* v8 ignore */` 策略一致。

## 計畫

1. 新增 Stryker 設定，範圍限定在一個包，即 llm（最小、最具演算法性），並測量執行時期間。
2. 擴充到所有包；在設定中記錄基線分數。
3. 接入每夜 job；執行時期間可接受後再新增 PR 範圍的增量 job。

## 驗收標準

- Stryker 設定在 `packages/*/src` 上以 vitest runner 執行；每夜 job 記錄變異分數並採用只升不降的閾值，分數低於已記錄的基線時任務失敗。
- PR 範圍的增量執行在執行時期間可接受後作為合併閘門；否則明確決定只保留每夜執行，並將該結論記錄於此。
- 等價變異體帶有註釋排除及理由，與 `/* v8 ignore */` 策略一致。

## 風險

執行時期間：變異測試開銷大；逐文件 100% 覆蓋率有所幫助（每個變異體至少會被執行到）。如果 PR 範圍的執行始終過慢，則保持僅每夜執行，依靠變異分數閾值的只升不降機制。
