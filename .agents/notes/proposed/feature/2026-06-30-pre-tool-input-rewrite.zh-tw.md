# Agent Note: 工具執行前輸入重寫——一致性設計

Status: proposed

[English](2026-06-30-pre-tool-input-rewrite.md) | 繁體中文

## 問題

[攔截擴充點 Agent Note](../../implemented/feature/2026-06-30-interception-extension-points.md) 將 `tools/pre-execute` 定義為一道針對執行的允許/拒絕/詢問閘門，此時執行的身份標識已受保護、參數已被深度凍結。Claude Code 的 `PreToolUse` 掛鉤還提供了 `updatedInput`，因此忠實的橋接需要一個顯式的重寫機制。重寫不能是對現有執行對象的可變逃逸口：它必須保持持久化歷史、審計記錄、展示層與實際執行值之間的一致性。

## 問題本質：執行前參數的三個讀取方

在 agent loop（代理循環）中，工具呼叫的參數在工具執行之前就已提交到日誌並被即時消費端讀取：

1. **`assistant/message`** 在工具分發之前追加——它是 `deriveMessages()` 重播時的模型歷史來源，因此攜帶模型自身輸出的工具呼叫參數。
2. **`tool/call`** 是持久化的審計記錄，在 `ctx.tools.execute()` 之前追加。
3. **面向人類的展示讀取 `tool/call.arguments`**：UI 渲染器將這些參數傳給 `presentResult`；`dsh-tool-bash` 從中派生卡片標題、rawInput、cwd 以及終端機/後臺處理方式。

如果只做執行層面的重寫，UI 會顯示一條命令而實際執行的是另一條，並且結果會對著錯誤的參數渲染。登錄檔目前透過以下方式防止這種失敗模式：對 `arguments` 做 structured-clone 並深度凍結，將執行身份屬性設為不可寫，且不暴露任何可替換它們的測試 shim 或監聽路徑。重寫設計必須維護這一受保護的身份邊界，而非削弱它。

## 提案

重寫是一個「身份標識建立前的一致性交易」。當掛鉤提供 `updatedInput` 時，有效值必須在登錄檔構造其不可變的 `ToolExecution` 之前確定，並且必須原子地反映到全部三個讀取方：

- `tool/call` 審計事件記錄重寫後的參數（原始參數保留在一個伴隨欄位中，作為審計線索——掛鉤修改了呼叫，原始參數與生效參數都是值得保留的事實）。
- 派生歷史中的 `assistant/message` 必須與實際執行一致。待評估的選項：就地重寫 assistant 訊息中的工具呼叫塊（改變模型「看到自己說了什麼」），或記錄一條單獨的修正讓下一次請求攜帶。Claude Code 的模型是讓模型看到重寫已生效。
- 展示層（`presentCall`/`presentResult`）讀取重寫後的參數，使 UI 顯示實際執行的內容。

在 `PreToolDecision` 當前的觸發點上做擴充是不夠的：此時兩條持久化記錄已經存在，執行身份已受保護。實作必須將相關決策移到日誌提交之前，或者增加一個專門的、更早的重寫決策點來處理待定的模型呼叫。agent loop 將生效參數提交到歷史和審計之後，再構造普通的不可變執行對象，並照常執行現有的允許/拒絕/詢問和工具管線。

## 曾考慮的替代方案

### 為什麼不直接修改執行對象？

允許 pre-execute 監聽器賦值 `exec.arguments` 只能提供執行層面的重寫，模型歷史、審計和展示層不會隨之改變。保持身份標識受保護使得這種區域性行為不可表達。在一致性交易實作之前，CC/Codex 橋接對 `updatedInput` 記錄日誌並行出警告，而非聲稱已兌現；迴圈分發點的 `TODO(pre-tool-input-rewrite)` 標記了缺失的更早階段。

## 驗收標準

- 請求的重寫在 `ToolExecution` 身份標識建立之前解決，並原子地反映到全部三個讀取方：`tool/call` 審計記錄重寫後的參數（原始參數保留在伴隨欄位中）、派生歷史與實際執行一致、展示層渲染重寫後的參數。
- 生效的 `ToolExecution.arguments` 在 pre-policy、守衛、分發、post-policy 和最終觀測全程保持深度凍結且不可寫；不引入任何可變 shim。
- CC/Codex 橋接兌現 `updatedInput`，不再記錄忠實但降級的警告。

## 風險

- 重寫 `assistant/message` 中的工具呼叫塊會改變模型「看到自己說了什麼」；是否有提供方在重播時拒絕這種改動，是一個需要透過實驗確定的開放問題，必須在決策結構定型之前解決。
- 更早的重寫階段改變了 `assistant/message`、`tool/call`、掛鉤審計事件與執行之間的順序關係；設計必須固定這一順序，同時不削弱輪次封閉性或呼叫/結果鄰接性。

## 開放問題

- 重寫 `assistant/message` 中的工具呼叫塊是否會破壞某些提供方在重播時的預期？還是單獨的修正更安全？
- 原始參數是否應保留在 `tool/call` 事件（審計）上？如果是，放在什麼欄位？
- 重寫決策是移到日誌提交之前，還是成為一個專門的更早擴充點？現有的 pre-tool 允許/拒絕掛鉤如何避免執行兩次？
- 這與未來的權限 `ask` 流程（使用者批准一個被重寫的呼叫）如何互動？
