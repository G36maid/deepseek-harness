# Agent Note: composer 鏈選舉的語義階段

Status: proposed

[English](2026-08-08-semantic-composer-chain-phases.md) | [简体中文](2026-08-08-semantic-composer-chain-phases.zh.md) | 繁體中文

## 問題

瀏覽器的 `conversation.composer` 鏈先按一個全域性數值 `priority` 對所有候選項排序，再選出第一個返回匹配項的選擇器。問題採用默認優先級 `0`，審批採用 `1`，一次性或父級不可用時使用的只讀 subagent composer 採用 `-10`。因此，選中一次性 subagent 歷史記錄後，即使其下方有等待應答的問題或審批，介面仍可能顯示只讀說明。

該缺陷並非某個數值有誤。當前鏈用同一個標量作出兩項不同的決策：候選項究竟用於解決現有互動，還是用於限制發起新工作；以及如何確定同一語義類別內各候選項的區域性優先順序。任何數值修復都會保留這種隱式耦合，讓後續註冊方可以再次引入同一缺陷。

## 提案

鏈聲明可以定義由所屬領域擁有的有序階段元組。`conversation.composer` 聲明 `['interaction', 'restriction']`；該分階段鏈上的每項註冊都必須指名一個階段，其數值 `priority` 只在該階段內排序。`SlotCore` 依次按聲明的階段索引、區域性優先級和穩定註冊順序排序。如果分階段鏈的註冊項省略階段，或指名聲明外的階段，註冊會立即失敗。未分階段的鏈繼續沿用當前的數值排序行為。

問題與審批註冊到 `interaction`，並保留問題先於審批的現有階段內順序。`SubagentReadOnlyComposer` 以普通區域性優先級註冊到 `restriction`。領域規則定義明確：互動用於使 Host 上已經存在且仍有效的等待完成；限制則阻止使用者透過普通 composer 發起工作。完成現有等待並非向一次性子級傳送新的後續訊息，因此互動階段排在前面。等待完成後，鏈會重新選舉，只讀限制會再次出現。

階段詞彙歸聲明該 slot 的領域所有，而不屬於全域性 slot 框架。`SlotMap` 攜帶確切的階段元組，用於編譯期註冊；執行時期 `SlotSpec` 重複該元組，作為排序依據。其他鏈不會獲得任何 composer 術語，也無需遷移，除非它們主動聲明階段。

本提案擴充 [Web subagent 對話](../../implemented/feature/2026-07-27-web-subagent-conversations.md)、[Web 權限與審批](../../implemented/feature/2026-07-23-web-permission-and-approval.md)和[計畫審閱呈現](../../implemented/feature/2026-07-30-plan-review-presentation-intent.md)約定，但不取代其中任何一項。[執行時期所有權子級守衛](../../implemented/bug-fix/2026-08-01-ask-user-delegated-caller-guard.md)仍然是防止子級新建自己負責的人類等待的權威機制。本提案落地時，不應歸檔任何活躍 Agent Note。

## 備選方案

**把只讀項的優先級移到問題和審批之後。** 這是最小的戰術修復，但它仍以未記載的數值間距編碼語義支配關係，並迫使下一種 composer 類型在同一個全域性尺度上猜測自身位置。

**當 `interactions` 非空時，讓只讀選擇器拒絕匹配。** 這可以修復當前這一對元件，但會迫使限制外掛程式理解每個可操作領域，並在各選擇器中重複選舉策略。每新增一種互動類型，都需要修改與其無關的限制項。

**只相依性執行時期子級守衛。** 該守衛可以修復新的模型呼叫，但無法定義瀏覽器對已有待處理等待、滾動升級中的版本重疊或審批等其他互動類型的排序。執行時期權限與呈現選舉是兩項獨立的不變數。

**把所有匹配的接管介面渲染成一個棧。** composer 只有一個操作席位。同時堆疊問題、審批和只讀介面，會使鍵盤焦點與回答所有權含混不清，而不是選出一個當前操作。

## 驗收標準

- `SlotCore` 測試證明階段順序優先於任意區域性優先級；區域性優先級和穩定註冊順序在階段內仍然有效；未知或缺失的階段會明確失敗；未分階段的鏈保持不變。
- Composer 測試覆蓋問題加只讀項、審批加只讀項、問題加審批加只讀項、解決後回到只讀項，以及所有選擇器均拒絕匹配時回退到 InputBar。問題在 `interaction` 內仍排在審批之前。
- dispose（資源釋放）、HMR（熱模組替換）重新註冊和重新連線重播均不能留下過時的當選階段；選舉仍是當前所有者 props 與當前註冊項的純函式。
- 一項無金鑰組裝 Web 快照固定已尋址的 one-shot 對話及其待處理互動：互動介面勝出，解決該互動後，只讀介面再次出現。
- slot、conversation、question、permission 和 subagent 的 README／JSDoc 約定共同描述階段所有權以及互動先於限制的規則。
- 該變更不修改任何模型可見的工具定義、系統提示詞章節、請求路由或工作階段事件。因此，瀏覽器選舉既不產生 token 開銷，也不會使 KV Cache 失效；測試會比較僅在用戶端發生狀態轉換前後的模型請求 header。

## 風險

階段名稱可能淪為含混的設計替代品。因此，每個分階段 slot 都要擁有一條簡短的排序規則，並拒絕無法說明自身歸屬哪一側的註冊項。未來如有必須優先於回答操作的硬性安全介面，不應將其誤標為 `restriction`；它需要一個顯式排在更前的階段，或位於該 composer 鏈以外的邊界。

通用 slot 類型與已儲存條目形態會增加一個條件欄位，因此遷移不完整時，程式碼可能在一個 face 中透過編譯，卻在執行時期失敗。之所以在執行時期聲明中重複確切元組，正是為了讓系統能以機械方式拒絕這種漂移。並行問題與審批仍採用單介面策略；本提案保留其當前順序，不解決多互動排隊問題。
