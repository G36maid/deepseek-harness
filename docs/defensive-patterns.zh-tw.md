# 防禦性模式

[English](defensive-patterns.md) | [简体中文](defensive-patterns.zh.md) | 繁體中文

來之不易的缺陷類別規則：下面每條模式都是本項目實際發布或差點發布的一類缺陷，以防止其復發的規則形式陳述。在編寫生命週期、並行、子行程或清理程式碼之前請先閱讀本文。測試層面的對應規則（真實入口路徑、驗證實際結果、資源歸屬）見 [testing.md](testing.md)。

## 正交結果獨立上報

一個結果可以同時具有多種性質：行程可能已經逾時，卻仍以退出碼 0 結束，因為它捕獲了終止訊號。每個獨立事實（`timedOut`、`signal`、`exitCode`）都應單獨上報；切勿把一個標志的上報巢狀在另一個標志的分支中，否則呼叫方可能把提前終止的執行誤判為正常成功。

## 公共約定兩側都要遵守

當一個實作收到同一結果的多種表示時，應在透過公共 API 返回前將其規範化。`LlmAdapter.stream()` 的實作可以拋出例外或寄出 `finish {kind:'error'|'aborted'}`，但 `LlmRuntime.stream()` 只會透過終止型 finish 區塊暴露模型請求失敗；middleware 缺陷與消費端缺陷仍會以例外形式拋出。這使消費端不必猜測捕獲的例外究竟來自提供方、包裝層、區塊日誌記錄還是自身組裝邏輯。請在類型定義處記錄規範化後的約定；透過真實消費端覆蓋每種來源形式。

## 非同步狀態不是同步狀態

`agent.followup()` 沒有逐訊息的完成狀態或結果；背景工作的完成與輪次邊界存在競爭；`reader.close()` 在 EOF 和 dispose（資源釋放）兩種情況下都會觸發。切勿把 `agent/status` 或 `whenIdle()` 當作某次 `followup()` 的結果：多條已排隊的後續訊息、steering（中途引導）和注入工作可能共用同一個 `running` 區間，而取消或資源釋放可能丟棄尚未啟動的項。真正擁有一次執行的自動化呼叫方必須顯式定義其區間——例如從訊息的持久 inbox 回執到整個 agent（代理）下一次進入 `idle`——並將選取的任何輸出描述為整個區間的輸出，而不是把因果關係歸於該訊息。這條守則是雙向的：如果等待的轉換永遠不會發生，等待就會掛起，因此應顯式處理「無需等待」的分支。

## dispose 必須達到完全靜止，而不僅僅是請求停止

如果清理流程只發出終止或中止訊號便返回，而不等待工作真正停止，就會留下孤兒行程。清理邏輯應採用非同步流程，並等待子行程退出（寄出終止訊號後等待 `done`）；還應在終止行程前關閉監聽器登錄檔和通知登錄檔，使遲到的完成事件保持靜默。

## 在分發器中隔離回呼例外

使用者提供的監聽器如果拋出例外，不得導致它所在的 promise 被 reject，也不得餓死排在它後面的監聽器。請用 try/catch 包裹分發迴圈並記錄日誌；一個行為不當的訂閱者絕不能破壞核心生命週期。

## 絕不將環境變數或可預測路徑暴露給不可信輸出

啟動的命令應使用經過清理的環境變數，移除名稱匹配 `*KEY*`、`*SECRET*`、`*TOKEN*` 或 `*PASSWORD*` 的項，防止 harness 憑證透過命令輸出、`env` 或 spill 文件洩漏。暫存檔和 spill 文件應放在權限為 0700 的私有目錄中，使用隨機檔名，並以獨佔且僅所有者可訪問的方式打開（`'wx'`、`0o600`）；可預測且全域性可讀的路徑會引發符號連結競態和資訊洩露。

## 用 unlink 刪除連結形態的路徑

可能是符號連結或 Windows junction 的路徑，應先用 `lstatSync().isSymbolicLink()` 判斷，再用 `unlinkSync` 刪除：unlink 只刪除連結本身並拒絕真實目錄，因此絕不會跟隨連結進入其目標。Windows 上對 junction 呼叫 `rmSync(link)` 會拋 `ERR_FS_EISDIR`；遞迴刪除可能穿過 junction 進入其目標。真實目錄才使用帶 `recursive` 的 `rmSync`。
