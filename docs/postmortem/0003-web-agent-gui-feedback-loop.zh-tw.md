# 事後檢討（postmortem） 0003：Web agent（代理）驗收了替代伺服器，而非其當前 GUI

[English](0003-web-agent-gui-feedback-loop.md) | [简体中文](0003-web-agent-gui-feedback-loop.zh.md) | 繁體中文

狀態：已解決

## 摘要

Web agent 修改了 GUI 原始碼，卻不知道當前工作階段對應哪個 URL、由哪個行程承載。它把驗收交還給使用者，隨後在 `window.__DSH_BOOT__` 缺失導致白屏的情況下，仍把裸 Vite 返回的 HTTP 200 當作成功；最後，原頁面其實已經載入了重建產物，它卻去驗收另一個埠上的替代 `dsh web` 伺服器。修復讓當前 URL 和執行模式對模型可見且可由 shell 查詢，在獨立 Vite 開始監聽前拒絕啟動，並依據外部狀態驗收生產模式刷新與開發模式 HMR（熱模組替換）。

## 概述

該工作階段執行在埠 3081 的 DeepSeek Harness Web GUI 中，而使用者選擇的 Workspace 是空的 `test/` 目錄。模型請求既未指明該 GUI，也未提供它的原始碼檢出目錄、URL、行程或更新模式。倉庫在 `apps/web` 中提供了 Vite 開發指令碼，完整的瀏覽器組合則由 `dsh web` 提供。

由此產生的各個動作單看都合理，卻沒有指向同一個驗收目標。原始碼修改、成功建置、HTTP 200、注入的啟動 manifest（中繼資料清單）和使用者原本打開的頁面，被當成了可以相互替代的事實。

證據源是 `session-3eb796c2-5159-4686-affe-df8719f6f987` 的持久化事件日誌，其頭部記錄的 cwd 為 `/Users/tn.shen/Documents/deepseek-harness-gui-master/test`。初始請求標頭位於序列 6；面向使用者的交接、裸 Vite 啟動、替代宿主啟動、啟動 manifest 探測，以及首次探測 3081 行程，分別位於序列 30939、31865、34309、34441 和 34681。下方時間線以這些事件為依據，而不是根據後續報告反推意圖。

## 影響

使用者不得不連續指出三個錯誤：agent 把驗收交還給使用者；建議預覽的頁面一片空白；報告成功的 URL 並不是使用者正在使用的頁面。一個不受管理的替代伺服器還持續執行到下一個輪次，直到使用者提出質疑。

本次調查沒有重新啟動或修改只讀的 3081 和 3082 試驗服務。

## 時間線

- 在第 2 個輪次中，agent 修改主題後，在序列 30939 的訊息中讓使用者執行 `pnpm run demo:tui` 或打開一個未明確指定的 Web 應用。它沒有對組裝後的 Web 應用執行任何驗收。
- 在第 3 個輪次中，agent 讀取 `apps/web/package.json`，在序列 31865 於埠 5173 上啟動裸 Vite，觀察到 HTTP 200 後便宣佈成功。瀏覽器卻拋出 `client-modules: window.__DSH_BOOT__ is missing or not an object`，並顯示白屏。
- 在第 4 個輪次中，agent 找到了完整的 `dsh web` 啟動路徑，重新建置 shell，在序列 34309 於埠 3334 上啟動一個不受管理的行程，並且只在序列 34441 檢查了這個替代服務是否返回 200 和啟動 manifest。它從未探測埠 3081。
- 在第 5 個輪次中，使用者在序列 34556 報告 3081 已經顯示新主題。直到序列 34681，agent 才檢查既有行程並移除冗餘伺服器。

## 根因

Web 組合沒有向模型提供當前 GUI、規範 URL 或執行模式的身份資訊。工作階段 cwd 正確標識了使用者選擇的 Workspace，但模型把這個項目目錄當成了應用目錄。系統也沒有持久記錄將 GUI 原始碼檢出目錄、建置產物、服務行程、目標 origin 和瀏覽器驗收關聯起來。

裸 Vite 返回 HTTP 200，使錯誤的啟動路徑看似合理。`window.__DSH_BOOT__` 只由完整宿主注入，因此傳輸層就緒不代表應用已就緒。首個回歸測試以另一種方式重複了同樣的錯誤：逾時機制終止 Vite 後，非零退出斷言仍會透過。真實復現暴露了這一誤報。

agent 還透過 shell `&` 繞過了後臺行程語義，因此任務身份、完成通知、結果收集和清理機制均未生效。驗證埠 3334 只能證明第二個服務可以工作。

## 已新增的防護措施

- Web 啟動器在記錄到日誌的 `app:web-surface` 提示詞區段，以及受管的 `$DSH_WEB_URL`/`$DSH_WEB_MODE` 環境變數中，發布規範環回 URL 和實際的生產／開發模式。
- 生產模式指南要求重新建置產物，並在刷新後驗證既有 URL。開發模式指南說明，`dsh web --dev` 只掛載 HMR 接收端；同一原始碼檢出目錄中的 `pnpm run dev:web` 還必須重新建置用戶端外掛程式 bundle，而 Web shell 和普通包的改動仍然需要重新整理頁面。
- `apps/web` 的獨立 Vite 服務模式會在設定階段拒絕啟動。其子行程測試驗證行程自然退出，並插樁 `Server.listen()`，確保短暫綁定埠也不會漏檢。
- 分層的真實路徑測試覆蓋 CLI（命令列介面）請求、精確的生產／開發模式提示詞、shell 執行時期事實、同埠靜態產物替換、原始碼 watcher 重建、宿主 stat 輪詢，以及頁面 identity 不變的瀏覽器 HMR。
- PR（Pull Request）證據保留了原始 3081 工作階段的截圖，以及真實模型驅動程式的 GUI 修改前後對比；驗收以外部瀏覽器、HTTP、行程和工作階段日誌的觀測結果為準。

## 教訓

- agent 必須先知道隱藏的執行時期前置條件，才能指導使用者；啟動模式屬於應用上下文，不應相依性團隊口口相傳。
- HTTP 就緒、建置成功和啟動 manifest 是不同的事實。驗收必須明確指定確切的 origin，並從外部觀察所請求的改動是否在該 origin 生效。
- 替代服務無法證明既有頁面已經改變。確實收到啟動長時間執行行程的請求時，應使用受管任務生命週期。
- 回歸測試必須能夠針對所報告的機制失敗。行程逾時不等同於快速失敗，行程退出後端口可用也不能證明該埠從未被綁定。
